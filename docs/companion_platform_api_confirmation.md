## 1. 회신 수신

9월 11일 ZIP의 C01~C49 회신을 반영했다.
각 행의 질문과 당시 코드 설명은 원문을 유지했다.
마지막 열은 상대방의 회신이며 구현 검증과 다르다.
대조 결과는 [v1 회신 검토](companion_platform_api_v1_review.md)를 본다.
상대 기준은 [API 계약 v1](hw_handoff/platform_api_v1/companion_platform_api_contract_v1.md)이다.

우리 companion은 ROS2 구조를 유지합니다.
고도·자세·비행 상태추정은 PX4가 담당합니다.
외부 JSON 이름은 합의한 계약에 맞출 수 있습니다.

| C42 | 스캔 ID를 같은 업로드 재시도에 재사용 | 서버가 `client_scan_id`로 중복 저장을 막나요? 유일성 범위·보존 기간을 알려 주세요. | 서버는 `client_scan_id`로 accepted/rejected 모두 중복 방지한다. 재시도는 같은 UUID를 쓴다. |
| C43 | 동일 QR 재판독은 새 ID가 될 수 있음 | 임무·라벨별 중복 스캔도 막나요, 여러 관측으로 저장하나요? | 새 판독 UUID는 별도 관측으로 기록될 수 있다. 임무/라벨 중복 정책은 업무 규칙 변경이므로 현 상태 유지다. |
| C44 | 로컬 저장만으로 `qr_scan_complete=true` | 저장 후 다음 지점 이동을 허용하나요? 수락 완료와 구분 표시할까요? | 현재는 네트워크 장애 시 로컬 저장 후 진행 허용이다. 수락 필수 정책은 별도 합의가 필요하다. |
| C45 | 버퍼는 `ok=true`면 accepted와 무관하게 삭제 | 거부 결과를 어디에 남기나요? 재전송 수락·거부 응답 규칙을 통일합시다. | `ok:true, accepted:false`는 rejected 로그가 DB에 저장된 정상 처리라 버퍼에서 제거한다. |
| C46 | 재전송 요청에 `attempts`, `last_error` 포함 | 서버가 이 추가 필드를 허용하나요? 로컬 관리 필드를 제외할까요? | `attempts`, `last_error`를 업로드에서 제외하도록 수정했다. |
| C47 | `final_rc`는 실제 송신 확인값이 아님 | 우리 PX4 구조에서 RC 필드는 생략할까요? 대신 필요한 FC 상태·모드·명령 결과를 정해 주세요. | `final_rc`는 선택 진단이다. PX4 실제 상태는 FC 필드로 분리했다. |
| C48 | WS에 FC connected·armed·mode 직접 필드 없음 | 실제 비행 상태 표시를 위해 별도 필드를 추가할까요? companion FSM과 분리합시다. | `fc_connected`, `fc_armed`, `fc_mode`를 추가했다. |
| C49 | WS에 활성 경유지·경로 개정·임무 ID 없음 | 경로 조작 결과 확인을 위해 이 값을 추가할까요? | `mission_db_id`, `mission_code`, `route_revision`, `active_waypoint_index`, `active_waypoint_id`를 텔레메트리에 추가했다. |

## 6. 처음 요청한 예시와 수신 범위

계약서의 GET·WS·POST 예시를 받았다.
실서버 전체 응답과 오류 예시는 아직 없다.
아래는 처음 요청한 자료 목록이다.

| 요청 자료 | 필요한 경우 |
|---|---|
| 임무 GET 응답 | 대기, 실행 승인, 비행 중 경로 변경, 취소 |
| 제어 요청 GET 응답 | 복귀, 착륙, 동일 요청 반복, 만료 |
| WS 수신 스키마 | 필수 필드, 선택 필드, null, 미지원 센서 |
| phase·ACK·출발 등록 응답 | 성공, 업무 거부, 중복 요청, 잘못된 임무 |
| QR 응답 | 수락, 라벨 불일치, 동일 ID 재시도, 잘못된 원문 |
| 창고 좌표 예시 | 원점, +x 이동점, +y 이동점, 고도 기준 |
| 앵커 설정 예시 | 실제 배치 ID·버전·A1~A4 좌표 |

이번 회신은 통신 규격을 구체화했다.
남은 차이는 v1 회신 검토 6·7절에 모았다.
이번 문서는 로드맵 변경을 확정하지 않는다.
