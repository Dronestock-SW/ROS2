# QR 스캔·ArUco 미세 정렬 명세
이 문서는 라벨 판독을 비행 임무에 연결하는 설계다.
행동 트리·스캐너·웹 결과 연동을 구현하기 전에 읽는다.

상태: 2026-10-04 합성 REPLAY의 스캔 BT·미세 정렬·3회 판독/카메라 폴백·영속 결과·대기점 복귀를 구현했다.
실제 센서는 읽기 전용 ROS 관측기에 연결하며, 실비행 판독·제어 연결은 후속이다.
`/qr_reader/data`는 HID 스캐너, `/qr_code/data`는 카메라이고 `/qr/data`는 기존 폴백의 통합 출처다. 새 BT는 두 판독 출처를 구분한다.
기존 String은 소스 시각·임무/작업/창 문맥이 없어 새 스캔 결과로 수락하지 않는다. ArucoDetection에는 촬영 header가 있지만 dictionary·크기·재투영 품질·승인된 장착/라벨 변환이 없어 단독으로 미세 이동을 승인하지 않는다.

## 1. 확정한 동작

ArUco로 미세 정렬한 뒤 호버링하며 스캔한다.

```text
라벨 좌표·정면 방향·장착 변환 -> 기체 접근/판독 위치·경로 검증
 -> 접근 대기점 도착 -> 초기 호버 안정 -> 검증된 근접 접근
 -> 카메라 ArUco 관측 -> 대상 마커 확인
 -> 미세 이동/yaw 조정 -> 정지·연속 호버 안정
 -> QR 스캐너 시도 1 -> 실패 -> 시도 2 -> 실패 -> 시도 3
      | 어느 시도든 유효 판독                 | 실패
      v                                      v
   결과 저장                            카메라 QR 판독
      |                               성공 / 최종 실패
      +---------------- 결과 저장 ------------+
                          |
                접근 경로 재검사·대기점 복귀
                          |
                 다음 순서의 임무 목표
```

| 정책 | 기준 |
|---|---|
| 스캐너 시도 | 최대 3회. 성공하면 남은 시도 생략 |
| 대체 판독 | 스캐너 3회 실패 후 카메라 QR 판독 |
| 최종 판독 실패 | 실패 기록 후 접근 대기점 복귀를 확인하고 다음 목표로 이동 |
| 스캔 입력 XYZ | QR 라벨 위치. 기체가 직접 도착할 좌표가 아님 |
| 스캔 후 이탈 | 성공·실패 모두 접근 대기점 복귀 후 다음 목표 진행 |
| 스캔 자세 | 호버 안정 상태에서만 판독을 채택 |
| 정렬 | 카메라 ArUco 정보로 위치·yaw 미세 조정 |
| 마커/카메라 실패 | 획득 한도 실패·카메라 고장 시 실패 기록→대기점 복귀→다음 목표. 비행 상태·이탈 경로 정상인 경우 |
| 라벨 배치 | QR마다 ArUco를 고정 배치. 두 코드의 상대 위치·방향·크기 기록 |
| 장착 | 카메라·스캐너는 기체 헤딩 전방. 정밀 장착 변환은 실측 |
| 판독 거리 | 사용자 제안 0.40~0.60m를 초기 시험 범위로 사용. 성능 검증값은 아님 |
| 비행 제어 | Jetson이 위치·yaw 목표 생성, PX4가 실행 |
| 안전 선점 | 기존 RC·PX4 비상·Land·복귀 정책 우선 |

카메라의 ArUco 검출은 정렬 단계부터 필요하다.
카메라 QR 디코딩만 세 번째 스캐너 실패 뒤 켠다.
카메라 전체를 그때까지 꺼 두면 정렬할 수 없다.
거리 기준은 판독 장치 전면에서 QR 라벨 면까지로 제안한다.
기체 중심 거리나 카메라 영상의 임의 깊이값과 혼용하지 않는다.
두 장치의 앞뒤·좌우·높이 차이는 각각 반영한다.
시험 범위 안에서도 실제 판독 성능과 기체 여유를 확인한다.
안전 여유가 부족하면 40cm까지 접근하도록 강제하지 않는다.

일반 이동점의 기체 방문과 라벨 작업 결과는 따로 기록한다.
모든 작업의 순서는 유지하되 기체가 라벨 좌표를 통과하지 않는다.
판독 실패는 다른 필수 이동점을 생략할 권한이 아니다.
다음 목표도 같은 지도·경로 검사를 거친다.

### 1.1 라벨 좌표와 기체 좌표

2026-10-04 사용자 확정: 웹 scan XYZ는 QR 라벨이 붙은 위치다.

| 좌표 | 의미 | 처리 |
|---|---|---|
| 일반 waypoint XYZ | 기체/PX4 기준점의 목표 위치 | 기존 도착·호버 판정 |
| scan 라벨 XYZ | 지도 기준 QR 위치. z는 공통 바닥에서 라벨까지 높이 | 고정 작업 대상, PX4 목표로 직접 전달 금지 |
| 접근 대기점 | 근접 접근 전 머무르고 작업 후 돌아오는 기체 위치 | Jetson이 경로·정지·회전 공간 검증 후 고정 |
| 판독 목표 pose | 장치가 QR을 볼 수 있는 기체 위치·방향 | 라벨 방향·판독 거리·장착 변환으로 계산, ArUco로 제한 보정 |

라벨의 정확한 기준점(예: QR 중심)도 웹·라벨 담당자와 합의한다.
라벨 정면은 선반에서 판독 가능한 통로 쪽으로 향하는 방향이다.
이 방향의 제공 방식·각도/법선 표현은 웹 담당자 협의 항목이다.
일반 이동점의 선택 yaw와 라벨 정면 방향을 같은 필드로 간주하지 않는다.
라벨 방향 미제공 시 최근 이동 방향이나 가까운 통로로 추측하지 않는다.
방향·좌표 변환·장착 변환·접근 공간을 검증하기 전에는 scan 임무 READY를 발급하지 않는다.

다음은 정면 수직 접근이 가능한 경우의 기하 관계이며 확정 JSON은 아니다.

```text
p_sensor = p_label + d * n_out
p_vehicle = p_sensor - R_vehicle_to_map * r_vehicle_to_sensor
```

p_label은 합의한 라벨 기준점, n_out은 지도 기준 바깥쪽 단위 법선이다.
d는 선택한 장치 기준의 승인된 판독 거리이며 0.40~0.60m는 시험 후보 범위다.
r은 기체 기준점에서 장치 기준점까지의 실측 장착 벡터다.
센서 광축이 라벨을 향하도록 기체 방향과 장착 회전을 함께 계산한다.
기체 높이도 장치 높이 오프셋을 반영하므로 라벨 z를 그대로 사용하지 않는다.
경사진 라벨 등 현재 고정 장착으로 볼 수 없는 자세는 가능한 자세로 검증되기 전 수락하지 않는다.
카메라와 스캐너의 위치 차이로 목표가 바뀌면 다시 공간 검사·이동·안정 후 판독한다.

충돌 검사는 라벨점이 아니라 기체 외형·위치 오차·제동 여유를 포함한 이동 공간에 적용한다.
라벨이 선반 표면에 있다는 이유로 그 선반을 장애물 검사에서 제외하지 않는다.
사용자 확정: 전체 비행 경계 제공 전에는 웹에 라벨별 접근·작업 허용 구역을 요청한다.
Jetson은 제공된 구역과 진입/이탈 구간을 검증한 뒤 그 안에서만 접근·미세 조정한다.
세부 JSON과 승인 자료 형식은 QS-W8 회신 후 확정한다.

### 1.2 라벨별 허용 구역

| 웹에 요청할 의미 | Jetson 검증 |
|---|---|
| 구역 ID·라벨 ID·지도/구역 개정 | 같은 불변 임무 snapshot과 연결, 잘못된 라벨 참조 거부 |
| 지도 기준 평면 외곽과 최저/최고 z | 유한한 3D 범위, 기존 구역별 z 제한과 교집합 검사 |
| 허용 범위의 기하 의미 | 물리 공간 또는 기체 기준점 허용 범위를 명시. 이중 여유 적용/여유 누락 금지 |
| 접근·작업 구역과 기존 비행 경로의 연결 | 접근 대기점·획득/판독 위치·진입/이탈 전체 이동 공간 검사 |
| 선반·천장·장애물·운영자 확인 참조 | 허용 구역이 장애물을 지우거나 상부 공간 확인을 대신하지 않음 |

요청 초안은 물리적 허용 공간을 받아 기체 외형·측위/지도 오차·제동 여유를 내부에서 반영하는 방식이다.
정확한 필드·도형 표현·확인 기록은 웹 담당자와 합의한다.
대기점은 이 공간과 경로를 사용해 Jetson이 산출·검증하며 웹에서 검증 결과를 표시한다.
대기점 위치·목표 자세, 근접 접근과 이탈의 회전 공간까지 포함한다.
별도 구역이 있어도 일반 경로 자동 우회는 전체 비행 경계 제공 전 보류한다.
라벨별 구역을 합쳐 창고 전체 비행 허용 경계로 간주하지 않는다.
자료가 없거나 연결 구간이 검증되지 않으면 해당 scan 포함 임무의 READY를 거부한다.
비행 중 구역 밖 보정 후보는 출력하지 않는다. 한도 안 정렬 불가 시 실패 기록·대기점 복귀 정책을 따른다.
실제 기체의 위치 상실·경로/공간 안전성 상실은 기존 비행 실패 정책으로 처리한다.

## 3. 상태·입출력 계약

스캔은 비동기 행동이다. BT tick을 막지 않는다.

| 상태 | 입력·진입 조건 | 출력·종료 |
|---|---|---|
| PREPARE_APPROACH | 라벨 pose·장착/지도 개정·승인 공간 | 기체 대기점/판독 후보·진입/이탈 구간 검증, 불가 시 시작 거부 |
| APPROACH | 대기점 도착·안정, 카메라 정상·검증된 근접 구간 | 제한된 기체 목표, 구간 진행 기록, 획득 위치에서 정지 |
| ACQUIRE_MARKER | 검증된 획득 위치·호버, 목표 marker_id | 신선한 대상 pose 확보 또는 한도 실패 |
| ALIGN | 보정값·캘리브레이션·안전 범위 | 제한된 XYZ/yaw 목표, 오차 충족 후 SETTLE |
| SETTLE | 유효 pose·속도·yaw·상대 정렬 | 연속 안정 충족 후 판독, 이탈 시 재정렬 |
| READER_SCAN | 안정·유효 시도 문맥 | 성공 또는 시간 창 종료. 최대 3회 |
| CAMERA_SCAN | 스캐너 3회 실패·안정·디코더 활성 확인 | 유효 판독 또는 카메라 한도 실패 |
| PERSIST_RESULT | 성공/실패와 실행 문맥 | 영속 저장 확인 후 RETURN_STAGING. 아직 전체 작업 종료 아님 |
| RETURN_STAGING | 저장된 대기점·지나온 구간·현재 상태 | 경로 재검사 후 대기점 복귀·정지 확인 |
| NEXT | 대기점 복귀·비행 정상·다음 경로 유효 | 작업 종료, 다음 순서 목표로 이동 |

| 입력 묶음 | 필수 의미 |
|---|---|
| 스캔 목표 | 작업·라벨 ID, 지도 기준 라벨 위치/정면, ArUco dictionary/ID/실측 크기 |
| 접근 계획 | 별도 기체 대기점/판독 pose·허용 작업 공간·진입/이탈 구간·개정 |
| 라벨 배치 | 마커와 QR의 상대 위치·방향, 기대 품목/라벨 규칙 |
| 장착 변환 | 기체↔카메라, 기체↔스캐너 위치·방향·개정 |
| 마커 관측 | 이미지 취득 시각, frame_id, ID, 상대 pose, 품질·원천 세션·순번 |
| 기체 상태 | 관측 시각에 대응한 PX4 pose, 현재 위치·속도·yaw·유효성 |
| QR 관측 | 원문·출처·소스 시각·세션·순번·활성 시도 문맥 |
| 출력 의도 | 기존 ControlIntent와 같은 제어권·세대·프레임·lease |

기존 QR String에는 취득 시각·시도 ID가 없다.
늦은 이전 지점 판독이 새 작업에 붙지 않게 보완한다.
수신 시각을 측정 시각으로 꾸미지 않는다.
카메라 결과는 실제 처리한 이미지 시각을 보존한다.

## 4. ArUco 미세 조정

관측으로 스캔 목표를 보정한다. 제어 실행은 PX4가 맡는다.

1. 대상 마커 ID·크기·관측 신선도를 검사한다.
2. 내참수·왜곡 계수와 장착 변환을 확인한다.
3. 촬영 시점 기체 pose로 상대 관측을 변환한다.
4. 마커↔QR 배치와 판독 장치 오프셋을 적용한다.
5. 목표 판독 거리·방향에 대한 오차를 계산한다.
6. 제한된 위치·yaw 목표를 기존 목표 생성기에 준다.
7. 이동 경로·고도·회전 공간을 검사한 뒤 출력한다.
8. 허용 오차와 연속 안정 시간을 만족하면 판독한다.

| 제한 | 요구 |
|---|---|
| 판독 위치 | 전방 카메라·스캐너 각각의 오프셋 적용. 라벨 면까지 0.40~0.60m 후보 범위에서 검증 |
| 이동량 | 1회 보정량과 지점 기준 전체 이동 범위 제한 |
| 동역학 | 속도·가속·yaw rate를 승인된 미세 조정 한도로 제한 |
| 높이 변경 | 기존 정책대로 안전 확인·수직 이동·안정 후 수평 이동 |
| 자세 | roll/pitch·추력 명령을 만들지 않음 |
| 관측 불량 | 잘못된 ID·pose 반전·급격한 점프·저품질·만료는 거부 |
| 품질 | 연속 관측·재투영 오차·거리/각도 유효 범위 확인 |
| 마커 상실 | 보정을 중단하고 유효한 PX4 위치 유지. 제한 시간 내 재획득 |

오래된 마커 pose로 접근을 계속하지 않는다.
작업 범위를 벗어난 탐색 비행은 하지 않는다.
ArUco 보정을 UWB/EKF 대체 위치로 사용하지 않는다.
EKF에 같은 보정 결과를 재입력하지 않는다.
관측 pose는 작업 정렬용이며 비행 상태는 PX4를 따른다.

단일 평면 마커의 방향 모호성과 측정 튐을 시험한다.
오차가 감소하지 않으면 작업 한도 내 실패 처리한다.
정렬 실패는 QR 미완료로 기록한다.
사용자 확정: 마커 획득 한도 실패·카메라 고장도 실패 기록 후 대기점 복귀·다음 목표로 진행한다.
기체 위치 유지와 이탈 경로가 정상일 때만 이 정책을 적용한다.
정렬을 검증할 수 없으면 스캐너 3회를 억지로 수행하거나 카메라 QR 단계로 바로 넘기지 않는다.
이때 scanner_attempts=0일 수 있으며 실패 원인으로 MARKER_UNAVAILABLE/CAMERA_UNAVAILABLE을 구분한다(코드명 제안).
비행 전 이미 카메라 준비가 실패한 경우의 scan READY 거부는 유지한다.
이동 중 카메라 고장을 확인한 뒤 마커를 찾으려고 추가 접근하지 않는다.

OpenCV는 마커 크기·내참수·왜곡 계수로 상대 pose를 구한다.
근거: [OpenCV ArUco API](https://docs.opencv.org/4.5.3/d9/d6a/group__aruco.html).
위 알고리즘과 품질·제한 규칙은 우리 설계안이다.
PX4 목표 전달은 기존 [PX4_INTERFACE.md](PX4_INTERFACE.md)를 따른다.
근거: [PX4 Offboard](https://docs.px4.io/v1.17/en/flight_modes/offboard).

## 5. 호버·시도·선점 규칙

미세 이동과 판독 창을 분리한다.

| 상황 | 처리 |
|---|---|
| 호버 승인 | XYZ/yaw·속도·상대 정렬·관측 나이를 연속 확인 |
| 판독 중 이탈 | 열린 창 종료, 결과 채택 중단, 재정렬·안정 후 재시도 |
| 시도 정의 | 안정 상태에서 연 판독 시간 창 1개. ROS 프레임 수가 아님 |
| 스캐너 3회 | 열린 창마다 1회 사용. 재정렬·pause로 횟수를 되돌리지 않음 |
| 카메라 전환 | ArUco 검출 유지, QR 디코더만 활성. 확인 응답 뒤 새 영상 판독 |
| RC·Land·복귀 | 즉시 선점. 새 이동이나 시도 재개 금지 |
| pause·위치 복구 | 현재 시도 폐기, 횟수·사용 예산 보존. 재검증 후 새 창 |
| 기체 위치/yaw 상실 | 기존 비행 실패 정책. 단순 스캔 실패로 다음 점 이동 금지 |
| 장애물·배터리·기록 실패 | 기존 비행 정책을 먼저 실행 |

재시도·재정렬에 유한한 전체 작업 예산을 둔다.
획득·정렬·판독 예산이 소진되면 실패를 기록하되 대기점 복귀 단계는 별도 이동 예산(M09/M11)으로 실행한다.
판독 한도 소진을 이탈 완료로 처리하거나 이탈 시간 제한을 무한대로 두지 않는다.
사용자 PAUSE 시간은 별도이며 배터리 정책은 유지한다.
새 QR이 없다는 사실만으로 장치 고장을 판정하지 않는다.
스캐너 준비 상태와 라벨 미판독을 분리한다.

## 6. 결과 저장과 웹 계약

판독 실패도 지점 결과로 남긴다.

| 정보 | 요구 |
|---|---|
| 식별 | 실행/비행/지점/라벨/스캔 ID, 지도·임무 개정 |
| 판독 | 원문·장치 출처·취득 시각·유효성·대상 일치 |
| 시도 | scanner_attempts 0~3, 카메라 사용, 각 실패 이유 |
| 정렬 | 마커 ID·잔여 오차·교정 개정·안정 근거 |
| 접근·이탈 | 라벨 위치와 기체 대기점/판독 목표, 접근 계획 ID, 대기점 복귀 상태·실패 원인 |
| 최종 작업 결과 | 성공/실패/선점. 기체 도착·판독 결과·이탈 완료를 분리 |
| 전송 | 로컬 저장/대기/서버 수락/서버 거부를 분리 |
| 임무 결과 | 방문 완료여도 실패 라벨 수를 표시. 전체 스캔 성공으로 표시하지 않음 |

기존 등록 API는 `POST /api/drones/{drone_id}/scan/`다.
같은 결과 재전송은 같은 `client_scan_id`를 유지한다.
HTTP 2xx와 업무상 `accepted=true`를 구분한다.
원문의 명령처럼 보이는 내용도 데이터로만 취급한다.
서버 미연결 시 로컬 영속 저장·후속 전송안을 사용한다.
다음 점 진행의 로컬 성공 조건은 웹과 검수한다.
서버 거부를 QR 판독 성공이나 업로드 성공으로 합치지 않는다.
필수 기록 실패는 기존 복귀·착륙 정책을 따른다.
QR 결과 보존 기간은 ULog 72시간 삭제와 별도다.

기존 파서는 name을 요구하나 서버 예제는 생략 사례가 있다.
웹 회신으로 필수 필드와 대상 일치 판정을 맞춘다.
기존 `scan_source=wifi`는 전송 문맥이다.
리더/카메라 관측 출처와 다른 의미로 유지한다.

### 6.1 접근 대기점 복귀

사용자 확정: 성공·최종 실패 모두 접근 대기점으로 돌아온 뒤 다음 목표로 간다.

1. 근접 접근 전에 검증된 대기점 pose와 지도·변환·계획 개정을 저장한다.
2. 근접 접근과 미세 조정 중 실제 지나온 유효 구간을 기록한다.
3. 판독 창을 닫고 결과를 저장한다. 늦은 판독은 다음 작업에 붙이지 않는다.
4. 현재 위치에서 대기점까지 기록 경로를 역순으로 연결하고 현재 장애물·고도·회전 여유를 재검사한다.
5. 역방향 이동 목표를 새로 생성한다. 과거 명령을 시간 역순으로 재생하거나 직선 후퇴를 가정하지 않는다.
6. 유효 경로로 대기점까지 이동해 정지·도착을 확인한 뒤에만 다음 목표로 전환한다.

후퇴를 위해 자동으로 180도 회전시키지 않는다. 후퇴 방향의 검증 공간과 관측 한계도 확인한다.
스캔 결과 저장만으로 대기점 복귀 완료나 임무 성공을 선언하지 않는다.
이탈 경로가 막히면 기존 B12 차단 정책(최대 10초 후 복귀)을 따른다.
10초 안에 해소되면 저장된 RETURN_STAGING을 재개하며 판독·시도 횟수를 다시 시작하지 않는다.
이탈 이동 자체가 도달 한도를 넘으면 B15 복귀, 복귀 경로도 불가하면 B16 Land다.
판독 실패의 ‘다음 목표 진행’ 규칙으로 이탈 실패를 건너뛰지 않는다.
RC/PX4 비상·Land는 즉시 선점하며 대기점 복귀를 기다리지 않는다.
저전력·취소 등 복귀 선점은 현재 위치부터 유효한 귀환 경로를 사용하고 스캔을 재개하지 않는다.
PAUSE/위치 복구 후에는 같은 대기점과 결과·시도 기록을 보존하고 이탈 경로를 다시 검사한다.
프로세스 재기동으로 같은 비행의 스캔/이동을 자동 재개하지 않는다.

횟수 3회와 실패 후 진행은 확정이다. 시간·기하는 실측한다.

| ID | 미정 값 |

| QS-M4 | 정렬/호버 허용 오차·속도·각속도·연속 안정 시간 |
| QS-M5 | 스캐너/카메라별 0.40~0.60m 후보 거리의 성능·안전 여유·각도·품질 한도 |

| 시험 | 통과 기준 |
|---|---|
| 정렬 | 알려진 오프셋 보정, 범위 내 오차 감소, 안정 후 판독 |
| 정상 QR | 1~3번째 성공에서 즉시 종료, 결과 한 번 저장 |

| 좌표 의미 | 라벨 XYZ 직접 비행 목표 없음. 장착 오프셋 적용된 기체 pose 사용 |

| 라벨별 구역 | 외곽·높이·기체 여유·경로 연결 모두 유효해야 시작. 구역 밖 보정과 일반 자동 우회 권한 확대 없음 |
| 이탈 | 미세 조정 구간 포함 재검사, 대기점 도착 전 다음 작업 시작 없음 |
| 이탈 차단·정체 | 기존 이동 실패·복귀/Land. 판독 실패를 이유로 우회 적용/다음 점 진행 없음 |
| 흔들림·관측 지연 | 안정 창 취소, 오래된 판독·이전 지점 결과 거부 |

| 마커 상실·카메라 고장 | 보정 중단·실패 기록·검증 경로로 대기점 복귀 후 다음 목표. 위치 상실을 단순 판독 실패로 처리하지 않음 |
| 중복·단절·재기동 | 같은 결과 ID 보존, 중복 업로드·허위 성공 없음 |
| RC·Land·저전력 | 스캔을 기다리지 않고 기존 안전 행동 선점 |

## 8. 정규화 센서 연결 v2 — 합성 개발 접점

C++ `scan.request` → ROS 요청 → 원천 producer `CaptureGate` → ROS 관측 → `scan.observe` → 기존 ScanAction/SQLite 흐름을 연결한다.
`ops/scan_replay_bridge.py`는 격리 TEST 기체·ROS domain 170~199·`/sangwon_synthetic_...` 이름공간만 허용한다. 자동 부팅 서비스에는 포함하지 않는다.
기본 HOST_OBSERVE는 `scan.observe`를 거부한다. `EXTERNAL_SENSOR_REPLAY` 구성에서만 외부 입력을 수용하며, 내부 `SYNTHETIC_SCAN_FIXTURE` 판독을 동시에 사용하지 않는다.

| 요청 필드 | 의미 |
|---|---|
| `schema_version=sangwon-scan-request/2` | 내부 센서 계약 개정. 웹 계약과 별도. 이전 v1과 혼용 거부 |
| `scope=SYNTHETIC_SENSOR_REPLAY`, 권한 false | 실제 장치/기체 승인 근거로 사용 금지 |
| `request_id`, `issued_monotonic_s`, `expires_monotonic_s` | C++ 발급 토큰, 200ms lease. 작업·단계·창·일시정지 변경 시 교체 |
| `context` | 기체·OS boot·C++ runtime·execution·task·window·frame epoch |
| `active`, `observe_marker`, `open_reader`, `enable_camera` | C++가 현재 허용한 관측 종류 |
| `marker_contract` | 대상 ID·dictionary·크기·교정/장착/라벨 배치 참조와 합성 기준 pose |
| `source_max_age_s` | kind별 원천 수락 최대 나이. 원천 전달 큐의 만료 기준 |

관측 envelope는 `schema_version=sangwon-scan-observation/2`, 고유 `observation_id`, 같은 scope·권한 false, 토큰/context, 승인된 producer ID, 양수 순번, 원천 `observed_monotonic_s`와 `observed_at`, `kind`, `data`를 갖는다.
소스 시각은 같은 장치/boot의 monotonic과 UTC를 함께 확인한다. 두 시각의 age 차이 50ms를 개발 검증 기준으로 사용한다. 해당 수치는 네트워크/기체 실측 결과가 아니다.
원천 시각은 토큰 발급 이후이고 미래가 아니어야 하며, 다시 받은 같은 프레임을 새 시각으로 바꾸지 않는다. 웹 `decoded_at`은 원천 시각을 보존한다.

| kind | data·수락 조건 |
|---|---|
| `STATUS` | camera/scanner 건강 boolean. 500ms 후 만료, 센서 미수신을 정상으로 만들지 않음 |
| `MARKER` | dictionary/ID/크기/교정/장착/배치 참조, reprojection, 유한 map 기체 pose, valid. 기존 마커 나이·횟수·공간 검사 유지 |
| `CAMERA_ACK` | 해당 카메라 창의 `enabled=true`. 200ms 후 만료 |
| `QR_SCANNER` | 해당 reader 창의 원본 raw 문자열. 기존 QR 일치 검사 유지 |
| `QR_CAMERA` | 해당 camera 창의 raw 문자열. 같은 창 ACK 확인 전 수락 금지 |

새 관측의 순번은 kind별로 이전 수락보다 커야 한다. 잘못된 입력은 순번을 소비하지 않는다. task/창 변경, pause, 종료, 재기동의 이전 응답을 새 관측으로 수락하지 않는다.
동일 ID·동일 본문의 재전송은 기존 입력 ACK만 반환한다. 같은 ID의 다른 본문은 `SCAN_OBSERVATION_ID_CONFLICT`, 같은 순번의 다른 ID는 `SCAN_OBSERVATION_OUT_OF_ORDER`다. 재전송으로 관측 시각·건강 상태·안정 샘플·판독 창을 갱신하지 않는다.
relay는 이전 String 토픽에 task/window를 나중에 붙여 수락하지 않는다. 실제 producer는 촬영/판독 시점에 원천 시각과 활성 요청 문맥을 함께 고정해야 한다.
현 구현의 marker 기준 pose는 합성 시험 자료다. 실제 카메라 optical pose → 기체/map 목표 변환은 승인된 외부파라미터·라벨 배치·PX4 pose가 있어야 구현/검증할 수 있다.

### 8.1 수신 확인과 단절 처리

relay는 별도 `receipt_topic`으로 `sangwon-scan-receipt/1`을 반환한다. 요청·관측·receipt 토픽은 서로 달라야 하고 격리 이름공간 조건을 따른다.
ACK는 원래 observation ID·토큰/context·producer·kind·순번, 실제 ROS 전달 bytes의 `transport_sha256`, 원천 시각을 확인한다. `acceptance_scope=INPUT_VALIDATION_ONLY`이며 QR 일치·호버 완료·판독 성공·작업 종료를 증명하지 않는다. 최종 결과는 기존 C++ ScanAction·SQLite·웹 결과 개정으로 확인한다.
`INGRESS_ACCEPTED`는 C++ 입력 수락, `REJECTED`는 명확한 거부, `RETRYABLE`은 core 연결/응답 미확인이다. 응답이 미확인인 전송은 이미 수락됐을 수 있으므로 본문·ID·시각을 그대로 재전송한다.
원천 `PendingObservations`는 QR/활성화 ACK만 최대 32개 메모리에 보관하고 25ms 시험 간격으로 재전송한다. 원래 관측의 최대 나이 후 만료하며, 재연결로 시각이나 deadline을 새로 만들지 않는다. STATUS/marker는 최신 원천 관측을 보내며 과거 프레임을 큐로 연장하지 않는다. 수신 확인·원본 본문 SHA가 맞아야 pending을 제거한다.
C++ 입력 ACK cache는 최대 64개 메타데이터만 보관한다. 창이 끝난 뒤에도 cache에 남은 정확히 같은 입력의 ACK를 조회할 수 있지만 행동/센서 상태를 재적용하지 않는다. 원본 QR은 ACK/cache/log에 포함하지 않는다.
이 cache와 원천 pending은 프로세스 메모리다. C++ 재기동·새 START는 cache를 초기화하며, 이전 실행을 자동 복구하지 않는다. 영속 작업 결과/outbox와 입력 ACK의 수명을 구분한다.
