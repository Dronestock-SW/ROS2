## 1. 사용자와 확인한 방향

AI는 명령과 상황에 맞는 행동을 선택한다.

| 항목 | 확인한 방향 |
|---|---|
| 제어 | PX4가 비행 제어를 담당 |
| 행동 | 준비된 행동을 계층으로 조합·선택 |
| 환경 | 실내 UWB 기반 호버링·(x,y,z,yaw) 이동 |
| 실기체 좌표 임무 | UWB 정확도·PX4 융합 검증 전에는 보류 |
| 입력 | 웹에서 Wi-Fi로 구조화 명령 전달 |
| 웹 계약 | 기존 Platform API v1 확장, 필드·버전은 협의 |
| 웹 명령 수락 기한 | 생성 후 10초 초기 시험값. 이미 수락한 임무 실행시간과 별개 |
| UWB 연동 | 전체 사양 수령 후 어댑터 설계. 현재 통신·출력 형식 확정 보류 |
| 지도 | 웹이 평면도·선반·통로 좌표를 생성 |
| 장애물 입력 | 웹이 장애물 외곽과 높이를 제공 가능 |
| 상하 구조 | 웹 지도에 선반·천장 형상과 높이 저장 |
| 지도 경계 | 웹 담당자에게 비행 경계·금지 구역 요청 필요 |
| 자동 우회 | 웹 비행 경계 전에는 활성화하지 않음 |
| 상부 공간 | 운영자가 임무 전 확인·승인 |
| 기체 크기 | 1호기 쿼드콥터 약 50×50cm, 6~7인치 |
| 속도 상한 | PX4의 실제 설정값을 따름 |
| 장애물 | 사용자가 경로를 제공하고, 필요 시 자동 우회 |
| 검증 자료 | 수동 RC 호버링 ULog를 분석·검증에 활용 |
| 임무 시작 | Jetson 자동 이륙을 기본으로, RC 이륙 후 인계는 예외로 지원 |
| RC 이륙 뒤 인계 | 웹 시작·PX4 상태 확인. 현 높이에서 인계 후 안전 지점에서 이륙 높이로 조정 |
| RC 예외 비행 범위 | 실제 이륙점 위로 수직 이륙·제자리 호버만 허용 |
| RC 예외 방향 | Jetson 인계 직전 현재 기체 앞 방향 확인, 사전 측량 변환 유효성 검사 |
| RC 연결 | Jetson 자동 이륙 전에 필수 아님. 없으면 수동 인계 불가 경고 |
| 자동 이륙 높이 | 웹 임무의 별도 필드, 첫 경유점 z와 구분 |
| 시작 목표 yaw | 웹 선택 필드. 있으면 이륙·호버 뒤 안전한 곳에서 제자리 회전 |
| 고도 목표 | 이동점 z는 기체 고도 목표로 변환. scan 라벨 z는 장착 오프셋·판독 자세로 기체 목표를 별도 계산 |
| z 기준 | 창고 바닥에서 위로 잰 높이(m) |
| 바닥 형상 | 한 층의 거의 평평한 바닥, 실제 높이 차이는 실측 |
| z 측정점 | 일반 이동은 기체 중심/PX4 기준점, scan은 라벨 위치 |
| 고도 변경 | 안전 지점에서 먼저 변경한 뒤 수평 이동 |
| z 제한 | 웹이 구역·통로별 최저·최고 높이 제공 예정 |
| 선반 위 비행 | 바닥 기준 고도 검증 전에는 보류 |
| 종료 | 마지막 경유점 뒤 출발 지점 복귀·이륙 직전 방향으로 회전·PX4 착륙 |
| 착륙 전 방향 회전 불가 | 복귀 지점에서 현재 방향 그대로 PX4 착륙 |
| 수동 인계 | 자율비행 중 RC 스틱 조작 시 비상으로 판단해 조종자에게 인계 |
| 일시정지 | 웹 재개·취소 명령까지 호버링 유지 |
| 복귀·착륙 중 일시정지/재개 | 거부. 긴급 착륙·RC 인계·비상 감시는 유지 |
| 취소 | 지상 준비 중단, 이륙 상승 중 현 위치 착륙, 임무 중 복귀·착륙 |
| 긴급 착륙 | 웹 명령을 받아 현 위치에서 PX4 착륙 요청 |
| 단일 이동 | 경유점 1개인 임무로 실행 |
| 임무 호버링 | 웹이 초 단위 유지 시간을 지정 |
| 방향 | 웹 yaw는 지도 절대 방향의 경유점 도착 자세. 미지정 시 이동 방향을 바라봄 |
| 시작 방향 불일치 | 임무 거부, 방향 재측량·센서 점검. 화살표만 고쳐 통과시키지 않음 |
| 비행 중 yaw 품질 상실 | PX4가 명확히 보고하면 이동 중단·PX4 Land |
| yaw 시험 기준 | 도착 목표 오차 ±10°로 시작, 실측 뒤 조정 |
| yaw 운용 구역 | 웹 지도에 승인 결과 저장, Jetson이 검증본 보관. 구역 안에서만 자동 임무 |
| 경유점/스캔 작업 | 모든 작업 순서 보존. 이동점은 기체가 방문, scan XYZ는 라벨 위치이므로 직접 비행 금지 |
| 스캔 이탈 | 결과 저장 후 검증된 접근 대기점 복귀·도착 확인 뒤 다음 목표 |
| 라벨 접근 방향 | 웹 담당자와 표현·제공 방식 협의. 미확정 방향으로 scan 시작 금지 |
| 스캔 작업 공간 | 웹에 라벨별 접근·작업 허용 구역 요청. 검증된 공간 안에서만 근접 접근·미세 조정·이탈 |
| Wi-Fi 단절 | 받아 둔 임무·지도로 계속 수행 |
| 단절 중 미전달 웹 요청 | 재연결 뒤 자동 실행 금지, 상태 확인 후 새 요청 |
| 새 임무·지도 개정 | 비행 중 새 임무는 거부, 현재 임무는 저장한 지도 개정 유지 |
| Offboard 송신 단절 | PX4 Land 실패 동작 사용 |
| 행동 목표 생성 정지 | 오래된 이동 목표 재송신 금지, 이동 정지 후 PX4 Land |
| RC 연결 단절 | Jetson 임무 계속 수행, 웹에 경고 |
| 경유점 차단 | 우회 불가 시 10초 대기 후 복귀 |
| 저전력 | PX4 보고 잔량 30% 이하에서 복귀 시도 |
| PX4 배터리 백업 | 위험 잔량에서 독립 Land, 임계값은 비행 시험으로 확정 |
| 위치 상실 | 정지·최대 8초 복구 대기 후 PX4 Land |
| 위치 복구 | 8초 안 연속 정상·PX4·좌표계·경로 재검증 통과 시 저장 단계 자동 재개 |
| 목표 도달 실패 | 현재 목표 실패 후 복귀, 복귀 불가 시 PX4 착륙 |
| 현 위치 착륙 | 하방 안전 불명확해도 비상 착륙 요청·위험 기록 |

| 비행 중 필수 기록 실패 | 복귀 후 착륙, 복귀 불가 시 현 위치 착륙 |

## 2. 전체 구조

임무 선택, 경로 계산, 비행 제어를 계층으로 나눈다.

```text
웹: 임무 + 경유점 + 지도
          |
       Wi-Fi
          v
입력 검증 / 좌표 변환 / 임무 버전 관리
          |
          v
행동 트리 <------ 공유 상태 <------ PX4 상태 + UWB 품질 + LiDAR
          |
          +-- Hover / Navigate / Wait / Land / Scan(설계)
                       |
                       v
            지도 기반 경로계획 + 장애물 우회
                       |
                       v
               3D 위치 목표 / 명령 중재
                       |
                     MAVROS
                       |
                       v
          PX4: EKF2 + 자세·고도·하위 비행 제어

별도 감시: RC 제어권, PX4 고장 대응, 상태 갱신 중단
기록: PX4 ULog + companion rosbag2 + 행동 전환 기록
```

1개 비행 출력 모듈만 MAVROS 명령을 발행한다.
BT와 웹 통신 지연이 출력 주기를 막지 않게 한다.
AI는 선택한 행동과 선택 이유를 항상 기록한다.
핵심 BT·임무·경로계획·PX4 출력/감시는 C++로 구현한다.
웹 연동·로그·보조 어댑터는 Python으로 분리한다.
BT는 BehaviorTree.CPP 4 계열을 사용하고 판단·출력 감시는 별도 프로세스로 둔다.
공통 계약과 모의 시험값은 [IMPLEMENTATION_BASELINE.md](IMPLEMENTATION_BASELINE.md)를 따른다.
목표 신선도 감시와 PX4 Land 경로는 언어 선택과 무관한 요구사항이다.

기존 [UWB 노드 설계](../../docs/uwb_node_design.md)는
`DWM3000EVB 태그 → CP2102 USB 시리얼 /dev/uwb (921600 8N1) →
JSON 한 줄씩 수신 → /uwb_pose → MAVROS vision_pose → PX4 EKF2`를 제안한다.
2026-09-27 원격 장치에서 `/dev/uwb` 링크는 보였지만,
저장소에서 UWB 노드 구현은 찾지 못했고 PX4 융합도 미검증이다.
장치 링크 존재를 유효 좌표 수신으로 간주하지 않는다.
기존 [HW팀 측정 기록](../../docs/report/draft_sw_section.md)의
약 0.66m 오차·43Hz는 태그 시리얼 단계의 보고값이다.
비행 좌표 정확도나 ROS2/PX4 융합 성능으로 재사용하지 않는다.
2026-10-02 결정: **UWB 전체 사양을 받은 뒤 어댑터를 설계한다.**
기존 장비의 프로토콜·필드·ROS 메시지를 새 장비의 확정 사양으로 쓰지 않는다.
UWB 입력·PX4 전달 구현 담당은 추후 확정한다.
현재는 [UWB_INTEGRATION_REQUEST.md](UWB_INTEGRATION_REQUEST.md)에 받을 자료와 검토 순서만 정한다.
메시지·QoS·좌표·시간·품질의 구체적 대응은 사양 수령 뒤 결정한다.
BT의 실제 위치 판단은 PX4 융합 상태를 사용하고,
원시 UWB와 품질 메시지는 감시·대조·기록에 사용한다.
새 장비가 지원하지 않는 z·yaw를 0 값의 유효 관측처럼 쓰지 않는다.
유효성·신규 관측·시간·좌표·불확실성·장치 식별의 의미를 확인해야 한다.
새 유효 관측만 융합하고 직전 값 유지·중복 재전송은 품질 상태로 기록한다.
좌표 숫자가 같아도 정지 중 새 관측일 수 있으므로 숫자만으로 중복 판정하지 않는다.
기존 `fix`·`xy_control_fresh`·`xy_control_held`는 과거 매핑 예시다.
위치 관측 상실 시간은 시리얼 줄 수신이 아니라
마지막 유효 신규 좌표의 시각부터 센다.
태그 단계의 예비 오차와 PX4 융합 정확도는 별도로 실측한다.
UWB 정확도·PX4 융합을 입증하기 전에는 자율 좌표 이동 실비행을 시작하지 않는다.
웹 도면 XY와 UWB XY는 기준점 측량으로 연결하는 방향으로 정했다.
운용 중 앵커 이동은 가정하지 않는다.
측량 방법·변환 수치·장치 사양은 UWB 구성이 확정될 때 정한다.

## 3. 행동 트리

노드별 입출력·전환·timeout·중단 규칙은 [BT_SPEC.md](BT_SPEC.md)에 둔다.
미정 수치는 [MEASUREMENT_REGISTER.md](MEASUREMENT_REGISTER.md)에서 관리한다.

우선순위가 높은 조건을 매 평가 때 확인한다.

```text
Root: 우선순위 선택
+-- RC 스틱 인계 / PX4 비상 모드 활성 -> 자율 출력 차단
+-- 착륙 잠금 -> Land 요청·실제 모드 확인·착륙 상태 감시
+-- 긴급 착륙 명령 -> PX4 착륙 요청 -> 착륙 상태 감시
+-- 비행 중 PX4 yaw 기준 변경 -> 이동 중단 -> PX4 착륙 요청
+-- PX4 yaw 추정 품질 상실 확인 -> 이동 중단 -> PX4 착륙 요청
+-- 행동 목표 갱신 상실 -> 이동 정지 -> PX4 착륙 요청
+-- 위치 상실 -> 이동 정지·최대 8초 복구 대기 / PX4 Land
+-- 잔량 30% 이하 / 필수 기록 실패 / 목표 도달 실패 -> 임무 중단 -> ReturnHome / 실패 시 PX4 착륙
+-- 이미 복귀·착륙 단계 -> 진행 유지 / 일시정지·재개 거부
+-- 취소·복귀 명령 -> 현재 단계별 준비 중단 / 현 위치 착륙 / ReturnHome
+-- 일시정지 명령 -> 임무 진행 보존 -> Hover / 재개·취소 대기
+-- 실행 임무
|   +-- 명령·지도·좌표계·yaw 검증 구역·제어권 확인
|   +-- 기본 지상 시작: 이륙 높이·출발점·시작 회전 공간 확인 -> 목표 선행 송신 -> PX4 arm·이륙
|   +-- 예외 RC 이륙 시작: 웹 승인·현 위치 유지 목표 선행 송신 -> Offboard 인계 -> 안전 지점에서 높이 조정
|   +-- 선택 시작 yaw가 있으면 안전 지점에서 PX4 회전·도착 확인
|   +-- 다음 목적지 선택
|   +-- Navigate
|   |   +-- 경로 유효 -> 경로 추종
|   |   +-- 경로 차단 -> 감속·정지 -> 우회 계산 -> 경로 추종
|   |   +-- 우회 불가 -> 정지·대기 -> 시간 초과 시 ReturnHome
|   +-- 도착 판정 -> 목적지 행동(Hover / 향후 Scan)
|   +-- 다음 목적지 또는 임무 완료 후 ReturnHome
|   +-- 출발 지점 도착 확인 -> 안전하면 이륙 직전 방향 회전 -> PX4 착륙
+-- 임무 없음 -> 지상 대기 / RC 비행 감시
```

이 그림의 상세 우선순위·중첩 사건 처리는 BT_SPEC을 따른다.
Jetson이 공중 제어권을 가진 채 실행 문맥을 잃으면 임의 호버를 계속하지 않고 Land로 종료한다.
복귀·회복 대기 같은 비행 행동은 비행 상태에서 평가한다.
지상에서는 같은 이상을 시작 거부 사유로 보고한다.
상승 중 취소는 앞서 합의한 현 위치 착륙으로 처리한다.
장애물 검사는 Navigate뿐 아니라 ReturnHome 이동에도 적용한다.
LiDAR 단절은 병렬 상태 감시로 경고하고 자동 우회를 끄되,
취소·복귀·일시정지 평가를 가리는 최상위 행동으로 두지 않는다.
반복 평가는 진행 중 행동을 처음부터 시작하지 않는다.
노드는 진행 중·성공·실패 상태를 반환한다.
명령 수락 ACK와 행동 성공은 서로 다른 사건이다.

| 행동 | 시작 조건 | 완료 조건 | 중단·실패 처리 |
|---|---|---|---|
| Hover | 비행 중, 위치 유지 가능 | 웹의 유지 시간 동안 위치·속도·도착 방향 조건 충족 | 일시정지는 재개·취소까지 유지 |
| Navigate | 좌표계 일치, 유효 위치·경로 | XYZ·yaw·속도 조건을 일정 시간 충족 | 차단 시 재계획, 시간 초과 시 실패 |
| Wait | 정지 상태를 유지할 수 있음 | 장애물 해소·재개 조건 충족 | 대기 한도 후 실패 보고 |
| Land | PX4 연결·명령 권한 확보 | 실제 landed·disarm 확인 | ACK만으로 완료 처리 금지 |
| Pause/Resume | 활성 임무 식별 가능 | 진행 저장 / 유효성 재검사 | 오래된 경로로 즉시 재개 금지 |
| Takeoff | 지상, PX4 준비 상태 확인 | PX4 자동 이륙 완료와 위치 유지 확인 | 시작 실패 시 목적지 이동 금지 |
| ManualHandover | RC 인계 감지 | PX4 모드 전환·출력 권한 반환 확인 | 착륙 후 새 임무만 허용 |
| ReturnHome | 실제 이륙점 좌표·복귀 지도 유효 | 이륙점 도착·정지 확인 | 우회 불가면 현 위치 PX4 착륙 요청 |
| RecoveryWait | 이동 중단·PX4 유지 가능 | 위치 관측 복구 후 재검증 | 시간 초과나 유지 불가 시 PX4 Land |

금지 사유: 실패 후 다음 목적지로 자동 진행하면
미완료 작업이 완료된 것처럼 보일 수 있다.
실패는 상위 임무에 원인과 함께 전달한다.

## 4. 지도와 자동 우회

웹 경로를 검증하고, 실제 장애물을 반영한다.

| 계층 | 입력 | 출력 |
|---|---|---|
| 지도 | 장애물 외곽·높이·이동 금지 영역 | 통과 가능한 영역 |
| 기본 경로 | 현재 위치·웹 경유점 | 목적지까지의 이동 경로 |
| 장애물 갱신 | LiDAR·PX4 자세/위치·센서 설치 변환 | 현재 통과 불가능한 영역 |
| 우회 | 기본 경로·새 장애물 | 허용 영역 안의 대체 경로 |
| 추종 | 승인된 경로·현재 PX4 상태 | 제한된 3D 위치 목표 |

좌표점뿐 아니라 점 사이 구간도 검사한다.
기체 크기·위치 불확실성·제동 거리를 반영한다.
기체 가로·세로는 현재 약 0.5m로 잡는다.
최종 충돌 외형은 조립 후 프로펠러 끝까지 실측한다.
속도 상한은 PX4 실제 설정과 상태에서 읽는다.
경로계획도 그 상한과 제동 거리를 반영한다.
웹에서 통로 폭을 따로 주는 것은 요구하지 않는다.
장애물 좌표만으로 형상을 알 수 없으면 통과를 승인하지 않는다.
오래된 LiDAR 관측을 새 장애물이 없다는 증거로 쓰지 않는다.
LiDAR 수신만 끊기면 별도 대기 없이 검증된 웹 경로를 계속한다.
그동안 자동 우회를 중단하고 관측 공백을 경고·기록한다.
끊기기 전에 감지한 장애물은 지우지 않는다.
기존 장애물이 경로를 막으면 장애물 차단 절차가 우선한다.
우회 탐색은 시간·거리·허용 영역에 상한을 둔다.
웹 비행 경계가 없으면 자동 우회를 비활성화한다.
그때는 웹이 지정한 경로만 검사·실행한다.
막힌 통로에서 진행할 길이 없으면 대기한다.
장애물 회피만을 위해 임의로 고도를 바꾸지 않는다.
이유: 현재 센서로 위쪽 장애물을 확인할 수 없다.
경유점 z 변경은 검증된 안전 지점에서만 수행한다.
2D LiDAR가 놓치는 상하 장애물은 지도에 반영해야 한다.
웹 지도는 선반·천장의 점유 공간과 높이를 담는다.
지도 형상 형식은 웹 계약을 정할 때 확정한다.
바닥 기준 고도가 실측으로 검증되기 전에는
선반 상판 위를 지나는 경로를 허용하지 않는다.

경유점 z가 바뀌면 먼저 안전 지점으로 이동한다.
그곳에서 정지해 새 z로 상승·하강한다.
고도 안정 확인 뒤 목표 x/y로 이동한다.
고도 변경 중 수평 경로를 동시에 진행하지 않는다.
수직 구간의 위·아래 여유도 지도에서 확인한다.
Jetson이 지도·PX4 상태·센서로 지점을 선정한다.
PX4가 정해진 지점과 높이로 이동한다.
선정에 필요한 공간 데이터 형식은 미정이다.
확인할 자료가 없으면 고도 변경 명령을 거부한다.
자동 이륙은 웹의 별도 이륙 높이까지 수직 상승한다.
그 위치의 상승 공간과 z 제한을 이륙 전에 검사한다.
첫 경유점 z가 다르면 일반 고도 변경 절차를 적용한다.

웹은 구역·통로마다 z 최저·최고를 제공한다.
Jetson은 경로의 모든 구간에서 이 범위를 확인한다.
경계에서는 양쪽 구역의 허용 범위를 함께 검사한다.
기체 크기와 위치 오차만큼 여유를 둔다.
허용 범위가 겹치지 않으면 해당 경로를 쓰지 않는다.

우회는 동일 경유점으로 가는 실행 경로를 바꾼다.
웹의 임무 개정 번호와 구분해 기록한다.
웹의 모든 경유점은 지정된 순서로 방문한다.
우회 중에도 다음 경유점으로 건너뛰지 않는다.
경유점이 계속 막히면 해당 지점 실패로 보고한다.
10초 동안 장애물 해소와 우회 가능성을 재평가한다.
10초가 끝나도 길이 없으면 복귀를 시작한다.
복귀도 막히면 현재 위치에서 PX4 착륙을 요청한다.

### 4.1 합성 지도 우회 구현 기준

`REPLAY`에서 `replay_static_detour_v1`을 선언한 불변 snapshot만 지원한다.
`global_detour_enabled=true`에는 웹 비행 경계와 명시적으로 제공된 금지 구역 목록이 필요하다.
Jetson의 승인된 시험 설정에는 격자 간격·노드/확장 수·경로 길이·탐색 시간 상한을 둔다.
초기 합성 설정은 0.25m 격자, 8192개 노드, 4096회 확장, 50m 경로, 50ms 탐색이다.
실측 비행 기본값이 아니며, 탐색 시간은 기하 연산 사이에서 확인하는 예산이다.

C++ A*는 목표 고도를 변경하지 않고 현재 고도의 XY 경로만 생성한다.
수직 선행 구간은 기존 공간 검사를 통과해야 하며, 불가능하면 임무 준비를 거부한다.
각 대각선·끝점 연결·단축 선분 전체에 기체/오차/제동 여유와 고도/yaw/경계 검사를 적용한다.
허용 구역은 선분마다 하나의 볼륨으로 덮여야 한다. 경계 없는 우회와 미검증 구역의 합집합은 승인하지 않는다.
격자 해상도·예산 한계로 찾지 못한 경우는 `PLAN_*` 실패이며 경로 부재의 수학적 증명은 아니다.

우회 중간점은 정지·안정 확인 후 다음 선분으로 진행하고, 필수 경유점 도착으로 세지 않는다.
도착 yaw·hover·scan은 원래 필수 목표에서만 실행한다. 비행 이력에는 중간점도 남겨 복귀에 사용한다.
실행 중 계획 실패는 같은 차단의 10초 예산 안에서 재평가하며 반복 탐색으로 예산을 늘리지 않는다.
복귀 중 계획 실패는 대기 없이 Land로 전환한다. RC/PX4 인계·위치/yaw 실패·긴급 착륙은 계획보다 우선한다.
정적 지도 계획만 먼저 구현한다. 실제 LiDAR 장애물 갱신·단절 시 우회 비활성화·안전한 고도 변경점 탐색은 후속이다.
"정확히 방문"은 XYZ와 yaw 허용범위에서 판정한다.
위치·방향 오차와 머무름 시간은 실측 뒤 정한다.
목표 yaw 오차 ±10°는 시험 시작값이다.
최종 값과 연속 유지 시간은 창고 실측 뒤 정한다.
허용범위를 연속해서 유지한 시간만 방문에 포함한다.
범위를 벗어나면 방문 유지 시간을 다시 센다.
웹의 호버 시간도 도착 판정 뒤부터 센다.
웹 yaw는 경유점에 도착한 뒤 기체가 바라볼 목표 방향이다.
XYZ 도착 후 회전 공간을 검사하고 제자리 회전한다.
미지정 시 이동 방향을 바라보는 기존안을 유지한다.
도착점에서는 마지막 수평 이동 구간의 방향을 기본 yaw로 쓴다.
수평 이동이 전혀 없었다면 현재 yaw를 유지한다.
이동 중 지정 yaw를 계속 유지하는 명령은 현재 범위가 아니다.
세부 검토와 검증 항목은 [YAW_RESEARCH.md](YAW_RESEARCH.md)에 둔다.
현재 확인된 방향 센서는 PX4 자력계뿐이다.
이 때문에 방향 정확도를 검증한 구역만 자동 임무에 쓴다.
출발·경유·복귀 경로가 검증 구역을 벗어나면 시작을 거부한다.
웹 임무가 검증 구역 밖이나 선반 위 경로를 요구하면
Jetson이 임의 수정하지 않고 사유를 웹에 반환한다.
웹 지도에 검증 구역의 경계·승인 결과를 보관한다.
Jetson은 지도 개정과 승인 결과를 함께 받은 뒤 검증본을 저장한다.
Wi-Fi가 끊겨도 같은 임무·지도 개정의 검증본으로 판단한다.
지도와 PX4 yaw의 변환은 사전 측량·검증해 버전으로 보관한다.
이륙 위치·방향이 바뀌어도 현재 방향으로 변환값을 재계산하지 않는다.
웹 시작 화살표는 실제 기체가 놓인 방향을 확인하는 용도다.
Jetson은 변환된 PX4 heading과 화살표의 일치 여부를 확인한다.
화살표 확인만으로 자력계 오차가 보정된 것으로 간주하지 않는다.
PX4는 변환된 yaw 목표의 회전 제어를 담당한다.

임무를 끝내면 Jetson이 출발 지점 복귀 경로를 만든다.
복귀에도 지도·고도 제한·LiDAR 검사를 적용한다.
웹 경계가 없으면 검증·기록한 진행 경로를 역추적한다.
역추적 중에도 새 장애물이 보이면 멈춰 검사한다.
출발 지점 도착을 확인하고 안전 공간에서 이륙 직전 방향으로 돈다.
방향 도착을 확인한 뒤 PX4 착륙을 요청한다.
회전 공간이 막혀 있으면 방향 복원을 생략하고 현재 방향에서
PX4 착륙을 요청한다. 생략 원인을 기록한다.
실내 선반을 고려해 PX4의 단순 RTL에 의존하지 않는다.
실제 이륙한 바닥 좌표를 출발 지점으로 기록한다.
RC 이륙을 허용하려면 이륙 전부터 좌표를 기록한다.
RC 예외 이륙 뒤에는 수평 이동 없이 출발점 위에서 호버한다.
이륙점에서 허용 오차 밖으로 이동하면 자동 인계를 거부한다.
허용 XY 오차는 실제 위치 정확도를 측정한 뒤 정한다.
유효한 출발 기록이 없으면 자동 복귀 임무를 시작하지 않는다.
이륙 전 출발 지점의 기체 외형·착륙 공간을 확인한다.
복귀 뒤 하강할 수직 공간도 지도에서 확인한다.
복귀 실패 시 현재 위치에서 PX4 착륙을 요청한다.
현 위치 착륙의 하방 상태는 ToF로 함께 확인한다.
하방 안전을 확인하지 못해도 비상 착륙을 요청한다.
그때 위험과 착륙 요청의 결과를 기록한다.

웹 지도는 미리 알려진 선반·통로를 제공한다.
LiDAR는 새로 나타난 장애물만 반영한다.
지도에 없는 영역을 통로로 자동 승인하지 않는다.
경로계획기는 충돌 없는 경로를 찾는다.
BT는 재계획 시점과 실패 뒤 행동을 결정한다.
운영자가 지정한 경로에 별도 고정 구역을 두지 않는다.
해당 경로도 지도 형상·z 제한 검사를 통과해야 한다.
새 상부 장애물은 현재 2D LiDAR로 감지할 수 없다.
운영자는 임무 전 해당 경로의 상부 공간을 확인한다.
승인이 없으면 자동 임무를 시작하지 않는다.
승인 뒤 새로 생긴 상부 장애물은 감지할 수 없다.
그 잔여 위험은 웹과 비행 기록에 명시한다.

Jetson에만 잔량 자료가 안 보이고 PX4 배터리 감시가 유효하면
임무를 계속하고 PX4 자체 실패 동작에 맡긴다.

웹 v1과 지도 데이터의 연결 형식은 아직 미확인이다.
실서버 통신이나 기존 ZIP의 비행 구현을 검증한 것은 아니다.

새 시작 요청·착륙 후 새 임무·실제 착륙 상태를 확장 계약에 맞춘다.
웹 회신 전에는 새 필드가 이미 지원되는 것으로 간주하지 않는다.
JSON/API 운반 방식은 입력 연결 모듈에서 처리한다.
BT는 같은 검증된 임무 구조만 읽는다.
지도 형상 전달은 현재 구현 예정으로만 둔다.
형식 미확정과 지도 검증 생략을 혼동하지 않는다.
기존 검토에서 두 앵커 축은 약 94.23°였다.
웹 축 정의를 실제 직교 좌표와 맞춰야 한다.
좌표계 변환 근거가 없으면 이동 명령을 거부한다.
근거: `docs/companion_platform_api_v1_review.md` 5절.

웹 v1 경유점에는 z가 포함된다.
현재 v1 예시에는 yaw와 지도 형상 필드가 없다.

기존 ZIP은 x/y/z를 모두 받아 도착을 판정한다.
이 설계도 기체 xyz 목표와 3D 도착 판정을 사용한다.
일반 이동점의 웹 z를 PX4 로컬 고도 목표로 변환해야 한다.
scan의 웹 XYZ는 라벨 위치다. 먼저 QR_SCAN_SPEC에 따라 기체 목표 pose를 산출한다.
기존 /cmd_vel 수평 속도 경계만으로는 부족하다.
3D 위치 목표와 지속 송신 계약을 새로 정한다.
웹 z의 기준은 창고 바닥 위 높이(m)다.
일반 이동점 높이의 측정점은 기체 중심 또는 PX4 위치다. scan z의 측정점은 라벨이다.
PX4 로컬 z의 원점·부호·기체 기준점을 확인한다.
이륙 전 변환 관계를 정하지 못하면 임무를 거부한다.
근거: `docs/companion_platform_api_dictionary.md` 3.2절.

**PX4는 변환된 기체 고도 목표를 추정·제어한다. scan 라벨 z를 직접 비행 목표로 쓰지 않는다.**
Jetson은 z용 PID나 추력 제어를 만들지 않는다.
MAVROS 목표 메시지·좌표 변환을 확인한다.
z 필드 생략이나 기본값 0으로 목표를 대신하지 않는다.
기존 altitude_policy의 "z 직접 제어 금지"는
이 경계를 명시하도록 구현 전에 문구 검토가 필요하다.
PX4의 ToF 융합과 고도 기준도 검증해야 한다.
현재 ULog의 `EKF2_HGT_REF=0`은 기압계 기준이고,
`EKF2_RNG_CTRL=1`은 조건부 ToF 융합이다.
ToF 장착만으로 웹의 바닥 기준 z가 보장되지 않는다.
ToF는 아래 물체까지의 거리를 측정한다.
아래에 선반이 있으면 바닥 높이와 달라질 수 있다.
창고 바닥 기준 z는 ToF 거리만으로 확정하지 않는다.
웹의 구역·통로별 z 제한과 기체 높이를 비교한다.
운용 구역은 한 층의 거의 평평한 바닥이라는 전제다.
구역별 바닥 높이 차이를 측정해 변환 오차에 포함한다.
후속 확장에서 바닥이 평평하지 않으면 웹 경유점 z를
공통 높이 기준으로 지정할 수 있다.
그때도 바닥·선반과의 여유 계산에는 바닥 높이 지도가 필요하다.
이 확장은 첫 버전 범위에서 제외한다.
[PX4 거리센서 설명](https://docs.px4.io/main/en/sensor/rangefinders)

기본 운용은 Jetson 자동 이륙이다.
RC 이륙은 예외이며, 자율비행 중 RC 조작은 비상 인계다.
자동 이륙은 웹의 별도 이륙 높이를 받으면 시작한다.
값이 없거나 출발 지점 수직 공간 검사를 통과하지 못하면 거부한다.
첫 구현안은 PX4 Offboard 3D 위치 목표를 사용한다.
PX4가 상승과 위치 유지를 수행하고 Jetson이 확인한다.
RC 이륙 뒤 시작할 때는 PX4 상태와 현 높이의 안전 경로를 먼저 확인한다.
Offboard 전환 전에는 유효한 목표를 먼저 연속 송신한다.
RC 비행 인계 때는 현재 위치 유지 목표로 시작한다.
실제 Offboard 전환을 확인한 뒤 경로 목표로 바꾼다.
RC 스틱 인계의 1차 판정은 PX4에서 수행한다.
Jetson은 PX4 모드 변경을 보고 임무를 중단한다.
첫 버전은 PX4의 설정된 스틱 임계값을 따른다.
인계 임계값과 실제 반응은 기체 시험으로 확인한다.
RC가 연결되어 있으면 PX4의 실제 수동 입력원이
물리 RC인지 이륙 전 확인한다.
RC 없이 이륙하는 경우에는 수동 인계 기능이 없음을 표시한다.
나중에 RC가 연결되면 실제 입력원 선택·스틱 인계를 시험한다.
첨부 로그의 `COM_RC_OVERRIDE=1`은 Auto만 허용한다.
Offboard 임무의 RC 인계에는 bit 1도 필요하다.
자동 이륙까지 포함해 두 모드 설정을 검토한다.
두 모드에서 실제 인계되는지는 별도로 시험한다.
두 모드 허용 후보는 `COM_RC_OVERRIDE=3`이다.
첨부 로그의 `COM_RC_IN_MODE=3`은 첫 입력원을 고정한다.
물리 RC만 쓰는 후보 `COM_RC_IN_MODE=0`도 검토한다.
`COM_RC_IN_MODE=4`는 수동 입력 자체를 비활성화하므로
이번 RC 비상 인계 요구에는 바로 적용할 수 없다.
RC 미연결 이륙과 연결 후 스틱 인계를 같은 설정으로 시험한다.
PX4 중대 저전력 반응 중에는 스틱 인계가 제한된다.
[해당 펌웨어의 설정 정의](https://raw.githubusercontent.com/PX4/PX4-Autopilot/d6f12ad1c4f70ad3230afd7d86e971421e02fef4/src/modules/commander/commander_params.c)

MAVLink Offboard는 setpoint가 생존 신호를 겸한다.
PX4 v1.17은 2Hz 초과와 진입 전 선행 송신을 요구한다.
SIM-01의 출력 주기는 20Hz다. 실기체 주기는 통신·부하 시험으로 승인한다.
최종 주기는 실제 지연·PX4 동작 시험으로 정한다.
목표 좌표가 같더라도 유효한 Hover 등은 행동 계층의
단조 시계 기반 생존 신호와 명령 세대를 계속 갱신한다.
출력 모듈은 목표값 변화 여부가 아니라 이 생존 신호의 나이를 본다.
기한이 지나면 이전 이동 목표를 재송신하지 않고 이동을 정지시킨 뒤
PX4 Land를 요청한다. 정지 목표는 현재 위치가 유효할 때만 만든다.
PX4 Land 전환이 확인되지 않으면 Offboard 송신을 멈춰
PX4의 독립 Offboard 상실 동작으로 넘기는 경로를 시험한다.
기한과 Land 전환 확인 시간은 실측으로 정한다.
Offboard 송신 상실 때 PX4 자체 동작은 Land로 정한다.
첨부 로그의 `COM_OBL_RC_ACT=0`은 Position 설정이다.
목표 설정 후보는 `COM_OBL_RC_ACT=4`다.
`COM_OF_LOSS_T=1.0초`를 시험 기준으로 유지한다.
첨부 로그에는 `COM_FAIL_ACT_T=5.0초`도 있다.
따라서 실제 Land 시작이 1초인지 단정하지 않는다.
두 지연의 실제 작동을 지상·시뮬레이션에서 측정한다.
추가 5초 대기가 확인되면 가능한 짧게 조정한다.
변경은 다른 PX4 실패 동작에도 영향을 주므로 함께 시험한다.
RC 상실 시에도 Offboard 임무를 계속하려면
`COM_RCL_EXCEPT`의 Offboard 예외 bit 2를 검토한다.
첨부 로그의 `COM_RCL_EXCEPT=0`은 예외가 없다.
후보값 4를 설정·시험한 뒤 적용한다.
실제 설정·작동 확인 전에는 자동 비행을 시작하지 않는다.
첨부 로그의 `COM_LOW_BAT_ACT=0`은 경고만 낸다.
현재 위험·긴급 잔량 기준은 각각 7%·5%다.
Jetson 잔량 수신 상실을 PX4에 맡기려면
독립적인 Land 동작과 잔량 기준을 설정·시험해야 한다.
해당 펌웨어의 `COM_LOW_BAT_ACT=2`가 Land 설정 후보이다.
`BAT_CRIT_THR`의 최종 값은 비행 시험으로 정한다.
Jetson의 30% 복귀와 PX4 Land의 우선순위를 함께 검증한다.
현재 기체 파라미터는 아직 변경하지 않았다.

## 7. 로그를 받는 곳과 처리 방식

비행 중에는 최신 상태를 읽고, 비행 뒤에는 기록을 분석한다.

| 자료 | 수집 위치·방법 | 쓰임 |
|---|---|---|
| ULog | Pixhawk SD → 비행 종료 후 Jetson 자동 다운로드 | PX4 상태·추력·비행 모드 확인 |
| rosbag2 | Jetson에서 필요한 ROS2 topic 기록 | UWB·LiDAR·웹 입력·실행 출력 비교 |
| 행동 기록 | Jetson에 전환마다 기록 | 선택 이유·시간 초과·우회 원인 추적 |
| 비행 메타정보 | 지도·기체·펌웨어·설정 버전과 비행 ID | 같은 시험의 자료를 연결 |

PX4 disarm 뒤 로그 파일이 닫힌 것을 확인하고 수집한다.
MAVLink 로그 목록과 조각 다운로드를 이용한다.
통신 중단 시 받은 위치부터 재시도하거나 처음부터 다시 받는다.
전송 완료·실패 뒤 `LOG_REQUEST_END`로 종료한다.
기체에서 해당 기능이 실제로 되는지는 지상 시험으로 검증한다.
후보 구현은 MAVROS `log_transfer` 또는 별도 MAVLink 클라이언트다.
현재 Jetson에는 `mavros_extras`와 LogRequest 서비스 형식이 있다.
실제 Pixhawk 연결·파일 전송은 아직 확인하지 않았다.
비행 출력 통신과 충돌하지 않도록 전송은 비행 후에만 시작한다.
새 비행이 시작되면 진행 중 로그 전송을 중단·재개 대기로 둔다.
[MAVLink 로그 메시지 정의](https://mavlink.io/en/messages/common.html),
[MAVROS 로그 플러그인](https://github.com/mavlink/mavros/blob/ros2/docs/plugins/index.md).

Jetson은 비행 ID별 임시 파일로 수집한다.
전송 완료·파일 크기·ULog 파싱·SHA256을 확인한다.
그 뒤 확정 파일과 검증 상태를 원자적으로 기록한다.
실패·미완료 파일은 검증 완료로 표시하지 않고 재시도한다.
rosbag2·행동 기록에도 같은 비행 ID와 종료 시각을 붙인다.
비행 종료 시각은 PX4 disarm을 기준으로 한다.
UTC 시계가 신뢰되지 않으면 보존 시각을 계산하지 않는다.

Jetson의 검증된 비행 로그 사본은 종료 72시간 뒤 삭제한다.
ULog·rosbag2·행동 기록을 비행 ID 단위로 정리한다.
수집이 실패했거나 검증되지 않은 묶음은 자동 삭제하지 않는다.
비행 중인 파일과 검증 중인 파일도 자동 삭제하지 않는다.
Pixhawk SD 원본은 이 정책의 삭제 대상이 아니다.
`LOG_ERASE`는 모든 PX4 로그를 지우므로 호출하지 않는다.
재시도 실패·저장공간 부족은 운영 경고로 보고한다.
ULog 수집 실패만으로 다음 자율 임무를 막지 않는다.
Pixhawk SD 원본은 남기고 실패 경고를 웹에 표시한다.
새 비행의 행동·센서 기록을 시작할 저장공간이 없으면
임무 시작을 거부하고 공간 복구 뒤 다시 받는다.
필요한 여유 용량은 실제 기록률·임무 길이 측정 후 정한다.
[MAVLink `LOG_ERASE` 정의](https://mavlink.io/en/messages/common.html).

```text
검증 전 ULog 원본·Jetson 사본 보존 + SHA256
 -> pyulog 해석 / topic·단위·기록 간격 확인
 -> PX4·Jetson 시간 기준 정렬
 -> RC 모드·이륙/착륙·위치 유지 구간 분리
 -> 행동 조건 후보 검토
 -> 기록을 재생해 BT 전환·실패 이유 확인
 -> 시뮬레이션에서 명령에 따른 비행 반응 확인
```

초기값·미사용 필드·기록 누락을 구분한다.
NaN을 일괄 0으로 바꾸면 명령 의미가 달라진다.
재생은 해당 시점까지 알려진 값만 제공한다.
센서 수신 시각과 PX4 부팅 경과 시각은 직접 빼지 않는다.
시간 정렬 오차와 데이터 나이를 함께 기록한다.

추력 기록은 호버링 구간과 부하 확인에 활용한다.
추력 명령을 그대로 재생해 좌표를 이동시키지 않는다.
이유: 같은 명령도 배터리·하중·현재 상태에 따라 달라진다.

| 로그 근거 | 추출할 값 | 행동 설계에 쓰는 곳 |
|---|---|---|
| hover_thrust_estimate·배터리 | 유효 호버 구간의 추정치 변화 | 부하 변화·PX4 유지 성능 검토 |
| PX4 위치 목표·실제 위치 | 이동 응답·정착 시간 | 속도 제한·도착 유지 시간 실측 |
| UWB·PX4 위치·기준 좌표 | 오차 분포·갱신 공백 | 허용 XY 오차·위치 상실 판정 |
| PX4 높이·ToF·바닥 기준 | 높이 편차·반사면 영향 | 허용 z 오차·변환 검증 |
| 배터리·복귀 경로 | 복귀 중 잔량 변화 | 30% 복귀 기준의 적정성 검증 |

제공된 수동 RC 로그에서는 호버링 구간과 설정을 일부 평가할 수 있다.
위치 목표에 대한 자동 추종 성능은 새 시험 로그가 필요하다.
분석 결과는 기체·배터리·PX4 설정 버전과 묶는다.
새 로그로 비행 중 제어 이득을 자동 변경하지 않는다.
조건이 바뀌면 새 제한값을 별도 시험으로 승인한다.
현재 로그의 관측 결과는 [LOG_REVIEW.md](LOG_REVIEW.md)에 있다.

위치 상실 때 Hover를 무조건 선택하지 않는다.
PX4가 위치 유지를 할 수 있는 상태인지 먼저 본다.
복구 후 재검증·자동 재개 정책은 확정했고, 실기체 연속 정상 시간은 측정한다.

검증 순서는 문서 합의 → 상태 재생 → 시뮬레이션이다.
그다음 실시간 판단만 비교하고 제한 비행으로 확인한다.
기록 재생만으로 새 경로의 비행 성능을 입증하지 않는다.
성능 판정은 도착 오차·호버링 유지·우회 성공으로 한다.
수치는 위치 측정 정확도와 사용자 목표를 확인해 정한다.

절대 좌표 이동의 선행 조건은 UWB의 PX4 융합 검증이다.
현재 제공된 ULog에서는 `EKF2_EV_CTRL=0`이다.
다음 시험에서는 UWB 품질과 PX4 수용을 함께 확인한다.
위치 유효 표식만으로 좌표 정확도를 승인하지 않는다.
