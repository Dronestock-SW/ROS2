# 3차 최종 검토

**표기:** [사실]은 제공된 기록·소스, [추정]은 미검증 판단, [제안]은 설계안입니다. 새 실기 수치는 쓰지 않았고, 실행 항목은 모두 향후 후보입니다.

---

## 1. 정정 7항에 대한 판단

**1항 (T_LM): 동의합니다. 2차안의 오류입니다.**
- EV−EKF 차이로 T_LM을 재추정하면 실제 drift가 프레임 offset으로 흡수되어 물리 목적지가 움직입니다.
- 네 층을 분리해야 합니다.
  - `goal_M`: 불변입니다.
  - `C_ME`: 축·원점·레버암을 담은 M→EV 입력변환입니다. frame revision으로만 갱신합니다.
  - EKF 추정오차: EKF가 처리합니다.
  - 제어 참조 연속성 offset: 임시이며 BRAKE/HOLD에만 적용합니다.
- `C_ME`는 좌표계 변경이 별도로 증명될 때만 바꿉니다.
- EV_CTRL=1(XY)은 yaw 정합의 증거가 아니라는 점에도 동의합니다. 이 문제는 아래 2절 ①에서 치명 조건으로 다룹니다.

**2항: 동의합니다.**
- delta 이동은 신뢰한 reset일 때, 임시 BRAKE/HOLD 참조에만 적용합니다.
- 다음 경우에는 자동 재개하지 않습니다.
  - xy/vxy/z/vz/heading reset이 한 묶음으로 설명되지 않을 때
  - 세대가 불명확할 때
  - 관측이 모순될 때
- 재계획은 현재 위치와 **실제 속도**에서 시작합니다.

**3항: 동의하며, 가장 중요한 정정입니다.**
- [사실] d6f12ad의 `adjustSetpointForEKFResets`는 오래된 setpoint에 delta를 자동으로 가산합니다.
- [추정] 따라서 companion이 delta를 직접 적용하면 이중 보정이 되고, 적용하지 않으면 다음 새 timestamp 송신이 FC의 보상을 취소합니다.
- companion이 reset을 인지하기 전까지의 창은 텔레메트리 지연에 좌우되며, 크기를 보장할 수 없습니다.
- 그러므로 companion 단독 shift는 해결책이 될 수 없습니다. 최종안에서는 "엄밀 연속성 미검증"을 명시합니다.
- 추가 확인 대상(미확인): MAVROS/mavlink 수신부에서 trajectory_setpoint timestamp를 어느 시점 기준으로 찍는지.

**4항: 동의합니다. 다만 단일 키보다 두 키로 나누기를 제안합니다.**
- **제어 참조 키**: (FC boot/session, 선택된 estimator instance, reset counter 묶음)
  - counter는 증가 비교가 아니라 "변화" 비교로 다루어 wrap에 대응합니다.
  - instance 전환은 그 자체를 reset 사건으로 취급합니다.
- **관측 키**: (clock epoch, geometry/frame revision, source seq·source timestamp)
- 둘 다 내부 일관성 계약이며, 외부 통신 규격을 강제하지 않습니다.

**5항: 동의합니다.**
- HOLD 허용은 다음을 모두 함께 보는 조건입니다.
  - 위치·속도 유효성과 신선도
  - fusion 건강(innovation 상태)
  - 현재 실제 속도
  - 추정오차 상계(eph는 입력의 하나일 뿐 증명이 아님)
  - 공간 여유
- velocity만 관측될 때는 절대오차가 시간에 따라 커지므로, HOLD 허용시간은 예산 소진으로 정의합니다.
- 순간 미갱신과 실제 소실은 다음으로 구분합니다.
  - "센서별 공칭주기 × 허용배수 + 진단 경로 지연"을 이름 붙은 파라미터로 둡니다(수치 미정).
  - PX4 자체 상태 플래그를 1차 근거로, companion이 관측한 `time_last_fuse`를 2차 근거로 씁니다.

**6항: 동의합니다.**
- OK 상태가 고착된 것을 감지하려면 다음을 함께 봅니다: 원시 측정시각 나이, status 메시지 나이, seq 증가 여부, epoch 동일성.
- 재개 근거는 "새 관측 + 새 융합"뿐입니다.

**7항: 동의합니다.**
- 독립 정답 기준의 10cm 요건과 내부 도착판정 설계(임계값과 체류조건)를 분리합니다.
- reset 차이는 위치에 더하지 않습니다. 기존 불확실성 예산에 없던 크기라면 **예산을 갱신**합니다. 2차의 "항상 이중계상"은 과잉 일반화였습니다.

**최종 우선순위 A~E: 동의합니다.** 다만 아래 ①과 ③은 A와 B의 진입 조건으로 넣어야 합니다.

## 2. 여전히 빠진 치명적 설계 조건

**① heading·회전 정합의 진실 출처** [추정, 치명 후보]
- 현재 확인된 정보로는 다음이 정해져 있지 않습니다.
  - EV가 yaw를 주지 않을 때 PX4 heading을 무엇으로 결정하는지
  - 실내에서 그 heading이 M 축과 어떤 관계인지
  - heading reset이 생겼을 때 `goal_M` → 제어 프레임 표현이 어떻게 바뀌는지
- 회전 오차는 거리에 비례하는 일관된 위치 편향을 만들고, 정지 상태에서도 드러나지 않을 수 있습니다.
- 이것이 확정되기 전에는 "원래 물리 목적지로 재개"를 보장할 수 없습니다.

**② fallback 경로의 실내 유효성** [추정]
- 지금까지 "기존 PX4 fallback 유지"는 전제였을 뿐 검증되지 않았습니다.
- 다음 경우에 실제로 어떤 모드로 가고, 그 모드가 현재 aid 조합에서 성립하는지 정의되어 있지 않습니다.
  - Offboard 송신 중단 (COM_OF_LOSS_T 계열)
  - 위치 유효성 상실
  - EV 상실 후 flow/LiDAR 속도만 남은 상태
- aid 상태별 fallback 표가 없으면 B 상태기계의 종착점이 비어 있게 됩니다.

**③ 이륙 전 차단 조건**
- geometry/frame revision, 레버암 소유자, `C_ME`가 일치하지 않을 때 비행 중 발행 거부만으로는 늦습니다.
- 이 경우 arming 전 차단 조건이어야 합니다.

**④ reset 모호 창에서의 제어 정책**
- 3항에 따라 companion이 reset을 인지하기 전 창이 존재합니다.
- 이 창에서 REENTRY 진입을 금지하고 HOLD 참조만 허용한다는 명시 규칙이 필요합니다.

## 3. 사용자에게 전달할 개선 3가지

**개선 1. 세션 구성 manifest와 프레임 계약 (우선순위 A)**
- 세션마다 하나의 manifest로 묶을 항목:
  - 운영/통합/시험 commit
  - 센서 신원
  - 앵커 ID↔좌표·높이와 geometry hash
  - 레버암 소유자 (EV_POS_Z −0.10 ↔ FRD −0.07 정합)
  - `C_ME` revision과 heading 출처
  - FC 파라미터 스냅샷 (MPC_XY_VEL_MAX 2.0 ↔ 경로 0.25, 도착판정)
- 불일치하면 bridge 시작과 arming을 차단합니다.
- log49 거리부족분의 앵커별 부호·일관성 분석은 판정 통계를 먼저 문서화한 뒤 수행합니다.

**개선 2. FREEZE를 확장한 신뢰 기반 상태기계 (B)**
- 상태 흐름: BRAKE → HOLD → REACQ → REENTRY / FALLBACK
- 입력은 세 가지입니다.
  - 관측 계약: 나이 + seq + epoch
  - aid 건강 계약: 주기 기반 유예 + 진단지연 분리
  - HOLD 예산 계약: 오차 성장 대비 공간 여유
- 재개 조건은 "새 관측 + 새 융합 + 두 키 일관"입니다.
- 모호하면 자동 재개하지 않습니다.
- 재진입은 실제 위치와 실제 속도에서 불변인 `goal_M`으로 재계획합니다.
- aid 상태별 fallback 표(②)를 동반합니다.

**개선 3. reset 경계를 한 곳에서 소유 (C)**
- 현재 상태는 다음과 같이 명시합니다.
  - FC가 오래된 setpoint를 자동 보상한다는 사실
  - companion shift와의 이중보정·취소 위험
  - 연속성이 미검증이라는 점
- 단기 규칙: reset 모호 창에서는 HOLD만 허용합니다(④).
- 후보: setpoint에 제어 참조 키를 실어 보내고, FC가 "참조 세대가 현재보다 오래되었을 때만 delta 적용"을 하도록 하는 작은 firmware 계약입니다.
- p/v/a feedforward는 이 계약 위에서만 검토합니다.

D(ClockMap·버퍼·부분프레임 후보의 기준선별 통합)와 E(GC 경로 격리, 서비스 수명 분리, 조건부 C++)는 위 순서를 막지 않는 범위에서 병행할 수 있습니다.

외부 실기 인증은 없으며, 위 판단은 제공 자료와 확인된 소스 범위에 근거한 기술 검토입니다.
