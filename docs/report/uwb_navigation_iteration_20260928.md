## 현재 판정

**정지한 Gazebo 기체의 696주기에서 B가 가장 작은 오차를 보였다.**
입력 자세·높이는 Gazebo 위치에서 구했다.
ToF 측정값 연결과 이동 비행은 아직 검증하지 않았다.
따라서 7cm 목표의 최종 달성 판정은 보류한다.
[누적 시행표](uwb_navigation_iteration_index_20260928.md)에 모든 시도의 판정을 모았다.

```text
사용자 WSL의 Gazebo 기체 위치
  → 가상 RAW 696주기와 평가용 정답 기록
  → 원본 그대로 원격 작업공간에 복사
  → RAW 시각·순서·정답·앵커 지도 검증
  → A/B/C/D/WLS 파일 계산 → 시행별 기록
```

## PX4 연결 상태 추가 확인

사용자가 같은 Gazebo 세션의 `pxh>` 출력을 제공했다.
MAVLink 네 인스턴스는 송신 중이지만 수신률은 모두 0 B/s였다.
`vehicle_status`는 `gcs_connection_lost=True`를 보고했다.
`arming_state=1`은 시동 해제 상태다.
`nav_state=4`는 [PX4 상태 메시지](https://github.com/PX4/PX4-Autopilot/blob/main/msg/versioned/VehicleStatus.msg)의 Auto Loiter 모드 식별값이다.
모드 식별값만으로 실제 위치 유지나 이동을 입증하지 않는다.
`pre_flight_checks_pass=False`이며 실패 원인은 아직 확인하지 않았다.
`accepts_offboard_setpoints=False`이므로 외부 목표점 입력 시험도 현재 상태에서는 미실시다.

다음 순서는 Windows QGroundControl 링크를 연결한 뒤
`commander check`와 `vehicle_local_position`을 조회하는 것이다.
검사 실패 사유를 확인하기 전에는 가상 이륙을 진행하지 않는다.
절차는 [WSL 실행 안내](../gazebo_wsl_runbook.md) 4~5절을 따른다.

후속 WSL의 `ip -4 -o addr show dev eth0`는 빈 출력을 보였다.
`eth0`의 IPv4 주소를 확인하지 못했다는 뜻이다.
다른 인터페이스·네트워크 모드·현재 연결 상태는 아직 미확인이다.
`ip -br -4 addr`와 `ip -4 route` 출력으로 QGroundControl 주소를 정한다.

뒤이어 받은 `ip -br -4 addr` 출력은 `eth0=172.25.0.249/20`을 확인했다.
이번 세션의 Windows QGroundControl 수동 UDP 링크 대상은
`172.25.0.249:18570`이다. WSL 주소는 다음 실행에서 다시 조회한다.
함께 붙여 넣은 `ip -4 route`의 출력은 아직 받지 못했다.

같은 세션의 추가 `pxh>` 출력에서 `commander check`는 계속 `FAILED`다.
`vehicle_local_position`은 `xy_valid=True`, `z_valid=True`,
`dist_bottom_valid=True`를 보고했다. `heading_good_for_control=False`였다.
위치 표본의 유효 여부만으로 사전 점검 통과를 판정하지 않는다.
MAVLink 네 인스턴스의 수신률은 모두 0 B/s였다.
`EKF2_EV_CTRL=0`이므로 외부 UWB 위치 융합은 비활성이다.
`EKF2_EV_NOISE_MD=0`은 메시지 분산을 사용하고 파라미터를 하한으로 두는 설정이다.
현재 출력은 사전 점검 실패의 구체적인 원인을 보여주지 않는다.
QGroundControl의 Arming Check Report와 `failsafe_flags`를 확인하기 전까지
가상 이륙·외부 관측 송신은 미실시로 둔다.
WSL의 `~/.venvs/px4/bin/python`은 `pymavlink/mavutil.py` 경로까지 찾았으나
가져오는 도중 사용자가 중단했다. 패키지 설치 여부와 별개로
실제 가져오기 완료·패킷 전송은 미확인이다.
