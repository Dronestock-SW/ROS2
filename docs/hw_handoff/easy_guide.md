# 1부. UWB 로그 해설서 쉽게 읽기

## 1.1 UWB가 뭘 하는 물건인가

교실에 네 귀퉁이가 있다고 하자. 각 귀퉁이에 **심판**이 한 명씩 서 있다. 이걸 **앵커(anchor)** 라고 부른다. 우리 창고에는 A1, A2, A3, A4 네 명이 있다.

교실 한가운데에 **술래**가 있다. 이게 드론에 붙은 **태그(tag)** 다.

술래가 "야!" 하고 소리치면 심판들이 "어!" 하고 대답한다. 소리가 갔다 오는 데 걸린 시간을 재면 심판까지의 거리를 알 수 있다. 소리 대신 전파를 쓰는 게 UWB다.

```text
       A3 ●──────────────● A4
          │              │
          │    ★ 태그    │      태그는 심판 4명까지의 거리를 잰다
          │              │      → "A1까지 1.9m, A2까지 4.7m..."
       A1 ●──────────────● A2
```

거리 4개를 알면 종이에 원 4개를 그릴 수 있다. **네 원이 겹치는 한 점**이 내 위치다. 이걸 컴퓨터가 계산하는 게 "위치 계산(solver)"이다.

## 1.2 지금 무슨 일이 벌어지고 있나

문제는 이거다. **네 원이 한 점에서 안 만난다.**

```text
       올바른 경우                    지금 우리 상태

         ╭─╮                        ╭───╮
        ╭┼─┼╮                     ╭─╯   ╰─╮
        │╰★╯│  ← 한 점에서 만남    │  ?    │  ← 겹치는 데가 없음
        ╰┼─┼╯                     ╰─╮   ╭─╯   컴퓨터: "몰라요"
         ╰─╯                        ╰───╯
```

왜냐하면 심판 4명이 서로 **다른 답**을 말하기 때문이다. 실제로 잰 결과가 이렇다.

| 심판 | 진짜 거리 | 심판이 말한 거리 | 얼마나 틀렸나 |
|---|---:|---:|---|
| A1 | 1.931 m | 1.932 m | 거의 정확 ✅ |
| A2 | 4.662 m | 5.468 m | **81 cm 뻥튀기** ❌ |
| A3 | 2.789 m | 3.124 m | 34 cm 뻥튀기 ❌ |
| A4 | 5.077 m | 5.284 m | 21 cm 뻥튀기 ❌ |

A2는 자기 자를 81 cm나 길게 쓰고 있다. 그런데 **항상 똑같이 81 cm 길게** 잰다. 손이 떨리는 게 아니라 자에 눈금이 밀려 있는 것이다.

이걸 **bias(고정 오차)** 라고 부른다.

> **여기가 핵심이다.**
> 값이 흔들리는 문제가 아니라 **일정하게 밀린** 문제다.
> 흔들림은 평균 내면 사라지지만, 밀린 건 아무리 평균 내도 그대로 밀려 있다.

## 1.3 그래서 필터로 고칠 수 있나 → 없다

"값이 이상하면 필터를 넣으면 되잖아?"라고 생각하기 쉽다. 안 된다.

```text
필터가 하는 일:  ~~~∿∿∿~~~   →   ‾‾‾‾‾‾‾‾    (울퉁불퉁 → 매끈)
필터가 못 하는 일: 매끈한데 81 cm 밀린 선을 제자리로 옮기는 것
```

체중계가 항상 5 kg 더 나온다고 하자. 열 번 재서 평균 내도 여전히 5 kg 더 나온다. 필터는 열 번 재서 평균 내는 도구다. **눈금을 다시 맞추는 도구가 아니다.**

문서 12.1의 실측이 정확히 이걸 보여준다. 필터를 통과시켜도 흔들림(SD)만 0.041 → 0.038로 줄고, 81 cm 오차는 1 cm도 안 줄었다.

## 1.4 시스템이 스스로 엉뚱한 심판을 자르고 있다

시스템에는 "말 안 듣는 심판은 빼자"는 기능이 있다. 이게 **적응형 제외(adaptive exclusion)** 다.

그런데 결과가 이렇게 나왔다.

```text
가장 많이 틀린 심판   : A2 (81 cm)
실제로 잘린 심판      : A3 (34 cm)   ← 33번 중 33번 잘림
```

**왜 억울한 A3가 잘렸나?**

시스템은 정답을 모른다. 정답을 알면 애초에 UWB가 필요 없다. 시스템이 할 수 있는 건 "누가 나머지랑 말이 안 맞나"를 보는 것뿐이다.

반 아이들 4명한테 "지금 몇 시야?"라고 물었다고 하자.

```text
A1: 3시 00분   ← 정답
A2: 3시 40분   ← 제일 많이 틀림. 근데 목소리가 크다
A3: 3시 17분
A4: 3시 10분

반 평균 = 3시 17분쯤
→ 평균에서 제일 멀어 보이는 사람은? A1(정답)이거나 A3
→ A2가 평균 자체를 끌어당겨 놨기 때문에 A2는 오히려 정상처럼 보인다
```

정확히 이 일이 일어났다. A2의 큰 오차가 "합의된 위치" 자체를 끌고 갔고, 그 왜곡된 합의에서 제일 어긋나 보이는 A3가 대신 희생됐다.

> **결론**: 지금 드론은 심판 4명 중 3명으로, 그것도 **제일 정확한 쪽을 빼고** 위치를 계산하고 있다.

## 1.5 화면에 위치가 떠 있어도 "새 위치"가 아닐 수 있다

이게 가장 위험한 오해 지점이다.

위치를 못 구했을 때 시스템은 화면을 비우지 않는다. **직전에 성공했던 좌표를 최대 0.5초 동안 그대로 붙들고 있는다.** 이걸 `hold`라고 부른다.

```text
[성공] [성공] [실패] [실패] [실패] [성공]
  ↓      ↓      ↓      ↓      ↓      ↓
 새값   새값   전값   전값   전값   새값     ← 화면은 계속 숫자가 떠 있다
                └──── 0.5초 넘으면 fix=false ────┘
```

실측에서 568줄 중 **225줄(40%)** 이 "새 위치를 못 만든 줄"이었다. 화면만 보면 전혀 티가 안 난다.

**그래서 볼 필드 3개:**

| 필드 | 이게 뭐냐 | 어떻게 읽나 |
|---|---|---|
| `fix` | 이 값 써도 되냐? | `false`면 숫자가 보여도 **절대 쓰지 마라** |
| `xy_control_fresh` | 방금 새로 만든 값이냐? | `true`여야 진짜 새 값 |
| `hybrid_source` | 어디서 나온 값이냐? | `none`이면 **새 위치 없음** |

## 1.6 점수 100점의 함정 (꼭 알아야 함)

로그에 `qscore`라는 점수가 있다. 100점이 최고다.

실측에서 **100점이 딱 한 번** 나왔다. 그 프레임을 열어봤더니:

```text
qscore              = 100     ← 만점!
solve_anchor_mask   = 0       ← 사용한 심판 0명
hybrid_source       = none    ← 새 위치 없음
실제 위치 오차       = 0.57 m  ← 57 cm 틀림
```

**만점인데 위치가 없다.**

이유는 이렇다. `qscore`는 "위치가 정확한가"를 재는 점수가 **아니다.** "이번에 감점당할 짓을 했나"를 재는 점수다. 위치 계산을 아예 안 하면 감점당할 짓도 안 한 셈이라 100점이 나온다.

```text
qscore = "숙제 감점 없음"        ← 숙제를 아예 안 냈어도 감점 없음
       ≠ "숙제 잘함"
```

> 대시보드에 qscore를 커다란 정확도 게이지로 만들면 안 된다. `fix`, `reason`과 반드시 같이 봐야 한다.

## 1.7 "필드가 없는 것"과 "false"는 다르다

로그 줄에는 두 종류가 있다.

```text
압축 줄  (90%, 511개) : 필드 13개   ← 자주 나온다. 위치·상태만
상세 줄  (10%,  57개) : 필드 94개   ← 10줄에 1번. 거리·품질 전부
```

압축 줄에는 `range_fail_a1` 같은 필드가 **아예 없다.** 이걸 보고 "앵커 통신이 실패했다"고 하면 틀린 얘기다. 그냥 그 줄에 안 적힌 것뿐이다.

```text
비유:
  시험지에 4번 문제 답이 비어 있다  →  "틀렸다"가 아니다
  애초에 그 시험지에 4번 문제가 없었다  →  "해당 없음"
```

`kf_*`(칼만 필터) 필드 6개도 마찬가지다. 568줄 전부에 **하나도 없다.** 이걸 `false`로 처리하면 "칼만 필터가 계속 값을 거부하고 있다"는 완전히 없는 사건을 만들어내게 된다. 실제로는 지금 태그 펌웨어가 이 필드를 안 찍는 것뿐이다.

> 대시보드 표시 규칙: 없는 필드는 **"미지원"** 회색. `false` 빨강으로 칠하지 말 것.

## 1.8 그래서 뭘 해야 하나 (순서 중요)

```text
1단계  앵커 A1~A4가 진짜 그 자리에 있는지 줄자로 재서 설정값과 대조
       (설정: A1(0,0) A2(5,0) A3(0,4.5) A4(5,4.5), 전부 높이 1.2m)

2단계  벽에 붙은 실제 상자가 정말 A1인지 사진 찍어 확인
       ★ 케이블 두 개 바꿔 꽂으면 이 증상이 그대로 나온다

3단계  antenna delay 교정 → range_bias_a*_m 에 값 입력
       ★ 지금 이 값이 전부 0이다. 즉 교정을 한 번도 안 한 상태다

4단계  다지점에서 다시 측정해 검증

5단계  ← 여기서부터가 필터·칼만 튜닝. 그 전엔 의미 없음
```

`range_bias_a*_m = 0`이라는 건 "자 눈금 보정을 아직 안 했다"는 뜻이다. 3번이 안 된 상태에서 필터를 아무리 만져도 소용없다.

# 2부. PX4 / MAVLink 문서 쉽게 읽기

## 2.1 등장인물

```text
Jetson    = 드론의 뇌.       "어디로 갈지" 생각한다. 우리(SW)가 만든다
Pixhawk   = 드론의 소뇌.     모터를 실제로 돌린다. PX4라는 프로그램이 돌아간다
MAVLink   = 둘이 쓰는 언어.  드론 업계 표준
MAVROS2   = 통역사.          Jetson의 ROS2 말 ↔ Pixhawk의 MAVLink 말
EKF2      = Pixhawk 안의 계산기. 센서 여러 개를 섞어서 "지금 위치"를 결정
```

```text
UWB ──→ Jetson ──→ MAVROS2 ──→ 케이블 ──→ Pixhawk
        (뇌)       (통역사)   (MAVLink)   (PX4 + EKF2)
```

## 2.2 가장 중요한 규칙: 선 두 개를 절대 섞지 마라

드론한테 넣어야 하는 정보는 **성격이 완전히 다른 두 가지**다.

```text
① "너 지금 어디 있어"  ← UWB가 알려주는 현재 위치
② "너 저기로 가"       ← 우리가 정하는 목표 위치
```

이 둘은 **다른 문으로** 들어가야 한다.

| | 들어가는 문 | MAVLink 메시지 이름 | 받는 쪽 |
|---|---|---|---|
| ① 현재 위치 | vision/odometry plugin | `VISION_POSITION_ESTIMATE` | EKF2 (위치 추정기) |
| ② 목표 위치 | setpoint plugin | `SET_POSITION_TARGET_LOCAL_NED` | OFFBOARD 제어기 |

**섞으면 어떻게 되나?**

UWB가 잰 현재 위치를 목표에도 넣으면 이렇게 된다.

```text
드론: 나 지금 (1, 2)에 있음
명령: (1, 2)로 가라
드론: ...나 이미 거기 있는데?  → 영원히 안 움직임
```

문서에서 "잘못하면 안 되는 부분"으로 빨간 박스 쳐 놓은 부분이 이거다.

## 2.3 OFFBOARD 모드 = "외부 컴퓨터 말 듣기" 모드

드론에는 비행 모드가 여러 개 있다. 조종기로 나는 모드, 자동으로 집에 가는 모드 등등. 그중 **OFFBOARD**는 "Jetson이 시키는 대로 나는" 모드다.

**규칙 하나만 기억하면 된다: 계속 말을 걸어야 한다.**

```text
Jetson: "(3,2)로 가"  "(3,2)로 가"  "(3,2)로 가"  ...  ← 1초에 최소 3번 이상
                                                          (공식 기준: 2 Hz 초과)
```

같은 자리에 가만히 있으라고 할 때도 **계속** 보내야 한다. 왜냐하면 PX4 입장에서 이 신호는 명령인 동시에 **"Jetson 아직 살아있음"** 표시이기 때문이다.

```text
비유: 산악 구조대 무전
     "이상 없음"  "이상 없음"  "이상 없음"  ...(끊김)...
                                            ↑ 1초 지나면 구조 시작
```

말을 1초(`COM_OF_LOSS_T` 기본값) 이상 안 걸면 PX4는 "Jetson 죽었다"고 판단하고 비상 조치에 들어간다.

**비상 조치는 우리가 골라야 한다** (`COM_OBL_RC_ACT`):

| 값 | 이름 | 뭘 하나 | 실내에서 |
|---|---|---|---|
| 0 | Position | 조종사가 스틱으로 이어받을 수 있는 상태 | 사람이 있으면 |
| 4 | Land | 그냥 내려앉음 | 안전 |
| 5 | Hold | 그 자리에 자동으로 떠 있음 | **위치 추정이 정상일 때만** |
| 3 | Return | 출발점으로 날아감 | 실내는 위험 (선반 충돌) |
| 6/7 | Terminate / Disarm | 제어 강제 종료 / 모터 즉시 정지 | 공중이면 추락 |

문서 권장: 실내 쿼드는 **Return보다 Hold나 Land**. 단 Hold는 "지금 어디 있는지"를 알아야 가능하므로, **UWB가 죽은 상황**과 **Jetson이 죽은 상황**을 따로 구분해서 시험해야 한다.

> 지금 우리 UWB 상태(1부 참고)를 생각하면 Hold를 기본값으로 두는 건 위험하다. Land가 안전하다.

## 2.4 EKF2 파라미터 = "어떤 센서를 믿을지 정해주는 스위치"

EKF2는 Pixhawk 안에서 이미 돌고 있다. 우리가 할 일은 **"이 센서 믿어라"** 하고 스위치를 켜주는 것뿐이다.

### `EKF2_EV_CTRL` — 외부 위치 중 뭘 쓸까

리모컨 버튼 4개를 켜고 끄는 것과 같다. 켠 것끼리 숫자를 더한다.

```text
1  = 좌우앞뒤 위치(X/Y)  켜기
2  = 높이(Z)            켜기
4  = 속도               켜기
8  = 방향(Yaw)          켜기

우리 값 = 1   (X/Y만 UWB에서 받고, 높이는 다른 센서로)
```

**왜 1인가?** 우리 UWB는 XY만 낸다 (`/uwb_pose`는 x, y만). 높이는 TFmini Plus 담당이다. 3으로 켜면 "높이도 UWB에서 받겠다"는 뜻인데, 안 오는 값을 기다리게 된다.

> 문서 주의사항 원문: "`EKF2_EV_CTRL = 3`으로 설정한다고 Z 값이 자동으로 생기는 것은 아니다."
> 이건 docs/altitude_policy.md 와 방향이 같다.

### `EKF2_EV_DELAY` — 늦게 도착한 편지 보정

UWB가 위치를 재고 → 계산하고 → Jetson 거치고 → 통역사 거치고 → 케이블 타고 → Pixhawk 도착. 이 사이에 시간이 걸린다.

```text
실제로 (1.0, 2.0)에 있던 순간: 0.000초
Pixhawk에 그 값이 도착한 순간: 0.050초   ← 이미 드론은 다른 데 있음
```

이 시차를 알려주는 값이다 (0~300 ms). **감으로 넣지 말고 실측해서 넣어야 한다.**

주의: UWB에 필터를 세게 걸면 지연이 더 늘어난다. 필터를 강화했으면 이 값도 같이 올려야 한다.

### `EKF2_GPS_CTRL` — 실내니까 GPS 끄기

창고 안에서 GPS는 안 잡힌다. 잘못 잡힌 GPS는 오히려 방해가 된다. 실내 전용이면 `0`.

### `EKF2_HGT_REF` — 높이를 뭘로 잴까

| 값 | 기준 |
|---|---|
| 0 | 기압계 |
| 1 | GPS |
| 2 | **거리센서 (TFmini Plus)** |
| 3 | 외부 위치(Vision) |

우리는 TFmini Plus로 바닥까지의 거리를 재므로 `2` 방향이다.

### 좌표계 — 축 뒤집힘 사고 주의

이게 실무에서 제일 많이 터지는 사고다. 시스템마다 **"위"의 방향이 다르다.**

```text
ROS  : ENU / Z Up    ← 위가 +
PX4  : NED / Z Down  ← 아래가 +  (!!)
UWB  : 우리가 설치할 때 정한 자체 축
```

MAVROS가 ROS↔PX4 변환은 알아서 해준다. **그런데 우리가 코드에서 한 번 더 뒤집으면 두 번 뒤집혀서 원위치가 된다.** 그럼 드론이 위로 가라는데 아래로 간다.

```text
올바름 :  우리 좌표 정렬 → MAVROS 변환 1회 → PX4     ✅
사고   :  우리가 변환 → MAVROS도 변환 → 축 반전      ❌
```

원칙: **UWB 좌표축을 처음부터 ROS 기준(ENU)에 맞춰 놓고, 변환은 MAVROS에게만 맡긴다.**

## 2.5 케이블 꽂는 포트 설정

| 파라미터 | 뭘 정하나 | 값 |
|---|---|---|
| `MAV_1_CONFIG` | Jetson을 어느 포트에 물리나 | 101=TELEM1, **102=TELEM2** |
| `MAV_1_MODE` | 그 포트 용도 | **2 = Onboard** (동반 컴퓨터용) |
| `SER_TEL2_BAUD` | 통신 속도 | 921600 (양쪽 같아야 함) |

문서 권장 구성:

```text
TELEM1 → 지상국(QGroundControl)
TELEM2 → Jetson          ← 이쪽이 표준
```

주의점 2개:
1. `MAV_1_CONFIG` 바꾸면 **PX4 재부팅해야** 나머지 `MAV_1_*` 항목이 QGC에 나타난다.
2. 통신 속도(baud)가 양쪽이 다르면 아예 대화가 안 된다. 전화는 걸리는데 서로 다른 언어를 하는 셈.

## 2.6 시험 순서 (문서 7장)

```text
0. ★ 프로펠러 뽑고 시작한다  ← 이거 안 지키면 손 다친다
1. 포트/속도 설정 → PX4 재부팅
2. MAVROS2에서 "FCU 연결됨" 확인
3. UWB 좌표가 PX4까지 들어가는지 확인
4. EKF2가 그 값을 실제로 쓰는지 확인
5. 축 방향 확인 (드론을 손으로 앞으로 옮겼을 때 X가 +로 가는가)
6. setpoint를 1초 이상 보낸 뒤 OFFBOARD 진입
7. 통신 끊김 failsafe를 지상에서 단계별로 시험
```

# 3부. 우리(SW 파트)한테 이게 무슨 의미인가

## 3.1 지금 UWB 값을 PX4에 넣으면 안 된다

1부에서 본 대로 현재 UWB 오차는 **약 0.66 m**다. 선반 사이 통로를 나는 드론한테 66 cm는 벽에 부딪히는 거리다.

```text
UWB 오차 0.66 m  →  EKF2에 넣으면  →  드론이 66 cm 어긋난 곳을 "여기"라고 믿음
                                    →  목표로 가라는 명령도 66 cm 어긋남
```

**bias 교정(1.8절 3단계)이 끝나기 전에는 vision_pose 연결을 실비행에 쓰지 않는다.** 벤치 테스트로 경로가 뚫리는지만 확인한다.

## 3.2 이건 HW 파트 작업이다

| 할 일 | 담당 |
|---|---|
| 앵커 실제 좌표 실측, 물리 ID 확인 | HW |
| antenna delay 교정, `range_bias_a*_m` 입력 | HW |
| 태그 펌웨어 버전 확정 | HW |
| UWB 값을 ROS2 topic으로 받기 | **SW (우리)** |
| 좌표축 정렬, vision_pose 발행 | **SW (우리)** |
| EKF2/MAVLink 파라미터 설정 | 협업 |

우리가 필터를 아무리 잘 짜도 3.1의 오차는 안 줄어든다. 지금 우리 쪽에서 할 수 있는 건 **파이프라인을 미리 만들어 두고, 교정된 값이 오면 바로 흘려보내는 것**이다.

## 3.3 로드맵과 대조해서 확인할 것 3가지

| 항목 | HW 문서 내용 | 우리 기준 | 판단 |
|---|---|---|---|
| 목표 위치 경로 | 웹 → Jetson → setpoint | roadmap 결정 3: 웹 개발 보류 | topic 경계만 유지. 웹 구현은 아직 안 함 |
| 위치 제어 주체 | PX4 Position Controller | roadmap 결정 4: companion이 위치제어 | **확인 필요** — 어느 쪽이 위치 루프를 도는지 정해야 함 |
| 고도 | `EKF2_EV_CTRL=1` + Range sensor | altitude_policy: companion z 제어 금지 | 일치 ✅ |

가운데 항목은 그냥 넘길 게 아니다. PX4가 위치 제어를 다 하면 companion은 목표점만 던지는 구조가 되고, roadmap 결정 4의 "게인 스케줄링"을 할 자리가 없어진다. 다음 설계 논의 때 정리해야 한다.

## 3.4 대시보드 만들 때 지킬 것

```text
1. fix=false 면 x,y 를 회색 처리하거나 아예 가린다
2. null 을 0 으로 렌더링하지 않는다 → "—" 로 표시
3. 필드가 없으면 "미지원" 회색. false 빨강 금지
4. qscore 를 큰 정확도 게이지로 만들지 않는다
5. adaptive_excluded_mask 는 solve_anchor_mask 와 비트 의미가 반대다
```

5번은 실수하기 딱 좋다.

```text
solve_anchor_mask      = 11 (1011) → A1,A2,A4를 "썼다"
adaptive_excluded_mask =  4 (0100) → A3를 "뺐다"

둘 다 같은 사실이다. 그런데 비트 1의 뜻이 정반대다.
```
