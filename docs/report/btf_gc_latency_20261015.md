# B_TF의 약 80ms 지연: GC 원인 확인과 로직 영향
2026-10-15. Jetson의 격리 재생 3회와 저장된 계측 자료를 근거로 작성했다.
결론: GC를 직접 계측한 두 사건의 약 80ms 추가 지연은 Python GC가 주요 원인인 것으로 확정한다.

## 확정 범위

**`2-baseline / seq 17047`과 `4-gc-on / seq 17041`의 큰 지연 원인은 generation 2 GC다.**
GC 시작·종료, 실행 스레드, 구간별 경과 시간과 스레드 CPU 시간을 함께 기록했다.
자동 GC를 켬 → 끔 → 다시 켬 순서의 대조에서도 큰 지연의 소실과 재발을 확인했다.

첫 사건에서는 다른 스레드의 GC와 위치 계산 스레드의 긴 대기가 겹쳤다.
두 번째 사건에서는 위치 계산 스레드 자신이 요청 JSON을 만드는 도중 GC를 수행했다.
따라서 같은 GC 문제가 계측 위치에 따라 ‘실행 대기’ 또는 ‘Python 처리 시간 증가’로 보일 수 있다.

다음 항목까지 확정한 것은 아니다.

- 과거 `CLOCK2 / seq 17029`의 process 122.581ms: 당시 GC 사건과 스레드 CPU 계측이 없어 직접 확정 불가. 같은 메커니즘을 유력 후보로 기록한다.
- 모든 80ms 이상 지연: GC 계측 없이 시간 길이만으로 같은 원인으로 분류하지 않는다.
- 첫 사건의 대기 시간 전체가 순수 GIL 획득 대기였다는 주장: OS 스케줄러/GIL 소유권 추적을 하지 않았으므로 정확한 분할은 불가하다.
- 운영본의 발생 빈도나 실비행 실패 원인: 계측이 포함된 짧은 재생 결과이며, 실제 비행 제어 결과를 측정하지 않았다.

## 재생 조건과 검증

- 장치: `bluewak-host`, 같은 Jetson의 공유 CPU 환경. ROS 통신은 domain 99와 localhost로 격리했다.
- 대상: `563960e-acache-trial-A`. A-cache를 적용하기 전의 비교 기준에 공통 계측이 포함된 시험본이다. 이후 운영 배포본을 검증한 결과가 아니다.
- Python: CPython 3.10.12.
- 입력: 2026-10-13 캡처의 부분 복구 로그, 24.362027771초, 1배속.
- 재생마다 입력 5,805개 발행, UWB 콜백 2,014개 관찰. 수신 집계에서 IMU 2,445개와 ToF 223개를 확인했다.
- 운영 소스 및 비행 설정을 수정하지 않았다. 시험 프로세스의 함수 경계만 감쌌다.
- 외부 FC 출력은 비활성화했다. GC 끄기는 대조 시험 프로세스에만 적용했다.
- 3회 모두 재생 실패 목록이 비어 있고, 계측 누락·계측 오류·내부 trace 누락이 0이었다.
- 실제 import 소스의 해시와 실행 manifest의 소스 해시를 대조했다. native 라이브러리는 3회 동일하다.
- native 요청 계측은 기존 코드와 정상 응답, 오류 응답, NaN 거부, 잘못된 JSON, 닫힌 핸들의 동작을 5개 사례로 비교했다.
- 추가 계측과 기존 시험 도구도 객체 생성 및 GC 시점에 영향을 줄 수 있다. 재생에서 확인한 원인을 운영 환경의 빈도로 그대로 환산하지 않는다.

### 다른 스레드의 GC를 기다린 사건

`2-baseline`, seq 17047, 입력 시작 후 약 8.778초.

- 핵심 C++ 계측: 0.581875ms.
- ctypes 호출 구간: 경과 80.767108ms, 해당 스레드 CPU 1.205376ms.
- 센서 수신 스레드의 generation 2 GC: 경과 84.725025ms, CPU 76.271680ms.
- 해당 GC와 전체 UWB 콜백의 겹침: 82.411512ms.
- native 잠금 획득: 0.004608ms. 요청 JSON 변환: 0.214118ms.

핵심 C++ 수치 계산이나 native 잠금 획득이 큰 지연의 원인이라는 해석은 이 사건의 계측과 맞지 않는다.
ctypes는 외부 함수 실행 중 GIL을 놓고 복귀 시 다시 획득하므로, 다른 스레드의 GC 때문에 Python 복귀가 늦어진 설명과 부합한다.
다만 ctypes 구간에는 C++ 입력 해석·출력 변환과 OS 실행 대기도 들어 있다.

### 자기 스레드에서 GC를 수행한 사건

`4-gc-on`, seq 17041, 입력 시작 후 약 8.640초.

- 핵심 C++ 계측: 0.423693ms.
- 요청 JSON 변환: 경과 81.972413ms, 스레드 CPU 78.495584ms.
- 같은 스레드의 generation 2 GC: 경과 81.800312ms, CPU 78.319232ms.
- GC 구간 전체가 해당 UWB 콜백 안에 포함됐다.

JSON 구간의 긴 CPU 사용은 대부분 GC로 설명된다. JSON 데이터 자체를 변환하는 데 원래 80ms가 필요하다는 뜻이 아니다.

## GC를 쉽게 설명하면

GC는 Garbage Collection의 줄임말로, 프로그램이 더 이상 사용하지 않는 메모리를 찾아 회수하는 작업이다.
센서 데이터나 중간 계산 결과를 담는 리스트·딕셔너리 같은 객체도 정리 대상이 된다.

CPython은 보통 참조 수가 0이 된 객체를 즉시 정리한다.
그러나 A가 B를 가리키고 B가 A를 가리키는 식의 순환 참조는 별도 검사가 필요하다.
이번에 계측한 GC는 이 순환 참조 등을 검사하는 수집기다.
generation 2 GC는 오래 살아남은 객체까지 폭넓게 검사한다.
이번 두 사건에서 회수한 객체 수는 각각 28개였지만, 검사 비용은 회수한 객체 수만으로 판단할 수 없다.

비유하면 작업 중간에 ‘대청소’가 끼어든 것이다.
위치 계산 담당자가 직접 청소하면 계산 구간의 CPU 사용 시간이 커진다.
다른 스레드가 청소하더라도 같은 Python 인터프리터의 GIL을 공유하므로 Python 실행이나 C++ 호출 후 복귀가 기다릴 수 있다.
GC는 위치 계산식의 일부가 아니며, GC 발생 자체가 메모리 누수나 계산식 오류의 증거는 아니다.

## 우리 로직에 미치는 영향

**약 80ms의 불규칙한 지연은 위치 출력의 최신성과 연속성에 영향을 주는 문제다.**
즉시 계산값이 틀어지거나 비행이 실패했다는 뜻은 아니지만, 코드가 가진 시간 여유를 크게 소모한다.

### 확인한 시간 제한

| 검사 | 시험 소스·설정의 한도 | GC와의 관계 |
| --- | ---: | --- |
| 콜백 진입 시 UWB 수신 나이 | 150ms | 뒤에 기다리던 입력이 오래되면 receiver_queue_expired로 거부될 수 있음 |
| 위치 발행 판정 시 좌표 나이 | 150ms | 계산은 성공해도 전체 나이가 한도를 넘으면 output_expired로 발행 차단 |
| UWB 표본 시각과 선택 ToF 시각의 차이 | 100ms | 센서 버퍼의 가용성·시각 관계를 검사하는 별도 조건 |
| 선택 ToF 시각과 IMU 시각의 차이 | 20ms | GC 80ms와 직접 비교하는 타이머가 아님 |

입력의 150ms와 출력의 150ms는 기준 시각이 다른 검사다. 150ms씩 더해 쓸 수 있는 총 300ms 예산이 아니다.
ToF·IMU 검사는 센서 타임스탬프끼리의 차이를 보므로, GC가 80ms 발생했다는 사실만으로 센서 시각 차이가 80ms 늘었다고 판단하지 않는다.
GC 때문에 필요한 센서 콜백이 늦어져 스냅샷에 표본이 부족해지는 영향은 별도로 확인해야 한다.

### 해당 두 사건에서 실제로 일어난 일

| 사건 | 발행 판정 시 좌표 나이 | 위치 발행 | ClockMap 상태 |
| --- | ---: | --- | --- |
| 2-baseline / seq 17047 | 108.977283ms | 발행됨 | ok |
| 4-gc-on / seq 17041 | 122.289304ms | 발행됨 | ok |

두 결과 모두 original_fit_consistent로 판정됐고, 150ms 한도 안이어서 발행됐다.
표의 나이는 코드가 좌표 stamp와 현재 ROS 시각을 비교한 값이다. 센서의 물리적 지연까지 보정한 절대 측정값은 아니다.

같은 seq 17047의 GC-off 실행에서는 발행 판정 나이가 27.577881ms였다.
GC-on의 108.977283ms와 약 81.40ms 차이가 난다.
seq 17041도 GC-off에서는 39.982471ms, GC-on에서는 122.289304ms였다.
이 비교 역시 공유 CPU와 센서 처리 순서의 변동을 포함하므로, 차이 전체를 정밀한 단일 원인 추정치로 취급하지 않는다.

일반적인 예로, 이미 80ms 지난 위치 결과가 처리 중 80ms 더 지연되면 약 160ms가 되어 현재 발행 한도를 넘을 수 있다.
지연 동안 뒤의 입력도 기다리므로, 한 번의 멈춤이 다음 콜백들의 대기로 이어질 수 있다.
드론이 1m/s로 이동한다면 80ms 동안 8cm를 움직인다. 이는 지연 동안의 이동 거리 예시이며 실제 위치 추정 오차가 8cm라는 측정 결과는 아니다.

전체 실행의 output_expired는 순서대로 2·6·13건, receiver_queue_expired는 80·79·91건이었다.
GC-off에서도 만료가 남았고 입력에는 이미 오래된 데이터가 포함되어 있다.
따라서 이 집계 차이를 전부 GC 탓으로 돌리거나, GC만 해결하면 모든 지연이 사라진다고 결론 내리지 않는다.

이번 재생은 FC로 위치를 보내지 않았다. 실제 제어기의 보정, 자세 안정성, 위치 유지 성능 또는 비행 실패 여부는 검증하지 않았다.
관찰된 멈춤은 보조컴퓨터의 해당 Python 위치 처리 경로에서 발생한 것이다.

## 후속 판단

1. 이번 계측 사건의 원인은 GC로 기록하고, 새로운 사건은 GC 계측과 함께 분류한다.
2. 평균 계산 속도뿐 아니라 출력 나이, 출력 간격, 큐 대기, 만료 거부를 함께 개선 지표로 삼는다.
3. 프로세스 분리를 검증한다면 센서 수신·시각 정합·필요한 버퍼·위치 계산·발행까지의 경로와 Python 진단·기록 경로의 경계를 대상으로 한다.
4. C++ 함수만 옮기거나 Python 스레드 하나만 분리하는 것으로 해결됐다고 판단하지 않는다. Python 프로세스는 분리 후에도 자기 GC를 수행할 수 있다.
5. 전체 경로를 C++ 프로세스로 옮기는 설계는 후속 검증 후보이며, 아직 구현하거나 개선 효과를 측정하지 않았다. 시각·버퍼·판정 동작의 동등성과 프로세스 간 전달 비용도 검증해야 한다.
6. 자동 GC 끄기는 이번 원인 대조용이다. 참조 수 기반 정리는 계속되지만 순환 참조 회수가 지연될 수 있으므로, 장시간 메모리 검증 없이 운영 해법으로 채택하지 않는다.
