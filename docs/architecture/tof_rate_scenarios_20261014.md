# 하향 ToF 주기 수정 시나리오

TFmini Plus 수집 주기와 B_TF 만료 기준의 수정 설계다.
2026-10-13 비행 분석 뒤 드라이버 변경을 검토할 때 읽는다.

## 결론

**I²C 50Hz 수집을 먼저 검증한다.**
센서 입력을 빠르게 받는 것이 우선이다.
100ms 만료를 200~300ms로 늘려 공백을 숨기지 않는다.
이 문서의 FC·센서 변경은 아직 적용하지 않았다.
이번 companion 수정은 기존 100ms·20ms 기준을 유지한다.

## 확인된 장치와 확인되지 않은 설정

장비 명세는 TFmini Plus다. FC 드라이버 이름은 TF02PRO다.
드라이버 이름만으로 실물 모델을 확정할 수 없다.

| 항목 | 근거와 상태 |
|---|---|
| 하향 센서 모델 | 사용자 확인을 반영한 [장비 명세](../equipment_inventory.md): TFmini Plus |
| 13일 FC 연결 | I²C 2, 주소 `0x10`, 방향 25, device type `0xE0` |
| 실행 명령 | `tf02pro start -X -b 2 -a 16 -f 400 -R 25` |
| `-f 400` | I²C 버스 400kHz. 거리 갱신 400Hz가 아니다 |
| `-R 25` | 하향 장착 방향. 거리 갱신 25Hz가 아니다 |
| FC가 선언한 거리 범위 | 0.1~35m. TFmini Plus의 12m 명세와 다르다 |
| 센서 내부 프레임률·저전력 모드 | 원본 로그로 확정할 수 없다 |
| 센서 라벨·펌웨어 버전 | 이번 작업에서 실물 재확인하지 않았다 |

제조사 [데이터시트 A07, p.3](https://en.benewake.com/uploadfiles/2024/04/20240426135842086.pdf)는
UART 1~1000Hz, I²C 1~100Hz를 구분한다.
I²C는 최대 400kbps, 기본 주소는 `0x10`이다.

[사용자 설명서](https://en.benewake.com/uploadfiles/2025/04/20250430175221028.pdf)의
§2.3·§7.4는 기본 100Hz와 `1000/n` 주기 규칙을 설명한다.
I²C 설계에는 별도 인터페이스 상한 100Hz를 적용한다.
§5.6의 일반 설정 대기 100ms와 거리 읽기를 구분한다.
거리 결과 요청 뒤에는 그 대기를 요구하지 않는다.
저전력 모드는 10Hz 이하로 제한한다.
설정 저장 후 재기동 확인이 필요하다.
이 내용은 제품 지원 범위다. 현재 실물 설정의 readback은 아니다.

## 현재 102ms가 생기는 경로

현재 PX4 코드는 수집 뒤 다음 읽기를 약 100ms 늦춘다.
센서 자체가 10Hz만 지원한다는 근거는 없다.

검토한 FC 코드 기준은 `d6f12ad1`이다.
경로는 `src/drivers/distance_sensor/tf02pro/`다.

| 파일·위치 | 현재 동작 | 수정 시 확인점 |
|---|---|---|
| `TF02PRO.hpp:56,87` | `_interval=100000µs` | 목표 수집 주기를 별도 설정으로 노출 |
| `TF02PRO.cpp:146–158` | mm 결과 요청 `5A 05 00 06 65` | 요청 시각과 성공 여부 기록 |
| `TF02PRO.cpp:165–183` | 이전 결과 수집 → 새 요청 → `ScheduleDelayed(_interval)` | 요청·읽기 쌍과 주기 대기를 분리 |
| `TF02PRO.cpp:118–134` | 읽기 직전 시각으로 거리 발행 | 실제 측정 시각의 불확실성 확인 |
| `TF02PRO.cpp:128–138` | strength≥60, distance<45000mm이면 발행 | 실물 모델에 맞는 품질·거리 검사 |

현재 `collect()`는 9바이트 헤더·체크섬을 검증하지 않는다.
strength로 발행을 생략해도 I²C 통신 오류는 늘지 않는다.
그러므로 `comms_errors=0`은 거리 무결성의 증거가 아니다.
주기를 높일 때 헤더·체크섬·품질 카운터도 함께 보완한다.

```text
현재: 요청(k) ── 약100ms ── 읽기(k)/시각표시 → 요청(k+1)
후보: 요청(k) → 짧은 읽기(k) ── 다음 주기까지 ── 요청(k+1)
```

응답이 요청 때 고정되는지는 이번 로그로 알 수 없다.
따라서 기존 값이 실제로 100ms 더 오래됐다고 단정하지 않는다.
요청·읽기 분리 실험으로 숨은 지연을 먼저 측정한다.
읽은 순간으로 timestamp만 갱신해 오래된 값을 새 값으로 만들지 않는다.

13일 거부 구간 주변의 header 간격은 다음과 같다.
중앙값 102.001536ms, 최대 304.002560ms다.
정상 한 주기도 100ms 제한을 넘는다.
한두 프레임을 놓치면 200~300ms 공백이 된다.

### B: I²C 50Hz 상세 설계

센서 측정, FC 읽기, MAVLink 전달을 각각 확인한다.
셋 중 하나라도 10Hz면 companion 입력은 50Hz가 되지 않는다.

1. 라벨과 펌웨어 버전을 기록한다.
   기존 PX4 펌웨어·시작 스크립트·설정도 보존한다.
   펌웨어 조회는 제조사 명령 `5A 04 01 5F`를 사용한다.
   FC 드라이버가 버스를 소유한 동안 별도 마스터를 붙이지 않는다.
2. 저전력 모드를 확인한다.
   내부 측정률은 50 또는 100Hz로 검증한다.
   내부 100Hz·FC 읽기 50Hz도 가능한 조합이다.
   같은 거리를 반복 출력한다는 이유만으로 중복 측정을 단정하지 않는다.
3. FC 읽기 20ms를 모델별 설정으로 만든다.
   기존 TF02PRO 전체에 상수를 일괄 적용하지 않는다.
   새 설정 이름과 CLI는 아직 구현되지 않은 제안이다.
4. 요청 직후 결과를 읽는 경로를 구현한다.
   워크큐에서 20ms 또는 100ms 동안 잠들지 않는다.
   장치가 즉시 읽기에 NACK하면 짧은 재예약으로 제한한다.
   무한 재시도와 밀린 주기의 몰아 읽기를 막는다.
5. 유효 프레임만 원래 측정 시각 근거로 발행한다.
   헤더, checksum, 범위, 신호 강도, 포화 여부를 구분한다.
   TFmini Plus 범위는 확인한 모델 명세를 따른다.
   `35m`·strength `60`을 검증 없이 유지하지 않는다.
6. 요청·읽기·uORB·MAVROS·B_TF 입력 시각을 대조한다.
   일정한 지연은 실제 측정 후 별도로 보정한다.
   50Hz 요청 성공률과 유효 거리 발행률을 따로 기록한다.
7. 설정 저장·재부팅 후 주기를 다시 읽는다.
   같은 기록 프로파일로 기존 10Hz와 비교한다.

50Hz가 통과하면 60~80ms 만료도 후속 비교할 수 있다.
이번 변경과 동시에 낮추지 않는다.
원인별 효과를 구분해야 하기 때문이다.

### E·F: 10Hz 제한 완화의 비용

100→120ms는 일부 경계만 구한다.
13일 기록의 ToF-stale 7회 중 나이 검사만 2회 통과한다.
seq `17484`, `17509`다.
이는 B3 잔차·연속성·발행 검사 통과를 뜻하지 않는다.
전체 재생의 결과는 [검증 보고서](../report/btf_sensor_timing_20261014.md)에서 비교한다.

| ToF 나이 | 0.5m/s 일정 수직 운동의 높이 변화 |
|---|---:|
| 100ms | 5.0cm |
| 120ms | 6.0cm |
| 150ms | 7.5cm |
| 200ms | 10.0cm |
| 304ms | 15.2cm |

이는 센서 정밀도가 아니라 시간차만의 예시다.
실제 속도·기울기·바닥 형태에 따라 달라진다.
기존 FC 상승 속도 설정 0.5m/s가 매 순간 실제 속도라는 뜻은 아니다.

앵커 i의 높이 오차 영향은 대략 다음과 같다.

```text
높이 변화 ≈ 수직 속도 × ToF 나이
거리 잔차 변화 ≈ (태그 높이 - 앵커 높이) / 사선거리 × 높이 오차
XY 오차 = 위 잔차와 앵커 배치에 따라 추가 증폭
```

B3의 6cm 잔차 한계를 높이 오차 예산 6cm로 해석하지 않는다.
IMU 20ms 제한도 함께 늘리지 않는다.
두 시각 오차가 동시에 커지면 원인을 분리하기 어렵다.

### G: 단절·부적합 바닥·빠른 회전

높이 미관측과 센서 품질 저하는 개별 이유로 기록한다.

| 상황 | 유지할 동작 | 확인할 기록 |
|---|---|---|
| 1~2 프레임 누락 | 마지막 값의 나이를 계속 증가 | 요청 실패, 읽기 실패, 품질 거부 |
| 범위 밖·저신호·포화 | 실측 높이 무효 | 원시 거리·strength·checksum |
| 기울기 큼 | 수직 투영 기준 유지 | quaternion, ToF 기준 선택 IMU |
| IMU가 ToF보다 미래 | 미래 샘플 사용 금지 | 앞/뒤 입력 시각과 receive_id |
| −2ms IMU가 계산 뒤 도착 | 현재 계산은 기존 스냅샷 유지 | 다음 계산의 선택 변화 |
| ToF stamp 역행 | 기존 버퍼 리셋을 기록 | `backward_stamp_reset` |
| FC 시각 점프·재연결 | 새 시각 자격 획득까지 높이 보류 | epoch·timesync·reset 이유 |
| A1 거리 튐 동시 발생 | 기존 B3 잔차·연속성 검사 유지 | A1 raw 및 후보별 RMS |
| 기록 디스크 오류 | 관측 계산 지속, 기록 실패 표시 | trace error/dropped 카운터 |

유효한 동일 높이 4앵커 B4 XY는 기존 예외를 유지한다.
B3에는 측정 높이가 필요하다.
없는 XYZ를 생성하거나 고정 높이로 비행 측정을 대신하지 않는다.
FC EKF·고도 제어·OFFBOARD 보호 정책은 이 변경 범위 밖이다.

## 단계별 실물 검증 설계

실기 적용은 이번 재생 결과를 검토한 뒤 별도로 진행한다.
아래 항목은 실행 결과가 아니라 다음 시험의 합격 제안이다.

| 단계 | 입력·기간 | 제안 합격 기준 | 실패 시 다음 확인 |
|---|---|---|---|
| 1. 센서 단독 | 고정 거리 여러 점, 각 60초 | 모델·단위·checksum 일치, 오류 계수 분리 | 펌웨어·배선·모델 |
| 2. FC 50Hz | 공유 버스 실제 부하, 10분 | header 간격 p99≤25ms, 설명 없는 >40ms 공백 0회 | 재예약·다른 I²C 장치 부하 |
| 3. 전체 수신 | MAVROS·B_TF·내부 기록 활성, 10분 | IMU/ToF 누락·역행·trace 손실 이유 추적 가능 | DDS 큐·콜백·기록 지연 |
| 4. 계산 부하 | 현장 H80 계산+웹·기록 부하 | 계산 중 IMU 콜백 진행, snapshot 선택 확인 | GIL·CPU·별도 프로세스 필요성 |
| 5. 정지 정확도 | 외부 거리 기준, 재질·조도별 | 10Hz 대비 편향·잡음 악화 허용값 사전 확정 | 강도·반사·설정 |
| 6. 높이 변화 | 별도 안전한 지그로 거리 변화 | 측정 지연과 최대 높이 오차 실측 | timestamp·요청/응답 위치 |
| 7. 누락 주입 | 기록 재생에서 1·2·3 프레임 삭제 | 만료가 정확히 작동, 미래값·가짜값 없음 | 나이 계산·복구 경로 |
| 8. PX4 지상 연계 | 프로펠러 비활성, 기존 설정과 비교 | uORB→MAVROS stamp 일치, 재부팅 후 설정 유지 | stream 제한·부팅 스크립트 |
| 9. 제한된 비행 | 검증 결과 승인 후 별도 계획 | ULog 융합·리셋·추종·실제 이동 동시 평가 | 센서·기하·제어 원인 분리 |

2단계 수치는 실측 후 조정할 수 있는 시작 기준이다.
스케줄 지연과 저신호 거부는 같은 통계로 섞지 않는다.
50Hz 원본이 없으므로 13일 10Hz 로그에서 새 샘플을 만들지 않는다.
이번 재생만으로 50Hz 실물 성능이나 비행 안전성을 증명하지 않는다.
