## 확인한 시각 결함과 수정

각도 배열 번호는 취득 순서 번호가 아니었다.
설치된 제조사 ROS 드라이버를 직접 읽었다.
드라이버는 SDK 점을 /scan의 각도 빈에 넣는다.
time_increment는 SDK 값을 그대로 전달한다.
이 조합에 배열 번호를 곱하면 시각이 어긋난다.

같은 드라이버의 /point_cloud는 순서를 보존한다.
stamps 채널에는 SDK 점 번호의 시간차가 있다.
고정 해상도 출력에는 마지막 점 반복도 있었다.
28–30개 반복점의 첫 시각만 남겼다.
없는 광선이나 균등 시각을 만들어 채우지 않았다.

FC 수신 간격과 원본 시각 간격은 다르다.
자세 보간은 원본 시각 간격을 검사한다.
FC 위치·속도를 점군 병진값으로 쓰지 않는다.
각 점의 자세 보정 뒤에만 각도 순으로 정렬한다.
C++ 스캔 간 dt도 원본 시각 차이를 쓴다.
UWB 기준점은 원본 시각 차이 30ms를 검사한다.
입력 거부 사유는 lidar_input_error로 남긴다.

이 결과는 시각 구조의 정지 일관성 확인이다.
SDK의 실제 광선 시각 정확도 인증은 아니다.
고정 지연·동적 회전·병진 대조는 남아 있다.

## 소프트웨어 검증과 남은 실행 공백

실제 C++와 모사 FC의 SDK 점군 미션은 END였다.
UWB 0.6초 공백 동안 기존 XY를 유지했다.
C++ 손실·LiDAR 손실·RC 인계도 성공과 구분했다.

| 검사 | 결과 |
|---|---|
| C++ 미션 계약 | 11개 통과 |
| C++ LiDAR 계약 | 13개 통과 |
| ROS 빌드 | 4개 패키지 통과 |
| Windows 순수 입력·수집·진단 검사 | 52개 통과 |
| Jetson 1차 묶음 | 342 통과·1 실패. B_TF 종료 예외 |
| 종료 수정 후 묶음 | 345 통과·1 실패. 실행기 시각 공백 |
| RC 인계 단독 반복 | 3회 통과. 반복 안정성 인증은 아님 |
| 최종 영향 범위 재검사 | 5 통과·1 실패. 지상 준비 중 216.736ms 공백 |
| 지연 지표 수정 후 C++ 연결 검사 | 정상 미션·SDK 공백 미션·C++ 정지 보호 3개 통과 |

B_TF 종료는 콜백 사이에서 정지하도록 고쳤다.
SIGTERM 중 Python 예외를 C++ 메시지 변환에 넣지 않는다.
동작 중 발생한 콜백 오류는 그대로 실패한다.
수정 뒤 ROS 전송 네 시나리오는 통과했다.

두 번째 실패는 C++ 처리 시간 초과가 아니었다.
실행기 호출 간격이 52ms에서 185.091ms로 늘었다.
그 순간 C++ 결정의 나이가 0.15초를 넘었다.
해당 시험의 최대 C++ 왕복은 11.007ms였다.
이 기존 왕복 지표는 요청 JSON 생성 시간을 제외했다.
후속 지표는 JSON 생성도 포함한다.
입력 제출 시간·입력부터 응답까지 나이도 기록한다.
기존 보호가 LAND를 요청해 성공 판정을 막았다.
RC 인계 주입 전에 발생한 호스트 실행 공백이다.
후속 시험 기록은 실행 session별 디렉터리도 보존한다.
반복 시험이 이전 실패 기록을 지우지 않도록 했다.

만료 기준을 늘리거나 실패를 END로 바꾸지 않았다.
호스트 지연의 원인과 현장 반복 안정성은 남았다.
정지 정합과 합성 END는 비행 준비 완료 인증이 아니다.

최종 SDK 재검사의 실패는 ARM 전이었다.
LiDAR는 정합·승인됐지만 실행기가 216.736ms 지연됐다.
기존 결정 만료 보호가 지상 복구를 요청했다.
이 실패의 원본은 execution-session 디렉터리에 보존했다.
공백 보완 자체의 실패와 실행기 호출 공백을 구분한다.

## C++ 실행기로의 후속 범위

현재는 C++ AI와 Python FC 실행기의 결합이다.
PX4 명령 송신은 아직 Python에 남아 있다.
실비행용 송신·시간 감시·명령 확인을 C++로 모으는 방향이 타당하다.
이 방향만으로 호스트 지연 해결을 보장하지 않는다.

기존 native_hover_node.cpp는 재사용 후보가 있다.
단일 writer 잠금·비동기 명령 확인·RC 인계다.
그 실행기는 AUTO.TAKEOFF 경로라 바로 대체할 수 없다.
현재 OFFBOARD의 고정 XY·1.7m·10초 호버 정책을 이식해야 한다.
센서 처리·웹·기록은 주기 송신과 분리해야 한다.
150ms 결정 만료와 200ms 주기 보호도 유지해야 한다.
Python과 C++가 동시에 PX4에 송신하면 안 된다.
두 실행기가 같은 기체를 지시하는 경쟁을 막기 위해서다.

이 브랜치에서 C++ FC 실행기 이식은 아직 하지 않았다.

최신 SDK 성공 미션의 입력 제출 최대는 9.632ms였다.
입력부터 응답까지 나이 최대는 41.551ms였다.
JSON 생성을 포함한 왕복 최대는 25.670ms였다.
앞선 185ms·217ms 호스트 공백의 원인은 여전히 미확정이다.
