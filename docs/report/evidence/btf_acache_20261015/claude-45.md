- 순간 XY wall p50 절감 69.65~71.19%. 절대값으로는 448/439/453/458µs입니다.
- 전처리 p50 절감 27.09~30.87%, process p50 절감 4.33~7.12%. XY의 p95와 CPU는 4쌍 모두 개선되었습니다.

## 1) 재시작 수명 계약

**통과로 봅니다.**
- 다음이 모두 확인되었습니다.
  - 실행 중 파일을 바꿔도 결과와 해시가 그대로임
  - 새 OS 프로세스에서는 새 해시가 나오고, 새 배치에서 기존 `solve_xy`와 같은 결과가 나옴
  - `builds==1`
  - ROS 4회에서 같은 `geometry_sha256`이 나왔고, `calls`가 계산 주기 수와 같음
- 실제 조건수 30의 양쪽 경계를 이분 탐색으로 찾은 시험과 원본 배열 변경 시험도 보완되었습니다.
- **덧붙일 사실:** A도 실행 중에는 설정 파일을 다시 읽지 않습니다. 따라서 캐시 때문에 "설정을 바꿨는데 반영되지 않는" 위험이 새로 생기지는 않습니다. 보고서에 한 줄로 넣으면 운영 측의 우려가 줄어듭니다.
- **범위 한계:** ROS launch나 systemd로 노드 전체를 재시작하는 절차를 시험한 것은 아닙니다. 운영 문서에 "앵커를 변경하면 노드를 반드시 재시작한다"는 절차와, 기동 로그에 `geometry_sha256`을 남기는 확인 방법을 명시해야 합니다.

## 2) 국소 효과와 전체 신호의 구분

- **국소 효과:** 일관되게 확인되었습니다.
  - 결정적 루프에서 XY는 약 0.38~0.39ms에서 약 0.105ms로 줄었습니다(약 270~286µs 절감).
  - ROS에서는 약 0.63~0.65ms에서 약 0.18~0.19ms로 줄었습니다.
  - A의 XY는 ROS에서 wall p95가 2.0~2.5ms, p99가 4.6~5.2ms로 CPU(p95 약 1.23ms)보다 크게 늘어나는 꼬리가 있었습니다. C에서는 이 꼬리가 거의 사라졌습니다.
  - [가설] 매 주기 LAPACK `lstsq`를 호출하면서 생기는 작업 공간 할당이나 BLAS 경로의 대기가 사라진 것일 수 있습니다. 확인된 원인은 아닙니다.
- **전체 신호:** 혼재합니다.
  - process p95: 1번 쌍은 C가 11.5% 악화, 3번 쌍은 5.8% 개선, 나머지 두 쌍은 거의 같습니다.
  - 최대 공백: 1·2번 쌍은 C가 짧고, 3·4번 쌍은 C가 깁니다.
  - 만료 합계는 C가 적지만 4쌍과 작은 건수로는 확정할 수 없습니다.
  - **회귀 신호도 없고 개선 확정도 아닙니다.**
- **큰 정지는 그대로 남아 있습니다.** 이 사실을 보고서에 명시하세요.
  - 2-C와 3-C에서 전처리 wall 85/73ms에 **스레드 CPU 72.7/65.2ms**가 나타났습니다. 이전 1-A와 같은 "CPU 급증" 유형입니다.
  - 4-A는 109ms였지만 CPU는 3.4ms로, 대기 유형입니다.
  - 위치는 다시 seq 17052~17056 부근입니다.
  - 캐시는 이 현상과 관계가 없으며, 원인은 여전히 확정되지 않았습니다.

## 3) 비용 대비 가치

**가치가 있다고 봅니다.** 다음 세 가지가 이유입니다.
- **효과:** 주기당 약 0.4~0.46ms 절감, process 중앙값 약 5% 개선
- **정확성:** 수치 동등성 확인(시퀀스 4회 차이 0, 계약 2,763사례)
- **비용:** 2파일 +55/−1줄. 새 ABI, 공유 라이브러리, 빌드 절차가 없고 Python만으로 유지보수 가능

이전 B(C++)와 비교하면, 관리 범위는 훨씬 작고 국소 절감 규모는 비슷합니다. 다만 두 결과는 서로 다른 실험이므로 직접 비교하거나 합산하지 마세요.

**남는 비용**
- 같은 XY 수식이 `solve_xy`와 `CachedXY` 두 곳에 존재합니다. 동등성 시험을 CI에 상시 유지해야 합니다.
- 재시작 절차 문서와 기동 로그 확인 방법이 필요합니다.
- colcon 전체 빌드와 실제 노드 재시작 확인이 남아 있습니다.
- 다른 입력이나 장시간 입력으로 확인해야 합니다. 현재는 부분 입력 24초만 썼습니다.
- 퇴화 기하는 매 주기 거부되고, 비유한 설정은 기동 시 실패한다는 동작 차이를 운영 문서에 남겨야 합니다.

## 4) 44차 추정의 정정

- **제 "수십 µs" 추정은 틀렸습니다.** 실측은 결정적 루프에서 약 270~286µs, ROS에서 약 440~460µs였습니다. 이 Jetson에서 3×2 `lstsq`의 Python·LAPACK 호출 비용을 크게 과소평가했습니다.
- "이전 B의 절감은 대부분 높이 투영에서 왔을 것"이라는 제 추정도 철회합니다. 고정 기하 재사용만으로 비슷한 규모가 관측되었기 때문입니다. 다만 B와는 다른 실험이므로, B 절감 중 캐시가 차지한 비율은 계산할 수 없다는 작성자의 표현이 맞습니다.

## 5) 후보 채택 여부와 남은 확인

- **판정:** "**운영 반영 후보로 채택 가능, 자동 승인은 아님**"을 권합니다.
- **운영 반영 전에 확인할 것**
  1. 최종 패치를 리뷰하고 colcon 전체 빌드를 실행합니다.
  2. 실제 노드를 재시작한 뒤 기동 로그의 기하 해시가 config와 일치하는지 확인합니다.
  3. 부분 입력이 아닌 다른 입력이나 장시간 입력으로 동등성을 재확인합니다.
  4. 재시작 절차를 운영 문서에 반영합니다.
- 큰 정지(GC 등 가설)는 이 후보와 별개의 다음 과제로 남겨 두세요.
