# 현장 웹 설정과 RC 인계
천장·자동 출발점·시험 경로를 준비하는 절차다.
현장이 바뀌거나 첫 비행을 준비할 때 읽는다.

## 시작 버튼과 비행 순서

START는 화면 하단에 항상 표시한다.
`미션 START · ARM·이륙 포함` 버튼을 사용한다.
저장 미션을 불러온 뒤 준비 상태를 확인한다.
회색 버튼은 숨김이 아니라 시작 조건 미충족이다.
하단에는 대기 항목 수와 주요 사유가 표시된다.

```text
미션 불러오기 -> 지상 준비 확인 -> START
  -> 실행기 재검사 -> ARM -> PX4 이륙
  -> 안정화 -> 미션 수행 -> 복귀 -> 착륙 -> END
```

별도로 먼저 시동을 걸지 않는다.
이유: START는 disarm·지상 상태에서 시작한다.
체크를 모두 표시하는 버튼은 없다.
수신 상태와 실측·검증 근거가 각 항목을 결정한다.
PX4 추정기 유효 표시만으로 EV 융합을 확정하지 않는다.
실제 융합은 별도의 ULog 확인 항목이다.

현재 자동 출발은 지상에서도 유효 ToF·B_TF를 요구한다.
센서 최소 거리 미만인 바닥 출발은 아직 지원하지 않는다.
이륙 후 센서가 읽힌다는 사실만으로 START를 허용하지 않는다.
이유: 출발점·초기 수평 추정을 먼저 검증해야 한다.
바닥 기준 상대고도 0과 안테나 실측 높이는 별개다.
유효 거리 확보 또는 별도 지상 초기화 검증이 필요하다.

재부팅하면 수동 실행한 웹·관측 launch는 종료된다.
기존 부팅 서비스가 떠 있어도 시험 웹과는 다르다.
포트 소유자와 부팅 ID를 확인한 뒤 관측 모드로 복구한다.
저장 미션 파일은 유지하고 이전 START를 재전송하지 않는다.
복구 후에는 센서·RC·전원·시각을 다시 확인한다.

## 1. 지상 세션에서 천장을 저장한다

웹의 천장 입력 또는 다음 명령을 사용한다.

```json
{"action":"set_ceiling","ceiling_height_m":3.0}
```

`POST /local/command`에 JSON으로 보낸다.
값은 공통 바닥에서 천장까지의 m다.
필요하면 가장 낮은 장애물 높이를 적용한다.
이 값만으로 지도 측량을 완료 처리하지 않는다.
실측 지도의 낮은 상한을 더 높이지 않는다.
기체 바닥 높이·수직 여유를 C++ 검사기에 전달한다.
실측 높이가 없으면 경로를 거부한다.

저장 응답의 `flight_command_sent`는 false다.
PX4 이륙 높이와 고도 제어는 바뀌지 않는다.
`--site-config` 파일에 기체·배치와 함께 저장한다.
생략 시 사용자 상태 폴더의 `site-<ID>.json`을 쓴다.
시험 환경은 반드시 별도 파일을 지정한다.
이유: 가상 환경 설정과 실물 설정을 섞지 않아야 한다.

START 후에는 천장을 바꿀 수 없다.
지상 상태가 오래됐거나 공중이면 변경을 거부한다.
새 현장은 착륙·disarm 확인 뒤 새 세션으로 준비한다.

## 2. 출발점을 자동 확인한다

PX4 EKF2 위치를 검증된 창고 좌표로 변환한다.
안테나 XY를 기체 위치로 대신 사용하지 않는다.
지상·최신 상태·좌표 정렬·추정기 유효성이 필요하다.
값이 없으면 `(0,0)`이나 과거 좌표로 채우지 않는다.
이유: 복귀점이 실제 출발점과 달라질 수 있다.

웹에서 시험 종류와 `시험 경로 만들기`를 선택한다.
시작 명령에서도 출발점을 다시 읽는다.

```json
{"action":"start","trial_case":"hover"}
```

| trial_case | 시작점 기준 계획 |
|---|---|
| hover | PX4 이륙·안정화·2초 체류·복귀 확인·착륙 |
| x | X +1m·출발점 복귀·착륙 |
| y | Y +1m·출발점 복귀·착륙 |
| xy | X +1m·Y +1m·역순 복귀·착륙 |

축은 A1→A2=X, A1→A3=Y다.
기체가 -X를 향하면 +X 이동은 후진이다.
heading이 달라도 웹의 고정 좌표축은 바뀌지 않는다.
A3가 A1→A2의 오른쪽이면 `map_y_axis_sign=-1`을 사용한다.
이 축 방향은 관측·명령·방위 경로가 함께 적용한다.
축 방향 설정만으로 회전·원점 보정을 완료하지 않는다.
1m 구간은 직선 위 0.5m 경유점을 거친다.
이유: 도착 오차가 실제 명령 거리 제한을 넘지 않게 한다.
기체 heading 방향의 앞·옆 이동이 아니다.
계획 후 PX4 출발점이 0.1m 넘게 바뀌면 거부한다.
전체 미션은 지상 정지 3초도 확인한다.
실행 시작 위치를 home으로 고정한다.
상승 목표는 PX4 `MIS_TAKEOFF_ALT`다.
정확히 2초 뒤 강제로 착륙시키지 않는다.
안정화·목표 적용·도착을 확인한 뒤 체류를 센다.

## 3. 실제 RC 인계를 검증한다

RC는 수신기에서 PX4로 직접 연결된다.
companion이나 웹을 경유하지 않는다.

```text
RC 스틱 / 모드 스위치 ──────> PX4 제어·failsafe
                                   │ 모드 관측
                                   v
웹 START -> 단일 미션 실행기 -> PILOT_OVERRIDE
                                   │
                          명령 중단·스캔 취소
                          자동 재개 없음
```

현재 읽힌 매핑은 모드 CH5·시동 CH8·킬 CH7이다.
2026-10-09 모드 스위치의 실제 전환을 확인했다.
사용자 승인으로 중앙 OFFBOARD를 Position으로 바꿨다.
현재 배치는 Altitude / Position / Land다.
`COM_FLTMODE4=2`를 저장·재조회했다.
이후 실제 ALTCTL→POSCTL 전환도 확인했다.
설정 변경 뒤 스위치를 한 번 전환해 실제 모드를 확인한다.
웹 START 전에 Position에서 대기한다.
웹 실행은 PX4 native 자동 모드를 요청한다.
RC OFFBOARD 위치는 필요하지 않다.
시동·킬 스위치와 공중 인계 시험은 아직 남았다.
프로펠러를 제거하고 수신·매핑·보정을 먼저 확인한다.
모드 스위치로 Position/Altitude 전환을 확인한다.
실제 stick override 비행 검증은 조종자가 별도로 수행한다.
RC가 꺼져 있으면 이 단계는 통과할 수 없다.

`COM_RC_OVERRIDE=3`은 AUTO·Offboard 비트를 켠다.
`COM_RC_STICK_OV=30`은 현재 PX4 문턱이다.
작은 잡음이나 모든 보조 버튼을 수동 인계로 해석하지 않는다.
실제 할당된 모드·시동·킬 기능은 PX4 설정을 따른다.
실행기는 FC가 지정한 스위치 채널을 읽는다.
시작값에서 100μs 이상 바뀌면 미션을 중단한다.
이는 새 모드 이름을 수신하기 전에도 적용된다.
보조 채널·10μs 흔들림은 수동 인계로 보지 않는다.
이 감시는 PX4에 가짜 RC 값을 주입하지 않는다.
인계 뒤 웹 START·복귀·착륙으로 RC를 덮지 않는다.
공중 프로세스 재시작도 명령을 보내지 않는다.
이미 보낸 명령의 전달 자체를 취소할 수는 없다.
늦은 응답을 후속 미션 명령의 근거로 쓰지 않는다.

새 비행은 착륙·disarm 뒤 새 지상 세션에서 시작한다.
설정·물리 검증 구분은 [현장 기록](../report/field_readiness_20261009.md)을 따른다.

## 4. 미션을 저장하고 중복 실행을 확인한다

저장 미션과 실제 실행 기록을 따로 관리한다.
앵커 연결 전에도 네 시험 종류를 저장할 수 있다.
저장·불러오기·삭제는 비행 명령을 만들지 않는다.

1. 이름과 시험 종류를 입력하고 `미션 저장`을 누른다.
2. 목록에서 선택하고 `불러오기`로 내용을 확인한다.
3. 수정한 미션은 저장 후 START를 누른다.
4. 실행 번호·기체 수락·진행 결과를 확인한다.
5. 종료 후 최신 착륙·disarm 상태에서 기록을 닫는다.

| 상황 | 처리 |
|---|---|
| 같은 내용 재저장 | 기존 저장 미션을 선택 |
| 같은 이름·다른 내용 신규 저장 | 거부·기존 미션 수정 필요 |
| 다른 창이 먼저 수정 | 버전 충돌 거부·다시 불러오기 |
| 진행 미션 수정·삭제 | 거부·실행 원본 보존 |
| START 중복 클릭·응답 재조회 | 같은 요청 번호의 접수 결과 반환 |
| 다른 창의 새 START | 열린 실행 기록이 있으면 거부 |
| 웹 재시작 | 경로·이력 복원·이전 명령 재전송 없음 |
| 저장소 쓰기 실패 | 명령 노출 전에 거부 |
| 과거 미션의 텔레메트리 | 현재 실행 결과에 반영하지 않음 |
| 삭제한 저장 미션 | 실행 이력은 보존 |

START 때 출발점과 경로를 다시 계산한다.
저장 시의 임시 좌표를 출발점으로 쓰지 않는다.
직접 경유지는 고급 JSON 입력을 사용한다.
서버도 경유지 형식·경계·작업 구성을 검사한다.
전체 미션 START는 최신 준비 상태가 필요하다.
비활성 버튼을 우회한 HTTP 요청도 거부한다.

`기록 닫기`는 companion 상태를 초기화하지 않는다.
RC 인계 잠금이나 비행 중 미션을 해제하지 않는다.
다음 비행에는 실행기가 IDLE인 새 지상 세션이 필요하다.
만료된 미수락 요청은 지상 IDLE에서 닫을 수 있다.
이 경우 성공·END로 바꾸지 않는다.
이유: 요청 정리와 실제 비행 완료는 다르다.

웹은 `--mission-store`의 SQLite 파일에 저장한다.
기체 ID와 앵커 배치가 다르면 파일을 거부한다.
생략 시 현장 설정 옆에 배치별 파일을 만든다.
실물·합성 시험은 서로 다른 파일을 지정한다.
파일은 비공개 현장 기록으로 백업한다.
기록 파일을 지워 중복 잠금을 우회하지 않는다.
이유: 이전 실행의 수락 여부가 사라질 수 있다.

```json
{"action":"save","name":"호버 2초","definition":{"trial_case":"hover"}}
```

저장은 `POST /local/missions`로 보낸다.
`GET /local/missions`는 저장 목록과 최근 실행을 반환한다.
START에는 저장 응답의 ID와 현재 버전을 보낸다.

```json
{"action":"start","draft_id":"저장 응답의 ID","revision":1,"client_request_id":"새 요청마다 고유한 식별자"}
```

START는 `POST /local/command`로 보낸다.
응답을 못 받으면 같은 내용·요청 식별자로 확인한다.
다른 내용을 같은 식별자로 보내면 거부한다.
브라우저는 현재 기체·배치도 요청에 함께 보낸다.
