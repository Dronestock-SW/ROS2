# 현장 1회 이륙 시험을 연결하는 순서

상시 관측과 웹 이륙 시험을 연결하는 절차다.
2026-10-09 현장 작업을 이어갈 때 읽는다.
목표는 1.3m 이륙 → 2초 호버 → 착륙이다.

현재 지상 UWB→PX4 융합은 확인했다.
실기 START 연결은 아직 끝나지 않았다.
남은 작업은 아래 1~4 순서로 진행한다.
같은 지상 이동을 원인 구분 없이 반복하지 않는다.

## 연결 구조

관측은 상시 유지하고, 명령은 새 START로 시작한다.

```text
Tag B 거리 + 앵커 배치 + ToF/IMU
  → B_TF 안테나 XY (원본 측정 시각 유지)
  → 창고 축 반전·회전·원점 변환
  → MAVROS vision_pose/pose_cov → PX4 EKF2 XY

하방 ToF → PX4 고도 추정 → PX4 이륙·호버·착륙
PC 웹 START → 단일 명령 실행기 → PX4 자동 모드
RC 개입 → 명령 실행 중단, 자동 재개 금지
```

ToF는 B_TF의 거리 해석에도 사용한다.
EV 고도·yaw 융합은 켜지 않는다.
지상 안테나 높이 0.15m는 실측 고도가 아니다.
공중 ToF 결측을 0.15m로 대체하지 않는다.
이유: 실제 상승을 지상 상태로 오인할 수 있다.

## 1. 좌표 계산 부하와 수신 지연을 분리한다

수치 결과를 유지하는 H80 최적화부터 적용한다.
앵커 선택·IRLS 수렴 검사 중복 연산을 줄였다.
반복 횟수와 거부 기준은 유지했다.

동일 Jetson의 실측 160개 재생 결과는 같다.
5회 평균의 중앙값은 10.147→9.066ms였다.
이는 계산 부분의 약 10.7% 감소다.
수신 공백 해소나 비행 성공의 증거는 아니다.
관련 Linux 시험은 64개 통과했다.

운영 프로세스 적용 뒤 아래 도구로 재측정한다.
기존 MAVROS PID를 읽어 인자로 전달한다.
새 기록 경로를 사용한다.

```bash
export ROS_DOMAIN_ID=2 ROS_LOCALHOST_ONLY=1
python3 src/drone_uwb/tools/observe_fc_transport.py \
  --seconds 90 --mavros-pid "$MAVROS_PID" \
  --output "$NEW_TRACE_DIRECTORY"
```

| 관찰 결과 | 다음 수정 대상 |
|---|---|
| FC router부터 공백 | FC 송신·USB·MAVROS 수신 경로 |
| router 정상, ROS 센서만 지연 | MAVROS/DDS 전달·실행 지연 |
| UWB 수신 정상, B_TF만 지연 | 좌표 계산·큐·직렬화 |
| B_TF 정상, EV 발행만 중단 | bridge gate·시계·설정 |

0.34초 공백 하나로 USB 불량을 단정하지 않는다.
웹 서버 이전이나 UART 추가는 현재 필수 해법이 아니다.
웹 CPU 합계는 약 4.3%였다.
B_TF 프로세스는 약 91.6%였다.
둘 다 3초 측정이며 한 코어를 100%로 센 값이다.

## 2. 적용할 좌표·시간 보정을 확정한다

운영 기본 회전·원점 0을 그대로 켜면 안 된다.
이유: 지상 시험에서 융합한 좌표계와 다르다.

현재 부팅의 후보 변환은 별도로 준비했다.
파일명은 `field-mission-flight-CANDIDATE.json`이다.
현재 부팅·배치에만 해당하는 후보로 취급한다.
재부팅·기체 또는 앵커 이동 시 다시 대조한다.
`alignment_confirmed`와 `timing_confirmed`는 false다.

기존 이동 기록만으로 고정 지연은 확정되지 않았다.
X 최적 지연은 탐색 경계인 -0.5초였다.
Y와 다른 왕복 기록도 서로 달랐다.
정지 중 XYZ 안정성은 동적 지연을 결정하지 못한다.

먼저 원본·호스트·B_TF·EV 시각을 대조한다.
큐 지연과 센서의 고정 지연을 구분한다.
추가 이동이 필요하면 한 번의 기록으로 묶는다.
프로펠러를 제거하고 유효 ToF 높이를 유지한다.
+X 왕복·+Y 왕복·정지를 한 파일에 남긴다.
실제 이동량과 순서를 함께 기록한다.
EV가 융합된 FC 위치만을 정답으로 쓰지 않는다.
이유: 비교 대상에 같은 UWB 입력이 포함된다.
독립 기준의 정확도와 시간 해상도를 먼저 기록한다.
예: 실제 바닥 눈금과 시각을 맞춘 영상 기준.
광류를 쓰면 원시 품질·축·거리 보정을 확인한다.

완료 조건은 두 축의 방향·이동량이 설명되는 것이다.
시간 보정은 반복 구간에서 일관되어야 한다.
유일하지 않으면 값을 추정 완료로 표시하지 않는다.
허용 오차는 기록 전에 시험 계획에 명시한다.

## 3. 지상 전용 발행기를 상시 bridge로 교체한다

명령 실행은 끈 채 관측 발행부터 연결한다.
지상 진단 발행기를 먼저 종료한다.
동시에 두 발행기를 FC에 연결하지 않는다.
이유: 서로 다른 원점의 관측이 섞일 수 있다.

| 설정 | 적용 내용 |
|---|---|
| 기체 | Tag B, ID 6, domain 2 |
| 관측 입력 | `/uwb/btf_pose` |
| 변환 | 2단계에서 확정한 회전·원점·축 |
| 장착 | FC→안테나 FRD (-0.1, 0, -0.1)m |
| `bridge_enabled` | true |
| `bridge_ground_only` | false |
| `execute` | false |
| EV 융합 | XY만. 높이·yaw 제외 |

기존 `test_flight.launch.py`가 이 조합을 지원한다.
MAVROS는 기존 단일 소유자를 유지한다.
실행 중 launch와 포트를 중복으로 열지 않는다.
현재 관측 launch 소유 그룹만 교체 대상으로 삼는다.
설정 파일은 bridge와 mission에 동일하게 적용한다.
mission의 목표 좌표와 관측 좌표가 같아야 한다.

프로펠러 없는 DISARM 상태에서 전환을 확인한다.
킬 스위치 변경만으로 관측이 종료되면 실패다.
수신이 끊기면 오래된 좌표를 새 시각으로 보내지 않는다.
복구 후 실제 새 관측부터 발행해야 한다.
FC `cs_ev_pos`, `xy_valid`, 실제 융합을 읽는다.
웹 표시와 bridge 발행 수만으로 완료하지 않는다.

## 4. 한 실행기에서 1회 웹 시험을 연다

첫 시험은 8350 단발 이륙 실행기만 사용한다.
8351 미션 실행기는 관측 상태로 유지한다.
이유: 두 경로의 ARM·착륙 요청 충돌을 막는다.

현재 단발 실행기 설정은 높이 1.3m다.
호버 시간은 2초다.
PX4가 목표 높이·정지 조건에 도달하면 시간을 센다.
버튼을 누른 순간부터 2초를 세지 않는다.
착륙·DISARM의 최신 FC 상태로 완료를 판정한다.

상시 관측 확인 뒤 실제 명령 출력을 연결한다.
현장 조종자가 새 START를 눌러 실행한다.
RC 개입 후 명령을 다시 보내지 않는다.
위치 상실 시 착륙 요청의 전달·수락을 기록한다.
FC 통신 상실 시 PX4 자체 failsafe를 구분한다.
통신이 없는데 LAND가 전달됐다고 기록하지 않는다.

착륙 확인 뒤에만 가까운 XY 경유점으로 넓힌다.
그 다음 8351 미션 관리 경로를 연결한다.
SITL·재생·지상 수신·실비행 결과를 따로 기록한다.

근거는 [수신 공백과 수정 기록](../report/fc_transport_gap_20261009.md)이다.
