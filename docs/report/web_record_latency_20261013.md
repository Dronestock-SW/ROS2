# 웹·기록 저장 지연 분리
웹과 기록 지연을 조사하고 수정한 결과다.
13일 저녁 시험과 후속 분석 전에 읽는다.

저장 대기가 입력 콜백과 LAND를 막던 경로를 분리했다.
실제 비행과 물리적 밀림 해결은 아직 검증하지 않았다.
통합 브랜치는 `이번에-상원-한거-통합-브랜치`다.

## 확인한 원인

저장 용량과 동기 저장 지연은 구분해야 한다.
디스크 여유 부족만으로 수초 지연을 설명할 수 없다.

| 경로 | 이전 동작 | 수정 |
|---|---|---|
| 웹 DB | 저장·조회·HTTP 응답이 같은 잠금 사용 | 저장만 직렬화. 조회는 마지막 확정 값 사용 |
| 웹 텔레메트리 | 수신 콜백에서 DB 쓰기 | 수신 즉시 갱신. DB 작업은 별도 큐 |
| Python 요청 원장 | ROS 콜백에서 파일·디렉터리 fsync | 별도 작업에서 저장. 완료 후 요청 전달 |
| Python 일반 기록 | 비행 표본마다 fsync | 비동기 기록. 1초 간격으로 묶어서 fsync |
| C++ 명령 | 기록 대기도 FC 응답 3초에 포함 | 실제 송신부터 FC 응답 시간 계산 |
| LAND | 앞선 명령 원장 저장 뒤에 대기 가능 | 독립 작업에서 송신. 저장은 후속 처리 |
| 웹 LAND 버튼 | 다른 요청 응답 대기 중 비활성 | 기존 START 응답 대기와 분리 |
| 별도 TAKEOFF | 수동 ARM용 3초 만료 검사 재사용 | 미션 요청의 기존 30초 기준으로 통일 |

START·TAKEOFF 원장은 전달 전에 저장한다.
수동 ARM의 3초 제한은 그대로 유지한다.
요청 시각과 센서 원본 시각은 새로 찍지 않는다.
이미 지난 요청의 유효시간을 연장하지 않는다.
명령 저장 대기는 30초로 제한한다.
실제 FC 송신 뒤 응답 제한은 여전히 3초다.
송신 직전에 FC·RC 권한을 다시 확인한다.
ARM·OFFBOARD는 현재 위치·UWB 입력도 다시 검사한다.

LAND 뒤에 늦은 START가 노출되지 않게 했다.
취소된 C++ 명령 token은 나중에 송신하지 않는다.
이전 ACK는 더 최신 LAND 원장을 덮어쓰지 않는다.
재시작 때 저장 요청을 자동으로 재실행하지 않는다.

SQLite는 WAL과 `synchronous=FULL`을 사용한다.
하나의 연결에서 쓰기를 직렬화한다.
저장 완료 전 START 응답을 성공으로 만들지 않는다.
일반 기록은 갑작스러운 전원 차단 때 일부를 잃을 수 있다.
명령 원장과 최종 결과는 별도 동기 저장을 유지한다.
최종 저장 대기는 `record_pending`으로 표시한다.
단순 대기를 미션 END로 꾸미지 않는다.

```text
웹 수신/조회 ─── 메모리 상태 ─── 요청·텔레메트리
                    │
                    └── 저장 큐 ─── SQLite FULL

ROS 관측 ─── Python 입력 어댑터 ─── C++ 판단
                    │                   │
                    └── 기록 작업       ├── 20Hz 목표 송신
                                        ├── 명령 저장 → 현재 권한 확인 → 송신
                                        └── LAND 송신 → 기록
```

## SSH 측정과 재현

수정 전 일반 실행에서는 과거 수초 지연을 재현하지 못했다.
웹 잠금 최대 139.75ms를 측정했다.
관측 기록 fsync 199회의 최대는 74.34ms였다.
별도 4KB 저장 20회는 최대 34.82ms였다.
따라서 과거 모든 지연의 원인이 확정됐다고 쓰지 않는다.

강제 지연 첫 시험은 TAKEOFF 만료로 IDLE에 남았다.
FC 명령은 0회였다.
3초 ARM 검사를 재사용한 경로를 이 시험에서 찾았다.
실패 결과는 `after-flow.log`에 보존했다.

수정 뒤에는 ROS domain 99에서 실제 실행 파일을 사용했다.
물리 FC 대신 가상 FC만 연결했다.
DB·Python 원장·일반 기록·C++ fsync에 4초를 주입했다.
주입 도구는 시험 디렉터리에만 있다.
운영 실행 파일에는 지연 스위치를 추가하지 않았다.

| 시험 | 결과 | 최대 목표 수신 간격 |
|---|---|---|
| 저장 지연 + 별도 이륙·START·호버 | END·착륙·DISARM | 65.05ms |
| POSITION 명령 저장 중 LAND | 취소·착륙·DISARM | 68.73ms |
| 별도 이륙·START·X 이동·복귀 | END·착륙·DISARM | 63.93ms |

저장 중 LAND는 웹 요청부터 가상 FC 수신까지 274ms였다.
취소된 POSITION 명령은 이후에도 실행되지 않았다.
취소 시험의 `FAILED`는 임무 취소를 뜻한다.
착륙 확인은 `landing_verified=true`로 별도 기록했다.
두 지연 시험의 HTTP 조회는 1,777회였다.
최대 응답 시간은 152.91ms였다.
지연 주입 TAKEOFF 응답은 약 4초였다.
그동안 다른 조회·입력·LAND는 계속 처리됐다.
일반 X 이동의 새 요청 응답은 27.65/29.26ms였다.
세 시험에서 HTTP timeout은 0회였다.
C++의 Python 입력 나이는 최대 105.21ms였다.
주입을 포함한 명령 저장은 최대 7.74초였다.
이 수치는 OS의 최악 실행시간을 보장하지 않는다.

추가 네 시험도 통과했다.
이륙 중 UWB 공백·보고 지연·재진입 전 공백을 포함한다.
LAND 지연 시험은 최종 기록 완료까지 다시 확인했다.
재시험 LAND 전달은 464ms였다.
추가 시험의 최대 목표 수신 간격은 72.06ms였다.
강제 지연이 없는 보고 지연 시험에서도
관측 기록 fsync가 최대 1.60초 걸렸다.
C++ 명령 기록은 최대 1.83초였다.
동시 빌드·디스크 조회가 있던 조건이다.
입력·목표 송신을 막지 않는 것을 확인했다.
[추가 시험 근거](evidence/web_record_latency_20261013/additional-verification.json)를 보존한다.

| 검증 | 결과 |
|---|---|
| Windows Python | 317 통과·17 제외. ROS 실행 시험은 별도 |
| 브라우저 명령 응답 역전 | 실제 JS 처리기 2개 통과 |
| Jetson Python 집중 검증 | 69 통과 |
| Jetson ROS 패키지 | 4개 빌드 성공 |
| Jetson C++ 빌드 | 실행기·재현기 성공 |
| CTest | 실행기·AI·상대 관측 계약 3그룹 통과 |
| Jetson HTTP/ROS/C++ | 6종 7회 통과. 두 묶음으로 실행 |

원격 CI 첫 실행은 Python 296개를 통과했다.
C++ 계약 3그룹과 Python 연동 9개도 통과했다.
브라우저 시험은 Node.js 12의 모듈 호환 오류로 멈췄다.
`assert/strict` 대신 `require('assert').strict`를 사용한다.
비행 실행 로직은 이 수정으로 바뀌지 않는다.
후속 CI 결과를 별도로 확인해야 한다.

## 디스크 현황

16:00 KST에 전체 파일시스템을 읽기 집계했다.
57GiB 중 약 52.2GiB를 사용했다.
일반 사용자에게 남은 공간은 약 2.25GiB였다.
이번 작업에서는 파일을 삭제하지 않았다.

| 항목 | 크기·범위 |
|---|---|
| 전체 사용자 홈 `/home` | 29.6GiB |
| 시스템 `/usr` | 15.1GiB |
| `/var` | 5.9GiB |
| 현재 계정 홈 | 9.6GiB. 전체 홈에 포함 |
| 현재 계정 원시 관측 `manual-captures` | 3.39GiB. 현재 홈에 포함 |
| 현재 저장소 `.review` | 2.32GiB. 현재 홈에 포함 |
| 현재 계정 VS Code 서버 | 1.32GiB. 현재 홈에 포함 |
| `/var`의 CUDA·cuDNN·TensorRT 로컬 설치 패키지 | 3.32GiB. `/var`에 포함 |

상위 폴더와 하위 항목을 합산하면 중복 계산이다.
다른 계정 홈에는 약 19.9GiB가 있다.
다른 작업자의 자료를 현재 시험 파일로 취급하지 않는다.
10월 12일 비행 원본은 계속 보존한다.
일반 계정의 최초 `du`는 권한 때문에 일부를 놓쳤다.
관리 권한 읽기 집계로 실제 사용량과 대조했다.
PC의 C 드라이브는 별개이며 약 13.9GiB가 남아 있었다.

## 실제 FC 읽기 검증

실제 FC는 DISARM·지상·AUTO.LOITER였다.
웹·C++·관측 어댑터의 출력은 비활성으로 실행했다.
웹 조회 20회의 최대는 25.13ms였다.
목표 송신 0개, 명령 원장 0바이트를 확인했다.
비공개 미션 DB와 기존 센서 서비스는 유지했다.

UWB 새 관측은 없었다.
RC·배터리·수평 추정 준비 조건도 미충족이었다.
저녁 앵커·조종기 전원 투입 후 다시 확인해야 한다.
이 검사만으로 실비행 준비 완료를 선언하지 않는다.
FC 파라미터·추력·상승 속도는 변경하지 않았다.

## 밀림 원인에 대한 판단

UWB 제약이 초기 밀림의 주원인이라는 결론은 아직 없다.
[실행 8 분석](run8_offboard_attitude_20261012.md)의 선후관계를 따른다.
ARM 후 2.368초에 FC 추정 XY가 3cm를 벗어났다.
최종 UWB 원본 시각은 7.767초로 추정했다.
LAND 요청은 8.051초였다.
초기 추정 이탈이 최종 공백보다 먼저다.
PX4 수평 추력 요구 104개 중 102개는 목표 쪽이었다.

소프트웨어 제약은 불필요한 조기 LAND를 설명할 수 있다.
물리적 이동·UWB 편향·광류 축·자세 추종은 별도 문제다.
이번 수정은 고정 출발 XY를 유지한다.
기수 오른쪽 보정값이나 별도 자세 제어는 추가하지 않았다.
다음 비행에서 ULog·B_TF 원시/decision·영상을 함께 남긴다.
`EKF2_EV_DELAY`는 실제 관측 시각 차이를 분석한 뒤 맞춘다.
