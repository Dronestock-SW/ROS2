# 다음 제어 개발 조사 — 수평 이동·감속·정지
이 문서는 다음 제어 개발의 조사 결과다.
기존 데모에서 제어 시험으로 넘어갈 때 읽는다.

## 1. 결론

**다음 작업은 수평 위치 P 제어와 감속·정지다.**
목표까지 남은 거리를 수평 속도 명령으로 바꾼다.
PX4가 그 속도를 따라가도록 기체를 조절한다.

기존 `fixed_z_m=1.2`를 데모에서 재사용한다.
새 PX4 시뮬레이션에서는 목표 높이로 활용한다.
고도를 유지하는 제어는 PX4가 맡는다.
companion에 고도 PID를 만들 필요는 없다.

개발 순서는 다음과 같이 제안한다.

| 순서 | 만들거나 비교할 것 | 확인할 결과 |
|---|---|---|
| 1 | 명령에 따라 움직이는 수평 데모 | 이동·감속·정지가 실제 경로를 바꿈 |
| 2 | PX4 기본 위치제어 | 비교 기준 성능 확보 |
| 3 | companion P 제어 → PX4 속도제어 | 같은 조건에서 기준 성능과 비교 |
| 4 | UWB 공백·지연·편향 시험 | 위치추정과 제어의 실패를 분리 |
| 5 | LiDAR 기반 수평 감속·정지 | 장애물 앞 제동거리 검증 |

현재 데모는 도착 여부를 판단한다.
제어 명령으로 경로를 바꾸지는 않는다.
따라서 기존 도착 성공은 제어 성능의 증거가 아니다.
[개발 1사이클 결과](demo_cycle_20260913.md)에 그 범위가 기록돼 있다.

이번에는 문서·소스·저장 로그를 조사했다.
새 제어 코드나 실제 비행 명령은 실행하지 않았다.

## 3. 기존 dummy z를 쓰는 방법

1.2m를 재사용하되, 현재 높이와 목표 높이를 구분한다.

| 위치 | z의 의미 | 다음 개발에서의 사용 |
|---|---|---|
| 현재 `/demo_pose` | 생성기가 정한 가상 높이 | 단순 수평 데모에서 1.2m 유지 |
| 현재 `/target_pose` | 데모 목표의 높이 | 목표값 1.2m 재사용 |
| 새 PX4 SITL의 목표 | PX4가 유지할 희망 높이 | SITL 전용 연결부에서 전달하는 안 |
| 새 물리 시뮬레이터의 현재 높이 | 모형이 실제로 움직인 결과 | 상승·하강·흔들림에 따라 변함 |
| `/uwb_pose`의 z=0 | UWB가 관측하지 않은 자리값 | 1.2m 실측값으로 바꾸지 않음 |
| 앵커의 z=2.2m | 앵커 설치 높이 | 드론의 목표 높이와 별개 |

현재 노드는 MAVROS에 명령을 보내지 않는다.
SITL 목표 전달은 다음 연결부의 설계 제안이다.
기존 데모의 격리 동작을 이미 바꿨다는 뜻은 아니다.
[고도 원칙](../altitude_policy.md)과 [데모 기준](../demo_design.md)을 함께 따른다.

PX4의 local z 원점과 바닥은 같다고 가정하지 않는다.
SITL에서는 바닥과 local 원점 관계부터 확인한다.
바닥의 ENU z가 0일 때 목표 z는 +1.2m다.
MAVROS가 전달하면 NED에서는 -1.2m가 된다.
원점이 다르면 그 차이를 목표값에 반영한다.
[MAVROS 2.14.0 변환 코드](https://github.com/mavlink/mavros/blob/2.14.0/mavros/src/plugins/setpoint_raw.cpp)가 ENU→NED 변환을 수행한다.

실측 전환 때는 검증한 PX4 상태를 현재값으로 쓴다.
T-mini Pro의 수평 스캔은 고도 측정을 대신하지 않는다.
[장비별 역할](../equipment_inventory.md)에 따른 구분이다.

현재 가상 거리는 데모 위치에서 앵커까지 계산한다.
기체 중심과 태그 안테나의 위치 차이는 아직 모형에 없다.
SITL에서는 목표 높이의 기준점을 기체로 명시한다.
가상 UWB 거리는 안테나 장착 위치를 반영해 만든다.
장착 예정치는 검증된 실측값으로 취급하지 않는다.

## 4. 어떤 제어를 먼저 만들 것인가

위치 P 제어로 시작하고, PX4 기본 제어와 비교한다.

| 대안 | 효과 | 전제·개발 부담 | 한계와 선택 |
|---|---|---|---|
| PX4에 목표 x·y·z 전달 | PX4 기본 위치·속도제어 활용 | 좌표·상태·목표 연결 필요. 부담 낮음 | 첫 비교 기준으로 사용 |
| companion P → 수평 속도 전달 | 근접 감속·가상벽 로직 연결 용이 | 속도 제한·공백 처리를 직접 검증. 부담 중간 | 다음 자체 제어의 우선안 |
| companion 위치 PID | 지속 오차·진동에 대응할 여지 | 누적값·포화·미분 잡음 관리. 부담 증가 | P 시험에서 필요성이 드러날 때 추가 |
| 상황별 게인 전환 | 접근·공백 때 반응 강도 조절 | 전환 시 명령 연속성 검증 필요 | P 기준 성능 확보 후 적용 |
| 강화학습 | 복잡한 상황별 선택을 학습 | 환경·보상·반복 평가 부담 큼 | 감속·정지 기준을 만든 뒤 비교 |

PX4 자체 구조도 위치 P와 속도 PID를 사용한다.
companion P는 목표 위치와 현재 위치의 차이를 본다.
PX4 속도 PID는 목표 속도와 현재 속도의 차이를 본다.
서로 다른 오차를 담당하는 구조다.
[PX4 v1.16 제어 구조](https://docs.px4.io/v1.16/en/flight_stack/controller_diagrams)에 근거한다.

반면 같은 위치 오차를 두 번 더하면 안 된다.
PX4에 목표 위치를 보내면서 같은 오차로 만든
속도 명령까지 더하면 의도보다 강하게 움직일 수 있다.
위치와 속도를 함께 주면 속도는 피드포워드로 더해진다.
[PositionControl 소스](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/mc_pos_control/PositionControl/PositionControl.cpp)의 `_positionControl()`에서 확인했다.

수평 P 제어의 기본 계산은 다음과 같다.

```text
위치 오차 = 목표 x·y - PX4가 추정한 현재 x·y
희망 수평 속도 = Kp × 위치 오차
실제 보낼 속도 = 속력·속도 변화·제동 조건을 적용한 값
```

아래는 계산을 설명하기 위한 초기 예시다.
`Kp=0.5 /s`, 최대 속력 0.25m/s로 둔다.

| 목표까지 거리 | P 계산 결과 | 속력 제한 후 |
|---:|---:|---:|
| 1.0m | 0.50m/s | 0.25m/s |
| 0.4m | 0.20m/s | 0.20m/s |
| 0.1m | 0.05m/s | 0.05m/s |

이 수치는 실기의 안전 속도나 최적 게인이 아니다.
가까워질수록 느려지는 원리를 보이는 예시다.
x·y 각각이 아닌 합성 속력을 제한한다.
대각선에서 최대 속력이 커지는 일을 막기 위해서다.

도착 후에도 같은 목표 오차를 계속 줄인다.
속도 0만 계속 보내면 위치가 밀려도 복귀하지 않는다.
목표 반경 진입·이탈에는 기존 히스테리시스를 재사용한다.

UWB 좌표의 편향은 PID만으로 교정되지 않는다.
예컨대 현재 위치를 실제보다 0.24m 크게 안다면,
제어기는 그 잘못된 좌표를 목표에 맞출 수 있다.
좌표 정확도와 제어 추종 정확도를 따로 평가해야 한다.

## 5. MAVLink 연결과 상태 입력

현재 구성에서는 MAVROS를 통한 MAVLink를 우선한다.

```text
UWB 거리 -> 전처리·좌표/시각 정합 -> MAVROS 관측 입력
                                           |
실제 또는 가상 IMU ---------------------> PX4 EKF2
                                           |
                                  현재 위치·속도·유효성
                                           |
서버/데모 목표 -> 좌표 정합 -> 임무 판단 -> 수평 P 제어
                                           |
                         속력 제한·제동·명령 유효기간 검사
                                           |
데모의 목표 높이 1.2m ----------------> SITL 출력 연결부
                                           |
                     /mavros/setpoint_raw/local
                                           |
                   MAVLink SET_POSITION_TARGET_LOCAL_NED
                                           |
                   PX4 속도·고도·자세 제어 -> 기체 움직임
```

위 그림의 UWB 융합과 제어 출력은 목표 구성이다.
현재 실기에 연결 완료된 흐름을 뜻하지 않는다.
PX4 상태를 다시 UWB 관측으로 넣지는 않는다.
이유는 같은 정보를 중복 융합하게 되기 때문이다.

### 5.1 수평 속도와 목표 높이의 조합

검토한 소스에서는 축별 목표 조합을 처리할 수 있다.

| `PositionTarget` 항목 | SITL 우선안 |
|---|---|
| `coordinate_frame` | `FRAME_LOCAL_NED` |
| ROS에 넣는 숫자의 좌표계 | MAVROS local ENU |
| `velocity.x`, `velocity.y` | 수평 제어기가 계산한 값 |
| `position.z` | local 원점에 맞춘 목표 높이 |
| 무시할 항목 | PX·PY·VZ·AFX·AFY·AFZ·YAW·YAW_RATE |
| 무시한 항목의 숫자 | 유한한 자리값 사용. 적용 여부는 `type_mask`로 지정 |
| 검증 상태 | 소스에서 가능성 확인. SITL 동작 시험은 미실시 |

PX4 수신부는 무시한 항목을 내부 NaN으로 바꾼다.
위치제어기는 각 축에 유효한 목표가 있는지 검사한다.
따라서 x·y 속도와 z 위치의 조합이 성립한다.
[PX4 MAVLink 수신부](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/mavlink/mavlink_receiver.cpp)와
[축별 입력 검사](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/mc_pos_control/PositionControl/PositionControl.cpp)를 대조했다.

이 조합에서도 수평 위치 유효성이 필요하다.
z 위치 하나만 써도 `offboard_control_mode.position`이 켜진다.
그러면 Offboard 검사가 local 위치 유효성을 요구한다.
수평 위치 상실을 우회하는 조합은 아니다.
[Offboard 유효성 검사](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/commander/HealthAndArmingChecks/checks/offboardCheck.cpp)에 근거한다.

`BODY_NED`는 같은 대안으로 바꾸어 쓰지 않는다.
이 버전은 body 경로에서 위치 목표를 무시한다.
속도 축 하나를 무시해도 전체 속도 벡터를 무시한다.
위의 혼합 명령에는 local 경로가 필요하다.
[수신부의 두 좌표계 분기](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/mavlink/mavlink_receiver.cpp)에서 확인했다.

yaw 목표를 무시한 경우의 응답도 SITL에서 확인한다.
검토한 위치제어기는 현재 yaw와 회전 속도 0을 사용한다.
별도의 절대 방위 유지 성능이 보장되는 것은 아니다.
[PX4 yaw 기본 처리](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/mc_pos_control/PositionControl/PositionControl.cpp)에 근거한다.

### 5.2 현재 위치·속도의 입력 계약

좌표 숫자 외에 유효성·시각·좌표계를 함께 받는다.

| 입력 | 사용할 내용 | 확인할 함정 |
|---|---|---|
| `/mavros/state` | 연결·시동·모드 | connected만으로 EKF 정상 판정 불가 |
| `/mavros/local_position/odom` | PX4 위치·속도 | pose와 twist의 기준 좌표계가 다름 |
| `/mavros/estimator_status` | 추정 상태의 플래그 | 모든 PX4 내부 유효성 정보가 전달되지는 않음 |
| UWB 처리 상태 | 관측 나이·새 표본 여부 | 재전송을 새 측정으로 세지 않음 |
| `/target_pose` | 목표·좌표계 | 서버와 `uwb_map`의 축·원점 정합 필요 |

MAVROS 2.14.0 소스의 odom pose는 local ENU다.
odom twist는 기체 기준 `base_link`로 회전된다.
제어에 쓸 수평 속도는 자세로 다시 local에 맞춘다.
기울어진 경우에는 yaw만이 아닌 전체 회전을 고려한다.
기본 `LOCAL_POSITION_NED` 경로의 공분산 0은
실제 오차가 0이라는 측정 결과가 아니다.
[MAVROS local_position 구현](https://github.com/mavlink/mavros/blob/2.14.0/mavros/src/plugins/local_position.cpp)을 확인한 결과다.

`estimator_status` ROS 메시지는 상태 플래그를 제공한다.
PX4 내부의 `eph`, `evh`, 초기화 횟수 등을 모두 싣지는 않는다.
필요한 상태 전달을 추가 확인할 때는 PX4 정보를 번역한다.
companion에서 새 상태추정기를 만들지는 않는다.
현재 플래그만으로 PX4 내부 허용 판정을 복제했다고 보지 않는다.
[MAVROS 상태 변환](https://github.com/mavlink/mavros/blob/2.14.0/mavros/src/plugins/sys_status.cpp)과
[PX4 내부 상태 정의](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/msg/versioned/VehicleLocalPosition.msg)를 대조했다.

`header.frame_id`를 적는 것만으로 목표가 변환되지는 않는다.
MAVROS raw setpoint 콜백은 임의의 TF를 조회하지 않는다.
`uwb_map` → PX4 local ENU 변환은 앞단에서 끝내야 한다.
[MAVROS raw setpoint 코드](https://github.com/mavlink/mavros/blob/2.14.0/mavros/src/plugins/setpoint_raw.cpp)에 근거한다.

실제 서버 좌표 정합은 별도 미완료 항목이다.
[좌표 정합 요청 문서](../companion_platform_alignment_request.md)를 재사용한다.
데모는 자체 목표를 쓰므로 이 확인을 기다리지 않고 개발할 수 있다.

### 5.3 명령의 주기와 유효기간

제어 명령은 주기적으로 보내되 계산 결과의 나이를 검사한다.

PX4 문서는 MAVLink setpoint를 2Hz보다 빠르게 요구한다.
Offboard 진입 전에도 1초 이상 보내야 한다.
첫 SITL 송신 주기는 20Hz를 제안한다.
이는 제어 명령 주기이며 UWB 측정률이 아니다.
[PX4 v1.16 Offboard 문서](https://docs.px4.io/v1.16/en/flight_modes/offboard)에 근거한다.

수신부는 패킷 도착 때 PX4 내부 시각을 기록한다.
오래된 계산 결과를 반복 송신해도 통신은 살아 보일 수 있다.
따라서 새 송신 시각과 명령 생성 시각을 구분한다.
[PX4 수신부의 시각 처리](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/mavlink/mavlink_receiver.cpp)를 근거로 한 설계 제안이다.

명령 발행자는 하나로 둔다.
서버 요청·영상 처리 때문에 제어 주기를 막지 않는다.
만료된 이동 명령을 재접속 뒤 다시 실행하지 않는다.
명령 송신·모드 수락·실제 이동은 각각 기록한다.
이유는 전송 성공만으로 제어 성공을 알 수 없기 때문이다.

## 6. 공백과 장애물에 대한 제어

센서 공백과 제어 통신 공백을 나누어 시험한다.

| 조건 | 제안하는 반응 | 성립 조건·한계 |
|---|---|---|
| UWB만 잠깐 끊김 | 목표 진행 축소, 감속·정지 검토 | PX4 상태가 계속 신선하고 유효해야 함 |
| PX4 위치 유효성 상실 | 좌표 이동 중단, 검증된 PX4 대응 사용 | 속도 명령으로 바꾸면 해결된다고 가정하지 않음 |
| 상태 입력 자체가 오래됨 | 도착 판정 해제, 이전 명령 만료 | 마지막 좌표로 계속 이동하지 않음 |
| 명령 생성기가 멎음 | 만료 탐지, PX4 공백 대응 시험 | 송신기만 이전 값을 반복하지 않도록 설계 |
| MAVLink 단절 | PX4의 Offboard 상실 대응 | 실제 설정·RC 상태·추정 상태를 함께 시험 |
| 서버 목표 취소 | 유효한 PX4 상태로 감속·정지 | HTTP 처리와 명령 주기를 분리 |
| UWB 복구 | 연속 정상 관측 후 이동 재개 | 순간 좌표 점프·방향 변화부터 검사 |

PX4의 공백 대응은 파라미터와 상태에 따라 달라진다.
Hold나 Land를 모든 상황의 정답으로 정하지 않는다.
실내 Return도 경로와 원점 검증 없이 선택하지 않는다.
이유는 정지·착륙·복귀가 요구하는 조건이 다르기 때문이다.
[PX4 failsafe 문서](https://docs.px4.io/v1.16/en/config/safety)와
[해당 버전의 failsafe 구현](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/commander/failsafe/failsafe.cpp)을 기준으로 시험한다.

기존 데모의 공백 임계값과 복구 조건은 재사용 출발점이다.
실기의 허용 공백 시간으로 확정한 값은 아니다.
공백 중 고주기 EKF 출력은 새 UWB 측정이 아니다.

LiDAR는 먼저 장애물 방향의 감속·정지에 활용한다.
스캔매칭은 로드맵의 다음 위치추정 단계로 둔다.

| 필요한 정보 | 이유 |
|---|---|
| 장착 위치·방향·가림 구간 | 스캔 방향과 실제 이동 방향 일치 |
| 스캔 시각과 기체 자세 | 회전·기울어짐 때의 관측 방향 확인 |
| 프레임·프로펠러를 포함한 외곽 | 센서 중심만 멈춰서는 충돌할 수 있음 |
| 측정 불가·반사 이상·통신 공백 | 읽지 못한 방향을 빈 공간으로 보지 않음 |
| 실제 감속 능력·전체 지연 | 장애물보다 앞에서 멈출 거리 계산 |

앵커 4기의 폴리곤은 비행 가능 공간과 같지 않다.
금속 랙·책상·사람과 기체 외곽을 별도로 반영한다.
한 평면의 LiDAR 스캔만으로 3차원 충돌을 보증할 수 없다.

PX4 Collision Prevention 문서는 Position 모드를 설명한다.
`OBSTACLE_DISTANCE`를 보내는 것만으로
현재 Offboard 경로까지 자동 보호된다고 보지 않는다.
[PX4 Collision Prevention 문서](https://docs.px4.io/v1.16/en/computer_vision/collision_prevention)에 따른 적용 범위 구분이다.

제동거리의 첫 근사는 다음처럼 계산할 수 있다.

```text
필요 거리 ≈ v × 지연 + v² / (2 × 감속도) + 여유 거리
```

직선·일정 감속을 가정한 운동학 계산이다.
지연 0.20초, 감속도 0.50m/s²를 예로 든다.

| 현재 속력 | 지연 중 이동 | 감속 중 이동 | 여유 거리 전 합계 |
|---:|---:|---:|---:|
| 0.25m/s | 0.050m | 0.0625m | 0.1125m |
| 0.50m/s | 0.100m | 0.2500m | 0.3500m |

이는 정지 보장 수치가 아니다.
자세 응답·감속도 변화·거리 오차를 추가 측정해야 한다.
명령 속도의 변화도 매 주기 제한한다.
원시 Offboard 명령이 PX4 경로 생성기의
모든 가속도 제한을 거친다고 가정하지 않는다.
[목표 생성과 제어의 구분](https://docs.px4.io/v1.16/en/config_mc/mc_trajectory_tuning)과
[Offboard 목표를 받는 위치제어 모듈](https://github.com/PX4/PX4-Autopilot/blob/6ea3539157ca358c70a515878b77077af7d4611d/src/modules/mc_pos_control/MulticopterPositionControl.cpp)을 근거로 한다.

## 7. 단계별 검증 제안

단순 데모를 먼저 만들고 같은 제어기를 SITL로 옮긴다.

| 단계 | 시험 | 기록·통과 판단 |
|---|---|---|
| 1. 명령 계산 | 목표 앞·뒤·대각선, 목표 일치 | 방향·속력 제한·0 나눗셈 처리 |
| 2. 닫힌 제어 데모 | 명령으로 위치가 변하는 모형 | 감속 명령으로 실제 경로가 달라짐 |
| 3. PX4 SITL 연결 | 목표 높이 1.2m, 수평 왕복 | ENU/NED·축별 마스크·모드 수락 확인 |
| 4. 제어 비교 | PX4 위치제어와 companion P | 같은 모형·조건에서 정착·초과 이동 비교 |
| 5. 입력 오류 | UWB 공백·지연·편향·중복 | 추정 오차와 제어 오차를 각각 기록 |
| 6. 실행 오류 | 제어기 중단·통신 단절·목표 취소 | 명령 만료·PX4 전환·재개 조건 확인 |
| 7. 장애물 | 벽·좁은 통로·가림·회전 | 최소 간격·정지거리·관측 불가 처리 |
| 8. 실기 준비 | 센서·좌표·시각·장착 상태 확인 | 실측 상태 연결 뒤 별도 지상·비행 검증 |

권장 첫 물리 환경은 PX4 v1.16 SITL과 Gazebo다.
공식 문서는 Ubuntu 22.04에 Harmonic을 안내한다.
x500은 기본 시험 모델로 사용할 수 있다.
[PX4 Gazebo 안내](https://docs.px4.io/v1.16/en/sim_gazebo_gz/)가 근거다.
이 모델은 우리 프레임·모터의 동특성을 재현한 모델이 아니다.
Jetson에서의 설치·실시간 성능은 아직 시험하지 않았다.

시뮬레이션 ROS는 DOMAIN_ID 99로 격리한다.
MAVLink 주소·UDP 포트·대상 시스템도 따로 정한다.
ROS_DOMAIN_ID만 바꿔서는 MAVLink가 격리되지 않는다.
실제 Pixhawk를 대상으로 하는 연결 설정을 재사용하지 않는다.
이유는 데모 명령의 실제 장치 전달을 막기 위해서다.

기존 데모 노드는 벽시계를 사용한다.
현재는 `use_sim_time=true`를 거부한다.
SITL 연결부에서는 시뮬레이션 시계를 따로 처리한다.
일시정지·배속·시각 초기화 때 공백 판정도 시험한다.
기존 노드를 설정만 바꿔 바로 연결할 수 있다는 뜻은 아니다.

SITL의 기본 GPS 사용 여부를 결과에 기록한다.
GPS를 켠 제어 시험과 UWB+IMU 시험을 분리한다.
GPS가 공백을 메웠다면 UWB+IMU만의 성능이 아니다.
시뮬레이터 정답 위치는 오차 평가에 사용한다.
UWB 공백 시험에서 정답 위치를 제어기에 직접 주지 않는다.
이유는 시험하려던 위치추정 공백이 사라지기 때문이다.

다음 항목을 공통 지표로 제안한다.

| 분류 | 측정 지표 |
|---|---|
| 위치추정 | 정답 대비 x·y 평균 편향·RMSE·95백분위 오차 |
| 목표 추종 | 최대 초과 이동·최종 오차·정착 시간 |
| 정지 | 정지 명령 후 시간·이동 거리·최대 잔여 속력 |
| 명령 | 송신 간격·생성 후 나이·제한 전후 속력 |
| 공백 | 탐지 시간·대응 모드·최대 위치 오차 |
| 복구 | 재개 시간·좌표 점프·속도 명령 변화 |
| 장애물 | 최소 실제 간격·관측 불가 방향 진입 여부 |
| PX4 상태 | 유효성·초기화 사건·모드·기울기 변화 |

같은 경로를 여러 seed와 지연 조건으로 반복한다.
기존 0.15m 도착 반경은 데모 비교 조건으로 시작한다.
실기 합격 기준은 작업 공간 여유와 실측 오차로 정한다.

## 8. 다음 개발 한 사이클의 범위

우선 기존 데모에 수평 제어의 되먹임을 추가한다.

| 재사용 | 새로 필요한 부분 |
|---|---|
| 고정 높이 1.2m·목표 생성 | 수평 P 계산과 속력 제한 |
| 도착·공백·복구 상태 판단 | 상태에 따른 감속·목표 유지 |
| UWB 공백·잡음 시나리오 | 명령에 반응하는 수평 이동 모형 |
| JSONL 기록·비교 방식 | 제어 명령·제동거리·추종 오차 기록 |

그다음 SITL 연결부에 같은 수평 제어를 넣는다.
PX4 상태 입력과 MAVROS 출력 형식을 그때 연결한다.
실기 센서 입고가 수평 데모 개발을 막지는 않는다.
실제 고도·자세 제어와 EKF2의 책임도 바뀌지 않는다.

이 조사로 확정하지 못한 항목은 다음과 같다.

| 미확인 | 다음 확인 방법 |
|---|---|
| 혼합 목표의 실제 PX4 반응 | 해당 커밋의 SITL에서 축별 입력 기록 |
| 실시간 상태 유효성 전달 | ROS 출력과 PX4 내부 상태를 동시 비교 |
| EKF 위치·방향 초기화 처리 | 초기화 전후 목표 좌표와 이동 방향 시험 |
| 실제 기체의 감속 능력 | 조립·PX4 기본 튜닝 후 별도 실측 |
| 실제 Offboard 공백 대응 | 현재 파라미터 읽기와 SITL 재현 |
| 최종 고도·LiDAR 장착 | 장비 입고·고정 후 원점과 가림 실측 |

용어는 [용어 사전](../glossary.md)을 따른다.
이 문서는 설계 제안과 근거를 기록한 설명 문서다.
실행 명령과 파라미터 적용 절차는 다음 구현 때 작성한다.
