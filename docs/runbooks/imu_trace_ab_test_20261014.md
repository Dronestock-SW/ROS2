# IMU 수신 대기와 내부 기록 비교 절차

2026-10-14. 내부 기록이 수신 지연에 기여하는지 확인하는 시험안이다.
Jetson 격리 재생을 준비하거나 결과를 판정할 때 읽는다.
현재 상태: 원본 부재 확인 후 사용자 지시로 시험 생략·마무리.

## 1. 이번에 확인할 질문

동일한 B1 코드에서 내부 기록을 끄면 수신 대기가 줄어드는가?
기존 A1/B1 버전 비교와 구분한다. 이번 이름은 TRACE_ON/OFF다.
GPU 전환, 계산 알고리즘, ToF 주기는 함께 변경하지 않는다.

확인된 사실:
- 기존 B1 발행 시작→수신 처리 시작 지연은 최대 약 233ms였다.
- 수신 처리 자체는 중앙값 약 0.13ms였다.
- 최악 지연 구간에는 B3 재계산이 없었다.
- 내부 기록 작업자는 같은 Python 프로세스에서 JSON 변환한다.
- 기존 재생 도구는 trace_directory를 켜도록 고정한다.
- 기존 수신 시각은 내부 기록에 들어간다. OFF에서 사라진다.

남은 가설:
- 기록 작업의 Python 실행권 경쟁이 수신 대기를 늘린다.
- 디스크 쓰기, 입력 몰림, 실행기 대기가 함께 작용한다.
- CPU 전체 평균 사용률만으로 원인을 구분할 수 없다.

| 항목 | 고정할 조건 |

원본의 시각을 새 실행 시각에 맞추는 이동량은 실행별로 기록한다.
입력의 상대 간격과 센서 간 시각 관계는 유지한다.
실제 발행 지연은 고정할 수 없으므로 반드시 측정한다.
원본 전체와 manifest를 확인한다. 보존 feeder 파일로 대체하지 않는다.

## 3. 기록을 꺼도 같은 자로 측정한다

시험 전용 복사본에 동일한 최소 계측을 넣는다.
고정 크기 메모리에 숫자만 저장하고 종료 후 파일로 내보낸다.
측정 중 JSON 변환·파일 쓰기·센서별 추가 ROS 발행을 피한다.
행 수와 누락·용량 초과를 검사한다. 같은 계측 코드를 양쪽에 쓴다.
계측도 비용이 있으므로 무계측 환경과 같다고 주장하지 않는다.

| 시각 | 의미 |
|---|---|
| t0 | 재생기의 예정 발행 시각 |
| t1/t2 | 실제 publish 호출 직전/직후 |
| t3 | IMU 콜백 첫 줄, 검증 전 |
| t4/t5 | 센서 잠금 요청/획득 |
| t6 | IMU 버퍼 반영 완료 |
| t7 | 콜백 작업 종료 직전 |

같은 Jetson의 monotonic_ns로 비교한다.
헤더 시각과 이벤트 순번으로 대응시키며 중복을 확인한다.
- 재생기 지연: t1-t0.
- 전달 및 콜백 시작 대기: t3-t1. DDS 전달·역직렬화·실행 대기를 포함한다.
- 잠금 대기: t5-t4.
- 잠금 안 처리: t6-t5.
- 콜백 처리: t7-t3.

t3-t1을 순수한 실행기 대기나 GIL 대기로 단정하지 않는다.
계산 시작·종료와 thread CPU 시간도 같은 최소 계측으로 수집한다.
계산 wall 시간과 CPU 시간 차이만으로 특정 대기 원인을 확정하지 않는다.
기존 B1의 sensor 함수 진입 시각과 새 t3의 위치 차이를 명시한다.

TRACE_ON: 기존 BtfTrace 큐·JSON 변환·파일 기록을 켠다.
TRACE_OFF: trace_directory를 비워 해당 작업자를 끈다.
record_directory는 양쪽 모두 비운다.
상태/결정 메시지 및 진단 객체 구성은 양쪽에서 유지한다.
따라서 첫 시험은 진단 전체가 아닌 BtfTrace 기록 경로의 효과를 잰다.

## 4. 실행 순서

1. 원본 해시와 실행 환경을 확인한다.
2. 운영본과 분리한 복사본에 계측과 ON/OFF 선택을 구현한다.
3. 짧은 합성 입력으로 양쪽 계측·대응·누락을 검사한다.
4. 실제 기체 연결 없이 격리 ROS 도메인과 재생 topic을 확인한다.
5. 전체 입력을 ON → OFF → OFF → ON 순서로 재생한다.
6. 효과가 일관되지 않으면 반대 순서 반복의 필요성을 판단한다.

새 버전 비교나 실행 구조 변경은 첫 네 번에 섞지 않는다.
실제 MAVROS·비행 실행기·실기 배포를 시작하지 않는다.
진행 중인 주 대화의 빌드·시험·프로세스를 중단하거나 재사용하지 않는다.

## 5. 결과와 완료 조건

실행별 p50/p95/p99/최대, 20ms·100ms 초과 비율을 보고한다.
20ms·100ms는 분포 관찰용이며 새로운 비행 합격선이 아니다.
개별 샘플을 독립 반복시험처럼 취급하지 않는다.
전체 구간과 기존 64~66초 부근을 함께 확인한다.
입력 몰림, 발행 지연, 수신 누락, 유효 출력과 최장 출력 공백을 비교한다.
CPU 코어별 사용량·프로세스/스레드 CPU·온도·클럭·I/O도 대조한다.
기록 ON에서는 기록 큐·누락·오류를 확인한다.
분기와 동기화 초기화 횟수도 확인한다. 변화 자체가 영향일 수 있다.

완료 조건:
- 모든 실행의 입력·코드·설정·계측 동일성이 확인된다.
- OFF에서도 수신 시각과 계산 시간이 수집된다.
- 반복별 결과와 실행 순서 효과를 제시한다.
- 기록의 기여 확인 / 뚜렷한 효과 없음 / 교란으로 미분리 중 하나로 판정한다.
- 효과가 없다는 결과를 기록 비용이 0이라는 뜻으로 해석하지 않는다.

기록 OFF에서 반복적으로 개선되고 ON 복귀에서 악화되면 기록 경로 기여를 지지한다.
JSON 실행권 경쟁과 디스크 쓰기 중 무엇인지는 이 시험만으로 나누지 못한다.
필요할 때만 후속 시험 한 가지를 선택한다.
후속 후보는 JSON 변환 후 쓰기 생략, 또는 기록 프로세스 분리다.
수신·계산 분리 방식 변경은 그 다음에 독립 비교한다.

## 6. 계획 작성 시 기록

- 로컬 코드에서 trace_directory OFF 경로를 확인했다.
- 기존 시험기의 trace_directory ON 고정을 확인했다.
- 이 대화 환경에서 bluewak-host SSH 별칭 해석이 실패했다.
- Jetson 주소/접속 설정 확인을 요청했다.
- 원본 복구 여부, 동시 작업 여부, 새 계측은 아직 확인하지 못했다.
- 새 재생·실기 변경은 하지 않았다. 본 계획은 새 Claude 검토를 받지 않았다.

## 7. 2026-10-14 주 대화 확인·종료 기록

원본이 없어 비교 시험을 시작하지 않았다.
사용자가 “없으면 제끼고 마무리”를 지시했다.

| 구분 | 결과 |
|---|---|
| SSH | 주 대화에서 bluewak-host 접속 성공 |
| 원본 폴더 | 복구되어 있으나 전체 events.jsonl 없음 |
| 복구 자료 | manifest·summary·25초 선택 주제 발췌 두 개 |
| 전체 원본 조건 | 124,382,507바이트·앞서 고정한 SHA256 |
| 복구 기록 | RESTORATION_PARTIAL.json도 전체 원본 부재 명시 |
| 새 계측·합성 검사·재생 | 모두 미실시. ON/OFF 실행0회 |
| 판단 | 기록의 지연 기여는 미판정 |
| 운영본 | tof-100-50-50-20261014-r1으로 고정. 코드·실기 변경 없음 |

[원본 확인 증거](../report/evidence/imu_trace_original_check_20261014.txt)를 남겼다.
발췌 파일이나 기존 feeder를 전체 원본 대신 쓰지 않았다.
재개 요청이 있으면 전체 원본 위치·해시부터 확인한다.

Claude17차는 비교 순서와 계측 방향을 타당하다고 봤다.
[검토 원문](../report/evidence/claude_tof_baseline_trace_review_20261014.txt)을 보존한다.
후속 구현 시 아래 항목을 먼저 고정한다.

- 실제 파라미터 차이는 trace_directory 하나인지 확인한다.
- 계측은 스레드별 사전 할당 숫자 버퍼를 쓴다.
- 넘침을 기록하고 해당 회차를 불완전으로 표시한다.
- 64~66초는 원본 상대 시각으로 고정한다.
- 디스크 여유·배경 부하 판정 기준을 실행 전에 정한다.
- 실제 프로세스 환경과 ROS 그래프에서 격리를 확인한다.

로컬 btf_node.py의 record()는 trace.write만 조건부다.
호출부에서 만든 row와 수신 시각 계산은 OFF에도 남는다.
OFF에서 사라지는 것은 그 기록의 저장 결과다.
진단 전체 비용이 제거되는 시험으로 해석하지 않는다.
