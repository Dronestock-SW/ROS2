# 수동 비행 후 관측·기록 코드 수정

10월 9일 로그로 확인한 코드 수정 기록이다.
다음 수동 비행의 기록·분석 준비 상태를 볼 때 읽는다.

## 결론

**관측 이력 복구와 PC 기록 복사를 수정했다.**
좌표·시간 보정이나 자동 비행 완료를 뜻하지 않는다.
수동 호버 복구는 다음 실제 시험에서 확인한다.
절차는 [수동 비행 기록](../runbooks/manual_flight_capture.md)을 따른다.

| 변경 코드 | 해결 내용 |
|---|---|
| `processing/measured_btf.py` | 실제 태그 재시작 뒤 오래된 좌표 prior 제거 |
| 같은 파일 `MeasuredHeight` | 중복 시각이 ToF·IMU 이력을 지우지 않음 |
| `processing/timing/clock.py` | 표본 부족·속도 비율·잔차 초과를 구분 |
| `integration/ros/node.py` | Linux 원시 단조 시계를 수신 시각과 함께 기록 |
| `integration/manual_capture.py` | 부팅·PID 시작 시각·남은 기록 용량·현재 생존 상태 |
| `tools/mirror_manual_capture.py` | 유한 길이 복사·재부팅·PID 재사용·파일 축소 검사 |
| `integration/manual_analysis.py` | 실제 기록의 거부·시계·모드·공백 자동 분석 |
| `ops/px4_sensor_readback.py` | 수동 시험 전후 고정 읽기 15개 프로필 |

위 UWB 경로는 `src/drone_uwb/drone_uwb` 아래다.
mirror 도구는 `src/drone_uwb/tools` 아래다.
FC 읽기 도구는 `src/sangwon_AI/ops` 아래다.

일반 수신 지연 때 좌표 점프 prior는 유지한다.
이유: 반복된 잘못된 좌표가 새 원점이 되면 안 된다.
실제 source 재시작 때만 새 관측 이력을 만든다.
새 이력에도 기존 시각·관측 수집 조건을 적용한다.
뒤로 간 센서 시각은 기존처럼 이력을 무효화한다.
같은 시각의 중복만 기존 이력을 보존한다.

## 오늘 자료의 시간 매핑 재생

원본의 거부 1,111건을 시계 단계에서 재현했다.
`manual-flight-20261009T111438Z`를 읽었다.
사건 파일 330,762,327바이트를 변경하지 않았다.
SHA256은 [Position 조사](position_hold_regression_20261009.md)와 같다.

| 시계 단계 결과 | 건수 |
|---|---:|
| 초기 표본 부족 | 29 |
| 속도 비율 범위 초과 | 1,082 |
| 시계 단계 통과 | 15,166 |

최악의 alpha는 `0.99168399695`였다.
당시 잔차 p95는 약 12.14ms였다.
잔차 50ms 초과가 이 구간의 거부 원인은 아니었다.
허용 속도 비율 편차 `0.001`을 넘었다.
소스 시각·수신 지연·호스트 시계 중 원인은 미확정이다.
호스트 원시 단조 시계가 과거 기록에 없었다.
따라서 NTP 영향이라고 단정하지 않는다.
다음 수신에는 그 시계도 같이 남긴다.
기존 ROS stamp와 시각·공백 기준은 바꾸지 않았다.

이 재생은 RAW·TDMA·시계 단계에 한정한다.
B_TF 기하 계산·ROS callback 순서를 재현하지 않는다.
정지나 수동 조종 궤적을 독립 정답으로 만들지 않는다.
고정 지연·회전·원점 확인 플래그는 false다.

| FC 고정 읽기 | DISARM 상태 15개 정상 응답 |
| 이번 수정의 SITL·실제 비행 | 미실시 |

PC 복사 시험 해시는 다음과 같다.
`fd2281210156c524202dfc4abd52fddc2d958270df5f6f9632df72afbc4c0793`
수집 오류·큐 거부는 0이었다.
시험 내내 FC는 DISARM이었다.
원본 UWB는 Tag B heartbeat 6개뿐이었다.
거리 cycle·B_TF decision은 없었다.
이를 정상 좌표 수신 시험으로 계산하지 않았다.
현재 센서 상태의 누락을 수집기가 정확히 남겼다.
원본·FC 읽기 자료는 PC에 보관하고 Git에서 제외한다.

복사 오류 시험은 다음을 포함한다.
부분 전송·파일 축소·원본 교체·재개 경계 불일치다.
부팅 변경·PID 재사용·오래된 checkpoint도 검사했다.
오류 때 기존 PC 원본에 다른 세션을 이어붙이지 않는다.
각 SSH 읽기는 30초 제한으로 끝난다.
최종 전체 해시 일치 후에만 복사 완료가 된다.
복사 완료와 원본 수집 오류는 별도로 표시한다.

## 현장 상태와 다음 단계

이번 작업에서 FC 파라미터를 쓰지 않았다.
12:02 UTC 읽기에서 MAG_TYPE=0을 확인했다.
EV_CTRL=1, RC_IN_MODE=0, OVERRIDE=3도 유지됐다.
MIS_TAKEOFF_ALT=1.3m를 유지했다.
flow 회전 4·배율 1도 그대로였다.

같은 읽기에서 FC logger가 실제 기록 중이었다.
`SDLOG_MODE=1`, `SDLOG_PROFILE=1`이었다.
경로는 `/fs/microsd/log/2026-10-08/20_59_19.ulg`였다.
56.40MiB 기록·마지막 조회 이후 dropout 0이었다.
앞선 재부팅 직후 상태와 시점을 구분한다.
이 파일이 이전 수동 비행의 ULog라는 뜻은 아니다.
날짜 폴더만으로 서로 다른 부팅 자료를 연결하지 않는다.

실행 중 MAVROS·웹·관측 프로세스를 보존했다.
수정 파일을 배포해도 기존 Python 메모리는 바뀌지 않는다.
새 수신 시계 기록과 B_TF 수정은 관측 재실행 때 적용된다.
다음 부팅에서는 배포한 코드로 관측을 시작한다.
이번 짧은 수집기·PC 복사기는 정상 종료했다.
execute와 bridge는 false를 유지한다.

다음 순서는 수동 호버 복구 확인이다.
그 시행의 ULog·ROS 기록·알려진 이동을 함께 확보한다.
좌표·시간 후보를 다른 구간에도 대조한다.
이후 UWB 융합과 자동 이착륙을 별도로 시험한다.
MAG_TYPE=0과 1.3m의 현행 자동 미션 방위 조건도 남아 있다.
수동 호버 복구와 자동 미션 조건 통과를 구분한다.
