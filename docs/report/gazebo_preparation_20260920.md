## 2026-09-20 당시 결론과 작업 범위

같은 가상 운동에서 IMU와 거리값을 만든다.
사용자는 이 방향을 선택했다.
사인파는 연속 운동을 표현하려고 제안한 예시다.
필수 파형이나 최종 시험 조건으로 확정하지 않았다.

| 구분 | 이번 논의에서 정리한 내용 |
|---|---|
| 사용자 선택 | 가상 높이와 IMU가 같은 운동을 나타내게 한다 |
| 준비 후보 | Gazebo + PX4 SITL |
| 첫 시험 제안 | 호버링과 부드러운 상승·하강 |
| 추가 시험 제안 | 사인파 운동, 수평 이동, 회전 |
| 아직 필요한 정보 | 실행 PC의 운영체제·CPU·RAM·GPU |

| 아직 하지 않은 작업 | Gazebo 설치·실행, 센서 모델 구현, 성능 측정 |

기술 방향은 [로드맵](../roadmap.md)을 따른다.
고도 책임은 [고도 처리 원칙](../altitude_policy.md)을 따른다.
이 문서는 두 기준을 변경하는 결정문이 아니다.

## 센서 구성과 확인 수준

사용자 설명과 기존 장비 기록을 구분한다.
모델명은 [장비 문서](../equipment_inventory.md)를 따른다.
과거 보유 표시로 현재 연결 상태를 단정하지 않는다.

| 항목 | 대화에서 확인한 내용 | 남은 확인 |
|---|---|---|
| UWB | 외부에서 보정된 x,y를 받는다 | 보정 방법, 남은 오차, 주기, 지연 |
| ToF | 사인파 가상값으로 먼저 시험하려 했다 | 실제 TFmini Plus의 연결·측정 상태 |
| LiDAR | 사용자가 x,y 추정용으로 설명했다 | 실제 연결 경로와 좌표 생성 프로그램 |
| IMU | PX4 보드에 2개가 있다 | 센서 선택과 복수 EKF 실행 설정 |
| PC | 사양을 아직 전달하지 않았다 | 운영체제, CPU 모델, RAM, GPU 모델 |

장비 문서의 LiDAR는 YDLIDAR T-mini Pro다.
로드맵은 companion의 스캔매칭을 계획한다.
따라서 LiDAR의 PX4 직결은 아직 확정하지 않는다.
스캔 수신과 x,y 생성은 서로 다른 처리 단계다.

하방 거리계의 모델명은 TFmini Plus다.
T-mini Pro와 이름이 비슷하지만 역할이 다르다.

## 센서 융합의 기본 방향

비행용 상태추정은 PX4 EKF2가 담당한다.
companion은 관측치를 공급한다.
로드맵 결정 10에 따른 책임 구분이다.

| 입력 | 역할 | 먼저 살펴볼 문제 |
|---|---|---|
| IMU | 짧은 시간의 움직임을 예측 | 바이어스, 진동, 시각 |
| UWB x,y | 수평 위치의 누적 오차를 제한 | 좌표축, 원점, 남은 편향, 지연 |
| 하방 거리 | 바닥 위 높이를 제약 | 자세, 장착 위치, 바닥 형상 |
| LiDAR 스캔매칭 | 수평 상대이동 관측을 공급 | 좌표계, 품질, 입력 경로 |

EKF2는 위치·속도·자세·IMU 바이어스를 추정한다.
이미 융합 중이면 입력과 설정부터 점검한다.
[PX4 EKF2 문서](https://docs.px4.io/main/en/advanced_config/tuning_the_ecl_ekf)

| 설정·입력 | 논의한 용도 | 적용 전 확인 |
|---|---|---|
| MAVLink `ODOMETRY` 등 | 외부 위치 전달 | 지원 좌표계, 불확실도, 실제 갱신율 |
| `EKF2_EV_CTRL` | 외부 관측의 사용 항목 선택 | UWB x,y와 미관측 z·yaw 구분 |
| `EKF2_EV_DELAY` | 외부 관측의 시각 차이 반영 | 측정 시각과 전달 지연 |
| `EKF2_RNG_CTRL` | 거리 센서 융합 방식 선택 | 센서 방향과 높이 모델 |
| `EKF2_HGT_REF` | 높이 기준 선택 | 바닥 조건과 다른 높이 입력 |

이 표는 설정값을 적용한 기록이 아니다.
실제 PX4 버전을 확인한 뒤 값을 정한다.
UWB와 LiDAR의 동시 입력 경로도 설계 전이다.
두 위치 스트림을 한 채널에 번갈아 넣지 않는다.
이유는 원점과 시각의 일관성이 깨질 수 있어서다.
[외부 위치 입력 문서](https://docs.px4.io/main/en/ros/external_position_estimation)

### IMU가 2개인 경우

IMU 개수와 융합 방식은 따로 확인한다.
두 센서가 있다고 자동 평균되는 것은 아니다.
PX4는 센서 선택과 복수 EKF 구성을 지원한다.
복수 EKF는 서로 다른 센서 조합을 비교한다.
센서 선택은 `SENS_IMU_MODE`로 확인한다.
복수 실행은 `EKF2_MULTI_IMU`로 확인한다.
[단일·복수 EKF 설명](https://docs.px4.io/main/en/advanced_config/tuning_the_ecl_ekf#running-multiple-ekf-instances)

첫 가상 시험은 IMU 1개로 시작하는 제안이다.
입력이 맞는지 확인한 뒤 2개로 확장한다.
실물 보드의 IMU 2개가 자동 복제된다고 가정하지 않는다.

## ToF 거리와 높이의 관계

ToF는 센서가 바라보는 방향의 거리를 잰다.
그 값을 고정 좌표계의 z와 구분해야 한다.

아래 식은 수평 바닥을 가정한다.
센서는 기체의 아래 방향에 정렬되어 있다.

```text
h = d * cos(roll) * cos(pitch)
```

`d`는 측정 거리다. `h`는 센서의 바닥 위 높이다.
한 축으로 30° 기울어져 2 m를 측정했다고 하자.
이때 수직 높이는 약 1.73 m다.
거리를 그대로 높이로 쓰면 약 27 cm 차이가 난다.
이 수치는 기하 계산 예시이며 실측 결과가 아니다.

장착 각도와 위치 오프셋도 반영해야 한다.
현재 자세 보정이 어디서 일어나는지 확인한다.
PX4가 보정한다면 중복 보정을 피한다.
[거리 센서 설정](https://docs.px4.io/main/en/sensor/rangefinders)

책상이나 계단 위에서는 바닥까지 거리가 달라진다.
자세 보정만으로 고정 좌표계의 z를 얻을 수는 없다.
높이 기준과 지면의 높이를 함께 구분해야 한다.
[거리 기반 높이 융합](https://docs.px4.io/main/en/advanced_config/tuning_the_ecl_ekf#range-height-fusion)

## 사인파를 쓰는 방법

사인파는 목표 운동의 한 종류로 사용한다.
센서값은 같은 가상 기체의 실제 운동에서 생성한다.
IMU와 ToF에 같은 숫자 배열을 넣는다는 뜻은 아니다.

```text
시험용 목표 궤적
        |
        v
PX4 제어 <---------------- EKF2 추정값
        |                       ^
        v                       |
Gazebo 기체 운동 --------> 가상 IMU·하방 거리
        |
        +---------------> 가상 UWB x,y 생성
        |                       |
        |                       +----> 외부 위치 관측 -> EKF2
        |
        +---------------> 기준값 저장 -> 추정 오차 평가
```

기체 운동에서 위치·속도·가속도가 함께 정해진다.
IMU 가속도 모델에는 자세와 중력도 반영한다.
시각은 시뮬레이션 시간을 기준으로 맞춘다.

실물 정지 IMU에 임의 높이를 섞는 안은 택하지 않았다.
고정 바닥에서 두 입력이 같은 운동을 설명하지 않기 때문이다.
이번 선택은 같은 가상 운동에서 입력을 생성하는 안이다.

목표 높이 변화는 PC의 가상 시험 범위다.
실기 companion의 z 제어 코드를 추가하는 결정이 아니다.
이유는 실기 고도·자세 책임이 PX4에 있기 때문이다.

### 시험 궤적 후보

정지·출발·감속을 나누면 오차 원인을 읽기 쉽다.

| 순서 | 궤적 | 확인할 내용 |
|---|---|---|
| 1 | 일정 높이 호버링 | 흔들림과 평균 편향 |
| 2 | 부드러운 상승·정지·하강 | 출발·감속·정지 시 지연 |
| 3 | 사인파 반복 운동 | 진폭 차이와 시간 지연 |
| 4 | 수평 이동과 회전 | UWB·LiDAR·IMU 결합 |

S자 궤적은 속도와 가속도를 부드럽게 바꾼다.
PX4는 저크를 제한하는 궤적 생성 기능을 제공한다.
외부 목표 입력도 실행 가능한 운동이어야 한다.
[궤적 생성](https://docs.px4.io/main/en/config_mc/mc_trajectory_tuning),
[목표 궤적 메시지](https://docs.px4.io/main/en/msg_docs/TrajectorySetpoint)

대화에서 제시한 사인파 예시는 다음과 같다.
장비 사양에서 도출한 값이나 채택값은 아니다.

| 항목 | 예시 |
|---|---|
| 중심 높이 | 2 m |
| 진폭 | ±0.3 m |
| 주기 | 10초 |
| 시작·종료 | 정지 구간과 부드럽게 연결 |

### 목표값·기준값·추정값

위치 추정 오차는 기준값과 추정값으로 계산한다.

| 값 | 의미 | 비교 목적 |
|---|---|---|
| 목표값 | 명령한 궤적 | 기체가 명령을 따라가는지 확인 |
| 기준값 | Gazebo에서 실제 계산한 기체 상태 | 시뮬레이션 내부의 정답 |
| 추정값 | EKF2가 센서로 계산한 상태 | 위치 추정 성능 평가 |

목표값과 추정값만 비교하면 제어 오차도 섞인다.
실물에서의 정확도는 별도 기준값으로 검증해야 한다.

## 가상 UWB와 LiDAR의 범위

외부에서 보정된 UWB 출력의 특성을 재현한다.
가상 기체의 x,y에 남은 오차와 지연을 반영한다.
실제 잔여 오차의 크기는 아직 확인하지 않았다.

잡음이 작은 조건으로 먼저 연결을 확인한다.
그다음 오류를 하나씩 추가하는 안을 제안했다.

| 변화시키는 조건 | 확인 목적 |
|---|---|
| 무작위 잡음 | 관측의 흔들림을 줄이는지 확인 |
| 일정한 바이어스 | 편향을 단순 잡음으로 처리하는지 확인 |
| 전달 지연 | 시각 보정과 응답 지연 확인 |
| 결손·복구 | 관측 공백과 재수신 시 추정 확인 |

UWB 보정에 같은 IMU가 쓰였는지도 확인한다.
같은 정보가 되돌아오면 오차가 서로 연관될 수 있다.
이 문제는 [추정기 캐스케이드](../glossary.md)와 연결된다.

LiDAR 스캔과 x,y 관측 생성은 별도 단계다.
기본 2D LiDAR 모델이 위치를 자동 계산하지는 않는다.
스캔매칭 프로그램과 입력 경로가 추가로 필요하다.
기본 `x500_lidar_2d`의 PX4 출력은 장애물 거리다.
[Gazebo 기체 모델](https://docs.px4.io/main/en/sim_gazebo_gz/vehicles)

## Gazebo와 PX4 SITL을 검토하는 이유

실물 보드 없이 PX4의 추정·제어를 시험할 수 있다.

| 프로그램 | 역할 |
|---|---|
| Gazebo | 가상 환경, 기체 운동, 센서값 생성 |
| PX4 SITL | PC에서 PX4 EKF2와 제어 모듈 실행 |
| QGroundControl | 상태 확인과 설정을 위한 선택 도구 |

Gazebo는 IMU와 거리 센서 모델을 제공한다.
센서별 잡음도 설정할 수 있다.
[Gazebo 센서 모델](https://gazebosim.org/libs/sensors/)

`x500_lidar_down`을 첫 모델 후보로 제안했다.
아래 명령은 설치 후 사용할 공식 실행 예시다.
이번 작업에서는 실행하지 않았다.

```bash
# PX4-Autopilot 저장소에서 실행하는 예시
make px4_sitl gz_x500_lidar_down
```

이 모델은 하향 1D LiDAR를 포함한다.
TFmini Plus의 제품 오차를 그대로 재현하지는 않는다.
[PX4 Gazebo 실행](https://docs.px4.io/main/en/sim_gazebo_gz/),
[거리 센서 가상 시험](https://docs.px4.io/main/en/sensor/rangefinders#simulation)

실물 보드를 쓰는 HITL은 이번 선택이 아니다.
SITL에서 조건을 먼저 정리하는 단계다.
[SITL·HITL 구분](https://docs.px4.io/main/en/simulation/hitl)

## 실행 PC 사양과 지원 환경

사양은 센서와 장면의 계산량에 따라 달라진다.
아래 표는 대화에서 제안한 작업용 추정치다.
공식 최소 사양이나 성능 측정 결과가 아니다.
가상 드론 1대를 기준으로 했다.

| 항목 | IMU·하방 거리·가상 UWB | LiDAR 스캔·위치 추정 확장 |
|---|---|---|
| CPU | 최근 4~6코어급 | 최근 6~8코어 이상 |
| RAM | 16 GB 권장 | 32 GB 권장 |
| GPU | 단순 장면은 내장 GPU로 시험 가능 | 외장 GPU 권장 |
| GPU 메모리 | 모델과 드라이버에 따라 확인 | VRAM 6~8 GB를 출발점으로 고려 |
| SSD 여유 공간 | 약 50 GB | 약 100 GB 이상 |

실시간 실행 여부는 실제 모델로 확인해야 한다.
LiDAR 측정점 수와 갱신율도 영향을 준다.
실물 IMU가 2개라는 이유만으로 고사양이 필요한 것은 아니다.

새 PC 환경은 Ubuntu 24.04를 우선 제안했다.
Gazebo Harmonic을 조합 후보로 삼았다.
기존 companion의 Ubuntu 22.04 변경을 뜻하지 않는다.
PC의 설치 버전은 실제 환경을 확인한 뒤 고른다.
[Ubuntu 지원 환경](https://docs.px4.io/main/en/dev_setup/dev_env_linux_ubuntu),
[Gazebo 설치 조합](https://docs.px4.io/main/en/sim_gazebo_gz/)

Windows에서는 WSL2 경로도 지원한다.
그래픽 가속과 드라이버는 별도로 확인한다.
[PX4 개발 환경](https://docs.px4.io/main/en/dev_setup/dev_env)

Harmonic의 기본 렌더러는 OpenGL 지원이 필요하다.
공식 문서는 3.3보다 높은 버전을 요구한다.
권장 버전은 4.3 이상이다.
[Gazebo 그래픽 조건](https://gazebosim.org/docs/harmonic/troubleshooting/)

GUI를 끄는 headless 실행으로 부담을 줄일 수 있다.

## 논문 탐색 방향

키워드는 현재 입력과 관찰한 오류에 맞춰 좁힌다.
아래는 검색 지도이며 채택 알고리즘 목록이 아니다.

| 분야 | 검색 키워드 | 확인할 내용 |
|---|---|---|
| 관성항법·상태 추정 | `UWB IMU fusion ESKF`, `UWB aided inertial navigation` | 예측·보정과 바이어스 추정 |
| 결합 구조 | `loosely coupled tightly coupled UWB INS` | 좌표와 원시 관측값의 차이 |
| ToF 높이 모델 | `downward rangefinder tilt compensation`, `range aided altitude estimation` | 자세·바닥 조건 |
| 높이 기반 UWB 보정 | `height constrained UWB localization`, `altitude aided UWB positioning` | 높이 가정과 수평 오차 |
| 가림·이상치 처리 | `UWB NLOS mitigation`, `innovation gating`, `adaptive measurement covariance` | 편향과 관측 거부 |
| 시공간 보정 | `UWB IMU temporal calibration`, `lever arm calibration` | 시각과 장착 위치 |
| 관측 가능성 | `UWB inertial yaw observability` | 방향을 추정할 수 있는 운동 조건 |
| 최적화 기반 융합 | `UWB IMU factor graph optimization`, `IMU preintegration` | 여러 시각의 관측 활용 |

### 결합 방식과 알고리즘의 구분

입력 종류와 추정 알고리즘은 다른 선택 축이다.

| 용어 | 의미 | 이번 범위 |
|---|---|---|
| 약결합 | 계산된 UWB x,y를 관측으로 사용 | 현재 입력에서 먼저 검토 |
| 강결합 | 앵커별 거리·TDoA 관측을 직접 사용 | 원시 관측 접근 가능 여부부터 확인 |
| ESKF | 오차상태를 이용하는 EKF 형태 | 원리 학습·연구 비교 |
| FGO | 여러 상태와 관측을 함께 최적화 | 후속 연구 비교 |

별도 ESKF나 FGO를 실기에 도입하는 결정은 아니다.
현재 비행 상태추정기는 로드맵의 EKF2를 유지한다.

UWB 거리는 앵커와 태그 사이의 3차원 거리다.
고정 높이를 가정하면 높이 변화가 x,y에 영향을 줄 수 있다.
이때 ToF 높이를 위치 계산에 넣는 안을 검토할 수 있다.
기하학적 제안이며 실측 개선 결과는 아니다.
외부 UWB 계산 방식과 수정 가능 여부를 먼저 확인한다.

| 참고 연구 | 이번 기록에서 참고한 범위 |
|---|---|
| [UWB–IMU 시공간 보정](https://arxiv.org/abs/2108.00133) | 결합 구조, 장착 위치, 시각 차이 |
| [UWB/INS 팩터 그래프](https://ira.lib.polyu.edu.hk/handle/10397/92759) | 최적화 기반 결합의 연구 사례 |
| [UWB 이상치 제거](https://pmc.ncbi.nlm.nih.gov/articles/PMC12737027/) | NLOS와 관측 거부의 연구 사례 |

마지막 연구에는 VIO도 포함되어 있다.
그 성능을 현재 센서 구성의 결과로 옮기지 않는다.
논문별 구현·실험 조건의 상세 비교는 다음 단계다.

## 2026-09-20에 남긴 후속 확인 목록

PC 사양과 설치 조합은 후속 시험에서 확인했다.
UWB 연동은 HW팀 정비로 보류했다.
아래 표는 설치 전 작성한 확인 순서를 보존한다.

| 순서 | 필요한 답 | 결정할 내용 |
|---|---|---|
| 1 | 운영체제·CPU·RAM·GPU 모델 | 설치 조합과 시작 가능한 모델 |
| 2 | LiDAR 연결 경로와 좌표 생성 프로그램 | 거리 스캔과 위치 관측의 연결 |
| 3 | UWB 보정 방식·시각·갱신율 | 가상 UWB의 잔여 오차 모델 |
| 4 | PX4 버전과 활성 EKF 설정 | 외부 위치·높이·IMU 사용 방식 |
| 5 | 실제 운동 범위와 비교 기준 | 궤적, 오차 지표, 반복 조건 |

평가는 위치 오차·지연·결손 복구를 나누어 기록한다.
매끈한 궤적만으로 정확도가 좋아졌다고 판정하지 않는다.
