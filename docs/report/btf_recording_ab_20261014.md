# C++ B_TF 기록 ON/OFF 비교
14일 Jetson 지연 비교와 수정 결과다.
기록 비용과 남은 관측 공백을 구분할 때 읽는다.

**기록 비용을 줄였다. 관측 공백 전체는 해결되지 않았다.**
기록 ON의 콜백 p95는 18.6~18.8ms였다.
최종 수정 뒤 두 실행 모두 약 16.3ms였다.
현재 실기 서비스에는 이 수정을 적용하지 않았다.
bluewak의 펌웨어·운영 배포와 분리했다.

## 비교 조건

같은 C++ 라이브러리와 같은 부분 입력을 썼다.
기준 코드는 통합 브랜치의 `85c743d`다.
이번 비교는 이 C++ 기준을 명시해 사용한다.
후속 병합의 B1 수신 구조 비교와 구분한다.
다른 작업의 전체 원본 시험은 부재로 보류됐다.
이번 부분 자료 시험이 그 전체 시험을 대체하지 않는다.

| 항목 | 고정 조건 |
|---|---|
| 순서 | ON → OFF → OFF → ON |
| 계산기 | C++ B_TF, 새 B4 이력 복구 ON |
| 입력 | 13일 비행에서 복구한 24.362초 부분 자료 |
| 입력 건수 | UWB 봉투 2,014·IMU 2,445·ToF 223 |
| 배속 | 수집기 수신 간격을 보존한 1배속 |
| 시각 | ROS 시각에 상수만 더함. 입력 나이 보존 |
| 격리 | DOMAIN_ID=99·localhost·재생 전용 토픽 |
| 계측 | 양쪽 동일 래퍼. 메모리에 측정 후 종료 시 저장 |
| 유지 | 센서 주기·후보 기준·150ms 입력 제한·100ms ToF 제한 |
| 미실시 | FC 송신·융합·비행·물리적 밀림 검증 |

입력 파일은 `events.recovered-uwb-imu-excerpt.jsonl`이다.
전체 원본의 복원 완료로 표시하지 않는다.
SHA256은 다음과 같다.
`6cb34fc5ccee92084d81d20bfaac106650e4004a3bafbbc106b572ea7a34e289`

C++ 라이브러리 SHA256은 다음과 같다.
`e33e76d62e85ca707c7632a993825f9b359661e15924a18a7f17091edc3b266f`
모든 비교에서 동일하다. C++ 재빌드는 하지 않았다.
설정·라이브러리·Python 소스 해시도 영수증에 있다.

## 결과

기록을 꺼도 모든 지연이 사라지지는 않았다.
단위는 ms다. 콜백은 발행·기록 요청까지 포함한다.
대기는 수집기 예정 시각부터 콜백 진입까지다.
대기에는 재생 발행자의 지연도 포함된다.

| 실행 | 기준 콜백 p95 | 최종 콜백 p95 | 기준 대기 p95 | 최종 대기 p95 |
|---|---:|---:|---:|---:|
| ON 1 | 18.809 | 16.333 | 58.362 | 35.219 |
| OFF 1 | 17.126 | 14.391 | 22.132 | 19.188 |
| OFF 2 | 17.262 | 15.137 | 21.863 | 21.664 |
| ON 2 | 18.606 | 16.336 | 64.968 | 41.752 |

표의 대기 수치는 아래 JSON 원본을 우선한다.
기록 ON 콜백 p95는 평균 약 12.7% 줄었다.
각 조건은 두 번이므로 장기 성능 보장은 아니다.
IMU·ToF는 최종 네 실행 모두 전량 수신했다.
ON의 내부 기록 오류·누락은 모두 0이었다.
최종 발행 pose 수는 순서대로 753·751·771·751개다.
관측 유효 판정은 실제 실행 시각의 영향을 받는다.
동일 입력이라도 실시간 ROS 재생 결과 수는 달라진다.
최종 발행 도구의 최대 지연은 5.75~9.15ms였다.
이 지연을 센서나 B_TF만의 비용으로 계산하지 않는다.

JSON 중복 제거만 한 중간 결과도 보존했다.
콜백 p95 개선은 작고 일관되지 않았다.
그 결과만으로 지연 해결을 주장하지 않았다.
후속 시각 통계 수정 뒤 위의 차이를 확인했다.

## 확인한 비용과 수정

기록과 계산의 불필요한 작업을 줄였다.

| 확인한 경로 | 수정 |
|---|---|
| 같은 판단을 발행·기록용으로 두 번 JSON 변환 | 검증된 발행 문자열을 기록에서도 재사용 |
| 시각 보정의 작은 배열 통계 호출 | 동일한 중앙값·선형 p95를 직접 계산 |
| 시각 보정 잔차 행렬 계산 중복 | 한 번 계산한 잔차를 재사용 |
| OFF에서 내부 진단 자료 소실 | 별도 메모리 계측기로 대기·잠금·계산 시간 보존 |
| 만료 통계에 원본 지연과 새 지연 혼합 | 원본 수집 나이와 재생 추가 지연 분리 |

기록 파일의 행 구조와 내용은 유지한다.
NaN·무한대 처리는 기존 JSON 경계를 사용한다.
기록 큐·디스크 부족 보호도 유지한다.
기록을 기본 OFF로 바꾸지 않았다.

별도 프로파일에서 `ClockMap.update` 누적은 3.524초였다.
C++ 어댑터의 `process` 누적은 1.502초였다.
프로파일 실행에는 계측 비용이 추가된다.
ROS 대기 함수 시간에는 실제 대기도 포함된다.
이 시간을 그대로 CPU 점유율로 해석하지 않는다.
성능 비교는 프로파일을 끈 위 네 실행을 사용했다.

## 남은 공백과 인과 한계

이번 시험은 수신 지연의 전체 원인 확정이 아니다.

원본 부분 자료의 UWB 봉투 77건은
수집기 수신 시각에서 이미 150ms를 넘었다.
수집기 지연을 실제 B_TF 수신 지연으로 단정하지 않는다.
원본 수집 순서는 당시 B_TF 콜백 순서가 아니다.
그 지연이 재생에 포함돼 만료도 재현된다.
현재 프로그램이 새로 만든 77건으로 집계하면 안 된다.

최종 재생의 추가 입력 만료는 1·3·1·8건이다.
출력 만료도 2·4·7·4건 남았다.
전체 승인 관측의 최대 시각 간격은
약 875·926·350·926ms다.
FREEZE로 새로운 UWB 관측을 만든 것으로 보지 않는다.
초기 상태·시계 준비·수집 지연·후보 거부가 섞여 있다.
13일 실제 비행 공백의 개선율로 환산하지 않는다.

기준 ON 두 실행은 호스트 I/O wait가 약 18%였다.
하지만 최종 OFF 한 실행에서도 약 13%였다.
다른 실행에서는 약 0.6~2.2%였다.
스왑 출력은 전 실행 0페이지였다.
소량의 스왑 입력은 관측됐다.
저장장치 경합은 후보지만 기록만의 영향으로 확정하지 않는다.
잠금 대기 p95는 수 µs여서 주된 비용으로 보이지 않았다.
다른 사용자 작업과 운영 서비스를 중지하지 않았다.
