# C++ 이륙·POSITION·별도 START 연결
이 문서는 13일 저녁 시험용 구현 기록이다.
실행 흐름과 검증 범위를 확인할 때 읽는다.

후속 [POSITION 5초·시작점 분리](position_origin_after_hold_20261013.md)가 최신 정책이다.
아래 3초 대기·원래 목표 재진입은 변경 전 이력이다.

후속 [웹·기록 지연 수정](web_record_latency_20261013.md)을 적용했다.
아래 간헐 지연·배포 해시는 수정 전 이력이다.
현재 배포 해시와 최신 CI는 후속 문서를 따른다.

## 구현

별도 이륙과 웹 미션 START를 C++에 연결했다.
Jetson 실행본과 저녁 설정에도 반영했다.
실제 밀림 해결과 실비행 성공은 아직 미확인이다.

```text
웹 이륙 → OFFBOARD 준비 → ARM 1회
 → 출발 XY 고정·높이 1.7m
 → XY·높이·속도·UWB 안정 3초
 → POSITION 요청·실제 POSCTL 확인
 → 목표 송신 중지·안정 3초·웹 START 대기
 → 별도 START·원래 목표 송신 1.2초
 → OFFBOARD 확인·ARM 재요청 없음
 → 선택 미션·복귀·LAND·지상/DISARM 확인
```

설정은 `takeoff_hold`와 `local_position`이다.
`ground_takeoff`의 기존 합친 START도 보존했다.
별도 native AUTO 이륙은 이번 C++ 경로에 포함하지 않는다.
실행기는 한 개이며 FC 송신은 C++만 담당한다.
Python은 센서·웹 계약과 명령 원장을 담당한다.
기록을 저장한 명시적 요청만 C++에 전달한다.
중복 HTTP 요청·지난 요청은 새 실행을 만들지 않는다.
수동 인계 이후 같은 실행을 자동 재개하지 않는다.
전체 300초 제한과 배터리·추정 무효 보호를 유지한다.
새 미션의 배터리 잔량 기준은 상승 안정화와 분리했다.
이륙 후 잔량 감소만으로 POSITION 전환을 막지 않는다.
POSITION은 FC가 전환 시 잡은 정지점을 유지한다.
companion의 출발점은 이륙 전 XY를 계속 보존한다.
미션 START 뒤에는 그 원래 목표로 다시 연결한다.

## 관측 공백의 처리

보고 지연과 실제 관측 공백을 구분한다.

| 상태 | 보고만 지연 | 실제 UWB·FC 위치 공백 |
|---|---|---|
| OFFBOARD 상승 | 계속 수행·경고 기록 | 고정 목표·안정 판정 보류 |
| POSITION 대기 | 지연만으로 LAND하지 않음 | FC 위치 유지·START 차단 |
| 재진입 준비 | 지연만으로 LAND하지 않음 | 원래 목표 유지·모드 요청 보류 |
| 미션 이동·호버 | 계속 수행·경고 기록 | 목표 유지·완료 판정 보류 |

모드 요청 ACK와 실제 모드 확인을 분리한다.
POSITION 확인 전까지 OFFBOARD 목표를 계속 보낸다.
조종기 움직임과 다른 모드 선택은 수동 인계다.
기존 RC 보정을 C++에서도 직접 적용해 검사한다.
Python 일시 정지가 스틱 변화를 가리지 않게 했다.
관측을 생성하거나 오래된 stamp를 갱신하지 않는다.

## 왼쪽 밀림을 해석하는 기준

OFFBOARD에서도 PX4가 위치 보정을 수행한다.
송신 `type_mask=2552`는 XYZ와 yaw를 활성화한다.
속도·가속도·yaw rate 입력은 무시한다.
companion에 자세·추력 PID를 추가하지 않았다.
[PX4 OFFBOARD 설명](https://docs.px4.io/main/en/flight_modes_mc/offboard)을 따른다.

기존 [실행 8 분석](run8_offboard_attitude_20261012.md)도 참고한다.
당시 위치·자세 제어 flag가 켜져 있었다.
수평 추력 요구 104개 중 102개는 목표 쪽이었다.
보정이 꺼졌다는 해석은 그 기록과 맞지 않는다.
이 기록은 오늘 기체 상태의 실측 결과가 아니다.

`position_tracking`에 기수 기준 진단값을 추가했다.
이는 FC 추정값의 좌표 변환이며 독립 실측이 아니다.

| 필드 | 뜻 |
|---|---|
| launch_displacement_body_flu_m | 출발점에서 앞·왼쪽 변위 |
| target_error_body_flu_m | 현재 위치에서 목표까지 앞·왼쪽 오차 |
| velocity_body_flu_m_s | FC가 추정한 앞·왼쪽 속도 |
| pose_fresh | 해당 위치 피드백의 신선도 |

왼쪽 변위가 양수면 목표 오차는 오른쪽이어야 한다.
원래 목표를 밀린 위치로 옮기지 않는지 함께 본다.
실제 영상과 추정 변위가 다르면 센서·추정을 조사한다.
목표·추정 오차가 정상인데 실제 기체가 못 따라가면
ULog의 자세 요구·실제 자세·출력을 비교한다.
방향·장착·광류·UWB 시각 보정은 실측 근거로 정한다.
POSITION 전환 자체가 물리적 밀림을 고치지는 않는다.

## 검증

Windows 선택 Python 84개가 통과했다.
Jetson C++ 빌드와 계약 시험 2묶음이 통과했다.
기존 C++ AI·Python 연결 시험 9개도 통과했다.
LiDAR용 3개는 이 연결 시험에서 제외했다.
Jetson 분리 흐름 10개는 각각 통과했다.
최종 통과 증거는 3개 묶음에서 확보했다.
전체 10개 연속 반복이 무실패였다는 뜻은 아니다.
실제 ARM·이륙·현장 동적 보정은 수행하지 않았다.

[CI c782817](https://github.com/Dronestock-SW/ROS2/actions/runs/38353006539)은 성공했다.
ROS 패키지 4개와 C++ 실행 파일을 빌드했다.
Python 267개와 C++ AI·Python 9개가 통과했다.
CTest 계약 3묶음이 통과했다.
HTTP·ROS·C++·합성 FC 31개가 통과했다.
여기에는 새 분리 흐름 10개가 포함된다.
수신 간격은 최대 90.44ms였다.
C++ 자체 송신 간격은 최대 51.45ms였다.
합성 FC는 PX4 비행 역학을 모사하지 않는다.

Jetson 수신 간격은 최대 64.20ms였다.
C++ 자체 송신 간격은 최대 60.47ms였다.
실행별 결과와 해시는 [검증 증거](evidence/cpp_position_handoff_20261013/verification.json)에 있다.

| Jetson 시나리오 | 확인 결과 |
|---|---|
| 정상 이륙·POSITION·START·호버 | END·착륙·DISARM |
| 상승 중 UWB 공백 | 목표 유지·복구 후 END |
| 상승 중 FC 위치 공백 | 목표 유지·복구 후 END |
| POSITION 중 UWB 공백 | START 보류·복구 후 END |

| 상태 보고 지연 | 지연만으로 LAND하지 않음·END |

실제 FC의 출력 차단 지상 검증도 통과했다.
FC는 연결·DISARM·AUTO.LOITER 상태였다.
웹에 C++ 실행기 신원과 분리 흐름이 표시됐다.
이륙·START는 차단됐고 FC 명령은 0건이었다.
로컬 위치 목표 수신도 0건이었다.
기존 미션 DB·원장은 이 검증에 사용하지 않았다.

후속 시험 도구 커밋은 `82a5f72`다.
운영 코드 변경은 없으며 CI 재실행은 별도 확인한다.

초기 실패 기록도 보존한다.
첫 CI의 기존 Python 시험 fixture에 출발점이 빠져 있었다.
실제 실행기의 출발점 필드를 쓰도록 fixture를 수정했다.
첫 Jetson 좌표 이동은 END까지 도달했다.
그러나 합성 FC 수신 간격 354ms로 검사에 실패했다.
같은 실행의 C++ 송신 간격은 최대 55ms였다.
합성 FC 발행 간격은 최대 232ms였다.
수신 과정의 정체 원인은 확정하지 않았다.
200ms 송신·수신 검사 한계는 유지했다.

재시험의 좌표 이동은 수신 간격 최대 58ms로 통과했다.
다음 시험은 웹 응답 2초 제한으로 중단됐다.
실제 웹의 동일 요청 ID 확인 절차를 시험에도 적용했다.
다음 반복에서는 2초씩 3회 응답 대기도 실패했다.
웹 이륙 접수 전이며 C++는 IDLE을 유지했다.
그 실행의 FC 명령 목록은 비어 있었다.
Jetson의 간헐적인 웹 응답 지연은 미해결로 남긴다.
CI 성공으로 해당 현장 지연을 없어진 것으로 보지 않는다.

또 다른 실행은 착륙 완료 기록의 저장을 기다렸다.
웹의 `record_pending=true`가 3초 검사를 넘었다.
실제 웹은 저장 완료까지 기다리도록 구현돼 있다.
시험의 HTTP 대기는 회당 10초, 최대 3회로 맞췄다.
재시도는 같은 요청 ID만 사용한다.
착륙 후 완료 기록 확인은 최대 15초로 검사한다.
두 변경은 시험 도구의 저장 응답 대기 범위다.
실제 비행 관측 제한이나 제어 주기는 바꾸지 않았다.
200ms 송신·수신 검사는 그대로 통과해야 한다.
최종 시험은 HTTP 시간과 완료 확인 대기를 기록한다.

첫 좌표 이동의 연속 기록도 따로 조사했다.
상승·이동 구간 표본 간격은 최대 153ms였다.
END 결과 동기 저장에서는 기록 간격이 2.25초였다.
일반 표본은 최신 값 방식의 비동기 기록이다.
고정 10Hz 무손실 기록으로 표현하지 않는다.
명령 원장과 완료 결과의 동기 저장은 별도로 유지한다.

## 배포

Jetson의 준비된 slot을 갱신했다.
경로는 저녁 절차의 `FLIGHT_SLOT`과 같다.
실행 패키지 5개의 추적 항목 725개를 대조했다.
699개는 바이트 일치, 6개는 줄바꿈만 달랐다.
20개 심볼릭 링크의 대상도 일치했다.
기존 센서 bringup 체크아웃은 덮어쓰지 않았다.

| 실행 파일 | SHA256 |
|---|---|
| C++ 실행기 | `8a69a01386ec7a0919a7c8cb3c13b9d7b614d240c6c6cd07a0d08914cdbcbb08` |
| 별도 C++ AI | `5dc0924df2fffa7f08ab1b4c6443706f7b86a3238ebc159ca01cab291026631d` |

비공개 미션 템플릿의 시작 방식 두 항목만 변경했다.
장착값·높이·속도·LiDAR 비활성 설정은 유지했다.
이 작업에서 FC 파라미터는 변경하지 않았다.
14:34 KST 조회에서 EV·광류 융합은 꺼져 있었다.
가짜 위치 상태만으로 현장 준비 완료를 선언하지 않는다.
저녁에 앵커·조종기를 켜고 실제 융합을 다시 확인한다.
