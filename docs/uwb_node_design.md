# uwb_node 설계 — UWB 태그를 ROS2 좌표로 옮기는 노드

이 문서는 **uwb_node를 왜 이렇게 만드는가**를 설명한다. 코드를 쓰기 전과 리뷰할 때 읽는다.
따라 하는 절차서가 아니다. 장치 배선·포트는 config/udev/99-dronestock.rules, 기술 방향은 docs/roadmap.md 를 본다.

---

## 결론 한 줄

```text
uwb_node = 번역기다. 계산기가 아니다.
태그가 케이블로 보내는 글자 줄을 ROS2 좌표 메시지로 바꿔 /uwb_pose 에 발행한다. 그게 전부다.
```

---

## 1. 이 문서를 읽는 데 필요한 용어

glossary에 있는 것은 링크로 대신하고, 여기서 처음 나오는 것만 적는다.

### 시리얼 통신 (Serial)
전선 한 가닥으로 글자를 한 개씩 순서대로 보내는 통신 방식.
- 비유: 좁은 문으로 사람을 한 줄로 통과시키는 것. 넓은 문(병렬)보다 느리지만 선이 적게 든다.
- 우리 프로젝트: UWB 태그는 USB-시리얼 변환칩(CP2102)을 통해 `/dev/uwb`로 잡힌다. 속도 921600 bps, 8N1.

### 8N1 / baudrate
`8N1` = 글자 1개를 데이터 8비트 + 패리티 없음(None) + 정지비트 1개로 보낸다는 약속. `baudrate` = 1초에 보내는 신호 개수.
- 비유: 말하는 속도와 띄어 읽는 규칙을 미리 맞추는 것. 양쪽이 다르면 말이 아니라 소음이 된다.
- 우리 프로젝트: 921600 8N1. 이 값이 틀리면 연결은 되는데 글자가 전부 깨져 나온다.

### 라인 프레이밍 (Line Framing)
끊겨 도착하는 글자 조각을 줄바꿈(`\n`) 기준으로 다시 한 줄로 맞추는 작업.
- 비유: 우편함에 반쪽씩 들어온 편지를 마침표가 나올 때까지 모아 붙이는 것.
- 왜 필요한가: 시리얼은 "한 줄"이라는 개념이 없다. 읽을 때마다 조각이 임의 길이로 온다.

```text
1번째 읽기: {"type":"uwb_po
2번째 읽기: se","seq":119,"fix":tr
3번째 읽기: ue,"x":0.267}\n      ← 여기서야 한 줄 완성
```

- 우리 프로젝트: 버퍼에 계속 이어 붙이고 `\n`이 나올 때만 잘라 파싱한다. 조각 상태로 파싱하면 매번 실패한다.

### JSON 파싱 (Parsing)
글자로 적힌 데이터를 프로그램이 다룰 수 있는 값으로 해석하는 것.
- 비유: 손글씨 메모를 읽어서 표에 옮겨 적는 것.
- 우리 프로젝트: 태그는 한 줄에 JSON 하나를 보낸다. Python `json.loads()` 한 번이면 된다.

### 공분산 행렬 (Covariance Matrix)
"이 값이 얼마나 못 미더운가"를 숫자로 적어 값과 함께 보내는 표. 확신도의 반대다.
- 비유: 시험지에 답을 쓰면서 옆에 "이건 확실함 / 이건 찍었음"을 같이 적어 두는 것. 채점자가 그걸 알면 판단이 달라진다.
- 읽는 법: **작을수록 믿을 만하다.** 숫자는 오차 범위를 제곱한 값이다.

```text
"0.66 m 쯤 틀릴 수 있다"  →  0.66 × 0.66 = 0.44
"0.1 m 쯤 틀릴 수 있다"   →  0.1 × 0.1  = 0.01   ← 훨씬 작다 = 훨씬 믿음직
```

- 왜 중요한가: EKF2는 UWB·IMU·기압계 값을 다 받아 **누구 말을 더 믿을지** 정해야 한다. 그 판단 근거가 이 값이다. 작게 적으면 "아주 정확함"이라고 우기는 셈이라 추정기가 과신한다.
- 한계: 공분산은 **흔들림**만 표현한다. 일정하게 밀린 오차(bias)는 공분산으로 표현할 수 없다. [거리 bias 항목](glossary.md) 참조.

### watchdog (감시 타이머)
"정해진 시간 안에 소식이 없으면 이상이다"라고 판단하는 타이머.
- 비유: 등산 무전이 5분간 없으면 사고로 간주하는 규칙.
- 우리 프로젝트: 태그 줄이 일정 시간 이상 안 오면 경고를 내고 발행을 멈춘다. 케이블이 빠졌는데 조용히 마지막 값만 붙들고 있는 상태가 제일 위험하다.

관련 glossary 항목: [fix](glossary.md), [제어 hold](glossary.md), [필드 없음 vs false](glossary.md), [QoS](glossary.md), [관측치 전처리](glossary.md), [보간/업샘플링](glossary.md), [vision_pose](glossary.md)

## 2. 전체 구조

```text
   UWB 태그 (DWM3000EVB)
        │  USB-시리얼, 921600 8N1, JSON 한 줄/샘플, 약 43Hz
        ▼
   /dev/uwb                       ← udev가 만든 고정 이름 (포트 1-2.1)
        │
   ┌────┴─────────────────────────────────────────┐
   │  uwb_node                                    │
   │                                              │
   │   ① 포트 열기 ── 첫 줄 type 검증             │
   │        ▼                                     │
   │   ② 라인 프레이밍 (버퍼 + \n)                │
   │        ▼                                     │
   │   ③ JSON 파싱 (필드 없음 허용)               │
   │        ▼                                     │
   │   ④ 발행 판정 (fix)                          │
   │        ▼                                     │
   │   ⑤ 메시지 조립 + 발행                       │
   │                                              │
   │   ⑥ watchdog (별도 타이머)                   │
   └────┬─────────────────────────────────────────┘
        ▼
   /uwb_pose  (BEST_EFFORT)
        │
        └──→ [Phase 1] vision_pose 변환 노드 ──→ MAVROS ──→ PX4 EKF2
```

> Phase 0의 범위는 `/uwb_pose` 발행까지다. vision_pose 연결은 Phase 1이며, HW 파트 bias 교정 후에 실비행에 넣는다.

## 3. 단계별 상세

### ① 포트 열기 + 첫 줄 검증

```text
포트     : /dev/uwb  (파라미터로 바꿀 수 있게 한다)
속도     : 921600, 8N1
타임아웃 : 읽기 블로킹으로 노드 전체가 멎지 않게 짧게 준다
```

**첫 줄에서 `type == "uwb_pose"`를 반드시 확인한다.** 아니면 즉시 에러를 내고 죽는다.

이유: LiDAR와 UWB 태그가 **둘 다 CP2102이고 공장 serial이 똑같이 `0001`** 이다. udev가 USB 포트 위치로 구분하므로, 잭을 바꿔 꽂으면 `/dev/uwb`가 LiDAR를 가리킨다. 검증 없이 진행하면 LiDAR 데이터를 위치로 착각한 채 비행하게 된다.

### ② 라인 프레이밍

```python
buf += port.read(available)
while b'\n' in buf:
    line, buf = buf.split(b'\n', 1)
    handle(line)
```

주의점 2개.

- 버퍼에 상한을 둔다. 줄바꿈이 영영 안 오는 고장 상황에서 메모리가 계속 늘어나면 안 된다. 상한을 넘으면 버리고 다음 `\n`부터 다시 맞춘다.
- 첫 줄은 잘려 있을 수 있다. 포트를 연 시점이 줄 중간일 수 있으므로 **첫 줄은 버리고 두 번째 줄부터** 쓰는 편이 안전하다. (①의 type 검증도 온전한 줄로 해야 한다)

### ③ JSON 파싱 — 필드가 없어도 정상이다

태그가 보내는 줄은 **두 종류**다.

| 줄 종류 | 필드 수 | 빈도 | 들어 있는 것 |
|---|---:|---|---|
| 압축 줄 | 13 | 10줄 중 9줄 | 위치·상태만 |
| 상세 줄 | 94 | 10줄 중 1줄 | + 앵커별 거리·품질·타이밍 |

**압축 줄만으로 노드가 완전히 동작해야 한다.** `raw_r1` 같은 상세 필드를 필수로 요구하면 90%의 줄에서 실패한다.

```text
금지: data["range_fail_a1"]           → 압축 줄에서 KeyError
금지: data.get("range_fail_a1", False) → 없는 걸 "실패"로 둔갑시킨다
권장: data.get("range_fail_a1")        → 없으면 None. "모름"으로 다룬다
```

`null`도 마찬가지다. `pose_residual_rms_m`이 `null`이면 0이 아니라 "계산할 후보가 없었다"는 뜻이다.

파싱 실패한 줄은 **버리고 카운터만 올린다.** 노드를 죽이지 않는다. 전선 노이즈로 한 줄 깨지는 건 정상 범위다. 다만 연속 실패가 이어지면 경고를 낸다(속도 설정 오류 신호).

### ④ 발행 판정

```text
fix == true   → 발행한다
fix == false  → 발행하지 않는다 (x, y 값이 들어 있어도)
```

`fix=false`인 줄의 x, y는 마지막 유효값을 붙들고 있는 값이다. 새 측정이 아니다.

> **알려진 이슈 — hold 구간 재발행 (HW 파트 판단으로 허용)**
>
> `fix=true` 중에도 태그가 직전 좌표를 최대 500ms 재사용하는 구간이 있다 (`xy_control_held=true`, `hybrid_source=none`). 실측 341개 `fix=true` 중 21개가 이 경우였다.
>
> 엄밀히는 `xy_control_fresh=true`까지 확인해야 같은 좌표를 새 관측처럼 반복 주입하는 일을 막을 수 있다. [보간/업샘플링](glossary.md) 항목이 경계하는 것과 같은 성격이다.
>
> **HW 파트 판단**: 실내는 철재 렉 등 장애물이 많아 UWB를 놓치는 구간이 잦지만, 그 짧은 시간 동안 기체가 직전 위치에서 크게 벗어나지 않는다. 따라서 hold 값을 그대로 써도 실용상 문제가 없다.
>
> **결정**: `fix`만 보고 발행한다. 이 항목은 이슈로 남겨두고 진행한다. 재검토 시점은 Phase 1의 EKF2 융합 튜닝 — innovation test ratio가 만성적으로 낮게 눌려 있으면(과신 징후) 이 항목을 먼저 의심한다.

### ⑤ 메시지 조립

**메시지 타입**: `geometry_msgs/PoseWithCovarianceStamped`

`PoseStamped`가 아니라 이걸 쓰는 이유는 공분산을 같이 실어야 하기 때문이다. Phase 1에서 MAVROS `vision_pose`로 넘길 때 EKF2가 이 값을 본다. 여기서 버리면 Phase 1에서 다시 만들어 붙여야 한다.

| 항목 | 값 | 이유 |
|---|---|---|
| `header.stamp` | 노드가 줄을 받은 ROS 시각 | 태그의 `t`는 태그 내부 시계라 ROS 시각과 기준이 다르다 |
| `header.frame_id` | `map` (결정 필요, 6장) | 앵커 좌표계는 창고에 고정된 절대 좌표계다 |
| `pose.position.x/y` | 태그의 `x`, `y` 그대로 | 가공하지 않는다 |
| `pose.position.z` | `0.0` | UWB는 z를 내지 않는다 |
| `pose.orientation` | 단위 사원수 (w=1) | UWB는 방향을 모른다 |
| `covariance` | x, y는 실측 기반. **z와 회전은 아주 크게** | "이 값은 믿지 마라"를 명시 |

**z 공분산을 크게 주는 것이 핵심이다.** z에 0.0을 넣는 것 자체는 문제가 아니다 — `EKF2_EV_CTRL=1`이면 EKF2가 z를 아예 안 본다. 문제는 나중에 누가 설정을 3으로 바꿨을 때다. 그때 z 공분산이 작으면 **"고도 0m를 확신함"** 이라는 신호가 되어 기체가 바닥으로 내려가려 한다. 공분산을 크게 박아 두는 것이 그 사고를 막는 안전장치다.

x, y 공분산 초기값: 실측 오차 약 0.66 m 기준으로 `0.66² ≈ 0.44` 정도에서 시작하되 파라미터로 뺀다. 단, **공분산은 흔들림만 표현한다.** 지금 오차의 정체는 일정하게 밀린 bias이고 이건 공분산으로 못 알린다. 교정 전에는 어떤 값을 넣어도 EKF2가 정직하게 다룰 수 없다는 뜻이다 — 실비행 투입을 미루는 이유가 이것이다.

**QoS**: `BEST_EFFORT`. 43Hz로 계속 새 값이 나오므로 유실된 값을 재전송받는 것보다 최신값을 받는 게 낫다. `/scan`과 같은 성격이다.

### ⑥ watchdog

```text
마지막 줄 수신 후 일정 시간(예: 0.5초) 경과 → 경고 로그 + 발행 중단
```

케이블이 빠지거나 태그가 멎었을 때, 아무 소리 없이 조용해지는 것이 가장 위험하다. 구독하는 쪽은 "값이 안 바뀌네" 정도로만 보이기 때문이다. 시간 기준은 파라미터로 뺀다.

## 5. 하지 말아야 할 것

각 항목에 이유를 붙인다. 이유 없는 금지는 지워진다.

| 금지 | 이유 |
|---|---|
| 거리(`raw_r*`)로 위치를 다시 계산 | 태그가 이미 계산했다. 두 개의 답이 생기면 어느 쪽이 틀렸는지 못 가린다 |
| 앵커 배제 로직 재구현 | 태그 펌웨어의 설계된 동작이다. companion이 흉내 내면 두 로직이 어긋난다 (udev 규칙 57~61행) |
| bias 보정값을 노드에 하드코딩 | 교정은 앵커·안테나 단위 작업이다. HW 파트가 태그 설정에 넣는다. 두 곳에 있으면 이중 보정이 된다 |
| 비행용 위치 추정기 추가 | roadmap 결정 10. 융합은 PX4 EKF2 하나만 한다 |
| 값이 없을 때 이전 값으로 채워 발행 | [보간/업샘플링](glossary.md). 새 정보 0인데 EKF2는 관측이 늘었다고 믿는다 |
| 좌표축을 노드에서 뒤집기 | MAVROS가 ENU↔NED를 이미 변환한다. 두 번 뒤집으면 원위치가 되어 축이 반대로 간다 |
| 없는 필드를 `False`로 기본값 처리 | 없는 사건을 만들어낸다. 압축 줄에는 진단 필드가 원래 없다 |

허용되는 것: **이상치 제거·평활은 Phase 1에서 해도 된다.** roadmap 결정 10이 명시적으로 허용한다 — 추정기가 아니라 관측치 전처리이기 때문이다. 단 Phase 0의 이 노드는 통과(pass-through)로 시작한다. 전처리를 섞으면 태그 출력과 노드 출력을 대조할 수 없어 문제 분리가 안 된다.

### 좌표축이 이미 확정인 이유

좌표계를 만드는 것은 `frame_id`가 아니라 **앵커를 박은 물리적 위치**다. 그 배치가 이미 좌표계 정의다.

```text
A3(0, 4.5) ●───────────● A4(5, 4.5)
           │           │
         y ↑           │        x축 = A1 → A2 방향
           │           │        y축 = A1 → A3 방향
A1(0, 0)   ●───────────● A2(5, 0)
              x →
```

이 정의는 **오른손 좌표계이며 z가 위**다. ROS ENU와 같은 성질이므로 노드에서 축을 변환할 이유가 없다. 파라미터로 뺄 필요도 없다.

`frame_id`는 좌표계를 만들지 않는다. 이미 있는 좌표계에 붙이는 **이름표**일 뿐이다. 같은 숫자라도 이름표가 다르면 다른 장소를 뜻하므로, 여러 노드가 같은 이름을 쓰기만 하면 된다.

### 남은 것은 Phase 1 사안이다 — 북쪽 정렬

```text
우리 x축   : A1 → A2 방향 (창고 벽 기준)
PX4의 북쪽 : 지자기 센서가 가리키는 자북

두 기준이 몇 도 틀어져 있는가?
```

PX4는 외부 위치를 받을 때 그 좌표계가 자기 북쪽 기준과 정렬돼 있다고 가정한다. 창고 벽이 자북과 나란하지 않으면 그만큼 틀어지고, EKF2는 "IMU로 적분한 이동 방향"과 "UWB가 준 위치 변화"가 어긋난다고 판단한다.

- **Phase 0에는 영향 없다.** `/uwb_pose` 발행까지는 이 문제가 나타나지 않는다.
- **Phase 1의 vision_pose 연결 시점에 확인한다.** 기체를 x축 방향으로 직선 이동시켜 EKF2가 같은 방향으로 움직였다고 보는지 대조하면 된다.

## 7. 테스트 순서

```text
1. 태그를 USB 포트 1-2.1 에 꽂는다        ← 다른 잭이면 /dev/lidar 와 뒤바뀐다
2. ls -l /dev/uwb 로 링크 확인
3. 노드 없이 원시 줄부터 눈으로 확인 (깨진 글자가 나오면 baudrate 문제)
4. 노드 실행 → ros2 topic hz /uwb_pose   → 약 43Hz 근처인지
5. ros2 topic echo /uwb_pose             → x, y가 태그 줄의 값과 일치하는지
6. 태그 케이블을 뽑아 watchdog 경고가 뜨는지
7. 태그를 LiDAR 잭에 꽂아 첫 줄 검증이 에러를 내는지  ← 안전장치 확인
```

7번은 빼먹기 쉬운데, 이 안전장치가 실제로 도는지 확인하지 않으면 있으나 마나다.
