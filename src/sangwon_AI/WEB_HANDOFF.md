# 웹 담당자 전달 패키지 — 자율비행 v1 확장
이 문서는 웹 담당자가 구현 범위·자료 요청·검수 방법을 한 번에 확인하는 요청서다.
아래 P0 항목의 대응표와 JSON 샘플을 회신하고 합성 연동 시험을 시작할 때 읽는다.

> 2026-10-04 외부 계약 검토 기준: [웹 전체 개편 요청서 r2](WEB_REDESIGN_REQUEST_2026-10-04.md)와 [draft.4 예제](contracts/web_v1_1_draft4/README.md)를 먼저 읽는다.
> 이 문서의 draft.2/부분 예제는 이전 근거다. 새 웹 개발에 혼용하지 않는다.

상태: 2026-10-04 웹 추가 자료 요청 회신 수령 / 최종 계약 합의 전.
웹팀의 WEB_HANDOFF_REQUESTS.md에 대한 [전체 흐름·UI·UX/API 개편 요청](WEB_REDESIGN_REQUEST_2026-10-04.md)을 함께 전달한다.
내부 비행 정책은 확정했으며, 외부 계약 `1.1-draft.2`의 필드·URL은 담당자 합의 전이다.
2026-10-04 보완: [QR_SCAN_SPEC.md](QR_SCAN_SPEC.md)의 QS-W1~W8도 함께 회신한다.
기존 요청서에 빠진 ArUco 정렬·호버·스캐너 3회·카메라 대체 판독을 추가한다.
성공·최종 스캔 실패 모두 기록 후 접근 대기점 복귀를 확인하고 다음 목표로 진행한다.
마커 획득 실패·카메라 고장도 비행·이탈 정상 시 같은 처리다. 세부 수치·JSON은 협의 대상이다.
웹·서버·Jetson의 실제 연동은 아직 검증하지 않았다.
기체 비행 코드는 현재 합성 REPLAY 단계다. 이 요청서가 실기체 비행 허가를 뜻하지 않는다.

## 1. 요청 요약

기존 Platform API v1에 임무·지도 묶음, 안전한 명령 처리, 부팅 점검·준비 상태를 확장한다.

```text
Jetson 전원 ON
  -> 서비스 자동 기동 -> PX4/장치 자동 연결 -> 자동 점검
  -> 시스템 준비 [웹: 시스템 점검 완료]
  -> 전체 임무/지도 수신 -> 경로/승인/현재 기체 재검사
  -> 임무 준비 [웹: 해당 임무 시작 준비 완료]
  -> 운영자 새 START -> Jetson 최종 재검사 -> PX4 이륙/임무 수행
```

부팅·시스템 점검 통과·서버의 ACTIVE/READY만으로 arm/이륙하지 않는다.
점검 미통과나 자료 미수신은 이유와 조치를 보여 주며 준비 완료로 표시하지 않는다.
준비 알림은 웹을 우선한다. 기존 스캐너의 LED 제어 가능 여부는 확인 중이며 별도 장치는 미정이다.
준비 알림을 위해 모터를 시동하거나 기체를 움직이지 않는다.

## 3. 화면별 변경 요청

### 3.1 기체 상세/점검 화면

| 영역 | 표시 항목 | 필수 동작 |
|---|---|---|
| 식별 | drone_id·boot_id·실행기 세션·프로파일 REPLAY/SITL/FLIGHT | 모의 시스템을 실기체 준비로 오표시 금지 |
| 부팅 | BOOTING/CONNECTING/CHECKING/RUNNING/FAULT | 현재 단계·시작 시각·차단 원인 표시 |
| 시스템 준비 | READY/NOT_READY/FAULT/CHECKING | 현재 장치/프로세스/설정 점검 결과 |
| 임무 준비 | NO_MISSION/CHECKING/READY/NOT_READY/BUSY | 대상 snapshot·준비 ID·준비 개정·유효성 |
| 점검 목록 | 체크 ID·PASS/FAIL/UNKNOWN/WARN·필수/차단 여부 | 오류 코드는 유지하고 사람이 읽을 원인·조치 표시 |
| 관측 근거 | source·last_seen_at·source_age_ms·check_seq | 미수신 null·오래된 값을 0/정상으로 변환 금지 |
| RC | 연결 가용 여부·수동 인계 잠금·현재 PX4 모드 | 미연결이면 인계 불가 경고, 비행 중 끊김만으로 복귀 유도 금지 |
| 준비 알림 | ‘시스템 점검 완료’와 ‘임무 시작 준비 완료’ | 같은 문구로 두 단계 합치지 않음 |

RC 수동 인계 후 웹은 ‘수동 조종 중/같은 비행 자율 재개 불가’를 표시한다.
Jetson은 기존 RC/PX4 수동·비상 설정을 유지한다. 웹이 제어권을 강제로 회수하지 않는다.
신규 RC Land/Kill 스위치 기능을 이번 웹 요청에 추가하지 않는다.

### 3.2 지도/임무 편집 화면

일반 이동점의 필수 입력은 기체 목표 XYZ, 순서별 고유 ID, 별도 takeoff_z_m, hold_s다.
일반 이동점 yaw는 선택값이며 도착 자세다. 생략과 숫자 0은 다르다.
입력 지도는 픽셀이 아닌 m 단위의 승인된 좌표계로 내보낸다.
좌표·높이·각도·속도 관련 값의 단위와 기준점을 화면에 표시한다.
웹의 경유점을 자동 삭제·대체하지 않고 하나라도 잘못되면 전체 임무를 수정하도록 안내한다.
목표 속도 프로파일/제동 한도는 Jetson 승인 설정을 따르며 웹에서 임의 상향하지 않는다.
새 속도 입력 기능을 추가하려면 승인 범위와 JSON 필드를 별도 합의한다.

필수 이동점 방문 순서와 선택 안내점을 혼용하지 않는다. scan도 같은 작업 순서를 지킨다.
scan XYZ는 라벨 위치이며 기체가 통과해야 하는 점이 아니다. 라벨 z와 기체 높이를 따로 표시한다.
QS-W7 회신에는 라벨 기준점·정면 방향의 필드/단위/축과 누락 처리안을 포함한다.
정면 방향은 라벨에서 통로 쪽으로 향한다. 기체 도착 yaw와 별도 의미로 정의한다.
Jetson이 생성한 접근 대기점·판독 pose·진입/이탈 구간을 라벨 아이콘과 구분해 표시한다.
QS-W8로 라벨별 접근·작업 허용 구역을 웹에 요청한다. 구역 제공은 사용자 확정, JSON은 협의 대상이다.
구역 ID·라벨/지도 참조·개정, 평면 외곽·높이 하한/상한, 기하 의미, 진입/이탈 경로 연결과 승인 참조를 회신한다.
Jetson은 제공 구역 안에서 기체 여유·장애물을 검사해 접근 대기점/판독 pose를 산출한다.
구역 미제공을 비행 허용으로 해석하지 않으며, 국소 스캔 승인으로 일반 자동 우회를 활성화하지 않는다.
스캔 결과가 저장되어도 대기점 복귀 전에는 다음 작업 진행/전체 완료로 표시하지 않는다.
지도 경계/금지 구역이 ‘미제공’인지 ‘제공됐고 없음’인지 구분해 저장한다.
웹이 기체 여유를 더한 형상인지 실제 장애물 형상인지 명시한다. 현재는 실제 형상을 요청한다.

### 3.3 비행 실행 화면

시작 버튼의 활성 조건은 로그인 권한·LIVE·현재 세션·시간 신뢰·신선한 시스템 READY·해당 임무 READY다.
상태 표시만으로 실제 시작을 확정하지 않는다. Jetson의 ACCEPTED 뒤 PREPARING/TAKING_OFF를 따로 표시한다.
비활성 버튼 옆에는 차단 체크와 운영자 조치를 보여 준다.
전송 후 응답 없음은 ‘결과 미확인’이며 ‘실행 실패’ 또는 ‘시작 안 됨’으로 단정하지 않는다.

| 현재 단계 | START | PAUSE/RESUME | CANCEL | LAND_NOW |
|---|---|---|---|---|
| 지상 준비 완료 | 새 운영자 요청 가능 | 불가 | 수락된 준비 실행이 있으면 중단 요청 | 비행 ID 없음이면 불가 |
| 이륙/이동/회전/체류 | 새 임무 불가 | BT가 허용하는 단계·위치 유지 조건에서 가능 | 상승 중 현 위치 착륙, 나머지 복귀·착륙 | 제어권·비행 문맥 확인 뒤 현 위치 착륙 |
| PAUSED | 새 임무 불가 | 재개 전 재검사 | 복귀·착륙, 상승 중 일시정지였다면 현 위치 착륙 | 가능 조건 재검사 |
| RETURNING/LANDING | 불가 | 불가 | 이미 진행한 복귀/착륙을 되돌리지 않음 | 현재 단계·제어권에서 중재 |
| RC 수동 인계 | 같은 비행 불가 | 불가 | 자율 제어 강제 회수 없음 | RC 제어권 강제 회수 없음 |
| OFFLINE/STALE | 신규 요청 생성/자동 대기열 금지 | 신규 요청 금지 | 전달 불가 표시 | 전달 보장 불가, 완료로 표시 금지 |

연결 복구 뒤 운영자가 현재 상태·기존 요청 결과를 확인한 후 새 요청한다.
START와 RESUME을 클라이언트 오프라인 큐나 브라우저 재시도 플러그인으로 새 ID 재생성하지 않는다.
같은 ID의 전송 재시도와 결과 조회는 별개이며 같은 동작을 재실행하지 않는다.

| 신규 API 제안 | 제어 세션 발급/확인, 요청 ID별 결과 조회 | 정확한 URL·method·인증·404/409 처리 |
| 임무/지도 자료 | 같은 snapshot/revision 불변 | 내용 해시 방식·지도 별도 다운로드 여부 |
| 명령 원장 | ID와 원문 식별·상태·revision·기체·문맥 보존 | 보존 기간·서버 재시작 복구 |
| 준비 최신 상태 | boot/runtime/seq/revision과 받은 시각 보존 | 오래된 세션/순서 수신 처리 |
| 사건 이력 | 동일 event_id 재전송 중복 방지 | 조회·페이지 처리·보존 기간 |

기존 v1 인증 방식을 검토해 재사용한다. 새 비밀키 원문을 문서·샘플·회신에 넣지 않는다.
장치 인증 정보 발급/회수·기체 대상 제한·운영자 권한 방법만 회신한다.
기존 control_action과 확장 control_requests를 동시에 실행하지 않는다.
웹 어댑터가 재기동돼도 C++의 명령 원장·수락 결과를 기준으로 복원한다.
서버의 HTTP 200은 요청 저장/전달 결과이며 물리 비행 완료가 아니다.

### 4.1 JSON 묶음과 필수 검증

실제 구문 예제는 [WEB_JSON_DRAFT.md](WEB_JSON_DRAFT.md)에 있다.

| 샘플 | 포함할 것 | 검증 포인트 |
|---|---|---|
| mission_full.json | 전체 snapshot + 지도 + 승인 + 빈 control_requests | 한 항목 누락 시 부분 실행 금지 |
| command_start.json | 새 START + 모든 세션 + preparation + 10초 만료 | 지상 flight_id=null, RC 예외는 실제 비행 참조 |
| command_active.json | PAUSE/RESUME/CANCEL/LAND_NOW 각각 | 현재 execution/flight 결합·단계별 거부 |
| result_accepted.json | ACK status/code/result_revision | 수락을 완료로 표시하지 않음 |
| result_rejected.json | 차단 check_id·reason·operator_action | 운영자가 수정할 항목 표시 |
| telemetry.json | 실제 모드·제어권·위치·관측 나이·활성 목표 | stale/null·UWB/PX4 출처 분리 |
| readiness_ready.json | 시스템/임무 READY·준비 수명·전체 필수 체크 | 준비 스냅샷 기준 START 문맥 생성 |
| readiness_blocked.json | 필수 UNKNOWN 또는 FAIL | 준비 ID 없음·can_start=false |
| event_ready_revoked.json | READY_REVOKED와 원인·준비 개정 | 배지 즉시 해제·과거 알림으로 재활성 금지 |

각 파일은 같은 계약 버전과 같은 합성 기체/임무/세션을 사용해야 한다.
지금 문서의 JSON은 합성 예시이며 서버 실제 URL·토큰·기체 승인 자료가 아니다.

### 4.2 오류 표시 최소 집합

| 코드 | 웹 안내 | 자동 새 요청 |
|---|---|---|
| SYSTEM_NOT_READY / MISSION_NOT_READY | 차단 체크·원인·운영자 조치 | 금지 |
| READINESS_STALE / PREPARATION_STALE | 현재 상태 수신·재검증 필요 | 금지 |
| STALE_RUNTIME_SESSION / STALE_CONTROL_SESSION | 현재 기체 세션 확인 필요 | 금지 |
| COMMAND_EXPIRED / CLOCK_UNTRUSTED | 명령 만료/시계 신뢰 미확인 | 금지 |
| REQUEST_ID_CONFLICT / SNAPSHOT_CONFLICT | 같은 ID의 내용 충돌, 운영 자료 수정 | 금지 |
| BUSY / INVALID_PHASE | 현재 임무/단계에서 처리 불가 | 금지 |
| MANUAL_LOCKED / CONTROL_NOT_OWNED | 수동/PX4 제어 중, 자율 재개 불가 | 금지 |
| STORAGE_NOT_READY | 새 비행 기록 공간/기록 경로 복구 필요 | 금지 |
| MISSING_APPROVAL / TRANSFORM_UNAVAILABLE | 승인 자료/측량 변환 필요 | 금지 |
| INVALID_MAP / INVALID_WAYPOINT | 해당 지도 영역/경유점 필드 수정 | 금지 |

목록 전체와 비행 중 원인 코드는 JSON 문서가 기준이다.
웹이 모르는 새 오류 코드도 원문 코드·설명·차단 여부를 보여 주며 성공으로 처리하지 않는다.

## 5. 부팅·준비 연동 검수 시나리오

기존 [VALIDATION_PLAN.md](VALIDATION_PLAN.md)의 WT 시험을 유지하며 아래 WH를 추가한다.
시험 자료에는 요청/응답 원문, 기체·서버 수신 시각, 화면 캡처, 기대/실제 결과를 남긴다.
개인정보·인증 비밀은 제거한다.

| ID | 시나리오 | 통과 조건 |
|---|---|---|
| WH01 | 전원 투입, 서버에 예전 ACTIVE/START 존재 | 자동 점검만 수행, 새 승인 없이 arm/이륙 없음 |
| WH02 | 시스템 정상, 임무 없음 | 시스템 준비 알림만, 임무 NO_MISSION·시작 비활성 |
| WH03 | UWB/위치 관측 미구현·미수신 | 필수 UNKNOWN·원인 표시, FLIGHT READY 불가 |
| WH04 | 준비 완료 뒤 센서 값은 멈추고 상태 메시지만 반복 | source age 초과 시 READY 해제·새 START 거부 |
| WH05 | 서버가 옛 READY 캐시를 다시 전달 | 원래 시각 보존, LIVE/READY로 부활하지 않음 |
| WH06 | READY 직후 조건 상실, 10초 안 START 도착 | 최신 준비 재검증에서 거부, arm 없음 |
| WH07 | OS 부팅 또는 C++ 실행기만 재기동 | 이전 boot/runtime/preparation 명령 거부, 원장 조회는 보존 |
| WH08 | Wi-Fi 단절 중 START/RESUME/LAND 클릭 후 복구 | 미전달 요청 자동 실행 없음, 현재 상태 대조 후 재요청 |
| WH09 | 동일 START 재전송·다른 ID 동시 START | 같은 ID 한 번만 실행·기존 결과, 다른 요청 BUSY/문맥 거부 |
| WH10 | 같은 준비 사건 여러 번·브라우저 재접속 | 알림 중복 없음, 과거 사건이 현재 READY를 바꾸지 않음 |
| WH11 | RC 미연결→연결→비상 수동 인계 | 미연결 경고, 인계 후 RC/PX4 모드 표시·동일 비행 RESUME 금지 |
| WH12 | REPLAY/SITL 프로파일·진단 모니터만 정상 | 시험/진단 상태 명시, 실기체 비행 준비·START 권한 발급 없음 |

준비 집계 기능을 임시 상수 true로 구현한 화면은 완료로 인정하지 않는다.
서비스가 실행 중이라는 정보와 연결된 실제 장치 데이터가 유효하다는 증거를 함께 확인한다.

## 6. 담당 분담과 개발 착수 순서

| 담당 | 작업 | 완료 조건 |
|---|---|---|
| 웹 화면 | 지도·임무·운영자 확인, 상태/점검/오류/알림, 명령 요청 | W 화면 및 WH 시나리오 재현 |
| Platform 서버 | 버전·snapshot·세션·명령/결과/사건 원장·인증 | 같은 계약 fixture 송수신·재시작 복구 |
| Jetson C++ | 실제 점검 집계·준비 발급·최종 수락·BT·제어권 | 준비/명령/중단 정책 시험 |
| Jetson Python | 웹 전송·재연결·로그·장치 보조 진단 | C++ 결과 그대로 전달, 임의 비행 승인 없음 |
| 비행/UWB 담당 | 센서 전체 사양·측량·펌웨어/RC/품질·실측 승인 | FLIGHT 체크별 검증 자료 |

착수 순서는 계약 대응표→합성 fixture→서버/화면→Jetson mock 연결→단절/재기동 검수다.
웹팀 회신 전에 합성 자료로 개발할 수 있지만 실제 서버 계약 완료로 표시하지 않는다.
UWB 전체 사양을 기다리는 동안 웹은 위치의 출처·유효성·나이 인터페이스를 구현한다.
UWB UART/원시 패킷 필드는 웹 계약에 미리 고정하지 않는다.

### 7.3 함께 받을 자료

[WEB_REQUIREMENTS.md](WEB_REQUIREMENTS.md)의 D01~D10을 요청한다.

첫 연동 완료 기준은 P0 회신·합의, 동일 fixture 양방향 통과, WT/WH 결과 확보까지다.
실기체 비행 승인은 위치·고도·yaw·제동·실패 처리 검증 이후 별도 진행한다.
