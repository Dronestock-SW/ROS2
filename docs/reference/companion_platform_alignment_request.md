# Platform 연동 역할·API 조정 요청서
이 문서는 Platform 담당자에게 전달할 합의 요청서다.
모니터링·목표 지시를 우리 구조에 연결할 때 읽는다.

아래 좌표 대조는 9월 API 협의 당시 기록이다.
현재 XY는 [6.3×4.6m 직사각형](uwb_anchor_layout.md)을 따른다.
현재 원점은 A1, +x는 A2 방향, +y는 A3 방향이다.

## 1. 요청 요지

Platform은 모니터링과 목표·임무 지시를 맡아 주세요.
QR 결과 저장과 임무 이력 관리도 서버 역할입니다.
실제 비행은 우리 ROS2·PX4 구조에서 처리합니다.

| 담당 | 역할 | 결정 권한 |
|---|---|---|
| 웹 화면 | 위치·상태 표시. 목표·경로 입력 | 사용자가 원하는 임무를 요청 |
| Platform 서버 | 임무·요청·배치 관리. 결과 저장 | 요청 ID·개정값·업무 처리 결과 관리 |
| companion | 입력 검증. 임무 처리. 수평 이동 제어 | 목표 수락·거부. 기체 상태에 따른 실행 판단 |
| PX4 | EKF2 상태추정. 고도·자세 제어 | 실제 비행 상태·모드·기체 보호 기능 |

```text
웹 목표·경로 → Platform API → companion 입력 검증 → 임무·수평 제어 → PX4
웹 표시     ← Platform API ← 관측·기체 상태·목표 처리 결과 ← companion
웹 재고 결과 ← Platform DB ← QR 원문·임무·라벨 ID ← companion
```

웹 목표 입력은 실제 이동 완료를 뜻하지 않습니다.
기체가 거부한 목표도 사유를 표시해 주세요.
Platform의 경로는 작업 순서·목표점 목록입니다.
기체는 실행 중 제약을 검사하고 이동을 수행합니다.

## 2. 현재 기준과 기합의 사항

기존 v1 계약을 유지하며 필요한 차이만 조정합니다.
아래 내용은 새 질문이 아닌 적용 기준입니다.

| 기합의 사항 | 유지할 내용 | 근거 |
|---|---|---|
| 내부 구조 | ROS2·PX4 내부 구조는 companion 팀 담당 | v1 계약 서문 |
| 임무 수신 | `GET /api/drones/{drone_id}/companion-mission/`, 0.5초 | 계약 1·2절 |
| 상태 송신 | `WS /ws/drones/{drone_id}/`, 목표 10Hz | 계약 1·2절 |
| 수평 위치 | 기존 `x`, `y`는 검증된 UWB 관측 | 회신 C09 |
| 선택 센서 | UWB XY-only 허용. 미지원은 null/생략 | 회신 C07·C15 |
| 현재 고도 | PX4 출처 `px4_ekf2` 허용 | 회신 C16 |
| 실제 FC 상태 | `fc_connected`, `fc_armed`, `fc_mode` 분리 | 회신 C48 |
| 실제 이동 경로 | `route_tasks`. 최상위 target은 표시·구형 호환 | 회신 C23 |
| 임무 식별 | `mission_db_id`와 `mission_code` 분리 | 회신 C30 |
| 제어 요청 | `return_to_home`, `land`. ID·원래 요청 시각 유지 | 회신 C32·C34 |
| ACK | 상태 진입 수락. 물리적 완료와 구분 | 회신 C35 |
| 비행 중 경로 수정 | v1에서 금지 | 회신 C24 |
| QR 재전송 | 같은 `client_scan_id`로 중복 방지 | 회신 C42 |

계약은 [수신 v1 원문](../hw_handoff/platform_api_v1/companion_platform_api_contract_v1.md)을 따릅니다.
회신 근거는 [9월 11일 확인표](../hw_handoff/platform_api_v1/API_CONFIRMATION_RESPONSE.md)입니다.

### W02. 좌표 기준

우리 `uwb_map`과 같은 축으로 목표를 해석해야 합니다.

| 요소 | 우리 기준 | 요청 |
|---|---|---|
| x·y 원점 | A1의 수평 위치 | 화면·목표·관측에서 동일하게 사용 |
| +y | A1에서 A3로 향하는 방향 | 기존 방향 유지 |
| +x | +y에 수직인 오른쪽 | `A1_TO_A2` 고정 정의 조정 |
| 단위 | m | 화면 cm 변환과 API m를 구분 |
| +z 의미 | 바닥에서 위 | 목표 고도·현재 고도·앵커 높이를 구분 |
| 버전 | 축·원점·배치와 경로의 대응 필요 | 정의가 바뀌면 기존 계약과 구별할 버전 제시 |

현재 잠정 실측에서 A1→A2는 +x와 다릅니다.
따라서 두 앵커 방향을 직교 축으로 간주할 수 없습니다.
서버가 다른 좌표계를 유지해야 하면 변환을 합의합니다.
단순히 좌표계 이름만 바꾸어 처리하지 않습니다.
이유: 같은 숫자가 다른 위치를 가리킬 수 있습니다.

2026-09-13 조회에서 배치 차이를 확인했습니다.

| 앵커 | 서버 x, y, z (m) | 우리 잠정 기록 x, y, z (m) |
|---|---|---|
| A1 | 0.01, 0.06, 2.10 | 0.00, 0.00, 2.20 |
| A2 | 4.91, 0.00, 0.00 | 5.810, -0.430, 2.20 |
| A3 | 0.01, 19.99, 0.00 | 0.00, 4.630, 2.20 |
| A4 | 5.00, 4.95, 2.10 | 6.110, 4.357, 2.20 |

우리 기록도 독립 검증 전 잠정값입니다.
이 표를 즉시 서버·태그에 적용하라는 요청은 아닙니다.
최종 검증 좌표와 적용 절차를 함께 맞춰 주세요.
조회 당시 `anchor_layout_valid=false`였습니다.
무효 사유는 응답에 없었습니다.
근거: [실제 연결 시험](../report/platform_connection_20260913.md).

### W03~W06. 표시 의미

화면의 정상 표시는 실제 확인한 범위에 한정합니다.

| 값·상태 | 표시 원칙 |
|---|---|
| `anchor_layout_version=4` | 4-anchor 형식 버전. 좌표 개정 번호가 아님 |
| 서버·태그 배치 ID | 각각 보존. 적용 확인 뒤 일치 여부 표시 |
| UWB `x`, `y` | 태그 수평 관측. PX4 EKF 위치로 이름을 바꾸지 않음 |
| 향후 PX4 위치 | 별도 출처·좌표계·기체 기준점으로 정의 |
| `fix`, `telemetry_verified` | 관측 유효성. 비행 가능·EKF 융합 완료가 아님 |
| 센서 없음 | null/생략. 위치 0, 배터리 0으로 대체하지 않음 |
| `sent_at_ms`, `uwb_age_ms` | 송신 시각과 관측 나이를 분리 |
| 센서만 단절 | 웹 연결은 유지돼도 위치를 무효·오래됨으로 표시 |
| 수신 목표와 실행 목표 | 서버 요청값과 기체가 수락한 값을 구분 |
| 제어 불가 상태 | 목표 수신 가능과 실제 실행 가능을 구분 |

현재 서비스는 통신 전용입니다.
`companion_mode=communication_only`를 송신합니다.
`flight_control_enabled=false`도 송신합니다.
두 이름은 아직 서버 계약에 없는 추가 필드입니다.
공식 필드명·값 또는 동등한 표시 방법을 제시해 주세요.
미상 FC 상태를 `disarmed`로 단정하지 않도록 요청합니다.

### W07~W10. 임무와 요청 식별

반복 조회나 화면 갱신이 새 실행을 만들면 안 됩니다.
이유: 같은 임무를 처음부터 다시 실행할 수 있습니다.

| 필요한 의미 | 기존 필드·현재 상태 | 요청 |
|---|---|---|
| 기체 | `drone_id` | 현재 5번의 실제 1호기 배정 확인 |
| 임무 | `mission_db_id`, `mission_code` | 두 값의 의미와 필수 여부 유지 |
| 전체 경로 | `route_revision` | 내용이 같으면 유지. 변경 시 새 값 |
| 좌표 문맥 | `coordinate_frame`, `anchor_layout_id` | 경로가 어느 축·배치 기준인지 명시 |
| 개별 작업 | `route_tasks[].id`, `type`, x·y | 지점 순서·단일 목표·scan 예시 |
| 복귀·착륙 요청 | `control_request_id`, `control_requested_at` | 반복 GET에서 동일 값 유지 |
| 목표 수락 결과 | v1에 전용 계약 없음 | 임무·개정·배치에 연결된 수락/거부 결과 추가 |
| 만료·동시 요청 | v1에서 미합의 | 유효기간·우선순위·재연결 처리 합의 |
| 프로세스 재시작 | 송신 순번이 처음부터 시작 가능 | 예전 상태와 새 세션의 구별 방법 |

field 이름은 상대 구현에 맞춰 제안해 주세요.
여기서는 의미와 대응 관계를 요청합니다.
우리 ROS2 topic 이름을 외부 API 이름으로 강제하지 않습니다.
웹 기체 ID와 `ROS_DOMAIN_ID`는 별도 값입니다.

### W11. 비행 중 목표 변경과 중지

v1에서는 비행 중 경로 교체를 비활성화해 주세요.
이는 기존 계약의 제한을 화면에도 반영하는 요청입니다.

| 상황 | 요청할 계약 |
|---|---|
| 새 경로 입력 | 실행 가능한 상태에서만 적용. 수락 전에는 대기 표시 |
| `status=HOLD` | 서버의 임무 보류인지 실제 기체 정지 요청인지 구분 |
| `status=CANCEL` | 미실행 요청 취소와 실행 중 임무 중단을 구분 |
| 복귀 | 요청 수락과 실제 복귀 완료를 별도 표시 |
| 착륙 | 요청 수락과 실제 착지·시동 해제를 별도 표시 |
| 비행 중 경로 변경 | 후속 계약으로 허용 상태·전환·거부·복구를 먼저 정의 |

HOLD 응답만으로 기체가 멈췄다고 판단하지 않습니다.
이유: 현재 ZIP은 이동 중 HOLD에도 이동 상태를 유지합니다.
기체의 실행 가능 상태와 실제 정지 보고가 필요합니다.
물리적인 정지·복귀·착륙 방법은 우리 비행 계층에서 정합니다.

### W12. 고도와 방향 지시

고도·방향 목표와 그 목표의 제어 방법을 분리합니다.

| 항목 | 요청 |
|---|---|
| `current_z_m` | 검증한 PX4 현재 고도 표시 |
| 경유지 z·`mission_target_alt_m` | 임무의 희망 고도 조건. 현재 고도나 관측값으로 사용하지 않음 |
| 수평 목표 단계 | z 미지원/null 허용 방식 또는 PX4가 관리하는 고정 운용 조건을 합의 |
| 미지원 고도 명령 | 조용히 성공 처리하지 않고 거부·보류 표시 |
| `yaw_policy` | 9월 13일 응답의 고정 방향 값에 대해 의미·선택 여부·미지원 처리를 명시 |

우리 companion은 고도 PID·자세 제어를 작성하지 않습니다.
이유: PX4가 해당 제어를 담당하는 구조입니다.
UWB의 z 자리값 0을 실제 고도로 보내지 않습니다.
이유: UWB는 수평 관측만 제공합니다.

## 5. 추가 요청: 재고 결과와 운영 연결

QR 결과와 운영 연결도 Platform의 역할에 포함됩니다.

| ID | 우선순위 | 요청 내용 | 필요한 회신 |
|---|---|---|---|
| W13 | 첫 연동 | 접속 주소·5번 기체 배정·장치 인증 설정 확인 | 현재 서버 주소. 장치 키 발급 방식. 미서명/서명 오류 예시 |
| W14 | 재고 연동 | QR 원문·임무·라벨·스캔 ID 연결을 유지 | 수락·거부·중복 재전송 예시. 최종 재고 집계 규칙 |
| W15 | 후속 운용 | 현재 Wi-Fi 직접 연결과 향후 지상국 경유를 구분 | LoRa 운용 때 별도 송신률·연결 만료 시간·중계 장치 식별 규칙 |

W14의 스캔 저장과 재고 집계는 다른 처리입니다.
같은 QR의 새 판독 ID는 별도 관측이 될 수 있습니다.
이를 재고 수량으로 어떻게 합치는지 알려 주세요.
`accepted:false` 저장 성공을 스캔 수락으로 표시하지 않습니다.
이유: 업무 거부 결과를 저장한 성공 응답이기 때문입니다.
QR 로컬 저장 후 다음 지점 진행 여부도 별도 운영 합의입니다.

W15는 이번 Wi-Fi 시험의 선행 조건이 아닙니다.
현재 HTTP·WS 계약과 10Hz 목표는 Wi-Fi 시험에 적용합니다.
LoRa에 같은 송신률을 그대로 요구하지 않습니다.
이유: LoRa는 저대역폭 요약 채널입니다.

## 6. 요청하는 전달 자료와 완료 판정

서버 동작을 확인할 예시를 함께 보내 주세요.

| 순서 | 전달 자료 | 양 팀이 확인할 완료 조건 |
|---|---|---|
| 1 | W01~W15 수락·대안·지원 시점 회신 | 기합의 사항과 변경 사항 구별 |
| 2 | 갱신 계약 버전과 필드 표 | 기존 1.0과 바뀐 의미를 식별 |
| 3 | 전체 GET 예시 | 임무 없음·한 점·다점·보류·취소·복귀·착륙 구분 |
| 4 | WS 수락 예시 | 통신 전용·센서 없음·XY-only·PX4 상태 표시 구분 |
| 5 | 결과 보고 예시 | 목표 수락·거부·실행 완료·실패·오래된 요청 구분 |
| 6 | 좌표 검증 예시 | 원점과 +x·+y의 1m 점이 화면·API에서 일치 |
| 7 | 단절·복구 예시 | 연결과 센서 최신성 분리. 과거 요청 재실행 방지 |
| 8 | QR 결과 예시 | 수락·거부·같은 ID 재전송과 임무/라벨 연결 확인 |

위 완료 판정은 웹 연동 계약의 검증입니다.
실제 비행 성능 합격과는 별도로 기록합니다.
우리 팀은 ROS2 값 변환·목표 검증·비행 연결을 담당합니다.
상대 팀에는 서버·화면의 계약과 결과 확인을 요청합니다.
