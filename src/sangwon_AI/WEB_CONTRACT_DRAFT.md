# 웹↔Jetson v1 확장 계약 초안
이 문서는 데이터·명령·결과의 의미를 정한다.
웹과 Jetson의 API 확장을 합의할 때 읽는다.

> 2026-10-04 외부 계약 검토 기준: [웹 전체 개편 요청서 r2](WEB_REDESIGN_REQUEST_2026-10-04.md)와 [draft.4 예제](contracts/web_v1_1_draft4/README.md)를 먼저 읽는다.
> 이 문서의 draft.2/부분 예제는 이전 근거다. 새 웹 개발에 혼용하지 않는다.

상태: 의미 계약 초안 / 2026-10-02.
기준: [설계](DESIGN.md), [웹 개발 요청서](WEB_REQUIREMENTS.md).
사용자는 기존 v1 확장 방향을 선택했다.
신규 필드명·상태명·URL·버전 번호는 제안이다.
구체적인 JSON·코드·버전 제안은 [WEB_JSON_DRAFT.md](WEB_JSON_DRAFT.md)에 작성했다.
웹팀이 수락한 최종 JSON Schema와 실행 코드는 아직 없다.
2026-10-04 보완: [QR_SCAN_SPEC.md](QR_SCAN_SPEC.md)의 QS-W1~W8을 추가 협의한다.
스캔 결과 저장→접근 대기점 복귀→다음 목표 진행과 임무의 부분 실패 표시를 계약에 포함해야 한다.
기존 draft.2를 scan 지원 계약으로 간주하지 않는다.
대조 자료: [기존 v1 계약](../../docs/hw_handoff/platform_api_v1/companion_platform_api_contract_v1.md),
[v1 검토 결과](../../docs/companion_platform_api_v1_review.md).

## 1. 기존 연결점과 확장 범위

기존 통신 구조에 필요한 의미를 추가한다.

| v1 연결점 | 유지할 역할 | 확장할 의미 |
|---|---|---|
| GET /api/drones/{drone_id}/companion-mission/ | 임무·요청 조회 | 전체 임무 묶음, 준비 결과 참조, 명령 문맥 |
| WS /ws/drones/{drone_id}/ | Jetson→서버 최신 상태 | 실행·비행·연결 세션, 실제 목표·품질 |
| POST /api/drones/{drone_id}/companion-phase/ | 단계 보고 | 사건 ID·원인·최종 결과 |
| POST /api/drones/{drone_id}/control-action/ack/ | 제어 수락 보고 | 수락·거부·실행 결과 연결 |
| POST /api/drones/{drone_id}/launch-snapshot/ | 출발점 등록 | 실제 이륙 기록·방향·변환본·비행 ID |

WS는 v1의 상태 송신 채널로 취급한다.
명령을 WS로 보내는 새 경로는 가정하지 않는다.
지도 다운로드·결과 조회 URL은 별도 협의한다.
기존 단일 control_action 필드를 덮어써서
미처리 요청이나 긴급 착륙을 잃지 않아야 한다.
요청 대기열·순서 번호의 전송 형식은 서버와 정한다.

새 의미를 기존 contract_version=1.0에 숨기지 않는다.
확장 버전과 지원 기능을 양측이 확인해야 한다.
미지원 제어 행동·필수 기능은 거부한다.
선택 진단 필드의 생략은 계약대로 허용할 수 있다.
이 구분은 구형 클라이언트의 부분 실행을 막는다.

## 2. 식별자와 버전

임무 정의와 한 번의 실행을 구분한다.

| 의미 | 형식·출처 | 규칙 |
|---|---|---|
| 기체 | v1 drone_id | 요청 대상과 접속 장치가 일치 |
| 임무 정의 | v1 mission_db_id·mission_code | 정수 DB ID와 문자열 코드 의미 유지 |
| 경로 개정 | v1 route_revision | 같은 값의 내용은 불변 |
| 지도 개정 | 지도 ID·개정 | 임무와 연결해 고정 |
| 좌표 변환 | 프레임·변환 ID·개정 | 지도·기체 설정과 호환 확인 |
| 임무 실행 | 신규 실행 ID 제안 | 새 시작 요청의 최초 수락마다 생성, 재시도로 변경하지 않음 |
| 물리 비행 | 신규 비행 ID 제안 | 실제 이륙~착륙 기록 연결. RC 이륙도 포함 |
| 명령 | v1 control_request_id | 같은 ID는 같은 대상·내용, 재시도해도 유지 |
| 사건 | 신규 사건 ID·순서 제안 | 재전송 시 같은 사건으로 저장 |
| 장치 부팅 | boot_id | Jetson OS 부팅마다 새 값, 서버 재접속과 구분 |
| 실행기 세션 | companion_session_id | 핵심 실행기 기동마다 새 값, 같은 OS 부팅에서 재기동해도 변경 |
| 제어 세션 | control_session_id | 새 연결 문맥 확인 뒤 사용, 미수락 과거 명령 재할당 금지 |
| 준비 검증 | preparation_id·readiness_revision | 임무 검증본과 현재 허가 상태를 START에 고정 |

비행 ID와 실행 ID의 발급자는 Jetson으로 제안한다.
지상에서 거부한 시작은 물리 비행을 만들지 않는다.
RC 예외 인계는 이미 기록 중인 비행에 연결한다.
서버가 새 접속을 새 비행으로 판단하지 않는다.

## 3. 임무 묶음

전체 자료가 검증되기 전에는 이륙하지 않는다.

| 자료 | 필요 정보 | 검증 |
|---|---|---|
| 공통 | 계약·기체·임무·경로 개정 | 지원 버전, 대상 일치 |
| 지도 참조 | 지도 ID·개정·내용 확인값 | 완전 수신·같은 내용 확인 |
| 좌표 기준 | 직교 축·원점·길이 단위·변환본 | 검증본과 일치 |
| 이륙 | 별도 목표 z, 선택 시작 yaw | 출발점 수직 공간·회전 가능 |
| 이동점 | 고유 ID·순서·기체 XYZ·선택 yaw·호버 초 | 모든 기체 점과 사이 구간 유효 |
| scan 작업 | 고유 작업/라벨 ID·순서·라벨 XYZ·정면·마커/QR 배치 | 도출한 기체 접근/판독 위치·작업 공간·이탈 경로 검증, 별도 확장 계약 필요 |
| 라벨별 허용 구역 | 웹 제공 구역 ID/개정·외곽·z 범위·기하 의미·경로 연결·승인 참조 | 기체 이동 공간 검증, 일반 우회 경계와 구분. QS-W8 형식 협의 |
| 임무 확인 | 상부 확인·방향 확인·검증 구역 참조 | 해당 임무·지도·기체에 적용 가능 |

화면 저장 → 자료 수신 → 준비 검증 → 시작 요청 → 실행으로 나눈다.
준비 검증 성공만으로 기체를 시동하지 않는다.
시작을 적용할 때 상태와 자료 버전을 다시 검사한다.
운영자 확인을 묶음에 넣는 구체 형식은 웹과 정한다.
방향 검증 구역·변환본은 비행 담당자의 실측 승인 자료다.
웹은 그 자료를 보관하고 참조한다.
현재 방향·상부 공간 확인은 임무 시작 때의 운영자 확인이다.
두 확인을 실측 승인 자료의 대체값으로 쓰지 않는다.

부분 수신본으로 누락 필드를 채워 실행하지 않는다.
실행 중에는 수락한 임무·지도·승인본을 고정한다.
새 개정은 다음 임무용으로 검증·저장할 수 있다.
같은 개정인데 내용이 다르면 충돌로 거부한다.
내용 확인값의 해시·정규화 규격은 협의 항목이다.

## 4. 좌표와 지도 자료

목표 좌표와 센서 관측의 출처를 명시한다.

| 값 | 의미 | 주의 |
|---|---|---|
| 웹 x/y | 웹 도면의 직교 좌표, m | 승인된 변환으로 제어 좌표에 연결 |
| 이동점 z | 공통 바닥→기체 중심/PX4 기준점, m | 기준점 차이는 장착 변환으로 반영 |
| scan XYZ | 지도상의 QR 라벨 위치, z는 공통 바닥→라벨, m | 직접 PX4 목표 금지. 라벨 방향·거리·장착 변환으로 기체 pose 도출 |
| 라벨 정면 | 라벨에서 판독 가능한 통로 쪽 방향 | 웹 협의 후 확정. 선택 기체 yaw와 혼용 금지 |
| yaw | 지도 절대 방향 | 0°·부호·단위는 웹 회의에서 확정 |
| yaw 없음 | 기본 방향 선택 | 숫자 0과 구분 |
| 시작 화살표 | 현재 기체 방향 확인 | 목표 yaw나 변환 보정값으로 사용하지 않음 |
| PX4 융합 위치 | 실제 제어용 위치를 지도에 환산 | 유효성·프레임·변환 버전 함께 송신 |
| UWB 관측 | 별도 센서 관측 | 기존 v1 x/y 의미와의 대응 명시 |

측정하지 않은 값은 null 또는 미지원으로 보낸다.
0은 실제 숫자이며 누락의 대체값이 아니다.
웹 픽셀 좌표를 그대로 비행 좌표로 사용하지 않는다.
UWB 변환 수치는 사용자 결정에 따라 보류한다.

| 지도 항목 | 의미 계약 | 거부 조건 |
|---|---|---|
| 장애물·선반 | 외곽, 점유 z 하한·상한 | 형상·높이 누락, 자기 교차 등 잘못된 형상 |
| 천장·상부 구조 | 외곽, 아래면 및 점유 z | 고도 검사 대상의 형상 불명 |
| z 제한 구역 | 외곽, 기체 기준 최저·최고 z | 최저>최고, 통과 구역의 제한 자료 없음 |
| 비행 가능 경계 | 제공 상태와 외곽 | 없으면 자동 우회 비활성 |
| 금지 구역 | 제공 상태와 영역·높이 범위 | 미제공을 '금지 구역 없음'으로 해석 금지 |
| yaw 검증 구역 | 승인 영역·근거·관련 버전 | 출발·경유·복귀 경로가 영역 밖 |

길이·각도·시간 값은 유한한 수여야 한다.
무한대·NaN·음수 호버 시간은 입력 오류다.
경유점 ID 중복과 잘못된 순서도 전체 거부 사유다.
잘못된 경유점만 삭제하면 필수 방문 요구를 잃기 때문이다.
XY/Z 도착 허용 오차는 실측 승인값을 사용한다.
기존 예시의 arrival_radius_m=0.2를 승인값으로 승격하지 않는다.
웹이 보낸 허용치가 승인 범위를 벗어나면 거부한다.

웹은 물리 장애물 형상을 제공한다.
Jetson이 기체 외형·측위 오차·제동 거리를 더한다.
웹에서도 같은 여유를 더했다면 중복 적용 여부를 명시한다.
z 제한은 기체 기준점의 허용 범위다.
물리 장애물 높이와 혼용하지 않는다.

## 5. 명령 수락과 중복 처리

재전송으로 같은 동작을 다시 시작하지 않는다.

| 명령 공통 정보 | 용도 |
|---|---|
| 요청 ID·기체 ID·행동 | 같은 요청 식별·대상 확인 |
| 임무·경로 개정 | 다른 경로에 요청 적용 방지 |
| 실행·비행 참조 | 이전 비행의 취소·착륙 요청 차단 |
| 생성·만료 시각 | 오래된 미수락 요청 처리 |
| 제어 세션·순서 | 재연결·역순 명령 판정 |

최종 필드명과 명령별 필수 참조는 웹과 정한다.
새 지상 시작은 준비 검증 문맥에 연결한다.
RC 인계 시작은 현재 비행 참조에도 연결한다.

| 수신 상황 | Jetson 처리 |
|---|---|
| 같은 ID·같은 내용 재수신 | 기록한 처리 결과 반환, 다시 실행하지 않음 |
| 같은 ID·다른 내용 | 요청 충돌로 거부 |
| 다른 비행·임무 대상 | 오래된 제어 문맥으로 거부 |
| 만료·미지원 행동·검증 실패 | 이유와 관련 항목 반환 |
| 진행 중 새 임무 시작 | 바쁨으로 거부, 자동 예약하지 않음 |
| 상위 비상 동작이 요청을 선점 | 선점 결과와 실제 진행 상태 보고 |
| 복귀·착륙 중 일시정지·재개 | 해당 단계에서 허용하지 않는 요청으로 거부 |

반복 GET은 요청 생성·만료 시각을 바꾸지 않는다.
v1 return_to_home과 이번 취소·복귀 의미의 대응도 확장 표에 명시한다.
명령 수락 기록과 결과 재전송은 행동 전환 뒤에도 남긴다.
결과 통신 실패만으로 기체 동작을 반복하지 않는다.
기록과 실제 출력 사이 재시작이 생기면 실행 여부를 확인한다.
확인되지 않은 시작·재개를 자동 재실행하지 않는다.
Jetson 재시작 뒤 같은 비행의 자동 임무 재개는 금지다.
기존 결정에 따라 착륙 후 새 임무만 허용한다.

요청 대기열 때문에 긴급 착륙이 일반 요청 뒤에 묻히지 않아야 한다.
Jetson의 제어권·비상 우선순위를 마지막에 적용한다.
웹 긴급 착륙도 RC 인계 뒤 제어권을 강제로 회수하지 않는다.
수락 불가 사유와 현재 제어권을 화면에 반환한다.
복귀·착륙 진입 뒤에는 낮은 우선순위 명령으로 임무를 되살리지 않는다.
복귀 중 긴급 착륙은 현 위치 착륙으로 전환할 수 있다.
이미 착륙 중 같은 의미 요청은 착륙 절차를 다시 시작하지 않는다.

신규 명령 수락은 생성 후 10초를 초기 시험값으로 사용한다.
이미 수락한 명령의 실행·결과 조회에는 이 기한을 적용하지 않는다.
허용 시계 오차·단절 감지 한도는 실측 전이다.
연결 단절 중 미전달 요청은 재연결 뒤 자동 실행하지 않는다.
운영자가 현재 상태를 확인한 뒤 새 요청을 만든다.
수락 여부가 불명확하면 기존 요청 결과를 먼저 조회한다.
단절 감지·재연결 뒤 제어 세션을 새로 확인하는 방식을 제안한다.
이전 세션의 미수락 요청은 실행하지 않고 만료 결과를 돌려준다.
진행 중 임무는 이 절차와 무관하게 계속 수행한다.
단절 감지 전 지연 요청도 있으므로 유효시간을 함께 검사한다.

## 6. 실행 상태와 결과

명령 결과·임무 결과·기체 상태를 각각 기록한다.

| 구분 | 제안 상태 | 판정 주체 |
|---|---|---|
| 명령 | 전송 대기 / 결과 미확인 / 수락 / 거부 / 실행 완료 / 실행 실패 / 선점 | Jetson 결과와 서버 수신 사실 |
| 임무 단계 | 준비 / 이륙 / 이동 / 호버 / 일시정지 / 장애물 대기 / 복귀 / 착륙 / 종료 | Jetson 행동 상태 |
| 임무 최종 결과 | 성공 / 취소 / 실패 / 수동 인계 | Jetson의 완료·중단 원인 |
| 기체 | PX4 모드·시동·착륙·제어권 | PX4와 제어권 감시 |
| 로그 | 수집 대기 / 수집 중 / 검증 완료 / 실패 | Jetson 로그 수집기 |

위 이름은 전송할 상태 코드의 확정값이 아니다.
임무 단계와 결과는 별도 필드로 제안한다.
성공은 모든 필수 방문·복귀·착륙 확인 뒤 판정한다.
취소나 저전력으로 착륙해도 임무 성공으로 바꾸지 않는다.
착륙 확인은 실제 landed 상태와 disarm을 함께 검증한다.
공중 disarm을 정상 착륙으로 처리하지 않기 위해서다.
RC 인계는 임무 중단이며 기체는 계속 비행 중일 수 있다.
로그 수집 실패는 완료한 비행의 결과를 바꾸지 않는다.

| 명령 | 수락 뒤 진행 | 해당 명령의 완료 |
|---|---|---|
| 시작 | 준비→이륙/인계→경유점→복귀→착륙 | 임무의 최종 결과 |
| 일시정지 | 진행 보존→감속·정지 | 유효한 위치 유지 확인 |
| 재개 | 상태·경로 재검사→진행 | 재개 전환 확인, 임무는 계속 |
| 취소 | 지상 준비 중단 / 상승 중 현 위치 착륙 / 임무 중 복귀·착륙 | 지상 종료 또는 착륙 확인, 임무 결과는 취소 |
| 긴급 착륙 | 현재 위치 Land 요청→착륙 | 실제 착륙 확인 |

아직 지상 준비 중이면 취소 뒤 이륙하지 않는다.
시동 상태까지 확인한 뒤 지상 취소 완료를 보고한다.
상승 중 취소하면 목표 이륙 높이 도달을 기다리지 않고
현재 위치에서 PX4 Land를 요청한다.
이륙하지 않은 취소는 비행 성공으로 기록하지 않는다.

일반 이동점은 기체 XYZ·방향 안정과 지정 호버를 확인한다.
scan은 검증된 기체 접근점 도착, 정렬·판독 결과 저장, 대기점 복귀를 별도 기록한다.
라벨 XYZ 통과를 요구하지 않고 판독 실패도 성공으로 표시하지 않는다.
활성 목표 번호가 바뀐 것만으로 방문 완료를 만들지 않는다.
착륙·복귀 같은 후속 동작이 아직 진행 중이면
중간 실패 원인과 현재 단계를 함께 보고한다.

## 7. 상태·사건·오류 보고

현재 화면은 최신 상태로, 이력은 사건으로 복구한다.

| 메시지 | 최소 의미 |
|---|---|
| 최신 상태 | 기체·실행·비행·세션, 순서·생성 시각, 각 관측 나이 |
| 임무 진행 | 임무/경로/지도 개정, 활성 경유점, 실제 목표 종류·좌표 |
| 제어 상태 | PX4 모드·시동·착륙, 제어권, 시작 가능 여부·이유 |
| 사건 | 사건 ID·실행·비행, 이전/다음 단계, 원인·시각 |
| 요청 결과 | 요청 ID·결과·실제 단계·사유·관련 경유점/필드 |
| 기록 상태 | 로그 수집 상태·남은 보존 시간·새 비행 기록 가능 여부 |

복귀 중 실제 목표는 홈 또는 복귀 경로점이다.
화면이 이전 임무 경유점을 현재 목표로 표시하지 않는다.
센서 측정 시각·Jetson 수신 시각·웹 수신 시각은 구분한다.
서로 다른 시계를 그대로 빼서 지연을 계산하지 않는다.

| 사유 예시 | 화면에 필요한 설명 |
|---|---|
| HEADING_UNALIGNED | 방향 확인 불일치, 재측량·센서 점검 |
| 지도/개정 불일치 | 어떤 자료 버전이 다른지 |
| 경로 검증 실패 | 해당 경유점·구간·구역과 이유 |
| 미지원 행동 | 지원하지 않는 임무 동작 |
| 제어권 없음 | RC 또는 PX4 비상 동작이 제어 중 |
| 기록 공간 부족 | 새 비행 거부, 공간 복구 필요 |
| 명령 충돌·만료 | 요청 ID·문맥과 재요청 필요 여부 |

오류 코드 문자열은 WEB_JSON_DRAFT.md의 목록을 구체안으로 검토한다.
동작 거부와 단순 경고를 같은 오류로 처리하지 않는다.

## 8. 단절·재연결·결과 보관

받은 임무를 수행하는 동안에도 웹 상태는 미확인일 수 있다.

| 상황 | 처리 |
|---|---|
| Wi-Fi 상실 | Jetson은 받은 임무 지속, 웹은 관측 단절 표시 |
| 상태 메시지 지연 | 마지막 값·나이를 표시, 실시간으로 단정하지 않음 |
| 명령 ACK 유실 | 같은 요청 ID 결과 조회, 신규 요청으로 중복 실행 금지 |
| 단절 중 미전달 명령 | 재연결 때 자동 실행 금지, 상태 대조 후 새 요청 |
| 사건 재전송 | 같은 사건 ID로 중복 저장 방지 |
| WS 재연결 | 현재 상태 1건으로 동기화, 오래된 위치 묶음 전송 금지 |
| 서버 재시작 | 저장한 명령·결과 이력과 Jetson 상태 대조 |
| Jetson 재시작 | 새 세션 표시, 이전 비행 자동 재개 금지 |

결과 보고는 임무 단계가 바뀌어도 재시도할 수 있어야 한다.
과거 요청의 결과라는 이유만으로 유효한 이력을 버리지 않는다.
알 수 없는 요청·다른 기체의 결과는 별도로 거부한다.
HTTP 2xx라도 본문 업무 결과가 실패면 성공 처리하지 않는다.
영구 거부와 일시 통신 실패의 재시도 규칙을 정한다.

72시간 로그 삭제와 명령 처리 이력은 구분한다.
로그 삭제로 과거 시작 요청이 다시 실행되면 안 된다.
명령·사건 이력 보존 기간과 정리 조건은 서버와 확정한다.
웹 단절 상태의 긴급 착륙 전달은 보장하지 않는다.
화면은 실제 수락·완료 응답만 확인 상태로 표시한다.

## 10. 자동 기동과 준비 상태의 의미

기동 자체는 비행 승인 사건이 아니다.
Jetson은 자동 연결과 자체 점검을 실행하고, 웹의 새로운 START를 기다린다.
기존에 저장된 START·READY·ACTIVE가 있어도 새 실행기에서 재비행하지 않는다.

| 층 | 상태 제안 | 판정 범위 |
|---|---|---|
| 부팅 단계 | BOOTING / CONNECTING / CHECKING / RUNNING / FAULT | 서비스 초기화·연결·검사 진행 |
| 시스템 준비 | CHECKING / READY / NOT_READY / FAULT | 프로파일에 등록된 필수 장치·연결·설정·기록·감시 경로 |
| 임무 준비 | NO_MISSION / CHECKING / READY / NOT_READY / BUSY | 특정 snapshot의 경로·승인·현재 기체·제어권·출발 기록 |
| 체크 하나 | PASS / FAIL / UNKNOWN / WARN | 원인, 관측 출처·나이, 실제 시작 차단 여부 포함 |
| 웹 연결 표시 | LIVE / STALE / OFFLINE | 서버/브라우저가 별도로 계산하는 관측 신선도 |

시스템 READY는 임무 시작 승인을 뜻하지 않는다.
REPLAY/SITL 시스템 READY를 FLIGHT READY로 표시하지 않는다.
미구현 UWB 또는 아직 승인되지 않은 FLIGHT 설정은 UNKNOWN/FAIL로 남는다.
필수 체크가 UNKNOWN이면 해당 준비 층은 READY가 될 수 없다.
선택 기능의 WARN은 경고 문구와 사용 불가 기능을 함께 표시한다.
체크의 required/blocking 분류는 기체 프로파일과 Jetson 정책에서 정하며 웹 사용자 설정으로 낮추지 않는다.

### 10.1 준비 상태 수명

준비는 현재 관측에 따른 짧은 권한이다. 파일에 저장된 영구 승인으로 쓰지 않는다.
준비 신선도 한도는 프로파일로 전달하며 START의 10초 수락 유효시간과 독립이다.
START가 10초 안에 도착해도 그 사이 준비가 무효화됐으면 거부한다.

1. Jetson은 같은 부팅/실행기에서 증가하는 readiness_seq로 체크 스냅샷을 보고한다.
2. 허가에 영향을 주는 체크 상태·지도·승인·기체 설정·제어 문맥 변경 시 readiness_revision을 증가시킨다.
3. 특정 임무 검증 통과 시 preparation_id를 발급하고 snapshot_id·변환·프로파일·두 준비 층·제어 세션과 묶는다.
4. READY 상실이나 문맥 변경 시 preparation_id를 무효화한다. 복구 뒤 검증을 통과하면 새 ID를 발급한다.
5. 단순 정상 heartbeat는 readiness_seq만 증가할 수 있다. 매 heartbeat마다 시작 버튼의 준비 ID가 바뀌어야 한다는 뜻은 아니다.
6. START는 웹이 본 boot_id·companion_session_id·control_session_id·preparation_id·readiness_revision을 담는다.
7. Jetson은 수락 직전에 최신 필수 상태와 준비 문맥을 다시 확인한다. 웹 버튼 상태만 신뢰하지 않는다.

단절·재연결 시 기존 preparation_id의 제어 세션 결합을 폐기한다.
현재 상태 대조와 새 세션 확인 뒤 준비를 재검증한다.
이미 비행 중인 수락 임무에는 새 START를 요구하지 않으며 저장 임무 계속 정책을 유지한다.
실행기 재기동 시 이전 준비 ID는 무효다. 복구된 원장 결과 조회와 실제 재실행을 구분한다.

### 10.2 오래된 정상 화면 방지

서버는 생성 시각, 기체에서 계산한 source_age_ms, 자신이 받은 시각을 각각 보존한다.
서버 캐시를 브라우저에 다시 보냈다는 이유로 기체 관측 시각을 갱신하지 않는다.
동일 세션의 sequence가 낮거나 같은 재전송은 최신 준비 상태를 덮어쓰지 않는다.
서로 다른 장치의 단조 시각을 직접 빼지 않는다.
시계 신뢰성이 없는 경우 새 START는 CLOCK_UNTRUSTED, 화면은 신선도를 확인할 수 없음으로 표시한다.
웹은 원천 관측 나이와 전송·캐시 경과 시간을 포함한 신선도를 확인할 수 있을 때만 READY를 표시한다.
구체 임계값은 승인된 프로파일로 전달한다. 수신 간격만 보고 무조건 정상으로 계산하지 않는다.

개별 체크에는 check_id, required, status, blocking, code, reason, operator_action,
source, last_seen_at, source_age_ms, max_age_ms, check_seq를 둔다.
관측이 한 번도 없으면 last_seen_at와 source_age_ms는 null이며 UNKNOWN이다.
진단 신호 하나가 최신이어도 그 신호가 참조하는 센서 값이 오래되면 PASS를 유지하지 않는다.

### 10.3 준비 완료 알림

SYSTEM_READY와 MISSION_READY는 서로 다른 사건으로 저장한다.
READY_REVOKED는 어느 준비 층이 해제됐는지와 원인을 포함한다.
동일 event_id 재전송은 재알림하지 않는다.
브라우저 재접속 때 오래된 MISSION_READY 사건을 수신해도 현재 배지를 READY로 바꾸지 않는다.
현재 배지는 최신 준비 스냅샷으로만 결정하고 이력 사건은 과거 시각을 표시한다.
현장 LED/부저 장치는 아직 미확정이며 웹의 준비 상태를 임의 비행 동작으로 대신하지 않는다.

준비 상태 신규 연동 시험은 [웹 전달 패키지](WEB_HANDOFF.md)의 WH01~WH12를 따른다.
