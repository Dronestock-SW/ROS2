## 2. 확정된 임무 동작

웹은 임무와 허용 범위를 제공하고 Jetson은 기체 목표를 계산한다.
PX4가 비행 제어를 실행한다.

```text
웹: 이동점 + 라벨 작업 + 지도/허용 구역
  -> Jetson 전체 검증 -> 임무 READY -> 새로운 START
  -> 이륙 -> 이동점 방문 -> 접근 대기점 도착
  -> 검증된 접근 -> ArUco 정렬 -> 정지·호버 안정
  -> 스캐너 최대 3회 -> 모두 실패하면 카메라 QR 판독
  -> 성공/실패 결과 로컬 저장
  -> 접근 대기점 복귀·정지 확인 -> 다음 목표
  -> 마지막 작업 후 출발점 복귀 -> PX4 착륙
```

| 상황 | 확정 동작 | 웹 표시 |
|---|---|---|
| 스캐너 성공 | 남은 스캐너 시도·카메라 QR 생략 | 성공 장치·시도 횟수 |
| 스캐너 3회 실패 | 카메라 QR로 전환 | 카메라 판독 중 |
| 최종 판독 실패 | 실패 기록·대기점 복귀·다음 목표 | 해당 라벨 실패, 다음 목표 진행 |
| 마커 획득 한도 실패·카메라 고장 | 비행·이탈 경로 정상 시 실패 기록·대기점 복귀·다음 목표 | 판독 실패와 원인 구분 |
| 이탈 차단·비행 위치 상실 | 기존 이동/비상 정책 적용 | 다음 작업 완료로 처리하지 않음 |
| RC 수동 인계 | Jetson 출력 권한 반환, 같은 비행 자율 재개 금지 | 수동 조종 중, 현재 PX4 모드 |
| Wi-Fi 단절 | 수락한 임무 계속, 결과 로컬 저장 | 통신 단절·마지막 확인 상태 |

ArUco 검출용 카메라는 정렬 시작부터 사용한다.
카메라 QR 디코딩만 세 번째 스캐너 실패 뒤 사용한다.
판독을 채택할 때는 호버 안정 조건을 만족해야 한다.
스캔 실패 후 진행은 비행·이탈 정상 조건에서만 가능하다.
비행 전 카메라 고장이 확인되면 스캔 READY를 거부한다.

## 3. UI·UX 변경 요청

화면의 첫 정보는 작업 이름·현재 단계·운영자 조치다.
내부 ID·개정·원천 시각은 상세 영역에 제공한다.
색상과 함께 텍스트·아이콘으로 상태를 구분한다.

### 3.1 지도·라벨 관리 화면

라벨 위치, 라벨 정면, 기체 목표를 따로 표시한다.

| 요소 | 변경 요청 | 입력 오류/미확정 처리 |
|---|---|---|
| 대상 추가 | ‘이동점 추가’와 ‘스캔 라벨 추가’ 분리 | 유형 없이 XYZ만 저장하지 않음 |
| 라벨 좌표 | 지도 XYZ와 라벨 기준점 표시 | ‘라벨 높이: 바닥 기준 m’ 문구 |
| 라벨 방향 | 라벨에서 통로 쪽 정면 화살표 편집 | 미지정은 ‘접근 방향 필요’ |
| 기체 방향 | 기체 yaw 화살표를 다른 모양으로 표시 | 라벨 정면을 기체 yaw로 복사하지 않음 |
| QR 연결 | 라벨 ID·기대 QR/품목 규칙·샘플 등록 | 다른 라벨 매핑·중복 연결 검사 |
| ArUco 연결 | dictionary·ID·크기·상대 배치 개정 참조 | 미수령은 ‘영상/기체 자료 대기’ |
| 허용 구역 | 라벨별 평면 다각형과 최저/최고 z 편집 | 자기 교차·높이 역전·누락 표시 |
| 주변 형상 | 선반·천장·장애물·금지 구역 중첩 표시 | 라벨 선택으로 장애물을 숨기지 않음 |
| 구역 연결 | 기존 비행 경로와 연결 지점을 지정/참조 | 연결 경로는 Jetson 검증 전 미확정 |
| 변경 관리 | 수정 내용을 새 지도/라벨/구역 개정으로 저장 | 사용 중 snapshot은 유지 |

라벨 기준점은 QR 중심 등 한 가지 정의로 합의한다.
정면 화살표의 각도·축·부호도 공동 확정한다.
마커 크기·장착 변환은 담당자가 실측해 제공한다.
웹팀에 해당 물리값의 추정을 요청하는 것은 아니다.

### 3.2 임무 편집·검증 화면

임무 목록에서 ‘방문할 기체 좌표’와 ‘스캔할 라벨’을 구분한다.

```text
[지도]                              [임무 순서]
기체 이동점 ○  라벨 ▣               1. 이동점 W01
기체 접근 대기점 ◇                  2. 라벨 L01 스캔
라벨 정면 화살표 / 허용 구역        3. 이동점 W02

[지도/입력 검증 요청]   [검증 결과]
                        라벨 방향: 확인 필요
                        작업 구역: 수신 완료 / 기체 경로 검증 대기
                        임무 준비: 시작 불가
```

| 요소 | 변경 요청 |
|---|---|
| 이동 작업 카드 | 기체 XYZ·선택 도착 yaw·hold_s 입력 |
| 스캔 작업 카드 | 라벨 선택·허용 구역·승인된 스캔 프로파일 참조 |
| 높이 설명 | 이동 z는 기체 높이, 스캔 z는 라벨 높이로 표시 |
| 순서 | 모든 작업 ID와 순서 보존. 잘못된 작업 자동 삭제 금지 |
| 경로 미리보기 | 웹 입력 경로와 Jetson 검증 경로를 다른 상태로 표시 |
| 스캔 위치 | Jetson 산출 대기점·기체 판독 목표·진입/이탈 구간 표시 |
| 방향/거리 | 기체 yaw와 센서 기준 판독 거리 표시. 40~60cm는 시험 범위임을 명시 |
| 검증 실패 | 해당 작업·필드·이유·운영자 조치를 표시하고 편집 위치로 이동 |
| 편집 후 | 기존 준비 결과를 새 편집본의 준비 결과로 사용하지 않음 |
| 실행 중 | 활성 임무는 읽기 전용. 별도 초안 편집과 다음 임무 준비만 가능 |

웹은 라벨에서 임의로 50cm 뺀 점을 비행 목표로 만들지 않는다.
기체 장착 오프셋과 방향·공간 검사가 필요하기 때문이다.
Jetson 검증 결과가 없으면 미리보기를 ‘검증 완료’로 표시하지 않는다.
`hold_s`와 스캔 안정 시간·판독 창은 별도 의미다.
미측정 판독 시간을 기존 호버 기본값으로 채우지 않는다.

### 3.3 점검·READY 화면

스캔 임무에 필요한 자료와 장치 상태를 준비 판정에 포함한다.

| 표시 묶음 | 포함할 확인 항목 |
|---|---|
| 기존 기체 준비 | PX4·위치·yaw·제어 경로·기록·명령 세션 |
| 영상/판독 준비 | 카메라·스캐너·ArUco 검출·교정 및 장착 개정 |
| 대상 준비 | 라벨 정면·QR/ArUco 매핑·대상 일치 규칙 |
| 공간 준비 | 라벨별 허용 구역·접근 대기점·진입/이탈·상하 여유 |
| 운용 프로파일 | 승인된 거리·정렬/호버 기준·유한한 작업 시간 |

실제 점검과 최종 READY는 Jetson이 판정한다.
웹은 PASS/FAIL/UNKNOWN/WARN과 차단 이유를 표시한다.
자료 등록 완료나 Python 진단 정상만으로 READY를 만들지 않는다.
스캔 체크의 정확한 check_id는 Jetson과 대응표로 합의한다.
원래 체크 의미를 바꾸거나 미구현 체크를 PASS로 채우지 않는다.

### 3.4 비행 진행 화면

‘어디로 이동 중인지’와 ‘무엇을 읽는지’를 함께 보여 준다.

| 영역 | 요구 |
|---|---|
| 상단 | 현재 임무·작업 이름·제어권·통신 상태·실제 비행 단계 |
| 지도 | 현재 기체, 대상 라벨, 실제 목표, 대기점, 허용 구역 |
| 스캔 카드 | 접근/정렬/안정/스캐너 n회/카메라/결과 저장/대기점 복귀 |
| 품질 | 마커 관측 나이·정렬 상태·센서 이상. 미상은 미상으로 표시 |
| 판독 결과 | 판독 성공/실패·장치·실패 원인·대상 일치 |
| 업로드 | 로컬 저장/전송 대기/서버 저장/업무 수락 또는 거부 |
| 진행률 | 이동 방문 수·스캔 처리 수·스캔 성공 수를 구분 |
| 명령 영역 | PAUSE/RESUME/CANCEL/LAND_NOW의 허용 상태와 결과 표시 |

QR을 읽었다는 사실만으로 다음 작업을 완료 처리하지 않는다.
대기점 복귀까지 Jetson 진행 상태를 따른다.
화면은 타이머로 단계를 자동 추측하지 않는다.
남은 시간은 Jetson이 유효한 예산을 보고할 때만 표시한다.
통신 단절 시 마지막 위치·단계와 확인 시각을 표시한다.
다시 연결돼도 미전달 명령을 자동 실행 대기열에 넣지 않는다.
명령 버튼과 결과는 작은 화면에서도 식별 가능해야 한다.
내부 ID가 운영자 조치 문구를 가리지 않도록 상세 영역으로 접는다.

### 3.5 임무 결과·재확인 화면

비행 종료, 라벨 판독, 서버 업무 반영을 별도로 요약한다.

| 결과 | 표시 예 |
|---|---|
| 비행 | 출발점 복귀·착륙 완료 / 중단 / 착륙 확인 불가 |
| 라벨 | 대상 10개, 성공 8개, 실패 2개 |
| 업무 반영 | 서버 수락 7개, 거부 1개, 미전송 2개 |
| 실패 상세 | 라벨별 원인·시도 횟수·장치·시각·원문 유무 |
| 전송 복구 | 기존 결과 ID로 재전송, 중복 재고 처리 없음 |
| 후속 임무 | 실패 라벨을 새 임무 초안으로 선택 가능. 자동 재이륙 없음 |

동일 비행의 스캔 재실행 명령은 이번 요구에 추가하지 않는다.
그 기능은 기존 시도·제어권 정책을 바꾸므로 별도 합의가 필요하다.

## 4. API 변경 요청

기존 통신 구조를 유지하고 스캔 입력·진행·결과 계약을 확장한다.
URL에 ‘신규 제안’이라고 표시한 경로는 구현된 주소가 아니다.
기존 연결점도 실제 서버 경로·인증·버전을 웹팀이 확인해 달라.

| ID | 연결점 | 변경 요청 | 확인할 응답 |
|---|---|---|---|
| API01 | 기존 GET `/api/drones/{drone_id}/companion-mission/` | 혼합 route_tasks·라벨·허용 구역·배치/프로파일 참조를 동일 snapshot에 포함 | 완전한 임무 묶음·버전·required_capabilities |
| API02 | 지도/라벨 관리 API, 경로는 웹팀 제안 | 라벨·정면·마커 연결·허용 구역의 생성/조회/개정 저장 | 새 개정·검증 오류·참조 무결성 |
| API03 | 기존 WS telemetry/readiness | scan_progress·실제 기체 목표 종류·스캔 차단 사유·계획 미리보기 참조 추가 | 순서/원천 시각/세션을 보존한 최신 상태 |
| API04 | 기존 POST companion-phase | 스캔 단계 전환·이탈 완료·선점 사건 저장 | event_id 중복 방지, 과거 사건으로 최신 상태 덮어쓰기 없음 |
| API05 | 신규 제안 POST `/api/drones/{drone_id}/scan-task-results/` | QR 원문 없는 실패까지 작업 결과를 영속 저장 | 저장 여부·수락 개정·중복 여부·업무 처리 결과 |
| API06 | 신규 제안 GET `/api/drones/{drone_id}/scan-task-results/{task_result_id}/` | 업로드 응답 유실 뒤 기존 결과 확인 | 최신 저장 개정·판독/이탈/업무 결과 |
| API07 | 기존 control-action/ack, 제어 세션·요청 결과 조회 | 지상 취소·스캔 단계 명령 제한과 기존 10초/중복 정책 대조 | 기체 처리 결과와 HTTP 결과 구분 |

제어 세션 발급·명령 조회 등 기존 미확정 URL도 함께 회신한다.
새 WS 비행 명령 채널을 추가하는 요청은 아니다.

### 4.1 임무·지도 입력 예시

아래는 기존 전체 snapshot에 추가/대체할 필드 예시다.
전체 임무 파일이 아니며, 좌표·ID·크기는 합성값이다.
기존 지도 형상·이륙 높이·변환·승인 필드는 별도로 필요하다.

```json
{
  "contract_version": "1.1-draft.3",
  "required_capabilities": ["mission_xyz", "arrival_yaw", "map_volumes", "command_session", "readiness_binding", "scan_task_v1", "label_pose_v1", "scan_workspace_v1"],
  "snapshot": {
    "snapshot_id": "snapshot-scan-demo-01",
    "route_revision": "route-scan-demo-r1",
    "coordinate_frame": "WAREHOUSE_MAP",
    "length_unit": "m",
    "route_tasks": [
      {"id": "W01", "type": "waypoint", "x": 1.5, "y": 1.5, "z": 1.2, "yaw_deg": 0, "hold_s": 0},
      {"id": "S01", "type": "scan", "label_point_id": "L01", "workspace_id": "SW01", "scan_profile_ref": {"id": "scan-profile-demo", "revision": "r1"}},
      {"id": "W02", "type": "waypoint", "x": 1.5, "y": 3.0, "z": 1.2, "hold_s": 0}
    ],
    "labels": [
      {
        "label_point_id": "L01",
        "revision": "label-r1",
        "position_reference": "QR_CENTER",
        "position_m": {"x": 4.5, "y": 1.5, "z": 1.2},
        "outward_normal_map": [-1.0, 0.0, 0.0],
        "expected_qr_ref": "expected-qr-L01-r1",
        "aruco": {"dictionary": "DICT_4X4_50", "marker_id": 17, "marker_size_m": 0.08, "qr_marker_transform_ref": "qr-marker-L01-r1"}
      }
    ],
    "scan_workspaces": [
      {
        "workspace_id": "SW01",
        "revision": "workspace-r1",
        "label_point_ids": ["L01"],
        "geometry_semantics": "PHYSICAL_ALLOWED_VOLUME",
        "polygon_xy_m": [[0.5,0.5],[4.4,0.5],[4.4,2.5],[0.5,2.5]],

```

| 필드/규칙 | 합의할 의미 |
|---|---|
| waypoint XYZ | 기체/PX4 기준점의 목표. 기존 의미 유지 |
| scan 입력 | 라벨·구역·프로파일 참조. 기체 XYZ 필드로 대체하지 않음 |
| position_reference | QR_CENTER는 제안. 실제 라벨 측량 기준점과 합의 필요 |
| outward_normal_map | 라벨에서 통로 쪽 단위 방향 벡터 제안. 좌표 기준과 방향 유효성 검사 |
| expected_qr_ref | 실제 QR 원문/품목/라벨 일치 규칙의 불변 참조 |
| qr_marker_transform_ref | 실측 상대 배치의 불변 참조. 변환 방향·단위·개정 포함 |
| scan_profile_ref | Jetson에 승인된 거리·시간·정렬 제한의 참조. 웹에서 임의 완화 금지 |
| PHYSICAL_ALLOWED_VOLUME | 기체 전체와 검증 여유가 들어갈 물리적 허용 공간이라는 제안 |
| entry_anchor_task_id | 기존 이동 경로와의 연결 기준점. 그 점부터의 접근을 검증했다는 뜻은 아님 |
| 참조 자료 | 필요한 자료를 동일 묶음 또는 내용 확인 가능한 불변 자료로 완전 수신해야 준비 가능 |

방향 벡터를 yaw 각도로 바꾸려면 동일한 물리 의미를 유지한다.
기체의 선택 도착 yaw와 라벨 정면 필드는 분리한다.
거리 0.40~0.60m는 시험 후보이며 웹 기본 승인값이 아니다.
판독 기체 위치는 센서 기준 거리와 장착 오프셋으로 계산한다.
구역과 장애물·고도 제한을 함께 검사한다.
구역을 등록했다고 그 내부 장애물이 사라지는 것은 아니다.
미지원 scan을 제거해 남은 이동점만 실행하지 않는다.
필수 작업 순서를 잃기 때문에 전체 임무를 거부한다.

서버가 작업을 자동 삽입/변환한다면 최종 route_tasks를 먼저 확정한다.
그 최종 목록에 snapshot·개정·승인·준비 ID를 결합한다.
READY 이후 같은 snapshot의 작업을 추가·재정렬하지 않는다.

비행 phase와 스캔 하위 단계를 분리한다.
아래는 기존 telemetry에 합칠 필드 예시다.

```json
{
  "contract_version": "1.1-draft.3",
  "type": "telemetry",
  "drone_id": "5",
  "execution_id": "execution-scan-demo-01",
  "flight_id": "flight-scan-demo-01",
  "phase": "HOVERING",
  "active_target": {"kind": "SCAN_POSE", "task_id": "S01", "frame": "WAREHOUSE_MAP", "x": 3.8, "y": 1.5, "z": 1.2, "yaw_deg": 0},

    "task_id": "S01",
```

| 항목 | 요청 |

| 미리보기 | Jetson 검증 plan_id·지도/변환/장착 개정·대기점/구간을 조회 또는 상태로 제공하는 방식 합의 |

### 4.3 실패까지 저장하는 작업 결과

QR 판독 성공과 이탈 완료를 하나의 성공값으로 합치지 않는다.
아래는 판독 실패를 저장하고 대기점 복귀 중인 예시다.

```json
{
  "contract_version": "1.1-draft.3",
  "drone_id": "5",
  "task_result_id": "scan-result-demo-01",
  "result_revision": 1,
  "client_scan_id": "scan-demo-01",
  "execution_id": "execution-scan-demo-01",
  "flight_id": "flight-scan-demo-01",
  "snapshot_id": "snapshot-scan-demo-01",
  "route_revision": "route-scan-demo-r1",
  "task_id": "S01",
  "label_point_id": "L01",
  "task_status": "RUNNING",
  "scan_outcome": "FAILED",
  "failure_code": "QR_UNREADABLE",
  "scanner_attempts_started": 3,
  "camera_qr_used": true,
  "reader_source": null,
  "raw_qr_data": null,
  "decoded_at": null,
  "egress_status": "IN_PROGRESS",
  "recorded_at": "2026-10-04T03:00:30Z"
}
```

```json
{
  "stored": true,
  "task_result_id": "scan-result-demo-01",
  "stored_revision": 1,
  "duplicate": false,
  "business_status": "NOT_APPLICABLE",
  "code": "OK"
}
```

| 계약 | 요구 |
|---|---|
| 상태 후보 | task_status는 RUNNING/COMPLETED/FAILED/PREEMPTED. scan_outcome은 PENDING/SUCCEEDED/FAILED/INTERRUPTED |
| 이탈 상태 후보 | NOT_STARTED/IN_PROGRESS/COMPLETED/FAILED/PREEMPTED. 판독 상태와 독립 |
| 식별 수명 | task_result_id·client_scan_id는 같은 실행/작업에서 고정. 새 비행/작업에 재사용하지 않음 |
| 대기점 복귀 완료 | 같은 task_result_id의 다음 result_revision으로 이탈 완료 보고 |
| 작업 완료 | task_status=COMPLETED여도 scan_outcome=FAILED일 수 있음 |
| 실패 원인 | 미판독·대상 불일치·마커 획득 실패·카메라 장애·비행 선점 구분 |
| QR 원문 | 실패 때 null 허용. 빈 성공 QR을 만들어 채우지 않음 |
| 판독 확정 후 | 늦은 관측·다른 작업 결과로 확정한 판독 내용을 덮어쓰지 않음 |
| 유효 판독 | 실제 원문·취득 시각·장치 출처·대상 일치·원천 세션/순번 기록 |
| 원문 표시 | QR 원문은 텍스트 데이터로 표시. HTML이나 명령으로 실행하지 않음 |
| 시도 기록 | 스캐너 0~3회와 카메라 사용 여부, 시도별 원인/시각을 상세 자료로 제공 |
| 장치 출처 | SCANNER/CAMERA와 기존 scan_source=wifi 전송 문맥 분리 |
| 로컬 저장 | 비행 중 다음 단계 판단은 Jetson 영속 저장·비행/이탈 조건 기준 |
| 서버 저장 | HTTP 성공·저장 완료·재고 등 업무 수락을 구분 |
| 업무 거부 | QR 판독 성공을 지우지 않고 별도 거부 이유 표시 |
| 보존 | QR 결과·명령/사건 보존 기간을 별도 합의. ULog 72시간 정책 재사용 금지 |

기존 `/scan/`과 신규 결과 경로의 역할을 웹팀이 회신한다.
제안은 신규 결과 경로를 새 스캔 임무의 단일 등록 경로로 쓰는 것이다.
서버가 기존 업무 등록으로 연결하되 client_scan_id로 중복을 막는다.
두 API에 같은 결과를 보내 재고를 두 번 반영하지 않는다.

실제 QR 원문의 정상·오류 예시도 함께 회신해 달라.
기존 파서의 name 필수 검사와 서버 예제의 생략 사례를 맞춰야 한다.
schema/code/name의 필수성·타입과 라벨 ID 연결 규칙을 확정한다.
HTTP 2xx여도 업무 거부라면 업무 성공으로 표시하지 않는다.

### 4.4 중복·재전송·오류 처리

결과 재전송은 새로운 비행 명령이나 새로운 판독으로 취급하지 않는다.

| 상황 | 요청 처리 |
|---|---|
| 같은 결과 ID·revision·동일 내용 | 기존 저장 결과 반환, 중복 업무 반영 없음 |
| 같은 결과 ID·revision·다른 내용 | 충돌 거부·사유 반환 |
| 이전 revision 지연 도착 | 현재 최신 상태 유지. 동일 과거 기록 재전송은 확인 응답 |
| 새 revision | 같은 기체·실행·작업 문맥과 허용 전환 검사 |
| 수락 뒤 저장 | 영속 저장 확인 후 stored=true 반환. 메모리 수신만으로 저장 완료 응답 금지 |
| 최초 업로드가 복귀 완료 뒤 도착 | 최신 누적 결과 저장 가능. 이전 WS 진행 사건 수신을 필수로 하지 않음 |
| 업로드 응답 유실 | 동일 ID 재전송 또는 GET 결과 조회 |
| 서버 업무 거부 | 이유 저장·운영자 확인. 자동 재비행/무한 재판독 없음 |
| 전송 장애 | 로컬 보존·제한된 재전송. 큐 용량·보존·포화 처리를 공동 합의 |

새 오류 코드는 아래 의미를 유지하는 이름으로 합의한다.
`LABEL_DIRECTION_MISSING`, `SCAN_WORKSPACE_INVALID`,
`MARKER_BINDING_UNAVAILABLE`, `SCAN_PROFILE_UNAPPROVED`,
`SCAN_TARGET_MISMATCH`, `SCAN_RESULT_CONFLICT`를 후보로 제안한다.
기존 `UNSUPPORTED_CAPABILITY`, `INVALID_PAYLOAD`,
`SNAPSHOT_CONFLICT`, `SYSTEM_NOT_READY` 등은 재사용한다.
구체 HTTP 코드와 기체 처리 코드는 기존 계약과 대응시킨다.

## 5. 기존 웹 회신에서 수정할 두 항목

지상 취소와 자료 담당을 다음과 같이 명확히 해 달라.

| 항목 | 수정 요청 |
|---|---|
| CANCEL | 지상 준비 중: 이륙 중단·실제 지상 상태에 따른 종료. 이륙 상승 중: 현 위치 착륙. 일반 임무 중: 복귀·착륙 |
| 상승 중 PAUSE 후 CANCEL | 원래 이륙 단계 문맥을 보존해 현 위치 착륙 |
| D01~D10 | 요청 목록은 우리가 전달. 웹 고유 API/환경/구현 증거까지 우리에게 작성 요청하지 않도록 담당 분리 |

RC 수동 인계 후 기존 수동 RC/PX4 설정을 유지한다.
웹 LAND_NOW도 수동 제어권을 강제로 회수하지 않는다.
미전달 명령의 자동 재실행 금지와 수락 기한 10초는 유지한다.

| UWB | 전체 사양과 실제 로그. 수령 전 장치 어댑터 확정 보류 |

웹팀이 요청한 상세 문서 6종은 다음과 같다.

이번 추가 요구는 [QR_SCAN_SPEC.md](QR_SCAN_SPEC.md)를 함께 따른다.
점검은 [BOOT_PREFLIGHT_SPEC.md](BOOT_PREFLIGHT_SPEC.md),

미측정 값은 [MEASUREMENT_REGISTER.md](MEASUREMENT_REGISTER.md)에 있다.

요청된 JSON 9종 전체가 완성됐다고 선언하는 문서는 아니다.
기존 MD 예시와 이번 스캔 예시를 합의 후 하나의 시험 묶음으로 맞춘다.
이 문서의 부분 JSON은 전체 임무/준비 검증을 통과하는 파일이 아니다.
센서 유효 나이·준비 수명·작업 시간은 시험값과 승인값을 분리한다.
모르는 값을 0·무한대·정상으로 대신하지 않는다.

## 7. 공동 검수·완료 기준

기존 WT/WH 시험에 아래 스캔 시험을 추가한다.
아래 목록은 실행 요구이며 통과 결과가 아니다.

| 시험 | 입력/상황 | 웹·Jetson에서 확인할 결과 |
|---|---|---|
| WA-T01 | 이동점→스캔→이동점 혼합 임무 | 동일 최종 작업 순서·snapshot 사용, 라벨 XYZ로 직접 비행 목표 없음 |
| WA-T02 | 방향·마커 배치·구역·프로파일 누락 | 해당 작업 차단·원인/조치 표시, 부분 실행 없음 |
| WA-T03 | 전체 경계 없음·라벨 구역만 유효 | 승인 구역 내 스캔만 가능, 일반 자동 우회 비활성 |
| WA-T04 | 외곽 안이지만 고도/기체 여유 밖 | 공간 검증 거부. 웹 저장 성공을 비행 승인으로 표시하지 않음 |
| WA-T05 | 스캐너 1/2/3회에서 각각 성공 | 남은 시도 생략, 카메라 QR 미사용, 결과 한 번 처리 |
| WA-T06 | 스캐너 3회 실패→카메라 성공/실패 | 정확한 장치 전환·실패 기록·대기점 복귀 후 다음 목표 |
| WA-T07 | 마커/카메라 실패, 기체 비행 정상 | 실패 저장·대기점 복귀·다음 목표. 기체 고장과 구분 |
| WA-T08 | 스캔 성공 후 이탈 차단 | 다음 작업으로 넘기지 않고 기존 차단/복귀/Land 표시 |
| WA-T09 | Wi-Fi 단절 중 판독·착륙, 이후 재접속 | 로컬 결과 복구·중복 업무 처리 없음·새 비행 자동 시작 없음 |
| WA-T10 | 다른 라벨 QR·이전 작업의 늦은 결과 | 대상 성공으로 오기록 없음, 작업/시각/원천 문맥 대조 |
| WA-T11 | 같은 결과 재전송·역순 revision·같은 ID 다른 내용 | 중복 방지·최신 상태 보존·충돌 거부 |
| WA-T12 | 지상/상승/상승 중 PAUSE/일반 임무 중 CANCEL | 단계별 정해진 종료·착륙·복귀 동작 |
| WA-T13 | 스캔/이탈 중 RC 인계·긴급 착륙 | 즉시 안전 선점, 스캔 완료를 기다리지 않음 |
| WA-T14 | 전 과정 수행 | 새 START→이륙→이동→스캔→대기점→다음 목표→출발점→착륙, 판독/비행/업무 결과 구분 |

시험 자료에는 기체·임무·실행·비행·세션 ID를 일관되게 사용한다.
요청/응답·원천/수신 시각·Jetson 사건·화면 결과를 함께 남긴다.
정상 사례와 실패 주입 사례의 기대 순서를 먼저 합의한다.
최초 검수는 웹 서버와 Jetson 모의 연결로 수행한다.
실제 기체 임무 검수는 PX4/UWB/영상·공간·RC 검증 뒤 진행한다.
웹 화면 시험 통과를 실비행 성공으로 표시하지 않는다.

## 8. 웹팀 회신 요청

WA01~WA07과 API01~API07의 대응표를 작성해 달라.

| 항목 ID | 수락/수정 제안/미지원 | 기존 기능/API | 구현할 필드·화면·API | 담당 | 시험 자료·완료 예정 |
|---|---|---|---|---|---|
| WAxx / APIxx | 회신 | 현재 경로/의미 | 변경안 | 담당자 | WA-T/WT/WH와 일정 |

우선 회신 순서는 다음과 같다.

1. 이동/스캔 좌표 분리와 라벨 정면·허용 구역 표현.
2. 스캔 결과 저장 API와 기존 `/scan/`의 연결 방식.
3. 화면 변경안과 단계·실패·오프라인 표시.
4. 실제 API 대응표·버전·테스트 서버·공통 시험 일정.

이 문서는 추가 요구를 전달하기 위한 자료다.
외부 발송·웹팀 수락·실제 구현 완료는 별도로 기록한다.
