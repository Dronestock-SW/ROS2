# LiDAR 제자리 이륙과 UWB 복구 대기
한글 통합 브랜치의 이륙 경로 변경 기록이다.
자동 이륙의 구현·검증 범위를 확인할 때 읽는다.

**제자리 상승 뒤 POSITION에서 UWB 복구를 기다린다.**
UWB 복구는 POSITION 진입의 전제 조건이 아니다.
임무 START에는 UWB 안정 확인이 필요하다.
PX4의 유효한 위치·고도 추정은 계속 필요하다.
LiDAR 속도만으로 최초 절대 위치를 만들지 않는다.

```text
지상 초기 XY + PX4 추정 + LiDAR 송신 준비
  -> TAKEOFF: 최초 XY 고정, PX4에 목표 고도 요청
  -> LiDAR/PX4 수평 정지 + 목표 고도 3초 확인
  -> 실제 POSCTL 확인
  -> 최초 XY 주변 POSITION 호버링
  -> UWB 5초 안정 확인
  -> 별도 웹 START 허용
```

## 두 센서의 역할

수평 속도와 하향 높이의 유효성을 분리했다.

| 입력 | 역할 | 누락 시 처리 |
|---|---|---|
| T-mini Pro SDK point cloud | 수평 이동·속도 | 관측 보류, 이륙 감시 |
| FC 시각의 IMU 자세·각속도 | scan 보정·방향 변환 | 외삽 없이 관측 보류 |
| TFmini Plus 하향 ToF | 실제 높이 | 높이를 미관측으로 기록 |
| UWB B_TF | 절대 XY·임무 진행 | POSITION 호버링 중 복구 대기 |
| PX4 EKF2·위치 제어 | 추정·XY 유지·상승 | 기존 추정 무효 보호 유지 |

C++ 실행기만 비행 명령을 보낸다.
LiDAR 노드는 수평 관측만 보낸다.
수직 속도·위치·자세를 만들어 넣지 않는다.
전용 2D 수신 경로의 `vz=NaN` 계약을 유지한다.
companion 고도 PID·추력·자세 제어는 추가하지 않았다.

## 저고도에서 막혔던 조건

ToF 필수 조건과 4m 범위가 각각 경로를 막았다.

기존 `MeasuredLidarMotion`은 ToF가 없으면 거부했다.
ToF는 scan의 XY 거리 환산에는 쓰이지 않았다.
지면 간격 검사에만 사용했다.
따라서 지상 ToF가 최소 0.1m 미만이면 막혔다.
수평 LiDAR가 정상을 관측해도 같은 결과였다.

새 `floor_policy=metric_scan`은 높이를 진단값으로 둔다.
없는 ToF·센서 높이는 `null`로 기록한다.
ToF가 복구돼도 XY 계산식을 바꾸지 않는다.
기존 `required` 정책도 그대로 지원한다.

이 정책에는 수직 구조물 검증 기록이 필요하다.
`vertical_structure_ref`가 없으면 차단한다.
지상부터 목표 높이까지 공통 벽면이 필요하다.
상승 중 선반·가림·경사면 변화는 별도 검증 대상이다.
장착·scan 평면·시간 보정 조건도 유지했다.
기울기·형상·상호 정합·속도 검사를 완화하지 않았다.

현장 예제의 최대 거리는 4m에서 12m로 바꿨다.
기존 `lidar_tmini.yaml`의 12m와 맞췄다.
설정 상한도 12m로 제한했다.
정합에 남은 점 수를 `usable_points`로 기록한다.
멀리 있는 벽을 제외해 관측이 사라지는 원인을 드러낸다.

## 이륙·호버링 조건

새 예제는 `takeoff_lidar_required=true`다.
기존 비행 설정은 자동으로 변경하지 않는다.

| 단계 | 적용 조건 |
|---|---|
| 지상 시작 | 기존 UWB·PX4 초기화, 3초 정지 |
| LiDAR 준비 | 단일 송신 노드, 유효 2D 관측, 전용 FC 설정 |
| 송신 신선도 | 관측 0.35초 이하, 상태 0.5초 이하 |
| 지상·공중 정지 | LiDAR 구간 평균·PX4 수평 속도 각각 0.1m/s 이하 |
| 자동 상승 | 지상에서 저장한 XY 유지, PX4 목표 고도 1.7m |
| 상승 제한 | 기존 PX4 최대 상승 0.5m/s 이하 확인 |
| POSITION 요청 | XY 0.15m, 높이 0.15m, 수직 속도 0.1m/s 이내 3초 |
| UWB 복구 | 최신 0.25초, 최초 XY와 0.25m 이내 |
| UWB 안정 | 5초 동안 시작 표본 대비 0.1m 이내 |
| 임무 START | POSITION 안정 5초와 UWB 안정 5초 모두 만족 |
| 이륙 중 XY 이탈 | 최초 XY에서 0.25m 초과 시 보호 착륙 |
| LiDAR 중단 | 지상 즉시 차단, 공중 0.5초 연속 불가 시 보호 착륙 |

POSITION 안정과 UWB 안정 시간은 병렬로 확인한다.
UWB가 늦게 돌아오면 그때 5초를 새로 센다.
UWB가 흔들리거나 다시 끊기면 누적을 초기화한다.
조종기 개입은 모든 복구·착륙 판단보다 우선한다.

LiDAR 정지는 최근 약 1초의 실측 구간 평균을 쓴다.
최소 8개 관측과 0.75초의 실제 관측량이 필요하다.
처음부터 끝까지의 길이도 0.9초 이상이어야 한다.
누락 구간을 속도 0이나 관측 시간으로 채우지 않는다.
중복·겹침·구간 리셋·큰 공백은 누적에서 구분한다.
FC에는 평균을 보내지 않고 원래 관측을 보낸다.
짧은 거부 뒤에는 마지막 발행 관측의 원래 시각을 쓴다.
최대 0.35초를 넘기거나 미래 시각이면 사용할 수 없다.

UWB가 없어도 LiDAR/PX4로 POSITION에 진입한다.
호버링 위치는 원래 이륙 XY를 기준으로 판정한다.
떠밀린 위치를 새 임무 시작점으로 채택하지 않는다.
실제 POSITION 제어는 PX4가 수행한다.
새 정책은 최초 XY를 임무 시작점에도 보존한다.
기존 정책의 이동한 시작점 저장과 구분한다.

## 실행 연결

기존 LiDAR2D 송신기를 필드 실행기에 연결했다.

`final_field_session.py --lidar-config <검증된 설정>`을 쓴다.
기존 센서·MAVROS를 구독하는 송신기를 시작한다.
이미 송신 중이면 `--external-lidar-bridge`를 쓴다.
`--external-observation-bridge`는 UWB에만 적용한다.
이륙 보호를 쓰면 C++ 실행기가 필수다.
`--check-only`는 설정만 검사하고 프로세스를 시작하지 않는다.

C++는 `/lidar/velocity_status`를 직접 구독한다.
Python 관측 어댑터의 갱신에 의존하지 않는다.
상태 수신 시각과 실제 관측 시각을 각각 확인한다.
중복 송신자·다른 태그·발행되지 않은 관측은 거부한다.
실행 시 검증한 설정과 송신 설정의 일치도 확인한다.
MAVLink 송신을 FC 융합 성공으로 표시하지 않는다.
`fusion_verified=false`를 유지한다.

`takeoff_lidar_fusion_ref`에는 융합 검증 기록을 넣는다.
수신·혁신·실제 융합을 확인한 기록이 필요하다.
이 값은 실시간 융합 상태를 대신하지 않는다.
현재 MAVROS 경로는 LiDAR 개별 융합 상태를 주지 않는다.
FC 기록과의 대조가 남아 있다.

## 실제 기록 재생

관측 생성 증가를 확인했다. 정확도 검증은 아니다.

13일 원본 124,382,507바이트의 해시를 다시 확인했다.
같은 이륙 구간에서 243개 scan을 추출했다.
IMU 2,445개와 ToF 223개를 함께 사용했다.
ToF 입력 자체는 159개 무효, 64개 유효였다.
처리 시점에 높이가 없던 scan은 174개였다.

| 진단 조건 | 채택 / 전체 scan | ToF 없이 채택 |
|---|---:|---:|
| 4m + 기존 ToF 필수 | 0 / 243 | 0 |
| 4m + ToF 분리 | 0 / 243 | 0 |
| 8m + ToF 분리 | 161 / 243 | 144 |
| 12m + 기존 ToF 필수 | 15 / 243 | 0 |
| 12m + ToF 분리 | 176 / 243 | 148 |
| 12m + ToF 전체 누락 주입 | 176 / 243 | 176 |

4m에서 정합 가능 점 수의 중앙값은 58개였다.
최소 대응점 조건은 60개다.
12m에서는 중앙값이 126개로 증가했다.
채택 속도값은 정확도 지표로 사용하지 않았다.
독립 속도 기준값이 없기 때문이다.

위 비교는 미검증 시간 오프셋 0초를 가정했다.
수직 구조물·평면 조건도 진단용으로만 가정했다.
저장소 예제는 미확인 평면 조건으로 243개 모두 차단한다.
재생은 기록된 수신 순서와 시각을 사용한다.
처리 타이머 20ms와 IMU 대기 50ms는 모사했다.
실제 브리지 CPU 시간·MAVLink·FC 융합은 포함하지 않는다.

재현 도구는 `replay_lidar_takeoff.py`다.
`--assume-geometry-for-diagnostics`가 가정을 표시한다.
`--diagnostic-max-range-m`으로 비교 범위를 명시한다.
원본과 운영 설정은 수정하지 않는다.

## 검증 범위와 남은 항목

Python 367개·C++ 53개·ROS 4개 시험을 통과했다.

| 검증 | 결과 | 범위 |

| `colcon build --symlink-install` | 4개 패키지 성공 | 격리 복사본 |
| C++ Release 빌드 | 경고 오류 처리 통과 | 실행기·재생 실행기 |
| Python 회귀 | 367 통과, 8 건너뜀 | 선택 C++ AI 실행 파일 시험 제외 |
| C++ 실행기 계약 | 53 통과 | 실제 C++ 코어·합성 상태 |
| ROS UWB 복구 | END, 원래 XY 복귀 | UWB 12초 중단 중 POSITION 진입 |
| ROS LiDAR 중단 | 예정된 FAILED·LAND | 공중 송신 중단 보호 |
| ROS 잘못된 LiDAR 상태 | 예정된 FAILED·LAND | 배열 형태 메시지 거부 |

빌드한 소스 18개와 작업 파일 해시가 모두 같았다.

실기 LiDAR2D 수신·혁신·융합 확인이 필요하다.
실제 제자리 이륙·POSITION 호버링은 미실시다.
실기 서비스·FC 파라미터·펌웨어는 변경하지 않았다.
예제 송신기는 `enabled=false`를 유지한다.
미검증 조건을 참으로 바꿔 이륙을 허용하지 않는다.
