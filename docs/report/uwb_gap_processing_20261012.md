# UWB 공백 — 계산 시간과 거절 경로
보존된 수동 호버 기록의 추가 분석이다.
관측 공백 수정과 FINAL 재개 때 읽는다.

**확인한 0.824초 공백은 계산 지연보다 이력과 거절 문제다.**
실행 8과 다른 수동 Position 비행의 근거다.
실행 8의 같은 원인을 확정한 것은 아니다.
반복한 수직 이동 지상 시험을 다시 요청하지 않았다.

## 원본에서 확인한 원인

원시 거리는 공백 중에도 들어왔다.
기록은 `capture-1791690206019693134-25223132`다.
원본 events SHA256은 아래와 같다.
`c4ca4e96ab93b078d1148da702232831690426e4a8917587479ae8a16cb48083`.

| 공백 안의 값 | 원본 확인 결과 |
|---|---:|
| XY 발행 간격 | 0.824388218초 |
| 원시 거리 패킷 | 33개 |
| 원시 패킷 최대 수신 간격 | 27.741ms |
| 발행 거절 | `no_height_consistent_subset` 32개 |
| 계산 시간 중앙값 / p95 / 최대 | 14.438 / 16.860 / 18.514ms |
| 시계 모델의 큐 나이 최대 | 0.466ms |
| `receiver_queue_expired` | 기록 전체 0개 |

큐 나이는 시계 모델을 사용한 진단값이다.
독립적으로 교정한 물리 지연이 아니다.
계산 시간은 로그에 저장된 callback 실행 시간이다.
모든 OS 지연을 측정한 값은 아니다.
그래도 이 공백을 큐 적체로 설명할 근거는 없다.

순서는 다음과 같다.

```text
A3 원시 거리 4.63m 부근 -> 2.6833m, seq 68326
  -> 원시 차분 잔차 0.475m
  -> 그 표본을 H80/B3 이력에 추가
  -> B4 RMS 약 0.168m
  -> 가장 좋은 B3 거리 RMS도 약 0.155m
  -> 기존 0.06m 검사에서 거절
  -> 원시 거리 회복 뒤에도 0.8초 이력 영향 지속
  -> 이상 표본이 창을 벗어나며 XY 발행 복구
```

원시 거리 한 번의 이상과 그 뒤 정상 입력을 구분했다.
느린 companion이 패킷을 놓친 구간은 아니다.
0.8초 창은 정상 관측의 고정 0.8초 지연을 뜻하지 않는다.
H80은 각 앵커 시각으로 최신 시점의 값을 계산한다.

## 파일 재생으로 좁힌 수정 방향

불일치한 표본을 이력에 넣지 않으면 해당 공백이 줄었다.
`probe_btf_history_admission.py`에서만 비교했다.
운영 MeasuredBtf는 변경하지 않았다.

원시 차분 잔차가 0.06m 이상인 현재 표본을 격리했다.
원래 source·TDMA·시계 검사는 그대로 사용했다.
격리한 표본을 H80와 B3 이력에 넣지 않았다.
신뢰하던 이력 전체를 초기화하지도 않았다.
오래된 좌표를 반복 발행하지 않았다.
높이·점프·신선도 임계값도 그대로다.

| 한 조각의 재생 | 기존 | 이력 입력 전 격리 |
|---|---:|---:|
| 가장 긴 완결 공중 공백 | 0.825796초 | 0.076131초 |
| 공중 XY 발행 | 3,343개 | 3,343개 |
| 이전 거절 위치의 새 발행 | — | 31개 |
| 이전 발행 위치의 새 거절 | — | 31개 |
| 공통 발행 좌표의 최대 차이 | — | 0.00556m |

좌표 정확도가 좋아졌다는 시험은 아니다.
발행 총수도 늘지 않았다.
0.8초 연속 거절을 짧은 격리로 바꾼 결과다.
이동 중 순차 거리도 순간 차분 검사에서 거절될 수 있다.
따라서 이 기준을 운영 기본값으로 배포하지 않았다.
다른 두 보존 비행에서도 비교했다.
중립 호버 조각은 발행 2,842→2,817개다.
영상 대조 호버 조각은 2,377→2,362개다.
새 격리의 좌표 정확도와 정상 가감속의 오거절은 남았다.

재생 조각 시작의 약 2.175초 공백은 남았다.
조각 이전 내부 이력을 재구성하지 않았기 때문이다.
실제 시작 구간의 수신 중단으로 해석하지 않는다.
원본 0.824초는 pose 수신 시각이다.
재생 0.826초는 원시 callback 재생 시각이다.
두 시간 정의를 구분한다.

위 재생의 기준은 Jetson 운영 `be36248`이다.
FINAL과 H80 코드는 같다.
MeasuredBtf·B3 후보에는 아래 높이 검사 차이가 있다.
이 결과를 수정 전 FINAL의 전체 결과로 표시하지 않는다.

## 좌표와 제어의 연속성

새 관측을 최대한 유지하되 결측을 숨기지는 않는다.
오래된 XY의 시각을 현재 시각으로 바꾸면 안 된다.
이유: 같은 오차를 새 독립 측정처럼 반복 융합한다.
FC 추정 위치를 다시 UWB 관측으로 넣어도 안 된다.
이유: PX4 추정 결과를 자기 근거로 되먹인다.

| 상황 | 수정 책임 |
|---|---|
| 단일 거리 이상 뒤 정상 복귀 | 이상 표본의 이력 유입과 빠른 관측 복구 |
| 일부 앵커 부족 | 실측 높이·기하 조건을 만족하는 새 B3 심사 |
| 모든 거리 관측을 신뢰할 수 없음 | 새 UWB 위치를 생성할 근거가 없음 |
| 짧은 결측 중 위치 유지 | PX4 광류·IMU 추정과 미션 정책을 함께 검증 |

현재 LocalXYMission은 UWB 나이 0.25초 초과 시 LAND한다.
`abort()`는 XY 목표 스트림도 비운다.
짧은 결측의 관측 복구와 제어 지속은 별개의 작업이다.
광류가 있다는 이유만으로 무기한 HOLD하지 않는다.
FC 추정 유효성·센서 융합·reset·RC 인계를 함께 봐야 한다.
실행 8은 LAND 후 XY 추정 reset도 기록했다.
기존 이륙 높이·속도·출발 XY·LAND 정책은 유지했다.

## FINAL과 운영 코드의 차이 수정

배포 보류 검사가 새 FINAL 설치에서 켜지는 문제를 수정했다.
운영 Jetson은 `be36248`이다.
FINAL에는 `342bea1`의 B4 높이 교차검사가 추가돼 있다.
이전 문서는 이 검사의 운영 배포를 보류했다.
하지만 기존 FINAL은 기본 B4 승인 경로에서 실행했다.
신규 설치가 운영과 다른 발행 거절을 만들 수 있었다.

`enforce_b4_height_integrity`를 명시했다.
기본값과 예제는 false다. 운영 관측 계약을 보존한다.
높이 검사의 진단 결과에는 `enforced=false`를 남긴다.
새 BTF 상태에도 적용 여부를 남긴다.
true면 기존 0.06m 검사·복구·freeze가 그대로 작동한다.
문자열·숫자·null은 설정 오류로 거절한다.
raw 점프·H80·B3·신선도 한계는 바꾸지 않았다.
이 변경은 높은 오차의 좌표가 옳다는 승인이 아니다.
배포 보류 연구 기능을 의도치 않게 켜지 않게 한 수정이다.
Jetson 운영 BTF 코드와 서비스는 갱신하지 않았다.

기존 높이 검사 연구를 재현할 때는 파일 재생에
`--enforce-b4-height-integrity`를 명시한다.
[이전 검사 결과](b4_height_integrity_20261011.md)를 함께 읽는다.

## 이번에 적용한 기록 수정

FINAL의 브리지 상태 토픽을 수집기에 추가했다.
기존 수집기는 `/uwb/bridge_status`만 수집했다.
ODOMETRY 발행기는 `/uwb/local_odometry_status`를 사용한다.
두 브리지의 토픽을 모두 기록하도록 했다.
`/uas1/mavlink_sink`에는 새 구독을 추가하지 않았다.
이유: 기존 단일 router 구독 계약을 유지한다.

`src/sangwon_AI/ops/uwb_gap_probe.py`도 추가했다.
수신 간격·거절 사유·계산 시간·CPU를 제한 시간 동안 읽는다.
ROS 발행·서비스 호출·FC 명령·파라미터 쓰기는 없다.
원시 거리 cycle과 5초 주기 status를 구분한다.
상태 토픽의 정상 1초 간격을 UWB 결측으로 판단하지 않는다.

현재 60초 측정에는 원시 거리 cycle이 0개였다.
따라서 현재 UWB 계산 성능을 확인한 시험은 아니다.
FC는 connected·DISARM·AUTO.LOITER로 관측됐다.
현재 상태를 실행 8 당시 상태로 소급하지 않는다.

## 공간 정리와 검증

패키지 다운로드 캐시와 폐기된 확장 버전을 정리했다.
VS Code가 폐기 표시한 구버전만 대상으로 삼았다.
프로세스·열린 파일 참조가 없는 것도 확인했다.
이 확장에서 606,994,432바이트를 확보했다.
비행 원본·요청 원장·미션 DB·FC SD 로그는 유지했다.
종료 지상 기록 13개·39개 파일을 PC에 백업했다.
압축본과 해제본을 원본 SHA256과 대조했다.
원격 파일도 삭제 직전에 다시 대조했다.
검증된 원격 지상 사본 1,847,693,514바이트를 정리했다.
이 작업에서 만든 재생 임시 파일 212,215,957바이트도 정리했다.
계산 비교 결과·원본 비행 기록은 보존했다.
정리 직후 여유 공간은 3,426,217,984바이트였다.
약 3.19GiB다. 처음 확인은 약 1.10GiB였다.
수집기를 재개한 뒤 `collecting`과 파일 증가를 확인했다.
새 기록은 약 89MB까지 증가했다.
새 manifest에 ODOMETRY 상태 토픽도 포함됐다.
MAVROS·UWB 수신·B_TF의 PID는 전후 동일했다.

수집기를 멈춰 백업과 자동 보존 정책의 경쟁을 피했다.
수집기만 중지했다. MAVROS·UWB 관측은 유지했다.
첫 압축 시도는 자동 지상 보존 정리와 충돌해 실패했다.
소스 삭제 전에 중지·재목록·재압축으로 해결했다.
최종 압축본만 검증 대상으로 사용한다.

| 검증 | 결과 |
|---|---|
| 수집·부팅·전송 진단 단위시험 | 32개 통과 |
| 관련 수집·BTF·높이 검사·이동 재획득 전체 확인 | Windows 109개 통과 |
| 같은 관련 파일을 명시한 격리 시험 | Jetson domain 99에서 109개 통과 |
| 별도 drone_uwb 빌드·설치 import | Jetson 성공 |
| 새 도구 구문·도움말 | Windows 통과 |
| 새 수신 도구 | Jetson에서 60초 실행 |
| 이력 격리 후보 | 보존 비행 3조각 재생 비교 |
| 새로운 실제 비행·운영 격리 후보 적용 | 미실시 |

전체 디렉터리 시험을 통과했다고 보고하지 않는다.
Windows 전체 수집에는 ROS·PyYAML·Git symlink 환경 문제가 있었다.
Jetson 디렉터리 지정도 1개 skip으로 시험을 수집하지 않았다.
관련 파일을 명시한 위 시험·빌드의 성공과 구분한다.

## 재현과 다음 작업

첫 명령은 센서 토픽을 읽기만 한다.
새 output 경로를 사용한다.
기존 MAVROS·B_TF와 같은 사용자·domain에서 실행한다.

```bash
python3 src/sangwon_AI/ops/uwb_gap_probe.py \
  --seconds 60 --output /private/new-gap-probe.json
```

두 번째 명령은 보존 파일만 읽는다.
ROS나 FC에 접속하지 않는다.

```bash
PYTHONPATH=src/drone_uwb:src/drone_uwb/tools OPENBLAS_NUM_THREADS=1 \
  python3 src/drone_uwb/tools/probe_btf_history_admission.py \
  /private/capture-1791690206019693134-25223132 \
  --output-dir /private/new-history-comparison
```

다음 수정은 이력 격리 후보를 다른 기록에 대조한다.
정상 이동에서 새로 거절하는 31개도 검토한다.
실행 8 동시 B_TF 원본은 아직 찾지 못했다.
이 원본 부재를 이미 확보한 ULog 부재와 혼동하지 않는다.
실행 8 분석은 [ULog·영상 분석](hover_run8_analysis_20261012.md)을 따른다.
연속 관측과 이륙 안정성의 완료 판정은 아직 남아 있다.
