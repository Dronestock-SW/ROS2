# 용어 사전 (Glossary)

> 프로젝트에 등장하는 기술 용어 설명. 새 용어가 코드/문서/회의에 등장하면 여기에 추가한다.
> 형식: 정의 → 비유 → 우리 프로젝트에서의 의미

### COMMAND_INT / DO_REPOSITION

정수 위도·경도를 담는 MAVLink 명령 형식과 이동 명령이다.
- 비유: 좌표를 적은 이동 지시서와 그 지시의 종류다.
- 우리 프로젝트: SITL의 수평 목표 전달 후보에 사용한다.
  PX4가 고도를 선택하며 실제 이동 시험은 남아 있다.
  위도·경도에 1e7을 곱한 정수 형식을 E7이라 한다.
  명령 접수와 목표 반영·도착은 각각 따로 확인한다.

### 방위정거 투영

기준점에서의 거리와 방향으로 평면 좌표를 연결하는 식이다.
- 비유: 지구상의 한 기준점에 작은 시험장 지도를 펼친다.
- 우리 프로젝트: PX4의 NED 목표를 전역 좌표로 바꾼다.
  이 좌표 변환 자체가 GNSS 센서 융합을 뜻하지는 않는다.

## 위치추정 (Localization)

### 독립 비행 평가

항법에 쓰지 않은 정답 기록으로 위치·도착을 대조하는 절차다.
- 비유: 선수의 자체 기록을 외부 심판의 기록과 맞춰 본다.
- 우리 프로젝트: Gazebo 정답과 UWB·PX4·목표 기록을 비교한다.
  측위 오차·추정 추종 오차·실제 도착 오차를 따로 계산한다.
  정답은 평가에만 쓰며 비행 피드백에 넣지 않는다.

### UWB (Ultra-Wideband)
초광대역 전파의 도달 시간으로 거리를 재는 실내 측위 기술. GPS가 안 되는 실내에서 수십 cm 정확도로 위치를 잡는다.
- 비유: 방 모서리마다 서 있는 심판들(앵커)이 "소리 지른 지 몇 초 만에 들렸나"로 선수(태그)의 위치를 삼각측량하는 것.
- 우리 프로젝트: 앵커(고정국) 여러 개 + 드론 탑재 태그 1개(DWM3000EVB). 결과는 /uwb_pose (x, y만).

### NLOS (Non-Line-of-Sight, 비가시경로)
송신기와 수신기 사이 직선 경로가 막혀, 전파가 반사되어 돌아 들어오는 상황. 돌아온 만큼 거리가 실제보다 멀게 측정된다.
- 비유: 벽 뒤 사람과 대화할 때 목소리가 벽을 돌아 들려서 실제보다 멀리 있는 것처럼 느껴지는 것.
- 우리 프로젝트: **금속 선반이 가득한 창고는 NLOS 다발 환경**이다. 청정 조건 UWB 오차 ~10cm가 실환경에서는 ~30cm로 벌어진다. 선반 사이 통로 비행이 최악 조건 — 정밀 정렬을 UWB가 아닌 마커에 맡기는 이유(prior_art_uwb_slam.md R2).

### TWR / TDoA

7월의 단일 태그 수치는 당시 기준선이다.
현재 멀티태그 주기는 아래 TDMA 항목을 따른다.
보정 좌표·웹 전송률과 원본 측정률은 구분한다.

UWB가 위치를 재는 두 방식. TWR(Two-Way Ranging) = 태그와 앵커가 서로 주고받아 왕복 시간으로 거리 산출. TDoA(Time Difference of Arrival) = 태그가 신호 한 번만 쏘고 앵커들이 도착 시간차로 계산.
- 차이: TWR은 태그 1개 측위에 메시지 9회가 필요해 태그가 늘면 **태그당 갱신율이 떨어진다.** TDoA는 태그가 한 번만 쏘므로 다수 태그에 훨씬 유리하다.
- 우리 프로젝트: 현재 TWR. 태그 1개 기준선은 43Hz다 (2026-07-30 실측, HW 파트 상향 후).
- 남은 리스크: 태그 2개면 단순 절반 가정으로 약 21Hz — EKF2 권장 하한 30Hz 아래다. 2호기 조립 전 실측 필요. EKF2는 전송률이 낮으면 융합을 거부한다.

### 업데이트율 / 레인징 레이트 (Update Rate / Ranging Rate)

2026-10-07에는 경로별 주기를 따로 기록한다.
아래 43Hz 이력은 현재 웹 송신 주기가 아니다.
[현재 주기 기준](reference/multitag_jetson_web_contract.md)을 따른다.

초당 위치가 몇 번 새로 나오는가(업데이트율)와, 그 위치를 만들려고 거리 측정을 초당 몇 번 하는가(레인징 레이트). 앞이 결과, 뒤가 원인이다.
- 비유: 업데이트율은 초침이 움직인 횟수, 레인징 레이트는 그 초침을 밀어주는 내부 톱니가 돈 횟수.
- 함께 쓰는 말: 폴링 주기(poll interval) = 태그가 앵커를 부르는 간격. 이 간격을 줄이면 레인징 레이트가 오른다. 전송률·갱신율도 같은 뜻으로 쓰인다.
- 천장이 있는 이유: TWR은 좌표 1개에 메시지 9회를 주고받는다. 그 왕복 시간이 곧 1프레임이라 무한정 못 줄인다.
- 우리 프로젝트: 태그 약 43Hz. EKF2 권장 30~50Hz 범위 안이다 — 현재 Hz 부족 문제는 없다.
  - 실측 근거: `pose_interval_ms` 중앙값 23ms (2026-07-30 정지 상태 230샘플). 최대 55ms까지 튄다.
  - 이력: 초기 약 12Hz → HW 파트가 상향해 43Hz 달성. 12Hz는 개선 전 값이다.
  - **상향은 태그·앵커 쪽 작업이라 companion에서는 못 올린다.** 이 개선도 HW 파트가 했다.

### 보간 / 업샘플링 (Interpolation / Upsampling)
띄엄띄엄 들어온 값 사이를 계산으로 채워 겉보기 Hz를 올리는 것.
- 비유: 10장짜리 만화를 40장으로 늘려 그리는 것. 장수는 늘지만 이야기는 그대로다.
- 왜 금지에 가까운가: 새 정보는 0인데 EKF2는 신선한 관측이 늘었다고 믿고 확신을 올린다. 과신하는 추정기가 되어 반대 증거를 무시한다(추정기 캐스케이드와 같은 성격의 오류).
- 우리 프로젝트: 현재 해당 없음. HW 파트 상향으로 43Hz를 확보해 EKF2 권장 범위를 만족한다.
  태그 2개 운용에서 Hz가 다시 모자랄 때만 최후 수단으로 검토한다. 쓴다면 반복본의 공분산을 키워 "이건 자신 없다"고 표시해야 한다.

### 관측치 전처리 (이상치 제거 · 평활)
센서 값을 추정기에 넘기기 전에 거짓값을 버리고 떨림을 줄이는 작업. 새 위치를 계산하는 게 아니라 받은 값을 걸러내는 것이다.
- 비유: 친구 5명에게 시간을 물어, "밤 11시"라 답한 고장 시계 하나만 빼고 나머지를 평균 내는 것.
- 두 단계: 이상치 제거(outlier rejection) = 직전 값 대비 크게 튄 값을 버린다. 평활(smoothing) = 남은 값을 이동평균·저역통과로 다듬는다.
- 대가: 평활은 지연을 만든다. 5개 이동평균은 약 2프레임 뒤처진다. 그만큼 `EKF2_EV_DELAY`에 반영해야 한다. Hz 확보와는 서로 상충한다.
- 우리 프로젝트: 결정 10이 명시적으로 허용하는 범위다. 추정기가 아니므로 companion에서 해도 된다. 출력은 PX4에 넘기는 관측치일 뿐, 비행제어가 쓰는 위치해가 아니다.

### 앵커 / 태그 (Anchor / Tag)
UWB의 두 역할. 앵커 = 위치를 아는 고정 기준국(최소 3~4개), 태그 = 위치를 알고 싶은 이동체 부착 장치.
- 우리 프로젝트: 태그 1개(DWM3000EVB) + 자체 제작 앵커 4기. 앵커는 설치·좌표계 검증까지 완료.

### fix (측위 확정)
태그가 계산한 위치를 "믿을 만하다"고 스스로 판정한 상태. 태그가 내보내는 JSON의 `fix` 필드가 그 판정 결과다.
- 비유: GPS 수신기가 위성을 잡는 중일 때와 좌표를 확정해 보여줄 때의 차이.
- 우리 프로젝트: `fix:false`면 x, y는 마지막 유효값을 붙잡고 있는 값이다. 새 측정이 아니다. 이 상태의 값을 vision_pose로 PX4에 넘기면 안 된다.

### 잔차 (Residual)
위치 해를 하나 정한 뒤, 그 위치라면 나왔어야 할 거리와 실제 측정 거리의 차이. 해가 관측과 얼마나 안 맞는지를 재는 값이다.
- 비유: 용의자를 한 명 지목한 뒤, 그 사람이라면 설명돼야 할 증언들이 실제로 얼마나 어긋나는지 세어보는 것.
- 판독법: 잔차가 크면 거리 측정이 틀렸거나 **앵커 좌표 설정이 틀렸다.** 거리값이 안정적인데 잔차만 크면 후자를 먼저 의심한다.
- 우리 프로젝트: 태그가 `pose_residual_rms_m`을 내보낸다. 2026-07-29 측정에서 0.44m가 지속되어 `fix`가 서지 않았다.

### anchor mask (앵커 사용 마스크)
이번 위치 해를 푸는 데 실제로 쓴 앵커를 이진 비트로 표시한 값. 비트 1개가 앵커 1기에 대응한다.
- 읽는 법: 15 = 이진 1111 = 앵커 4기 전부 사용. 7 = 0111 = 앵커 1·2·3만 사용, 4번은 제외.
- 우리 프로젝트: 태그의 `solve_anchor_mask`. 3기만 쓰면 해의 기하가 나빠져 정확도가 떨어진다. 값이 15가 아니면 원인을 찾아야 한다.
- **함정**: `adaptive_excluded_mask`는 비트 규칙(bit0=A1…)은 같지만 **비트=1이 "제외"** 다. `solve_anchor_mask`와 정반대다. `solve_anchor_mask=11` + `adaptive_excluded_mask=4`는 "A3를 빼고 3기로 풀었다"는 같은 사실을 반대로 적은 것이다.

### 거리 bias / antenna delay (고정 오차 / 안테나 지연)
bias = 앵커가 항상 일정하게 길거나 짧게 재는 고정 오차. antenna delay = 그 원인이 되는, 안테나·회로를 통과하는 데 걸리는 고정 시간. 교정으로 상쇄한다.
- 비유: 눈금이 5cm 밀린 자. 열 번 재서 평균 내도 여전히 5cm 밀려 있다.
- 흔들림(sigma)과 다르다: 흔들림은 평균으로 줄지만 bias는 안 준다. **필터로는 절대 못 고친다.**
- 우리 프로젝트: 태그의 `range_bias_a*_m`. 2026-08-09 실측 기준 4기 전부 0 — 교정 미실시 상태다. 이 때문에 A2가 +81cm, A3가 +34cm 길게 재고 위치 오차 약 0.66m가 난다. 교정은 HW 파트 작업이다. [hw_handoff 참조](hw_handoff/easy_guide.md)

### 적응형 앵커 제외 (Adaptive Anchor Exclusion)
거리가 다른 앵커들과 계속 모순되는 앵커를 태그가 스스로 위치 계산에서 빼는 기능.
- 비유: 반 아이들에게 시간을 물어 다수결에서 제일 동떨어진 한 명을 빼는 것.
- **한계**: 진짜 좌표를 모르고 "나머지와의 합의"만 본다. 그래서 가장 큰 bias를 가진 앵커가 합의 자체를 끌고 가 버리면, **엉뚱하게 정확한 앵커가 잘린다.** 실측에서 오차 최대는 A2(+81cm)인데 33/34회 잘린 건 A3(+34cm)였다.
- 우리 프로젝트: `adaptive_excluded_mask`, `adaptive_exclusion_state_mask`. 3기 운용은 설계된 동작이지 이상 징후가 아니다. 다만 **잘린 앵커가 범인이라는 뜻은 아니다.**

### 제어 hold (hold_bridge)
새 위치를 못 구했을 때 직전 유효 좌표를 짧게(최대 500ms) 재사용해 제어 공백을 메우는 동작.
- 비유: 말이 잠깐 끊긴 통역사가 앞 문장을 그대로 다시 읽어 대화를 잇는 것.
- 우리 프로젝트: `reason=hold_bridge`, `xy_control_held=true`. 이때 `hybrid_source=none`이면 **화면에 좌표가 떠 있어도 새 위치는 하나도 만들어지지 않았다.** 500ms를 넘기면 `fix=false`로 떨어진다. 2026-08-09 실측에서 568프레임 중 225(40%)가 `none`이었다.

### qscore / quality_score (처리 품질점수)
한 사이클 처리에 감점 사유(시간 초과·재시도·gate 거부·앵커 제외 등)가 있었는지 100점 만점으로 표시한 값.
- 비유: 숙제 감점표. 감점이 없다는 뜻이지 잘했다는 뜻이 아니다 — 숙제를 아예 안 내도 감점은 0이다.
- **정확도가 아니다.** 실측에서 100점이 나온 유일한 프레임은 `solve_anchor_mask=0`(위치 계산 실패)이었고 실제 오차는 0.57m였다.
- 우리 프로젝트: 단독 표시 금지. `fix`, `reason`과 항상 함께 본다. 대시보드에서 정확도 게이지로 만들지 않는다.

### 필드 없음 vs false (로그 판독 원칙)
로그에 필드가 **아예 없는 것**과 필드가 `false`인 것은 완전히 다르다. 없는 것은 "미측정/미지원"이다.
- 비유: 시험지에 4번 답이 비어 있는 것과, 애초에 4번 문제가 없는 시험지는 다르다.
- 우리 프로젝트: 태그 로그는 압축 프레임(13필드, 90%)과 상세 프레임(94필드, 10 seq마다)이 섞여 나온다. 압축 프레임에 `range_fail_a1`이 없다고 통신 실패가 아니다. `kf_*` 6개는 현재 펌웨어에서 전부 미출력 — `false`로 렌더링하면 있지도 않은 "칼만 거부"를 만들어낸다. 마찬가지로 `pose_residual_rms_m`의 `null`은 0이 아니라 "후보 없음"이다.

### EKF (Extended Kalman Filter, 확장 칼만 필터)
노이즈 낀 여러 센서 값을 "예측 + 관측 보정"으로 융합해 진짜 상태를 추정하는 알고리즘.
- 비유: 시계가 여러 개인데 다 조금씩 틀릴 때, 각 시계의 못 믿을 정도를 반영해 가중 평균으로 진짜 시각을 추정하는 것. 단순 평균과 달리 "방금 전 추정치"도 근거로 쓴다.
- 우리 프로젝트: 융합은 전부 PX4 EKF2가 담당한다(결정 10). companion에는 비행용 EKF를 두지 않는다.

### EKF2
PX4 펌웨어에 내장된 상태추정 모듈의 이름. IMU·기압계·거리계·광학흐름·외부 pose를 융합해 기체의 위치·속도·자세를 추정한다.
- 주의: Pixhawk 6C Mini는 **하드웨어 보드**이고, PX4는 그 위에 올라간 **펌웨어**이며, EKF2는 PX4 안의 **모듈**이다. 보드를 샀다고 딸려오는 게 아니라 PX4가 제공하는 것이고, 파라미터(`EKF2_*`)로 어떤 센서를 믿을지 지정해줘야 동작한다.
- 우리 프로젝트: 비행제어의 유일한 상태추정기(결정 10). Phase 0의 TFmini/PMW3901 작업이 곧 EKF2 파라미터 설정 작업이다.

### EKF2_EV_CTRL / EKF2_EV_DELAY (외부 위치 융합 설정)
EKF2에게 "외부 pose 중 뭘 믿을지"와 "그 값이 얼마나 늦게 도착하는지"를 알려주는 파라미터 두 개.
- `EKF2_EV_CTRL`: 비트 합. 1=XY 위치, 2=Z 위치, 4=속도, 8=Yaw. 비유하면 리모컨 버튼 4개를 켜고 끄는 것.
- `EKF2_EV_DELAY`: 외부 pose가 IMU보다 얼마나 늦게 도착하는지(0~300ms). 감으로 넣지 말고 실측한다. 관측치 전처리(평활)를 강화하면 이 값도 함께 올려야 한다.
- 우리 프로젝트: **`EKF2_EV_CTRL=1`이 맞다.** UWB는 x, y만 낸다(`/uwb_pose`). 3으로 켜면 오지 않는 Z를 기다리게 된다. 높이는 TFmini Plus 담당이며 `EKF2_HGT_REF=2`(Range sensor) 방향이다 — altitude_policy.md와 같은 결론이다.

### 공분산 행렬 (Covariance Matrix)
"이 값이 얼마나 못 미더운가"를 숫자로 적어 값과 함께 보내는 표. ROS 메시지에서는 `PoseWithCovarianceStamped`의 `covariance` 필드다.
- 비유: 답을 말하면서 "확신 80%"라고 같이 말해 주는 것. 듣는 쪽이 얼마나 믿을지 정할 수 있다.
- 왜 중요한가: EKF2는 이 값을 보고 센서를 얼마나 신뢰할지 정한다. 작게 적으면 "아주 정확함"이라고 우기는 셈이라 추정기가 과신한다.
- **한계**: 공분산은 흔들림만 표현한다. 일정하게 밀린 [bias](glossary.md)는 공분산으로 알릴 방법이 없다. 교정 전 UWB는 어떤 값을 넣어도 EKF2가 정직하게 다룰 수 없다.
- 우리 프로젝트: `/uwb_pose`는 x, y에 실측 기반 값을, **z와 회전에는 아주 큰 값**을 넣는다. UWB는 z와 방향을 모르기 때문이다. z 공분산을 작게 두면 나중에 `EKF2_EV_CTRL`을 3으로 바꿨을 때 "고도 0m를 확신함"이 되어 기체가 바닥으로 내려가려 한다.

### 좌표계 중복 변환 (ENU / NED 축 반전 사고)
ROS는 ENU(Z Up), PX4는 NED(Z Down)를 쓴다. MAVROS 표준 plugin이 이 변환을 대신 해준다.
- 비유: 통역사가 이미 번역해 주는데 내가 한 번 더 번역하면 원래 말로 되돌아간다.
- 사고 형태: 우리 코드에서 축을 뒤집고 MAVROS도 뒤집으면 **두 번 뒤집혀 원위치**가 된다. 드론이 위로 가라는 명령에 아래로 간다.
- 우리 프로젝트: UWB 좌표축을 처음부터 ROS ENU 기준에 맞춰 발행하고, PX4 변환은 MAVROS에게만 맡긴다. 우리 노드에서 추가 변환 금지.

### Innovation / Innovation Test Ratio (혁신량 / 혁신 검정비)
Innovation = "센서가 말한 값 − 필터가 예측한 값"의 차이. Test ratio = 그 차이를 허용 한계로 나눈 정규화 지표.
- 비유: 일기예보(예측)와 실제 날씨(관측)의 차이. 매번 조금씩 어긋나는 건 정상이고, 크게 어긋나면 예보 모델이 잘못된 것이다.
- 판독법: **평상시 0.5 이하**면 정상, 가끔 튀는 건 무방. **1.0 초과 시 해당 측정은 기각**되어 융합에 쓰이지 않는다.
- 우리 프로젝트: EKF2 튜닝이 맞았는지 확인하는 **객관적 지표**. 만성적으로 높으면 노이즈 파라미터를 너무 작게 줬거나(센서 과신) `EKF2_EV_DELAY` 보정이 틀렸다는 뜻. 튜닝이 감이 아니라 검증 가능한 작업인 근거.

### 퇴화 (Degeneration)
LiDAR 스캔매칭이 방향을 특정하지 못하는 상태. 특징 없는 긴 복도처럼 어느 쪽으로 움직여도 스캔 모양이 같으면, 이동량을 역산할 수 없다.
- 비유: 무늬 없는 벽지 앞에서 눈 감고 옆으로 걸으면, 손으로 더듬어봐야 얼마나 갔는지 알 수 없는 것.
- 우리 프로젝트: 창고의 균일한 선반 통로가 전형적 퇴화 환경. UWB가 절대 위치를 잡아줘 이를 구제하는 것이 결정 1(UWB+스캔매칭 융합)의 핵심 근거다.

### 관측치 vs 추정치 (Observation vs Estimate)
관측치 = 센서가 잰 날것의 값("앵커에서 3.2m"). 추정치 = 여러 관측치를 융합해 나온 결론("나는 (1.2, 4.5)에 있다").
- 비유: 관측치는 목격자 증언, 추정치는 그 증언들을 종합한 수사 결론.
- 우리 프로젝트: companion은 **관측치만 만들어 PX4에 넘긴다.** 추정치를 만드는 건 EKF2의 몫이다(결정 10).

### 추정기 캐스케이드 (Estimator Cascade)
이미 융합된 추정치를 다시 다른 필터에 넣어 융합하는 잘못된 구조.
- 왜 문제인가: 뒤쪽 필터는 앞쪽 결과를 "새로운 독립 증언"으로 착각한다. 실제 증언은 3개인데 6개로 세는 셈이라 **공분산(확실도)이 실제보다 낙관적으로 나온다.** 과신하는 추정기는 반대되는 증거를 무시하므로 틀렸을 때 스스로 못 고친다. 게다가 고장 시 어느 필터가 범인인지 분리할 수 없다.
- 비유: 내가 퍼뜨린 소문이 여러 사람을 거쳐 돌아오면 남들도 다 아는 사실처럼 느껴지는 것. 정보가 늘어난 게 아니라 메아리친 것이다.
- 우리 프로젝트: 결정 10이 금지하는 대상. `robot_localization` 도입 제안이 나오면 이 항목을 근거로 검토한다.

### vision_pose
PX4가 외부 위치추정 장치로부터 pose를 받아들이는 표준 입력 채널(MAVROS의 `/mavros/vision_pose/pose`). 이름은 "vision"이지만 카메라 전용이 아니라 UWB·모션캡처·SLAM 등 어떤 외부 pose 소스든 쓸 수 있다.
- 우리 프로젝트: UWB의 (x, y)를 PX4 EKF2에 넣는 통로. `/uwb_pose` 노드의 최종 출력 목적지.

### 스캔매칭 (Scan Matching)
LiDAR의 이번 스캔과 직전 스캔(또는 지도)을 겹쳐 맞춰보고, "얼마나 움직였는지"를 역산하는 기법.
- 비유: 어두운 방에서 눈 감고 걸으며, 손으로 더듬은 벽 모양의 변화로 내가 얼마나 이동했는지 알아내는 것.
- 우리 프로젝트: Phase 2에서 UWB 드리프트 보정용으로 도입. scan-to-scan(직전과 비교) → scan-to-map(누적 지도와 비교) 순.

### SLAM (Simultaneous Localization and Mapping)
지도를 만들면서 동시에 그 지도 안에서 내 위치를 추정하는 기술. 스캔매칭을 지도 구축까지 확장하면 SLAM이 된다.
- 우리 프로젝트: 구 WBS는 배제했으나 전면 재설계에서 Phase 2 방향으로 채택.

### 광학 흐름 (Optical Flow)
카메라 영상에서 바닥 무늬가 흘러가는 방향/속도로 수평 이동을 추정하는 기법.
- 비유: 기차 창밖 풍경이 뒤로 흐르는 속도로 기차 속도를 짐작하는 것.
- 우리 프로젝트: PMW3901 센서 보유(BOM). Phase 2에서 융합 후보로 평가.

### H80 / Q_S10
- 정의: 참고 ZIP과 `preimu` 코드의 계산 방식 이름이다.
  H80은 최근 거리들을 모아 수평 위치를 계산한다.
  Q_S10은 높이 입력과 임시 거리 편향을 함께 사용한다.
- 비유: 최근 기록을 함께 읽는 계산과 복구용 재검산이다.
- 우리 프로젝트: [UWB 참고 자료](reference/uwb_h80_qs10_reference.md)를 따른다.
  H80 창은 기본 0.8초다.
  Q_S10의 복구 조건과 실시간 높이 연결은 검증 대상이다.

### 거리·위치 게이트
- 정의: 값의 변화가 허용 범위 안인지 판별하는 조건이다.
- 비유: 갑자기 튄 값을 통과시키기 전 확인하는 문이다.
- 우리 프로젝트: 고정 여유에 속도와 경과 시간을 곱해 더한다.
  기본값은 `preimu/settings.py`에 있다.
  값이 정의되어도 실제 입력 경로의 동작은 따로 검증한다.

### Huber 기준 / 적합 RMS
- 정의: Huber 기준은 큰 잔차의 영향을 줄이는 경계다.
  적합 RMS는 계산한 거리와 관측 거리의 잔차 크기다.
- 비유: 튄 답의 영향 조절값과 전체 답의 불일치 점수다.
- 우리 프로젝트: 기본값은 각각 0.12 m와 상한 0.10 m다.
  적합 잔차가 작다고 실제 위치 오차까지 작다는 뜻은 아니다.

### Shadow 모드
- 정의: 계산 결과를 기록하되 비행제어에 적용하지 않는 시험이다.
- 비유: 실제 조종 옆에서 답만 적어 보는 모의 운용이다.
- 우리 프로젝트: UWB RAW·후보값·판정 결과를 비교한다.
  제어 전달 여부와 로그 저장 여부를 따로 확인한다.

### 출력 계약
- 정의: 결과 필드와 받는 쪽의 사용 규칙이다.
- 비유: 수치·측정일·판정을 함께 적는 검사 결과표다.
- 우리 프로젝트: UWB 결과의 출처·시각·사용 여부를 적는다.
  `null`은 계산값 없음이며 0m가 아니다.
  현재 파이프라인의 `valid=false`는 사용 보류다.
  자세한 필드는 [파이프라인 기준](architecture/uwb_pipeline_design.md)에 있다.

### 계산 게이트
- 정의: 수식 함수를 실행할지 정하는 경계다.
- 비유: 자료 접수 후 계산실 앞에서 멈추는 문이다.
- 우리 프로젝트: ToF 자료 축적 중에는 닫아 둔다.
  거리 게이트의 이상치 판별과는 다른 기능이다.
  Z·XY 수식 실행과 좌표 외부 전달을 각각 차단한다.

## 제어 (Control)

### 자세제어 vs 위치제어 (Attitude vs Position Control)
자세제어 = 기체의 기울기/회전을 밀리초 단위로 잡는 안쪽 루프. 위치제어 = "어디로 갈지" 속도/위치를 명령하는 바깥 루프.
- 비유: 자세제어는 소뇌(균형 반사), 위치제어는 대뇌(어디로 걸을지).
- 우리 프로젝트: 자세제어는 PX4 전담(건드리지 않음, 확정). companion(Jetson)은 위치제어만.

### PID 제어
오차에 비례(P), 누적(I), 변화율(D)로 반응하는 고전 제어기. P만 쓰면 P-control.
- 비유: 목표까지 남은 거리만큼 액셀(P), 계속 못 미치면 조금 더(I), 너무 빨리 접근하면 브레이크(D).
- 우리 프로젝트: Phase 1에서 위치제어를 P → PID로.

### 게인 스케줄링 (Gain Scheduling)
상황에 따라 제어기 게인(민감도) 세트를 갈아끼우는 기법.
- 비유: 고속도로에서는 둔감한 핸들, 주차장에서는 민감한 핸들로 자동 전환.
- 우리 프로젝트: 목표 근접 시 감속 게인 세트 등. "자세제어 AI" 항목의 실제 의미가 이것으로 확정됨.

### Offboard 모드
PX4의 비행 모드 중 하나. 외부 컴퓨터(companion)가 보내는 setpoint를 따라 비행하는 모드.
- 우리 프로젝트: Jetson의 /cmd_vel → MAVROS → PX4 Offboard가 기본 제어 경로.
- **setpoint 자체가 생존 신호다**: PX4 v1.17은 setpoint 스트림을 2Hz보다 빠르게 계속 받아야 한다. 제자리에 머무를 때도 같은 목표를 계속 보내야 한다. 진입 전 최소 1초 이상 스트림이 먼저 들어와 있어야 한다.
- **현재 위치와 목표 위치는 다른 경로다**: UWB 현재 좌표는 vision_pose → EKF2로, 목표 좌표는 setpoint → Offboard 제어기로 간다. 현재 위치를 setpoint에 넣으면 "지금 자리로 가라"가 되어 드론이 움직이지 않는다.

### Offboard loss failsafe (COM_OF_LOSS_T / COM_OBL_RC_ACT)
setpoint 스트림이 끊겼을 때 PX4가 자동으로 취하는 안전 조치. 대기 시간과 조치 내용을 따로 정한다.
- 비유: 무전 정기 교신("이상 없음")이 끊기면 정해둔 시간 뒤 수색을 시작하는 규칙.
- `COM_OF_LOSS_T`: 끊긴 뒤 failsafe 발동까지 기다리는 시간(기본 1.0s). `COM_OBL_RC_ACT`: 그때 할 행동 — 0=Position, 1=Altitude, 2=Stabilized, 3=Return, 4=Land, 5=Hold, 6=Terminate, 7=Disarm.
- 우리 프로젝트: 실내 창고에서 3(Return)은 선반 충돌 위험이 크다. 5(Hold)는 **현재 위치 추정이 정상일 때만** 성립하므로, UWB bias 교정 전에는 4(Land)가 안전하다. UWB 상실과 Jetson 통신 상실은 서로 다른 고장이므로 failsafe를 분리해 시험한다.

### Loiter
PX4 비행 모드. 현재 위치·고도를 스스로 유지하며 제자리 비행(호버링)하는 모드.
- 우리 프로젝트: 이륙 시퀀스의 목표 상태. arm → 상승 → Loiter 진입까지가 Phase 1의 자동화 구간.

### Position 모드 / 위치 유지 (Position hold)

Position은 조종기로 이동을 지시하는 PX4 모드다.
수평 스틱을 놓으면 감속하고 위치를 유지한다.
- 비유: 손을 놓으면 그 자리에 멈추는 이동 보조다.
- 우리 프로젝트: 9월 27일 `POSCTL=2`를 확인했다.
  위치 유지는 동작을 뜻한다.
  자동 Hold 모드인 `AUTO_LOITER=4`와 구별한다.
  [최초 분석](report/position_hold_20260927.md)을 따른다.

### .params 파라미터 파일

### FSM (Finite State Machine, 유한 상태 기계)
시스템이 가질 수 있는 상태들과 상태 간 전환 조건을 명시한 설계. 
- 비유: 신호등. 빨강→초록→노랑, 각 전환에는 조건(타이머)이 있고 동시에 두 상태일 수 없다.
- 우리 프로젝트: 임무 로직의 시작점. IDLE → TAKEOFF → LOITER → GOTO → ARRIVED → LAND.

### Behavior Tree (BT, 행동 트리)
행동을 트리 구조로 조합하는 임무 설계 기법. FSM보다 복잡한 임무(재시도, 우선순위, 병렬 감시)를 깔끔하게 표현한다. 게임 AI와 로보틱스의 표준.
- 비유: FSM이 "역마다 정해진 다음 역이 있는 노선도"라면, BT는 "상황 보고 하위 계획을 갈아끼우는 작전 트리".
- 우리 프로젝트: 임무가 다중 목표 순회 + 마커 시퀀스로 복잡해지는 시점(Phase 3~4)에 FSM에서 전환.

### 비주얼 서보잉 (Visual Servoing)
카메라에 보이는 대상(마커 등)의 위치 오차를 직접 제어 입력으로 써서 기체를 정렬시키는 기법.
- 비유: 주차 카메라의 가이드라인이 가운데 오도록 핸들을 트는 것.
- 우리 프로젝트: Phase 3. 마커가 화면 중앙·정면에 오도록 드론 위치를 미세 조정.

### 정면성
카메라 광축과 라벨 면이 얼마나 마주 보는가. 0도면 정면, 각도가 커질수록 비스듬히 본다.
- 비유: 책을 똑바로 펴서 읽는 것과 비스듬히 눕혀 읽는 것의 차이. 글자 크기는 같아도 눕히면 안 읽힌다.
- 우리 프로젝트: QR 판독을 거리보다 더 좌우하는 변수다(2026-10-04 실측 — 9~10도는 판독률 85~100%, 13도는 55%). 허용 예산은 10도 안팎이다. 측정으로 보정하지 않고 임무 계획의 선반 방위로 맞춘다 (`aruco_alignment_node.py`의 "정면성 미사용" 참조).

## 마커 / 비전 (Markers / Vision)

### ArUco 마커
pose(위치+기울기) 추정 전용으로 설계된 흑백 격자 마커. 프린터로 출력해 붙이면 되는 종이 한 장이다.
- 왜 QR이 아니라 이것인가: QR은 근거리 정면 판독용이라 멀리서/비스듬히/흔들리며 보면 검출이 잘 깨진다. ArUco는 굵은 격자라 몇 픽셀만 잡혀도 검출되고, OpenCV 내장 검출기가 꼭짓점을 서브픽셀 정밀도로 준다. 내장 ID(숫자)로 선반 구분도 가능.
- 실전 규칙: 한 변 10~15cm(대략 변 길이의 100배 거리까지 안정 검출), 무광 용지, 평평하게 부착, 인쇄 후 실측 크기를 파라미터로 입력(프린터 축소 오차 보정).
- 우리 프로젝트: 하이브리드 라벨(ArUco=정렬용 + QR=데이터용)로 사용. 단 Phase 3에서 QR 단독 pose 실험을 먼저 하고 한계를 문서화한 뒤 전환.

### AprilTag
ArUco와 같은 목적의 마커. 로보틱스 연구계 표준에 가깝고 검출 강건성이 다소 우수. ArUco 대안으로 언제든 교체 가능.

### solvePnP
"모양과 실제 크기를 아는 무늬"의 꼭짓점들이 영상 어디에 찍혔는지로부터, 카메라와 무늬 사이의 3D 위치·각도를 역산하는 OpenCV 함수. 마커 기반 자세보정의 수학적 심장.
- 이것 때문에 마커의 "실측 크기"가 반드시 필요하다.

### QR 코드
데이터(문자열) 저장·판독용 2D 코드. 세 모서리의 파인더 패턴 꼭짓점으로 pose 추정도 가능은 하나(QRCodeDetector + solvePnP), 검출 거리/각도/연산량에서 ArUco에 밀린다.
- 우리 프로젝트: 재고 데이터 운반 담당. USB 스캐너(DE2110)는 문자열만 출력하므로 pose 추정에는 사용 불가 — pose는 카메라(IMX219) 몫.

### pyzbar
libzbar(오픈소스 바코드/QR 디코딩 엔진)를 감싼 Python 바인딩. 이미지 배열을 넣으면 디코딩된 문자열과 꼭짓점 좌표(rect)를 돌려준다.
- 비유: 사진 속 글자를 읽어주는 통역사. OpenCV는 사진을 다루는 도구일 뿐 글자를 읽지는 못한다.
- 함정: 3채널(BGR/RGB) numpy 배열을 그대로 넣으면 그레이스케일 변환 없이 **첫 채널만 떼어 쓴다**(파란 채널만 보는 셈). `cv_bridge`에서 `desired_encoding='mono8'`로 받아 이 함정을 피한다.
- 우리 프로젝트: `qr_decoder_node`가 `/camera/image_raw`를 구독해 pyzbar로 QR을 디코딩한다.

### 이진화 (Binarization) / Otsu 방법
회색조 이미지의 각 픽셀을 임계값 하나와 비교해 흑 아니면 백으로만 가르는 것. Otsu 방법은 그 임계값을 사람이 정하지 않고 밝기 히스토그램에서 흑·백 두 덩어리가 가장 잘 갈리는 지점으로 자동 계산한다.
- 비유: 시험 점수로 합격·불합격을 가를 때, 커트라인을 60점으로 미리 정해두는 게 고정 임계값이고, 실제 점수 분포를 보고 두 무리가 가장 뚜렷하게 갈리는 지점을 커트라인으로 잡는 게 Otsu다.
- 왜 필요한가: zbar는 내부에 자체 이진화를 갖고 있지만, 라벨이 충분히 밝지 않아 밝기가 중간 구간에 몰리면 임계값을 못 잡는다. 디코딩 실패로만 보이고 이유는 안 드러난다.
- 한계: 전역 Otsu는 임계값 하나를 영역 전체에 쓴다. 조명 기울기가 심해 한쪽은 다 희고 한쪽은 다 검게 나오면 깨진다. 그때는 영역을 잘게 나눠 각각 임계값을 잡는 `adaptiveThreshold`가 답이다.
- 우리 프로젝트: `qr_decoder_node`가 ROI·전체 프레임 각 단계에서 원본으로 먼저 디코딩하고, 실패할 때만 Otsu 이진화로 재시도한다([폴백](glossary.md) 구조). 2026-10-04 실측에서 원본·CLAHE·2배확대·샤픈은 전부 실패하고 Otsu만 성공했다 — QR 영역 밝기가 35~180에 몰려 있었고(같은 프레임 다른 곳은 255까지 오름) Otsu가 임계값 101을 직접 찾아 통과했다. 이 폴백 이전에는 244프레임 연속 미검출이었다.

### 키보드 웨지 (Keyboard Wedge)
바코드/QR 스캐너가 디코딩한 문자열을 USB HID 키보드 입력인 것처럼 흉내내서 보내는 출력 방식. 호스트 쪽에서 보면 누군가 타이핑한 것과 구별이 안 된다.
- 비유: 번역기가 통역한 말을 직접 말하는 대신, 옆에서 대신 받아 적어주는 대필자를 끼워 넣는 것 — 원래 대화(USB 키보드 입력)에 "끼어드는(wedge)" 방식이라 이런 이름이 붙었다.
- 함정: 포커스 잡은 아무 창에나 그대로 입력된다. 터미널이 포커스면 스캔한 문자열이 명령어처럼 실행될 수 있다. 리눅스에서는 evdev로 해당 장치를 `grab()`해 다른 프로그램에 새지 않게 막아야 한다.
- 우리 프로젝트: DYSCAN DE2110이 이 방식(USB Mode, Communication Interface 설정값)으로 동작한다. `qr_reader_node`가 evdev로 전용 grab해서 읽는다.

### Sense Mode / Manual Mode (스캐너 트리거 방식)
바코드 스캐너가 언제 디코딩을 시도할지 정하는 설정. Manual Mode = 버튼을 눌러야 스캔. Sense Mode = 렌즈 앞에 코드가 나타나면 자동으로 스캔.
- 비유: Manual Mode는 초인종을 눌러야 응답하는 것, Sense Mode는 사람이 오면 스스로 반응하는 자동문.
- 우리 프로젝트: DE2110 기본값은 Manual Mode다. 물리 버튼을 소프트웨어로 대신 누르게 만드는 대신, 설정용 QR코드(Reading Mode → Sense Mode)를 스캔해 트리거 자체를 없앴다(2026-08-23).
- **함정(정정)**: 처음엔 "USB 재연결(전원 재인가) 시 Manual Mode로 되돌아간다"고 오판했다. 실제로는 Sense Mode가 재연결 후에도 유지되고 있었고, 진짜 원인은 `qr_reader_node`가 재연결 전의 죽은 evdev 파일디스크립터를 계속 붙들고 있었던 소프트웨어 버그였다(2026-08-23 재검증, 노드만 재시작하니 버튼 없이 바로 인식). 스캐너 자체는 설정을 전원 재인가 후에도 유지한다 — 자세한 내막은 [evdev](glossary.md) 항목·`qr_reader_node`의 "USB 재연결 자동 복구" 주석 참조.

### ROI (Region of Interest, 관심 영역)
이미지 전체가 아니라 처리할 필요가 있는 일부 영역만 잘라내는 것.
- 비유: 신문 전체를 다시 읽지 않고, 어제 기사가 있던 페이지 근처만 펼쳐보는 것.
- 우리 프로젝트: `qr_decoder_node`가 QR을 한 번 찾으면, 다음 프레임부터는 그 위치 주변(여백 `roi_margin_px`)만 잘라 디코딩해 처리 시간을 줄인다. ROI에서 못 찾으면 그 프레임 안에서 즉시 전체 프레임으로 재시도한다.

### 폴백 (Fallback)
1순위 방법이 계속 실패할 때 2순위 방법으로 자동 전환하는 것. 1순위가 복구되면 다시 2순위를 끈다.
- 비유: 주 출입문이 잠겨 있으면 비상구로 돌아가는 것 — 평소엔 비상구를 열어두지 않는다(자원 낭비라서).
- 우리 프로젝트: `qr_fallback_node`가 DE2110 리더기(`/qr_reader/data`)를 1순위로 쓰다가, `attempt_timeout_sec`(기본 3초) 창에서 `fallback_threshold`(기본 3)회 연속 스캔이 없으면 카메라+pyzbar(`qr_decoder_node`)를 `~/set_enabled`로 켠다. 리더기가 다시 스캔에 성공하면 즉시 카메라를 꺼서 CPU를 아낀다 — `qr_decoder_node`는 프레임당 100ms대라 상시 켜두는 비용이 크다. 두 경로 중 어느 쪽에서 오든 결과는 `/qr/data`로 통일해 발행해, 하위 소비자는 소스를 몰라도 된다.

## ROS2 기초

### ROS2 (Robot Operating System 2)
이름에 OS가 들어가지만 운영체제가 아니다. 여러 프로그램이 데이터를 주고받게 해주는 통신 규약 + 도구 모음이며, 우분투 위에서 도는 라이브러리다.
- 왜 쓰는가: 센서 읽기·위치 계산·모터 명령을 한 프로그램에 다 넣으면 하나가 죽을 때 전부 죽고, 센서를 바꾸면 전체를 고쳐야 한다. ROS2는 작은 프로그램 여러 개로 쪼개고 그 사이 배선을 표준화한다.
- 우리 프로젝트: Humble 배포판. companion(Jetson) 위에서 돈다. Pixhawk 안에는 ROS2가 없다 — 거긴 PX4 펌웨어다.

### Node / Topic
Node = 하나의 일을 하는 프로그램 단위. Topic = 노드들이 데이터를 주고받는 방송 채널. 발행(publish)하는 쪽과 구독(subscribe)하는 쪽이 서로를 몰라도 채널명만 맞으면 통신된다.
- 이 분리 덕에 센서를 교체해도 구독자 코드는 불변 — 본 프로젝트 아키텍처의 근간.
- 우리 프로젝트: 웹 API 경계(`/target_pose` 등)를 topic으로 고정한 것이 같은 원리다(roadmap 결정 3).

### Service / Action
Topic 외의 두 가지 통신 방식. Service = 요청 → 응답 1회. Action = 오래 걸리는 작업 + 중간 보고 + 취소.
- 비유: Topic은 라디오 방송, Service는 전화 문의, Action은 택배 배송 조회.
- 고르는 법: 응답이 필요 없고 계속 흐르면 Topic. 즉답이 필요하면 Service. 수 초 이상 걸리고 취소가 필요하면 Action.
- 우리 프로젝트: 센서는 전부 Topic. "지정 좌표까지 이동"은 Action 후보(Phase 1).

### DDS / discovery
ROS2의 통신 엔진. 항공·국방에서 쓰던 표준을 채택했다. 중앙 관리자가 없고, 각 노드가 "나 여기 있고 무엇을 발행한다"고 스스로 알려 서로를 찾는다(discovery).
- ROS1과의 차이: ROS1은 중앙 관리자(roscore)가 죽으면 전체가 멈췄다. ROS2는 그 단일 실패점이 없다.
- 우리 프로젝트: ROS_DOMAIN_ID가 이 discovery 범위를 가르는 수단이고, QoS가 연결 성립 조건이다(각 항목 참조).

### QoS (Quality of Service, 서비스 품질)
발행자와 구독자가 연결 전에 맺는 배달 계약. 조건이 안 맞으면 통신이 나빠지는 게 아니라 **아예 연결되지 않는다.**
- 핵심 조건 Reliability: `RELIABLE` = 유실 시 재전송(등기우편). `BEST_EFFORT` = 한 번 쏘고 끝(일반우편).
- 센서에 BEST_EFFORT를 쓰는 이유: LiDAR 스캔은 0.1초마다 새로 나온다. 유실된 3번째 스캔을 재전송받아 봐야 그때는 5번째가 최신이다. 낡은 데이터를 기다리다 최신이 밀리는 게 더 나쁘다.
- 방향성: 발행자 RELIABLE + 구독자 BEST_EFFORT는 연결된다. 그 반대는 안 된다.
- 함정: 토픽 이름이 맞고 `ros2 topic hz`도 정상인데 내 노드만 메시지가 0개면 QoS 불일치다. 토픽 이름을 의심하다 시간을 버리는 지점이다.
- 우리 프로젝트: `/scan`은 BEST_EFFORT다. 구독 시 `qos_profile_sensor_data`를 명시해야 한다. `/uwb_pose`도 같은 성격이라 BEST_EFFORT, `/target_pose`(명령)는 RELIABLE이 맞다.

### 메시지 타입 (Message Type)
topic에 실리는 데이터의 형식 정의. 발행자와 구독자가 같은 타입을 써야 통한다.
- 우리 프로젝트: `sensor_msgs/LaserScan`(/scan), `geometry_msgs/PoseWithCovarianceStamped`(pose 계열).

### 파라미터 (Parameter)
노드가 실행 시점에 읽는 설정값. 코드를 안 고치고 동작을 바꾸는 수단이며, 보통 yaml 파일로 준다.
- 우리 프로젝트: `Tmini.yaml`의 `port`, `baudrate` 등. `port: /dev/lidar`로 고정한 것이 이 파일이다.

### Launch 파일
여러 노드 실행 + 설정 파일 연결 + 옵션을 한 번에 수행하는 실행 대본. `옵션이름:=값`으로 대본을 안 고치고 설정만 갈아끼울 수 있다.
- `ros2 run`과의 차이: `run`은 노드 하나만 띄운다. `launch`는 여러 노드와 설정을 묶어 재생한다.

### 패키지 / 워크스페이스 (Package / Workspace)
패키지 = 노드·설정·실행 대본을 묶은 배포 단위(폴더 하나). 워크스페이스 = 패키지들을 모아 함께 빌드하는 작업장 전체.
- 우리 프로젝트: 워크스페이스는 `drone_ws`. 사람이 쓰는 코드는 `src/` 아래에만 둔다. `build/`, `install/`, `log/`는 자동 생성물이라 수정 금지.

### colcon / --symlink-install
colcon = ROS2 워크스페이스 빌드 도구. `src/`를 읽어 `install/`을 만든다.
- `--symlink-install`: 결과물을 복사하는 대신 원본을 가리키게 한다. Python 코드와 yaml 설정을 고치면 **재빌드 없이 바로 반영**된다.
- 우리 프로젝트: 빌드는 항상 워크스페이스 루트에서 `colcon build --symlink-install`.

### setup.bash 소싱 (source)
`source install/setup.bash`는 "이 워크스페이스의 패키지를 쓰겠다"고 셸에 알리는 환경변수 설정이다. 안 하면 `ros2 launch`가 패키지를 못 찾는다.
- 주의: 환경변수는 **자식 프로세스에만 물려준다.** 터미널에서 실행하면 되지만 systemd가 띄운 프로세스는 못 받는다(`.bashrc` / systemd 항목 참조).

### TF2 / 좌표계 프레임 (Frame)
같은 위치를 서로 다른 기준으로 말할 때, 그 기준들 사이를 변환해주는 체계. LiDAR는 자기 몸 기준으로, UWB는 창고 기준으로 말한다.
- 표준 이름 3개: `map` = 창고 전체의 고정 원점(안 튀지만 가끔 점프 보정). `odom` = 이륙 지점 기준 누적 이동(부드럽지만 드리프트). `base_link` = 기체 자신의 중심.
- 우리 프로젝트: 결정 10의 "`map → odom` 발행자는 하나만 둔다" 조항이 이 체계 얘기다. `odom → base_link`는 `/mavros/local_position/odom`을 형식 변환만 해서 발행한다.

### rclpy / rclcpp
ROS2 기능을 코드에서 쓰기 위한 클라이언트 라이브러리. rclpy = Python용, rclcpp = C++용.
- 우리 프로젝트: 노드는 rclpy로 작성한다.

### rosbag2
topic을 파일로 녹화·재생하는 도구. 같은 상황을 여러 번 돌려보며 알고리즘을 비교할 수 있다.
- 우리 프로젝트: Phase 2 완료 판정("UWB 단독 대비 오차 감소를 로그로 입증")의 근거 자료를 만드는 수단.

### RViz2
ROS2 데이터 시각화 도구. `/scan` 점군, TF 좌표계, 경로 등을 3D로 그려 눈으로 확인한다.

### cv_bridge
ROS2의 영상 메시지(`sensor_msgs/Image`)와 OpenCV 이미지 사이를 변환해주는 라이브러리.
- 비유: 같은 사진을 ROS2용 봉투와 OpenCV용 봉투에 바꿔 담는 도구.
- 우리 프로젝트: Phase 3에서 마커 검출 코드가 topic 영상을 OpenCV로 받을 때 쓴다.

### image_transport
영상 topic을 압축해서 주고받게 해주는 계층. 같은 topic에 `raw`, `compressed` 등 여러 형식을 함께 제공한다.
- 비유: 같은 영상을 원본 파일과 압축 파일로 동시에 내보내고, 받는 쪽이 골라 받게 하는 것.
- 우리 프로젝트: 원본 영상은 대역폭이 크다. 압축본은 디버깅용 원격 확인에 쓴다. LoRa로는 보내지 않는다(대용량 금지 규칙).

### camera_info / camera_info_manager
`camera_info` = 카메라 내부 파라미터(초점거리 fx·fy, 중심 cx·cy, 왜곡계수)를 담은 메시지. `camera_info_manager` = 그 값을 YAML로 저장·배포하는 패키지.
- 비유: 렌즈의 신분증. 이 값이 없으면 영상 속 크기를 실제 거리로 환산할 수 없다.
- 우리 프로젝트: `solvePnP`로 마커 pose를 뽑으려면 필수. 캘리브레이션으로 만들어 YAML로 보관한다.

### gscam
GStreamer 파이프라인의 영상을 ROS2 topic으로 발행해주는 패키지.
- 비유: 카메라 전용 배관(GStreamer)을 ROS2 수도관에 연결하는 어댑터.
- 우리 프로젝트: IMX219는 CSI 카메라라 Jetson ISP(`nvarguscamerasrc`)를 거쳐야 한다. USB 카메라용 `v4l2_camera`로는 이 경로를 못 타서 gscam을 쓴다.

## 통신 / 미들웨어

### MAVLink / MAVROS
MAVLink = 드론 업계 표준 통신 언어(Pixhawk가 말하는 말). MAVROS = MAVLink를 ROS2 topic으로 번역해주는 통역사 패키지.
- 우리 프로젝트: Jetson과 Pixhawk 사이의 다리. /mavros/state의 connected: true가 연결 성립의 증거(heartbeat).

### baudrate (통신 속도)
시리얼 통신에서 초당 신호 수. 장치와 다르게 설정하면 통신 자체가 깨진다.
- 우리 장비: T-mini Pro = 230400, UWB 태그(DWM3000EVB) = 921600, TFmini Plus = 115200, Pixhawk USB = 115200.
- 함께 보는 값 `8N1`: 글자 1개를 데이터 8비트 + 패리티 없음(None) + 정지비트 1개로 보낸다는 약속. baudrate와 함께 양쪽이 같아야 한다. 틀리면 연결은 되는데 글자가 전부 깨져 나온다.

### 라인 프레이밍 (Line Framing)
끊겨 도착하는 시리얼 글자 조각을 줄바꿈(`\n`) 기준으로 다시 한 줄로 맞추는 작업.
- 비유: 우편함에 반쪽씩 들어온 편지를 마침표가 나올 때까지 모아 붙이는 것.
- 왜 필요한가: 시리얼에는 "한 줄"이라는 개념이 없다. 읽을 때마다 조각이 임의 길이로 온다. 조각 상태로 JSON 파싱을 시도하면 매번 실패한다.
- 우리 프로젝트: uwb_node가 버퍼에 이어 붙이고 `\n`이 나올 때만 잘라 파싱한다. 버퍼에 상한을 두고(줄바꿈이 영영 안 오는 고장 대비), 포트를 연 직후 첫 줄은 잘려 있을 수 있으므로 버린다. [uwb_node_design.md](architecture/uwb_node_design.md) 참조.

### watchdog (감시 타이머)
정해진 시간 안에 소식이 없으면 이상으로 판단하는 타이머.
- 비유: 등산 무전이 5분간 없으면 사고로 간주하는 규칙.
- 왜 필요한가: 센서가 멎을 때 에러가 나는 게 아니라 **그냥 조용해진다.** 구독하는 쪽에서는 "값이 안 바뀌네" 정도로만 보여서 늦게 발견된다.
- 우리 프로젝트: uwb_node는 마지막 줄 수신 후 0.5초가 지나면 경고를 내고 발행을 멈춘다. 케이블이 빠졌는데 마지막 값을 계속 붙들고 있는 상태가 가장 위험하다.

### ToF (Time of Flight)
빛을 쏘고 돌아오는 시간으로 거리를 재는 원리. T-mini Pro(회전 스캔)와 TFmini Plus(단방향 거리계) 모두 ToF 방식.
- 주의: 프로젝트 문서에서 "ToF 센서"는 보통 하방 TFmini Plus를 지칭.

## 시스템 / 장치 (System / Devices)

### 장치 파일 (Device File) / ttyUSB, ttyACM
리눅스는 하드웨어를 `/dev` 폴더 안의 파일로 다룬다. 프로그램은 그 파일을 열고 읽어서 센서 값을 받는다.
- 이름 읽는 법: `tty` = 직렬 통신 창구(옛 전신 타자기에서 온 이름). `ttyUSB*` = USB-시리얼 변환 칩이 만든 창구. `ttyACM*` = 같은 시리얼이되 칩 방식이 다른 창구.
- 우리 프로젝트: LiDAR와 UWB 태그는 `ttyUSB*`, Pixhawk는 `ttyACM*`로 잡힌다.

### 열거 순서 (Enumeration Order)
`/dev/ttyUSB0`의 `0`이 정해지는 방식. 장치의 정체와 무관하게 **먼저 인식된 장치가 0번을 가져간다.**
- 비유: 병원 대기표. 3번 표를 받았다고 "3번 환자"인 게 아니라 세 번째로 왔을 뿐이다. 다음 날 오면 7번을 받는다.
- 왜 위험한가: 설정 파일에 `/dev/ttyUSB0`을 박아두면 재부팅 한 번에 엉뚱한 장치를 열게 된다. 평소엔 잘 되다가 어느 날 갑자기 터지는 종류의 고장이다.
- 우리 프로젝트: LiDAR 혼자일 땐 안 보이던 문제가 UWB 태그 연결(2026-07-29)로 드러났다. udev 규칙으로 해결.

### 심볼릭 링크 (Symbolic Link, symlink)
다른 파일을 가리키는 바로가기 파일.
- 비유: 바탕화면 아이콘. 아이콘을 눌러도 실제 프로그램이 실행된다.
- 우리 프로젝트: `/dev/lidar`가 그때그때 진짜 `ttyUSB0`이든 `ttyUSB1`이든 알아서 가리킨다. 덕분에 설정 파일에는 영원히 `/dev/lidar`만 적으면 된다.

### udev
장치가 꽂히거나 빠질 때마다 깨어나서, 미리 정해둔 규칙에 따라 `/dev` 밑에 이름과 권한을 만들어주는 리눅스 서비스.
- 비유: 회사 정문 안내 데스크. 방문자가 들어올 때마다 명부를 확인하고 이름표를 발급한다.
- 규칙 파일: `/etc/udev/rules.d/*.rules`. 앞의 숫자는 적용 순서이고 클수록 나중에 처리된다.
- 우리 프로젝트: 원본은 `config/udev/99-dronestock.rules`에 두고, 적용할 때 위 폴더로 복사한다(sudo 필요).

### evdev (Event Device)
리눅스 커널이 키보드·마우스·조이스틱 같은 입력 장치의 이벤트(키 눌림/뗌 등)를 `/dev/input/eventN` 파일로 흘려보내는 인터페이스. 같은 이름의 Python 라이브러리(`python3-evdev`)로 읽는다.
- 비유: 모든 입력 장치가 같은 규격의 우편함(`/dev/input/eventN`)에 편지(이벤트)를 넣고, 프로그램은 그 우편함을 열어 읽기만 하면 된다.
- `grab()`: 이 우편함을 한 프로그램이 독점하게 만드는 호출. 걸지 않으면 같은 이벤트가 포커스 잡은 다른 프로그램에도 동시에 전달된다.
- 우리 프로젝트: QR 리더기(DE2110)가 [키보드 웨지](glossary.md)로 문자를 보내므로, `qr_reader_node`가 evdev로 전용 장치를 열어(grab) 문자로 재조립한다. udev 권한 규칙은 [udev](glossary.md) 항목 참조.

### VID / PID / serial
USB 장치가 꽂힐 때 하는 자기소개 3종. VID = 제조사 번호, PID = 제품 번호, serial = 개체 고유번호.
- 비유: 여권의 발급국·여권종류·여권번호.
- 함정: serial은 제조사가 공장에서 구워 넣어야 하는데, 안 굽고 기본값 그대로 출하하는 경우가 흔하다.
- 우리 프로젝트: LiDAR와 UWB 태그가 둘 다 같은 변환 칩(CP2102)을 쓰고 serial도 똑같이 `0001`이다. 세 값이 완전히 겹쳐 **이 단서로는 두 장치를 구분할 수 없다.**

### USB 포트경로 (Port Path, udev의 KERNELS)
장치가 꽂힌 물리적 구멍의 주소. `1-2.4` = 1번 버스 → 2번 포트(허브) → 그 허브의 4번 포트.
- 비유: 사람 이름 대신 좌석 번호로 부르는 것. 누가 앉든 "3열 4번석"은 그 자리다.
- 대가: 정체가 아니라 위치로 구분하므로 **케이블을 다른 잭에 꽂으면 장치가 뒤바뀐다.** 잭 배치가 곧 설정의 일부가 된다.
- 우리 프로젝트: serial 충돌 때문에 채택. `1-2.4`=LiDAR, `1-2.1`=UWB 태그. 뒤바뀜은 조용히 일어나므로, 노드가 포트를 연 뒤 첫 데이터로 장치 정체를 확인해야 한다.

### /dev/serial/by-id, /dev/serial/by-path
udev 규칙을 안 써도 리눅스가 자동으로 만들어주는 별명 폴더. `by-id`는 VID·PID·serial 기준, `by-path`는 포트 위치 기준이다.
- 우리 프로젝트: `by-id`는 두 장치의 이름이 똑같아 충돌해 하나만 살아남는다 — serial 충돌의 증거로 볼 수 있다. `by-path`는 정상 동작하지만 이름이 길고 사람이 읽을 수 없어, 같은 정보를 udev 규칙으로 `/dev/lidar`·`/dev/uwb`로 바꿔 쓴다.

### CSI (MIPI CSI-2) / nvarguscamerasrc
CSI = 카메라 전용 고속 배선 규격. 보드의 리본 케이블 커넥터로 직결한다. USB가 아니다.
- 비유: USB가 아무나 드나드는 공용 출입구라면, CSI는 카메라만 쓰는 전용 통로다.
- USB와의 차이: 열거 순서 문제가 없다. 어느 커넥터가 몇 번 장치인지 device tree에 미리 고정돼 있어, 재부팅해도 `/dev/video0`이 그대로다. **따라서 CSI 카메라에는 udev 규칙이 필요 없다.**
- 대신 생기는 제약: device tree에 정의된 커넥터에만 꽂아야 한다. 다른 커넥터에 꽂으면 장치가 아예 안 뜬다.
- `nvarguscamerasrc`: Jetson의 ISP(영상 신호 처리기)를 거쳐 CSI 영상을 꺼내는 GStreamer 요소. CSI 카메라는 이 경로를 타야 한다.
- 우리 프로젝트: IMX219를 CAM0에 고정. `imx219 9-0010`, `/dev/video0`. 배치는 equipment_inventory 참조.

### dialout 그룹
시리얼 포트를 열 수 있는 사용자 그룹. 전화 접속 모뎀 시절부터 내려온 이름이다.
- 우리 프로젝트: 이 그룹에 속해야 `sudo` 없이 센서 포트를 연다. udev 규칙의 `GROUP="dialout"`, `MODE="0660"`이 그 권한을 부여한다.

### `.bashrc` / systemd — 환경변수가 전달되는 경로
둘 다 "실행 환경을 정하는 것"이지만 주체와 시점이 다르다. 혼동하면 부팅 자동 기동에서 설정이 통째로 빠진다.

| | `.bashrc` | systemd |
|---|---|---|
| 정체 | 셸 시작 스크립트(파일 1개) | 시스템 관리자 프로그램(PID 1) |
| 언제 | 사람이 터미널을 열 때마다 1회 | 전원 켤 때 + 그 뒤로 상주 |
| 무엇을 | 환경변수·별칭·프롬프트 | 서비스 기동·재시작·의존성·로그 |

- 오해 주의: `.bashrc`는 명령을 칠 때마다 읽히지 않는다. 셸이 시작될 때 위에서 아래로 한 번 읽고 끝이다. 또한 **대화형 셸에서만** 실행된다(파일 앞머리의 `case $- in *i*` 방어막).
- 전달 원리: 터미널이 읽은 환경변수는 그 셸의 **자식 프로세스에만** 물려간다. systemd가 띄운 프로세스의 부모는 터미널이 아니므로 `.bashrc`를 거치지 않는다.
- 우리 프로젝트: `ROS_DOMAIN_ID=1`과 `source install/setup.bash`가 `.bashrc`에 있다. 터미널에서 수동 실행하는 지금은 문제없다. 부팅 자동 기동을 systemd로 붙이는 순간 값이 비어 DOMAIN 0으로 떨어지므로, 서비스 파일에 `Environment=ROS_DOMAIN_ID=1`을 따로 명시해야 한다(결정 7의 격리가 깨지는 경로).

## 군집 / 통신 (Swarm / Communication)

### LoRa
장거리·저전력·저대역폭 무선 통신 기술. 수 km를 날아가지만 속도는 수 kbps로 매우 느리다.
- 비유: 무전기. 멀리까지 잘 들리지만 사진은 못 보내고 말(짧은 텍스트)만 주고받는다.
- 우리 프로젝트: 드론→지상국 상태 텔레메트리 전용. 반드시 양단에 모듈이 필요하다(드론 2 + 지상국 1 = 총 3개). /scan 같은 대용량 데이터 송신 금지.

### 텔레메트리 (Telemetry)
원격지 장비의 상태(위치, 배터리, 모드 등)를 주기적으로 송신하는 것. 원격 계측.
- 비유: 멀리 있는 장비가 보내는 상태 보고다.
- 우리 프로젝트: 웹에는 Wi-Fi/WebSocket으로 보낸다.
  LoRa 요약 전송은 별도 채널이다.

### 지상국 (Ground Station)
드론을 원격 감시·관제하는 지상 거점. 우리 구조에서는 LoRa 수신 모듈을 단 컴퓨터 1대.
- 비유: 별도 무선 상태 보고를 받는 수신소다.
- 우리 프로젝트: 다중 드론의 LoRa 요약을 수신한다.
  웹 좌표는 각 companion이 Wi-Fi로 직접 전송한다.
  드론 간 ROS 통신은 가정하지 않는다.

### ROS_DOMAIN_ID
ROS2에서 통신 세계를 분리하는 번호. 같은 네트워크라도 ID가 다르면 서로의 topic이 전혀 보이지 않는다.
- 비유: 무전기 채널. 채널 1의 대화는 채널 2에서 안 들린다.
- 우리 프로젝트: 1호기=1, 2호기=2로 고정(.bashrc). 두 드론의 ROS2를 완전 격리하는 채택된 방식 — 네임스페이스 개조 없이 환경변수 한 줄로 해결.

### 네임스페이스 (Namespace)
topic 이름 앞에 접두어를 붙여 구분하는 방식(/d1/scan, /d2/scan). 여러 로봇이 한 ROS2 세계를 공유해야 할 때 쓴다.
- 우리 프로젝트: 미채택. 드론 간 통신이 없어 ROS_DOMAIN_ID 분리로 충분하다고 결정(roadmap 결정 7). 향후 드론 간 협조가 필요해지면 재검토.

### 군집 (Swarm)
여러 대의 로봇이 하나의 임무를 나눠 수행하는 운용 형태.
- 우리 프로젝트: 2대가 사전 분할된 구역을 독립적으로 순회하는 최소 군집. 동적 협조·상호 회피는 범위 외.

## 웹 연동 계약

이 절은 companion–Platform 계약 검토에 쓴다.
상대 회신은 [v1 검토](reference/companion_platform_api_v1_review.md)를 본다.

### API / 엔드포인트
- 정의: 프로그램끼리 요청·응답하는 약속이다.
  엔드포인트는 요청 방식과 주소의 조합이다.
- 비유: 접수 창구마다 정한 신청서와 처리 규칙이다.
- 우리 프로젝트: 임무 GET과 결과 POST를 검토한다.
  [필드 사전](reference/companion_platform_api_dictionary.md)에 계약을 적는다.

### HTTP / GET / POST
- 정의: 요청에 응답을 돌려주는 웹 통신 방식이다.
  GET은 조회에 쓴다. POST는 값 제출에 쓴다.
- 비유: 질문서를 보내고 답장을 받는 방식이다.
- 우리 프로젝트: 임무는 GET으로 조회한다.
  단계·ACK·출발 좌표·QR 결과는 POST 후보다.

### WebSocket
- 정의: 연결을 유지하며 메시지를 주고받는 방식이다.
- 비유: 전화를 연결한 채 여러 번 소식을 전한다.
- 우리 프로젝트: `drone_platform_link`가 상태를 보낸다.
  웹 좌표는 Wi-Fi 연결의 WebSocket을 사용한다.
  임무 조회는 HTTP이며 실제 명령 실행과 구분한다.

### JSON / JSONL / 스키마
- 정의: JSON은 이름과 값으로 데이터를 적는 형식이다.
  JSONL은 한 줄마다 JSON 한 건을 적는다.
  스키마는 필드 이름·형식·필수 여부의 계약이다.
- 비유: JSON은 신청서 한 장이다.
  JSONL은 신청서 묶음이다. 스키마는 빈 양식이다.
- 우리 프로젝트: 웹 통신은 JSON 계약을 검토한다.
  ZIP의 QR 미전송 기록은 JSONL을 쓴다.

### 폴링 (Polling)
- 정의: 새 값이 있는지 일정 간격으로 조회한다.
- 비유: 우편함을 30분마다 열어 보는 방식이다.
- 우리 프로젝트: ZIP은 임무를 기본 0.5초마다 조회한다.
  실제 간격은 요청 지연에 따라 늘어날 수 있다.

### ACK / 멱등성
- 정의: ACK는 수신·처리 여부를 알리는 응답이다.
  멱등성은 같은 요청을 반복해도 결과가 중복되지 않음이다.
- 비유: 같은 접수번호로 재문의해도 주문은 한 건이다.
- 우리 프로젝트: 명령 ACK와 물리적 완료를 구분한다.
  상대는 QR 스캔 ID로 중복을 막는다고 회신했다.
  서버의 실제 저장 동작은 아직 검증하지 않았다.

### HMAC / nonce / TLS
- 정의: HMAC은 공유 비밀키로 메시지 검증값을 만든다.
  nonce는 매 요청을 구별하는 고유값이다.
  TLS는 통신 내용을 암호화하고 상대를 확인하는 규약이다.
- 비유: HMAC은 봉인 도장이다.
  nonce는 일회용 접수번호다. TLS는 잠긴 전달 통로다.
- 우리 프로젝트: v1 계약은 HTTP HMAC을 사용한다.
  키·경로·본문·시각·nonce로 요청을 검증한다.
  `wss`는 TLS를 쓰는 WebSocket 주소다.
  HMAC만으로 통신 내용이 암호화되지는 않는다.

### 파이프라인 / 스냅샷
- 정의: 파이프라인은 값이 흐르는 처리 순서다.
  스냅샷은 한 시점의 상태를 모은 기록이다.
- 비유: 파이프라인은 조립 순서다.
  스냅샷은 작업 중 찍은 사진 한 장이다.
- 우리 프로젝트: 필드 사전에 생성·변환·소비 경로를 적는다.
  출발 스냅샷 API는 출발 좌표 등록을 요청한다.

### Unix 시각 / ISO 8601 / 단조 시계
- 정의: Unix 시각은 기준 시점 이후의 경과값이다.
  ISO 8601은 날짜·시간을 적는 표기 규칙이다.
  단조 시계는 뒤로 가지 않는 경과 시간 기준이다.
- 비유: 앞의 두 값은 달력 시계다.
  단조 시계는 구간 시간을 재는 초시계다.
- 우리 프로젝트: WS의 `t`는 Unix 밀리초다.
  QR 시각은 UTC ISO 8601 문자열이다.
  수신 나이는 companion 단조 시계로 계산한다.

### MAVLink TIMESYNC
- 정의: 두 MAVLink 구성요소가 시각 차이를 추정하는 왕복 메시지다.
  요청 시각을 되돌려 받아 왕복 지연도 잰다.
- 비유: 시계를 맞추려고 질문과 답의 이동 시간을 함께 재는 일이다.
- 우리 프로젝트: WSL과 PX4 부트 시각 차이를 진단한다.
  Gazebo 측정시각 변환은 별도 검증 전까지 열지 않는다.

### UUID / SHA256 / SHA1
- 정의: UUID는 항목을 구별하는 식별자 형식이다.
  SHA256·SHA1은 내용에서 고정 길이 값을 만든다.
- 비유: UUID는 접수번호다. 해시는 내용의 지문이다.
- 우리 프로젝트: ZIP은 스캔 ID로 UUID4를 쓴다.
  ZIP 파일 일치는 SHA256으로 확인한다.
  경로 변경은 SHA1 계산값으로 감지한다.
  경로 해시는 인증이나 변경 승인값이 아니다.

## 측정 / 통계 (Measurement)

이 절의 용어는 성능 지표 측정에서 쓴다. 사용 절차는 docs/report/scripts/README.md 를 본다.

### 백분위수 (Percentile, p95 / p99)
값을 작은 것부터 줄 세웠을 때 특정 위치에 오는 값. `p99 = 상위 1%를 뺀 나머지 중 가장 큰 값`.
- 비유: 100명이 줄을 서면 p95는 앞에서 95번째 사람의 키다. 제일 큰 사람 한 명에 휘둘리지 않는다.
- 왜 쓰나: **평균은 드문 지연을 숨긴다.** 100번 중 1번 크게 늦는 것이 제어에서는 치명적인데, 평균에는 1/100만 반영된다.
- 우리 프로젝트: 토픽 발행 간격과 지연을 평균만 적지 않고 p95·p99·최대와 함께 적는다. 2026-08-16 카메라 측정에서 평균 간격은 0.0333초였으나 최대 간격은 0.323초(약 10배)였다.

### 지터 (Jitter)
주기적으로 와야 할 신호의 도착 간격이 흔들리는 정도. 평균 주기가 같아도 지터가 크면 불안정하다.
- 비유: 지하철이 평균 5분 간격이라도 3분·7분·2분·8분으로 오면 계획을 세울 수 없다.
- 읽는 법: 간격의 표준편차, 또는 (최대 간격 − 중앙값 간격)으로 본다.
- 우리 프로젝트: EKF2는 관측치가 일정한 간격으로 온다고 가정한다. 지터가 크면 `EKF2_EV_DELAY` 한 값으로 보정할 수 없다.

### 결손 (Dropout)
와야 할 메시지가 오지 않아 간격이 비정상적으로 벌어진 구간.
- 판정 기준(우리 정의): 중앙값 간격의 2배를 넘으면 결손 1회로 센다.
- 왜 따로 세나: 평균 Hz만 보면 결손이 보이지 않는다. 19초에 1회 빠져도 평균은 거의 안 움직인다.
- 우리 프로젝트: `analyze_metrics.py`가 결손 횟수와 최대 결손 간격을 함께 낸다.

### 기준값 (Ground Truth)
정답으로 삼는 참값. 추정값의 오차를 재려면 반드시 있어야 한다.
- 비유: 저울을 검사하려면 무게를 정확히 아는 추가 있어야 한다. 추가 없으면 저울 두 대가 다르다는 것만 알 뿐 어느 쪽이 맞는지 모른다.
- 우리 프로젝트: 측위 RMSE 산출에 필요하다. **확보 수단 미정** — 바닥 마킹 실측 / 스캔매칭 결과 / 외부 측위 장비 중 미결정 (docs/report/03_metrics_plan.md 1.3).

### RMSE (Root Mean Square Error, 평균제곱근오차)
오차를 제곱해 평균 낸 뒤 제곱근을 씌운 값. 오차 크기의 대표값이다.
- 비유: 과녁에서 화살들이 중심으로부터 평균 몇 cm 벗어났는지.
- **한계**: RMSE 하나로는 "일정하게 밀린 것(bias)"과 "제자리에서 흔들리는 것(산포)"을 구분할 수 없다. 둘은 원인도 대책도 다르다.
- 우리 프로젝트: 측위 오차 보고 시 RMSE 단독으로 적지 않고 **평균 오차 벡터(bias)와 표준편차를 함께** 적는다. 현 UWB 오차의 정체가 bias이기 때문이다. [공분산 행렬](glossary.md) 항목의 "공분산은 흔들림만 표현한다"와 같은 이유다.



## 가속도계와 자세의 기초

이 절은 센서 측정값과 자세 추정값을 구분한다.
쉬운 원리는 [가속도계 설명](reference/accelerometer_gravity_explained.md)을 본다.

### 가속도계와 비력
가속도계는 비력을 측정하는 센서다.
비력은 중력 외의 힘을 질량으로 나눈 값이다.
- 비유: 바닥이 몸을 받치거나 밀어주는 정도다.
- 우리 프로젝트: `sensor_accel`의 단위는 m/s²다.
  수평 정지 시 보드 Z축 출력은 약 −9.8이다.
  자유낙하에서는 이상적으로 세 축 모두 0이다.
  움직임이 있으면 중력 방향만 따로 읽을 수 없다.

### 자이로와 각속도
자이로는 각 축의 회전 속도를 측정하는 센서다.
각속도는 시간당 회전 각도다.
- 비유: 회전판이 얼마나 빠르게 도는지 읽는 계기다.
- 우리 프로젝트: `sensor_gyro`의 단위는 rad/s다.
  1 rad/s는 약 57.3°/초다.
  각속도를 누적하면 각도 변화와 오차가 함께 쌓인다.

### IMU (관성 측정 장치)
가속도계와 자이로를 묶은 측정 장치다.
- 비유: 움직임을 읽는 두 계기를 담은 상자다.
- 우리 프로젝트: BMI088과 ICM-42688-P를 쓴다.
  각 IMU는 가속도 3축과 각속도 3축을 측정한다.

### Roll / Pitch / Yaw
기체의 자세를 세 회전 각도로 표현한 것이다.
- 비유: 고개를 옆으로 기울이고, 끄덕이고, 돌린다.
- 우리 프로젝트: Roll은 좌우 기울기다.
  Pitch는 앞뒤 기울기다. Yaw는 바라보는 방향이다.
  중력은 기울기의 기준이며 절대 Yaw의 기준은 아니다.

### 칩 원시값 / PX4 센서 측정값 / PX4 추정값
센서에서 자세까지의 서로 다른 처리 단계다.
- 비유: 저울의 내부 신호, 무게 표시, 무게로 한 판단이다.
- 우리 프로젝트: 칩 원시값은 센서의 정수 출력이다.
  PX4 센서 측정값에는 단위·축 변환 등이 들어간다.
  PX4 추정값은 여러 관측으로 계산한 자세·위치다.
  raw라고 쓸 때는 어느 단계인지 함께 적는다.

### SQLite
- 정의: 데이터를 파일 하나에 저장하는 DB다.
  별도 서버 없이 읽고 쓴다.
- 비유: 프로그램 안에서 관리하는 기록 장부다.
- 우리 프로젝트: QR 관측을 로컬 파일에 저장한다.
  서버 수락 기록이나 재고 수량을 뜻하지 않는다.
## 가상 시험과 센서 융합 연구

Gazebo 시험 문서를 읽을 때 쓰는 용어다.
[기본 시험 결과](report/gazebo_sitl_20260921.md)를 함께 본다.

### Gazebo
기체 운동과 가상 센서를 계산하는 시뮬레이터다.
- 비유: 드론을 움직여 볼 수 있는 가상 실험실이다.
- 우리 프로젝트: IMU와 거리값을 같은 운동에서 만든다.
  2026-09-21 기본 가상 이착륙을 확인했다.

### SITL / HITL
SITL은 PC에서 비행 소프트웨어를 실행하는 시험이다.
HITL은 실제 비행제어 보드에 가상 입력을 주는 시험이다.
- 비유: PC 속 제어기와 실물 제어기를 고르는 차이다.
- 우리 프로젝트: 별도 Windows PC의 WSL에서 PX4 SITL을 실행했다.
  실물 IMU가 가상 센서로 자동 복제되지는 않는다.

### QGroundControl
기체 상태와 설정을 확인하는 지상국 프로그램이다.
- 비유: 가상 기체에도 연결할 수 있는 계기판이다.
- 우리 프로젝트: Windows 앱을 WSL의 SITL에 UDP로 연결했다.

### GCS (Ground Control Station)
비행체의 상태 확인과 명령을 맡는 지상국이다.
- 비유: 기체 밖에서 보는 운용 계기판이다.
- 우리 프로젝트: 이번 SITL의 GCS는 QGroundControl이다.
  `No connection to the GCS`는 지상국 연결 경고다.

### UDP 포트 / localhost
UDP 포트는 통신을 받을 프로그램을 구분하는 번호다.
localhost는 해당 실행 환경 자신을 가리키는 주소다.
- 비유: 건물 안의 수신 창구 번호와 자기 건물 주소다.
- 우리 프로젝트: Windows QGroundControl은 14550을 쓴다.
  WSL의 PX4 GCS 연결 포트는 18570이다.
  이번 구성은 WSL IP를 직접 등록해 연결했다.

### GNSS / GPS
GNSS는 위성항법 체계의 총칭이다. GPS는 그중 하나다.
- 비유: 여러 위성망을 묶어 부르는 이름과 개별 망 이름이다.
- 우리 프로젝트: 이번 SITL은 가상 위성항법도 사용했다.
  따라서 기본 이착륙 성공은 UWB 융합의 근거가 아니다.

### headless 실행
화면 없이 프로그램을 실행하는 방식이다.
- 비유: 계기판 화면을 끄고 계산은 계속하는 것이다.
- 우리 프로젝트: Gazebo GUI 부하를 줄이는 후보 방식이다.
  GPU LiDAR의 센서 렌더링까지 없애지는 않는다.

### 저크 / S자 궤적
저크는 가속도가 시간에 따라 변하는 비율이다.
S자 궤적은 속도와 가속도를 부드럽게 연결한다.
- 비유: 엘리베이터가 출발·정지할 때 충격을 줄인다.
- 우리 프로젝트: 상승·정지·하강 시험의 궤적 후보다.
  저크를 제한한 PX4 궤적을 검토한다.

### 목표값 / 가상 기준값 / 추정값
명령한 상태, 가상 실제 상태, 계산한 상태의 구분이다.
- 비유: 목표 거리, 줄자로 잰 거리, 눈대중 거리다.
- 우리 프로젝트: EKF2 오차는 가상 기준값과 비교한다.
  목표값과의 차이에는 제어 오차도 섞인다.

### IMU 바이어스
가속도·각속도 측정에 섞이는 지속적인 치우침이다.
- 비유: 영점이 밀린 저울이 계속 더 무겁게 표시한다.
- 우리 프로젝트: EKF2가 추정하는 오차 항목이다.
  가상 시험에서 잡음과 구분해 영향을 살펴본다.

### 약결합 / 강결합
계산된 위치와 원시 관측 중 무엇을 결합할지 구분한다.
- 비유: 계산된 답을 모으거나 계산 전 자료를 모은다.
- 우리 프로젝트: 보정된 UWB x,y는 약결합 입력 후보다.
  강결합은 앵커별 원시 관측 접근이 필요하다.

### ESKF (Error-State Kalman Filter)
전체 상태 주변의 오차를 추정하는 EKF 형태다.
- 비유: 지도 위 위치에서 얼마를 고칠지 계산한다.
- 우리 프로젝트: UWB–IMU 연구를 읽는 검색어다.
  별도 실기 추정기를 도입했다는 뜻은 아니다.

### FGO (Factor Graph Optimization)
상태와 관측의 관계를 모아 함께 최적화하는 방법이다.
- 비유: 여러 시점의 증거를 연결해 경로를 맞춘다.
- 우리 프로젝트: 후속 연구의 비교 대상이다.
  현재 비행용 상태추정기는 PX4 EKF2다.

### IMU 사전적분 (Preintegration)
두 시점 사이 IMU 측정을 상대 운동으로 요약한다.
- 비유: 이동 중 기록을 두 정류장 사이 이동량으로 묶는다.
- 우리 프로젝트: FGO 논문에서 찾아볼 개념이다.
  센서 시계의 동기화를 자동 해결하는 기능은 아니다.

### 레버암 (Lever arm)
IMU와 다른 센서 기준점 사이의 위치 차이다.
- 비유: 회전판 중심과 가장자리는 다른 원을 그린다.
- 우리 프로젝트: UWB 태그와 IMU의 장착 위치를 다룬다.
  실측 전 장착 거리를 확정값으로 쓰지 않는다.

### 관측 가능성 (Observability)
관측과 운동으로 상태를 구별할 수 있는 성질이다.
- 비유: 한 장면의 단서로 어느 방향인지 알 수 있는가다.
- 우리 프로젝트: UWB·IMU의 yaw 추정 조건을 검토한다.
  정지와 이동 조건을 나누어 확인한다.

### VIO (Visual-Inertial Odometry)
카메라와 IMU로 상대 운동을 추정하는 방법이다.
- 비유: 보이는 장면 변화와 몸의 움직임을 함께 읽는다.
- 우리 프로젝트: 참고 논문의 추가 입력을 구분하는 용어다.
  VIO를 쓴 연구의 성능을 현재 구성에 그대로 옮기지 않는다.

### WSL2 / OpenGL / VRAM
WSL2는 Windows에서 Linux를 실행하는 환경이다.
OpenGL은 그래픽 기능을 제공하는 인터페이스다.
VRAM은 GPU가 사용하는 메모리다.
- 비유: 실행 공간, 그림을 그리는 규칙, 그림 작업용 책상이다.
- 우리 프로젝트: Gazebo PC의 실행 조건을 확인할 때 쓴다.
  VRAM 용량과 그래픽 드라이버 지원은 별개로 확인한다.


## UWB 선행 필터 이식

이 절은 HW팀 필터를 companion에 옮길 때 쓴다.
[이식 계획](architecture/uwb_jetson_port_plan_20260920.md)을 함께 읽는다.

### H80

최근 0.8초의 거리와 시각으로 XY를 구하는 회귀법이다.
- 비유: 여러 시점의 거리 증언을 한 경로에 맞춘다.
- 우리 프로젝트: 정상 구간에서 비교할 4앵커 UWB 전처리 후보다.
  앵커 높이가 같다는 조건으로 사용한다.

### Q_S10

복귀 구간의 위치·이동 추세·임시 편향을 함께 구한다.
- 비유: 끊긴 증언이 돌아오면 거리의 밀림도 함께 확인한다.
- 우리 프로젝트: 실시간 Z가 유효할 때만 사용한다.
  단절 뒤 초기 구간에서 앵커별 양의 편향을 추정한다.

### Shadow

후보 계산을 실행하되 실제 제어 입력에는 연결하지 않는다.
- 비유: 새 계산기를 옆에서 돌려 기존 결과와 비교한다.
- 우리 프로젝트: 이식한 XYZ와 판정·지연을 먼저 기록한다.

### 결정론적 재생 (Deterministic replay)

같은 입력·시각·순서에서 같은 계산 결과를 재현한다.
- 비유: 같은 시험지를 같은 조건으로 다시 채점한다.
- 우리 프로젝트: RAW·ToF·자세와 도착 순서를 기록한다.
  좌표·판정은 비교하고 CPU 소요시간은 별도로 측정한다.

### 장착 오프셋 (Lever arm)

FC 원점에서 센서 기준점까지의 기체 기준 벡터다.
- 비유: 사람의 위치와 머리 위 안테나 위치의 차이다.
- 우리 프로젝트: 자세로 회전해 센서↔FC 위치를 보정한다.

### Clock mapping

서로 다른 장치 시각의 속도와 원점을 맞추는 계산이다.
- 비유: 빨리 가고 늦게 시작한 시계를 기준 시계에 맞춘다.
- 우리 프로젝트: ESP32·FC·ToF 자료를 공통 시간축에 둔다.
  편도 수신만으로 확정하지 못한 전송 지연도 기록한다.

### Source age

원본 측정시각부터 출력시각까지 지난 시간이다.
- 비유: 뉴스가 화면에 뜬 때보다 사건 발생 시각을 따진다.
- 우리 프로젝트: 오래된 좌표를 새 관측처럼 보내지 않는다.

### SLERP

두 회전 사이의 중간 자세를 구하는 보간법이다.
- 비유: 두 방향 사이에서 매끄럽게 고개를 돌린다.
- 우리 프로젝트: 도착한 앞뒤 자세로 거리 측정시각을 맞춘다.

### Median3 / Alpha-Beta

Median3는 세 관측의 중앙값을 고른다.
Alpha-Beta는 위치와 속도를 유지하는 간단한 필터다.
- 비유: 앞은 세 값의 가운데를, 뒤는 이동 추세를 본다.
- 우리 프로젝트: Z 평활의 비교 후보로 둔다.
  정지·이동별 선택 방식은 시험 후 정한다.
  두 내부 상태를 비교할 때는 독립적으로 유지한다.

### valid / fresh / reason

관측 사용 가능·측정 신선도·판정 이유를 나타낸다.
- 비유: 값이 있어도 오래됐거나 보류 중이면 채택하지 않는다.
- 우리 프로젝트: 외부 관측은 valid와 fresh를 모두 요구한다.
  무효 후보와 reason은 내부 로그에 보존한다.


### venv (Python 가상환경)
프로젝트별 Python 실행기·패키지를 분리하는 환경이다.
- 비유: Python 도구만 담는 작업별 도구함이다.
- 우리 프로젝트: WSL 안의 `~/.venvs/px4`를 사용한다.
  Gazebo와 C++ 의존성은 WSL에 별도로 설치한다.

### Protobuf / protoc / CMake 캐시
Protobuf는 메시지 구조와 직렬화 도구 체계다.
protoc는 메시지 정의에서 코드를 생성한다.
CMake 캐시는 빌드가 선택한 경로·설정의 기록이다.
- 비유: 양식 규칙, 양식 생성기, 사용할 도구 주소록이다.
- 우리 프로젝트: Gazebo 메시지 빌드에서 함께 확인한다.
  Windows Anaconda 경로 혼입을 조사한 이력이 있다.

### ULog
PX4가 센서·상태 등을 저장하는 로그 형식이다.
- 비유: 비행 중 계기 변화를 담는 기록장이다.
- 우리 프로젝트: 9월 21일 SITL은 출력 발췌만 있다.
  9월 26일·27일 ULog 원본은 저장소 루트에 있다.
  27일 파일은 Position 위치 유지 분석에 사용했다.

### WLS (Weighted Least Squares, 가중 최소제곱법)

관측별 오차 크기를 반영해 잔차 제곱의 가중 합을 줄이는 방법이다.

- 비유: 정밀도가 다른 여러 자의 측정에 서로 다른 비중을 준다.
- 우리 프로젝트: UWB 거리 풀이에서 균등 가중과 비교할 시험 모델이다.
  같은 품질 정보를 분산과 추가 가중치에 중복 적용하지 않는다.

### FLU / 장착 위치 벡터

FLU는 앞·왼쪽·위를 양수로 삼는 기체 좌표축이다.
장착 위치 벡터는 기준점에서 센서까지의 거리와 방향이다.

- 비유: 드론 중심에서 센서까지 자로 재는 세 방향 거리다.
- 우리 프로젝트: Gazebo 기체 중심에서 안테나까지의 위치를 저장한다.
  회전한 위치는 `p_tag=p_body+R_WB*l_tag`로 계산한다.
  PX4 FRD는 오른쪽·아래가 양수이므로 축을 구분한다.

### SDF / Gazebo Transport

SDF는 가상 기체·센서·월드의 배치를 적는 파일 형식이다.
Gazebo Transport는 시뮬레이터 메시지를 전달하는 통신 체계다.

- 비유: SDF가 시험장의 설계도라면 Transport는 센서의 신호선이다.
- 우리 프로젝트: 새 기체·앵커 월드를 SDF로 만든다.
  가상 UWB RAW는 Gazebo의 StringMsg 안에 JSON으로 전달한다.

### gz_bridge / uORB

gz_bridge는 Gazebo와 PX4를 연결하는 모듈이다.
uORB는 PX4 내부 모듈들이 메시지를 주고받는 체계다.

- 비유: gz_bridge는 외부 자료를 들여오는 연결부다.
  uORB는 비행제어기 내부의 메시지 전달망이다.
- 우리 프로젝트: Gazebo 센서를 PX4 입력으로 전달한다.
  `listener`로 PX4 내부의 실제 수신값을 확인한다.

### Gazebo 플러그인

Gazebo 플러그인은 실행 중 불러오는 확장 프로그램이다.
센서 생성·물리 계산·모터 동작 등의 역할을 맡는다.

- 비유: 가상 시험장에 필요한 기능을 끼우는 부품이다.
- 우리 프로젝트: 기본 센서 시스템과 모터 모델을 재사용한다.
  광학흐름은 PX4의 `OpticalFlowSystem`도 사용한다.

### Rank / 조건수 / QR 분해 / SVD

Rank는 행렬에 독립된 정보가 몇 개 있는지를 나타낸다.
조건수는 작은 입력 오차에 대한 풀이의 민감도를 나타낸다.
QR 분해와 SVD는 선형 문제를 푸는 행렬 분해 방법이다.

- 비유: 서로 다른 방향의 단서 수와 답이 흔들리는 정도를 살핀다.
- 우리 프로젝트: 앵커 배치와 H80 행렬의 계산 성립 여부를 검사한다.
  QR 분해는 영상 인식용 QR 코드와 다른 용어다.

### Cholesky 분해 / 백색화 / Jacobian

Cholesky 분해는 양정치 공분산을 `L*L^T`로 나눈다.
백색화는 그 `L`로 잔차의 크기와 상관을 정규화한다.
Jacobian은 위치 변화에 따른 예측 거리의 변화율이다.

- 비유: 측정마다 다른 눈금을 맞춘 뒤 조정 방향을 찾는다.
- 우리 프로젝트: WLS에서 잔차와 Jacobian을 함께 변환한다.
  제공된 거리 공분산을 사용하며 품질을 자동 판정하지 않는다.

### DOP / HDOP

DOP는 관측 장치의 배치가 위치 오차를 얼마나 확대하는지 나타낸다.
HDOP는 수평 방향에 대한 지표다.

- 비유: 여러 방향에서 보는 것과 한 방향에서만 보는 것의 차이다.
- 우리 프로젝트: XY 거리 모델의 배치 지표를 계산한다.
  GNSS의 시계 오차 포함 모델과 값의 의미를 구분한다.
  DOP 자체가 실제 위치 오차나 정확도 보장은 아니다.

### RAIM / FDE

RAIM은 중복된 GNSS 관측으로 항법 결과의 일관성을 검사하는 방법이다.
FDE는 이상 관측 검출과 제외를 뜻한다.

- 비유: 여러 증언이 서로 맞는지 확인하고 의심되는 증언을 따로 본다.
- 우리 프로젝트: UWB 잔차 검사와 조건부 재계산의 시험 아이디어다.
  앵커가 적으면 이상을 발견해도 원인을 구별하지 못할 수 있다.

### RF 품질 / CIR (Channel Impulse Response)

RF 품질은 무선 신호 상태를 나타내는 측정 정보다.
CIR은 무선 채널을 통과한 신호가 시간에 따라 도착하는 형태다.

- 비유: 직접 들린 소리와 벽에서 반사되어 뒤늦게 들린 소리를 살핀다.
- 우리 프로젝트: 거리 오차 분산을 추정할 후보 입력이다.
  현재 장치가 실제 제공하는 필드를 확인한 뒤 사용한다.

### KF / UKF / Sigma point

KF는 선형 모델에서 예측과 관측을 결합하는 칼만 필터다.
UKF는 대표점들을 비선형 함수에 통과시켜 평균·공분산을 근사한다.
이 대표점을 sigma point라고 한다.

- 비유: 한 점의 예상 위치 대신 주변의 가능한 위치도 함께 옮겨 본다.
- 우리 프로젝트: UWB 평활·추종 지연을 비교하는 파일 시험 후보다.
  비행제어의 상태추정기는 PX4 EKF2로 유지한다.

### 휴리스틱 (Heuristic)

- 정의: 경험과 시험 결과로 정한 판단 규칙이다.
- 비유: 여러 번 주행한 결과로 속도별 설정표를 만든다.
- 우리 프로젝트: LiDAR 보정의 비교 후보를 정하는 방법이다.
  조정에 쓰지 않은 세션에서 효과를 다시 확인한다.

### 반응 시간 상수 (tau)

- 정의: 1차 응답이 차이의 약 63%를 줄이는 시간이다.
  고정 입력에 대한 지수 응답을 전제로 한다.
- 비유: 틀어진 눈금을 얼마나 천천히 맞출지 정한다.
- 우리 프로젝트: 단순 보정의 주기 영향을 분리할 때 쓴다.
  EKF의 보정 이득 K와는 다른 시험 설정이다.

### 필터링 / 스무딩 (Filtering / Smoothing)

- 정의: 필터링은 현재까지의 관측으로 현재 상태를 추정한다.
  스무딩은 뒤에 얻은 관측으로 과거 상태도 재추정한다.
- 비유: 현재 위치를 고치는 일과 지나온 경로도 고치는 일이다.
- 우리 프로젝트: 먼저 PX4 EKF2의 예측·관측 보정을 평가한다.
  과거 구간 재추정은 추가 효과를 확인할 후속 후보다.

### IRLS (Iteratively Reweighted Least Squares)

잔차에 따라 가중치를 갱신하며 최소제곱 풀이를 반복하는 방법이다.

- 비유: 답에서 지나치게 벗어나는 측정의 비중을 다시 조정한다.
- 우리 프로젝트: H80의 Huber 강건 회귀를 이해하는 계산 절차다.
  반복 횟수와 수렴 여부를 기록한다.

### Covariance intersection (CI)

추정치 사이의 교차 상관을 모를 때 평균·공분산을 결합하는 방법이다.
입력 공분산 자체가 타당하다는 조건은 별도로 필요하다.

- 비유: 같은 출처를 참고했을지 모르는 두 보고서를 신중히 합친다.
- 우리 프로젝트: GNSS·UWB 위치 결합의 비교 후보다.
  관측 오차가 독립이라는 가정을 자동으로 두지 않는다.

### Coverage (새 관측 가용률)

평가 시각들 중 새로 수용한 관측을 제공한 비율이다.

- 비유: 답의 정확도와 함께 실제로 답한 질문의 비율을 센다.
- 우리 프로젝트: 모든 모델에 같은 평가 시각과 분모를 적용한다.
  과거 위치 유지와 관측 없는 예측은 새 관측으로 세지 않는다.

### Observation recovery time (관측 복구 시간)

입력 이상 종료 뒤 관측 조건을 다시 만족한 시간이다.

- 비유: 통화가 다시 들린 때와 끊김 없이 들린 때를 나눠 잰다.
- 우리 프로젝트: 첫 신선 관측과 정확도 안정화를 따로 기록한다.
  주입 종료와 관측 표본 시각의 차이로 계산한다.
  PX4 수신·기체 정지·비행 복구 시간과 구분한다.

### Variant / RunManifest

Variant는 같은 기능에서 설정이나 계산법을 바꾼 시험 변형이다.
RunManifest는 입력·설정·버전·평가 조건을 묶은 실행 명세다.

- 비유: 실험 조건표와 각 조건에 붙인 이름이다.
- 우리 프로젝트: 참고값과 시험 후보값을 구분하고 재생을 재현한다.
  결과를 본 뒤 설정을 바꾸면 별도 실행으로 기록한다.

### 응집도·결합도

응집도는 한 모듈의 책임이 얼마나 모이는지를 뜻한다.
결합도는 모듈끼리 서로 얼마나 의존하는지를 뜻한다.
- 비유: 수신 담당과 계산 담당이 정해진 양식으로 자료를 넘긴다.
- 우리 프로젝트: 수신·보정·ROS 연결을 별도 폴더로 둔다.
  수신부는 보정 계산기를 import하지 않는다.

### 심볼릭 링크

다른 경로의 파일을 가리키는 파일시스템 연결이다.
- 비유: 원본을 복사하지 않고 새 보관 위치를 알려주는 표지다.
- 우리 프로젝트: 데이터 이동 후 기존 증빙 경로를 유지한다.
  링크와 실제 대상 파일을 함께 보존한다.

### B_TF

H80 위치 후보를 ToF 높이로 검사하는 UWB 보정 방식이다.
- 비유: 네 거리자의 답이 맞지 않을 때 높이도 대조한다.
- 우리 프로젝트: 정상 때 네 앵커 B 결과를 사용한다.
  불일치 때는 한 앵커씩 제외한 후보를 비교한다.
  후보가 구별되고 최근 좌표와 이어질 때만 수용한다.
  실물 연결은 앵커별 실제 측정시각을 보존한다.
  계산 가능 여부와 실제 위치 정확도는 구분한다.

## 멀티태그·웹 연결 — 2026-10-07

[연결 기준](reference/multitag_jetson_web_contract.md)의 용어다.
과거 단일 태그 수치를 현재 전체 시스템에 적용하지 않는다.

### TDMA / Superframe

공통 시간표에서 장치별 송신 구간을 나누는 방식이다.
Superframe은 그 시간표가 반복되는 한 주기다.
- 비유: 같은 교차로를 정해진 신호에 따라 통과한다.
- 우리 프로젝트: UWB 25ms 주기 안에서 A/B가 측정한다.
  LoRa도 같은 SYNC 순번에 맞춰 교대한다.
  Tag A/B의 주소는 5/6이다.

### 원본 측정률 / 보정 관측률 / 웹 전송률

새 거리·새 좌표·송신 패킷을 각각 세는 지표다.
- 비유: 사진 촬영·사진 처리·화면 새로고침 횟수다.
- 우리 프로젝트: UWB는 태그당 40Hz 목표다.
  B_TF는 새로 수용한 관측만 센다.
  웹은 기본 10Hz, LoRa는 명목 1Hz다.
  같은 좌표의 반복 전송은 새 측정이 아니다.

### 기체별 식별자

각 연결 계층에서 장치를 구분하는 값이다.
- 비유: 집 주소·전화번호·회원번호는 역할이 다르다.
- 우리 프로젝트: Tag ID는 5/6이다.
  ROS_DOMAIN_ID는 1/2다.
  웹 ID는 서버에 등록한 값을 지정한다.
  어느 하나를 바꿔도 나머지는 자동으로 바뀌지 않는다.

### 관측 ACK / 원본 나이 상한
- 정의: ACK는 웹 서버의 수락 응답이다. 나이 상한은 측정부터 표시까지의 보수적 경과값이다.
- 비유: 소포 수령 확인과 내용물의 유통 시간을 따로 보는 것이다.
- 우리 프로젝트: `observation.ack`로 서버 수락을 센다.
  웹 원본 나이는 송신기 나이·전송 경과·시계 여유 250ms를 합한다.
  500ms를 넘으면 XY/XYZ 표시값을 만료한다.

### 관측 세션 / HOST_OBSERVE
- 정의: 관측 세션은 송신 프로세스의 실행 식별자다. HOST_OBSERVE는 관측 전용 장치 등록 프로필이다.
- 비유: 보고자의 출입증과 근무 회차를 따로 확인한다.
- 우리 프로젝트: 인증 ID를 웹 기체에 묶고 세션·순번을 검사한다.
  이 연결로 비행 권한을 얻거나 임무를 실행하지 않는다.
