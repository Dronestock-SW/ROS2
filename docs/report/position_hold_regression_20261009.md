# 10월 9일 수동 Position 시험과 설정 비교
수동 시험의 흐름 현상을 조사한 기록이다.
기존 호버 설정으로 복구 범위를 정할 때 읽는다.

## 결론

**광류 회전·배율과 제어 게인은 기존 파일과 같다.**
사용자는 Position에서 기체가 흐른다고 보고했다.
기존 파일은 `perfect_holdv2.params`로 확인했다.
전체 1,095개를 읽고 같은 이름 1,095개를 비교했다.
float32 값으로 비교한 실제 차이는 22개다.
비교 단계에서는 FC 파라미터를 쓰지 않았다.
이후 사용자 지정으로 MAG_TYPE만 0으로 복원했다.
원인 하나나 호버 복구 성공을 확정하지 않는다.

Windows에서는 그 경로를 직접 읽어 비교했다.

## 복구 범위 제안 — 미적용

먼저 수동 호버의 추정기 기준을 분리해 복원한다.
검토 후보는 MAG_TYPE 6→0, EV_CTRL 1→0이다.
이는 기존 수동 광류 비행과 같은 융합 정책 비교다.
호버가 복구된다고 보장하거나 원인 확정으로 쓰지 않는다.
EV_CTRL=1은 앞서 사용자가 지정한 값이다.
반대로 바꾸는 범위를 확인하기 전에는 쓰지 않는다.

RC 입력·인계 설정과 이륙 높이는 유지한다.
측정한 EV 장착값은 보존한다.
CAL 교정값·편각·누적값은 일괄 원복하지 않는다.
이유: 변경 시점과 교정의 유효성이 확인되지 않았다.
과거 전체 params를 덮으면 RC 정책도 되돌아간다.

적용 시에는 새 DISARM·지상 상태부터 확인한다.
현재 백업을 보존하고 두 값만 저장·재조회한다.
MAG_TYPE의 재부팅 요구도 반영한다.
재부팅 뒤 읽기와 관측 복구를 마쳐야 적용 완료다.
자동 미션·UWB bridge는 이 비교에서 활성화하지 않는다.
MAG_TYPE=0으로 바꾸면 현장 미션 예상값도 달라진다.
그 차이를 숨기거나 시작 조건을 자동 통과시키지 않는다.

이 제안 중 사용자 선택은 MAG_TYPE 단독 복원이었다.
아래 적용 기록이 최종 범위다.
호버 재시험·보정 확정은 아직 미실시다.
동일 시행 ULog는 아직 확보하지 못했다.
FC SD의 날짜 목록만으로 로그 존재를 판단하지 않는다.

## 사용자 선택 적용: MAG_TYPE만 0

사용자는 `MAG_TYPE만 0으로 복원`을 지정했다.
새 DISARM·ON_GROUND 메시지를 확인했다.
변경 전 전체 백업의 완전성도 확인했다.
EKF2_MAG_TYPE만 6→0으로 썼다.
독립 parameter read로 0을 다시 읽었다.
파라미터 저장 ACK와 재부팅 ACK는 ACCEPTED였다.
각 전송 직전에 DISARM·지상 상태를 다시 확인했다.
ARM·모드·비행 명령은 보내지 않았다.

재부팅 뒤 shell 읽기 11개를 완료했다.
MAG_TYPE=0과 `cs_mag_hdg=True`를 확인했다.
이는 지상 heading 융합 근거다.
수동 호버가 회복됐다는 근거는 아니다.

| 유지 확인 | 재부팅 뒤 값 |
|---|---:|
| EKF2_EV_CTRL | 1 |

현장 파일의 예상 MAG_TYPE도 0으로 맞췄다.
원래 현장 파일을 별도 백업했다.
execute·bridge는 false로 유지했다.
heading·alignment·timing 확인값도 올리지 않았다.
낮은 고도의 자동 미션 정책은 이번 복원과 별개다.

재부팅으로 종료된 웹·관측을 다시 시작했다.
첫 시작은 누락된 websockets 경로 때문에 실패했다.
기존 `.test-deps`를 ROS 경로에 추가해 복구했다.
새 프로그램 설치나 기존 서비스 수정은 하지 않았다.
HTTP 200·최신 FC 연결·DISARM·지상 상태를 확인했다.
웹 START는 비활성이고 실제 비행 명령은 보내지 않았다.
FC logger는 재부팅 뒤 `not running`으로 읽혔다.
다음 비교 시험에서는 실제 ULog 기록 시작도 확인해야 한다.

## 10월 10일 재조회: 회전·추력 기준은 유지됨

수평 흐름만으로 FLOW_ROT를 0으로 바꾸지 않는다.

파라미터 쓰기·ARM·모드 명령은 보내지 않았다.

FLOW_ROT=4는 기체 기준 센서 yaw 180도다.

현재 지상 광류는 들어오지만 융합은 false다.
광류 품질은 30~31이다.
ToF 원본은 0.011m, 명시 최소거리는 0.1m다.
광류 명시 최소 높이도 0.08m다.
이 지상 상태로 이전 비행 중 융합을 판단하지 않는다.
두 EKF 인스턴스 모두 EV 위치 융합은 false다.
선택 인스턴스는 1이며 heading 제어 적합성은 false다.
기존 수동 비행과 같은 시행의 ULog 분석은 남았다.

관측 연결 중단과 수동 흐름은 별도로 조사한다.
10일 09:51 KST에 MAVROS가 SIGABRT로 종료됐다.
로그는 `malloc(): unaligned fastbin chunk detected`다.
launch가 나머지 관측 노드도 종료했다.
이 로그만으로 메모리 부족이나 원인을 확정하지 않는다.
Jetson 루트 가용량은 약 495MiB다.
이번 읽기 결과는 RAM과 PC에 보존했다.

FC ULog 기록 중단 원인은 별도로 확인됐다.
`logger status`는 실행 중이나 `Not logging`이다.
`dmesg`에 `errno:27 (File too large)`가 남았다.
해당 파일은 2,147,482,325 bytes다.
파일명 날짜만으로 수동 시험 로그로 간주하지 않는다.
다음 시험 전 새 로그의 실제 증가를 확인해야 한다.
이번에는 로그 삭제나 logger 재시작을 하지 않았다.

증거 파일은 PC `.integration`에 별도 보존한다.
`hover-baseline-compare-20261010.json`은 13개 조회다.
`manual-fc-current-20261010.json`은 15개 조회다.
센서 진단은 `hover-diagnostics-20261010.json`이다.
SD 목록과 오류는 `hover-log-index-20261010.json`이다.
원본과 장치 식별자는 Git에 넣지 않는다.

최종 임무 실행 주체는 기존 C++ 설계를 따른다.
Python 시험 미션을 최종 AI 통합으로 보지 않는다.
C++ 계획 검사와 C++ 전체 실행기는 구분한다.
수동 Position 호버는 PX4의 센서 융합·제어 경로다.
C++ 이관 완료만으로 수동 호버 회복을 선언하지 않는다.

## 통합 영향 조사: 당시 설정과 현재 설정을 구분

미션 비활성만으로 통합 영향을 배제하지 않는다.
확보한 흐름 발생 비행은 MAG_TYPE=6일 때다.
0 복원은 10월 9일 20:37:55 KST에 했다.
복원 후 같은 현상의 비행 로그는 아직 없다.
현재 0이라는 사실을 이전 비행에 소급하지 않는다.
MAG_TYPE은 수동 Position도 사용하는 EKF 설정이다.
따라서 자동 미션 비활성과 별개로 영향을 검토한다.
원인이 MAG_TYPE이었다는 결론은 아직 내리지 않는다.

`execute=false`는 FC 무송신을 뜻하지 않는다.
해당 시행의 코드 리비전은 `35a57b9`다.
`FlightNode.query()`는 관측 중에도 요청을 보낸다.
시작 때 COMMAND_LONG 511로 송신 주기를 요청한다.
전역 원점이 없으면 512로 5초마다 조회한다.
기록의 COMMAND_ACK 77개는 모두 512의 DENIED다.
이는 ARM·목표 위치·모드 전환 명령과 구분한다.
기록된 COMMAND_LONG 12개는 명령 1000/1001이다.
