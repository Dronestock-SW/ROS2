# 센서 송신·비행 연동 검증 기준 초안
이 문서는 두 기능의 책임과 성공 판정 초안이다.
다음 구현·시험의 완료 조건을 합의할 때 읽는다.

## 1. 적용 범위

통신 성공과 비행 성공을 별도 판정한다.
이 문서는 실제 비행 허가를 뜻하지 않는다.

| 상태 | 의미 |
|---|---|
| 확정 | 기존 로드맵·고도 정책·수신 API 계약의 기준 |
| 제안 | 이번 검토에서 제시한 시험 횟수·방법 |
| 미정 | 현장 조건과 사용자 결정이 필요한 수치·동작 |

1차 목표는 현재 로드맵을 비교 기준으로 사용했다.
내용은 tether 상태의 경로 이동·안전정지 검증이다.
사용자에게 목표 범위를 질문했다. 답변 전에는 확정하지 않는다.
비행 중 웹 경로 교체는 API v1 범위 밖이다.

## 2. 역할과 책임

센서 송신은 상태를 알린다. 비행제어는 움직임을 만든다.

| 항목 | 정의·비유 | 우리 프로젝트 역할 | 성공을 증명하는 것 |
|---|---|---|---|
| 센서값 송신 | 관측·기체 상태를 웹에 전달. 계기판으로 비유 | 실제 출처·시각·유효성을 보존 | ROS2 값과 서버·화면 값이 같은 의미로 일치 |
| 명령 수신 | 웹 요청을 로컬 임무 입력으로 전달. 작업 지시서로 비유 | 기체·임무·경로·요청 ID를 검사 | 지시가 정확히 수신되고 수락·거부가 구분됨 |
| 비행제어 | 목표에 맞춰 움직임을 조절. 운전으로 비유 | companion은 임무·수평 제어. PX4는 EKF2·고도·자세 | 독립 위치 기준으로 이동·정지·착륙 확인 |

```text
UWB 수평 관측 --+--> 송신용 필드 변환 --> 서버 --> 웹 표시
PX4 기체 상태 -+

웹 목표 --> 요청 검증 --> 임무·수평 제어 --> PX4 --> 실제 움직임
                              ^                       |
                              +------ PX4 상태 -------+
독립 기준 위치 ----------------------------------> 성능 판정
```

## 3. 센서값 송신의 완료 조건

값·출처·시각·표시를 모두 대조해야 완료다.

| 항목 | 기준 | 판정·근거 |
|---|---|---|
| 입력 소유권 | 기존 ROS2 출력을 읽음 | 시리얼을 다른 노드와 중복 소유하지 않음 |
| 수평 위치 | 검증한 `/uwb_pose` x·y와 상태 사용 | `uwb_map`과 서버 좌표 정의를 먼저 합의 |
| 고도 | 검증한 PX4 고도 출력 사용 | `current_z_source=px4_ekf2`. UWB 자리값 z=0은 제외 |
| FC 상태 | FC 연결·armed·mode를 별도 필드로 전송 | 미관측은 null/생략. 추측한 정상값 금지 |
| 배터리 | 실제 측정 %·V 사용 | 미상·오래된 값과 숫자 0을 구분 |
| 관측 유효성 | 노드 판정과 관측 나이를 함께 사용 | 웹 연결이 살아 있어도 관측은 무효일 수 있음 |
| 송신률 | 계약 목표 10Hz | 센서 수신률과 송신률을 각각 측정 |
| 시각·순번 | 송신 시각과 관측 시각을 구분 | 반복 송신으로 센서 관측 나이를 초기화하지 않음 |
| 연결 단절 | 서버는 마지막 텔레메트리 후 10초에 단절 표시 | API 계약값. 비행 대응 시간으로 전용하지 않음 |
| 재접속 | 최신 상태만 송신 | 오래된 위치 이력을 한꺼번에 보내지 않음 |
| 서버 결과 | 서버 수신·UI 표시 확인 | WS send 성공만으로 완료 판정하지 않음 |

관측 품질 기준은 기존 UWB 노드 설정을 출발점으로 쓴다.
이를 비행 정확도 보증으로 읽지 않는다.

| 현재 설정 | 값 | 의미 |
|---|---:|---|
| RAW 사이클 상한 | 0.10초 | 오래 걸린 거리 묶음 검사 |
| 거리 묶음 시각 차 | 0.04초 | 같은 관측 묶음의 시각 검사 |
| UWB watchdog | 0.5초 | 관측 공백 진단 |
| PX4 브리지 관측 나이 상한 | 0.20초 | 전달 후보의 최신성 검사. 브리지는 현재 비활성 |
| 초기 x·y 표준편차 설정 | 0.30m | 설정한 불확실성. 실측 위치 정확도가 아님 |

근거: [현재 UWB 설정](../../src/drone_uwb/config/runtime/uwb.yaml).
웹의 `fix` 만료 시간은 API 필드와 함께 정해야 한다.
소스 노드 watchdog 주기만으로 UI 반영 시간을 보장하지 않는다.

## 4. 비행제어의 완료 조건

도착 오차뿐 아니라 상태 전이와 실패 대응을 확인한다.

| 항목 | 필요한 성공 조건 | 상태 |
|---|---|---|
| 제어 권한 | 활성 명령 작성자는 하나. 수동 전환이 우선 | 구현·시험 필요 |
| 목표 검증 | 기체 ID·단위·좌표·유효 구역·개정값 검사 | 경계 topic은 로드맵 확정 |
| 상태추정 | PX4 EKF2의 유효한 상태 사용 | 융합·방향·시각·장착 위치 검증 필요 |
| 고도·자세 | PX4가 담당 | 정책 확정 |
| 경로 이동 | 독립 기준 위치로 오차·속도·초과 이동 측정 | 허용 수치 미정 |
| 도착 | 유효한 위치·속도와 목표 근처 유지시간을 함께 검사 | 허용 반경·정지 속도·시간 미정 |
| 스캔 | 원하는 라벨 ID의 판독·서버 결과 확인 | 목표 범위에 따라 Phase 3 이후 |
| 착륙 | PX4 착지 상태와 실제 착지를 대조 | 높이 한 번 낮게 읽힌 것만으로 완료 처리하지 않음 |
| 요청 응답 | 수신·수락·실행·완료·실패를 구분 | ACK는 수락 의미로 계약 확정 |
| 장애 대응 | 웹·UWB·FC·프로세스 실패를 각각 시험 | 상황별 동작·최대 대응 시간 미정 |

ZIP의 반경 0.20m와 대기 0.7초는 현재 구현값이다.
우리 기체의 성공 기준으로 확정한 값이 아니다.
위치 판정은 독립 기준점의 오차를 먼저 확인한다.
같은 UWB 값으로 제어와 정확도 평가를 모두 끝내지 않는다.
이유: 측위 편향이 있어도 자기 좌표에서는 도착으로 보인다.

## 5. 단계별 판정 제안

앞 단계의 증거를 확보한 뒤 다음 단계를 평가한다.
아래 횟수는 검토용 제안이며 실측 결과가 아니다.

| 단계 | 제안 시험 | 통과 증거 |
|---|---|---|
| A. 상시 통신 | 10분 연속. 연결 끊김·복구 3회 | GET·WS·서버 수신·UI 기록. 재접속 뒤 최신 값 확인 |
| B. 센서 표시 | 입력·서버 샘플 100건 대조. 센서 공백 3회 | 허용 반올림 외 값 차이 없음. 출처·나이·무효 표시 보존 |
| C. 임무 수신 | 정상·기체 불일치·낡은 요청·중복·취소·경로 수정 입력 | 모터 출력 없이 수락·거부·중복 처리 확인 |
| D. 측위 검증 | 최소 5점. 점당 60초, 3회 | 평균 오차·표준편차·공백·동적 기준 별도 기록 |
| E. 제어 모의 시험 | 정상 이동·통신 지연·관측 공백·프로세스 종료 | 안전 출력과 상태 전이 확인. 정상 경로만 통과해서는 완료 아님 |
| F. tether 검증 | 승인한 경로의 이동·정지 10회 | 합의한 오차·속도·구역 준수. 중단·수동 전환 확인 |

D는 [기존 측정 계획](../report/03_metrics_plan.md)을 따른다.
F의 10회 성공은 신뢰성 인증을 뜻하지 않는다.
이번 작업에서 A~F 전체를 통과한 것은 아니다.
현재는 통신 서비스의 연결·송신·재시작을 확인한 상태다.

## 6. 구현 시 지킬 경계

기존 정책과 이번에 확인한 결함을 함께 반영한다.

| 지킬 사항 | 이유·출처 |
|---|---|
| companion에 고도 PID·자세 제어를 추가하지 않음 | PX4 책임과 중복. 로드맵·고도 정책 |
| FC yaw·고도를 독립 센서 관측처럼 되먹이지 않음 | 상관된 정보를 중복 융합할 수 있음. 로드맵 결정 10 |
| 데모 값을 실측으로 표시하거나 FC로 보내지 않음 | 고정값은 실제 움직임을 관측하지 않음. 고도 정책 |
| 미상값을 0·정상으로 바꾸지 않음 | 센서 결손을 정상 측정으로 오해함. API 계약 |
| HTTP·QR 대기로 FC 제어 주기를 막지 않음 | 서버 지연이 비행 출력 공백으로 이어짐 |
| 최종 제한 뒤에 다른 코드가 출력을 덮어쓰지 않음 | 검증한 안전 제한을 우회함. 검토 F02 |
| HOLD 수신만으로 정지 완료를 보고하지 않음 | 요청과 실제 움직임이 다름. 검토 F05 |
| 낡은 위치로 도착·착륙 완료를 보고하지 않음 | 실제 이동·접지를 확인할 수 없음. 검토 F03·F04 |
| 잘못된 제어 모드를 RC 방식으로 자동 변경하지 않음 | 설정 실수가 실기 출력 방식 변경으로 이어짐 |
| 비행 중 v1 경로를 무조건 교체하지 않음 | 진행 번호가 초기화됨. API 계약·검토 F06 |
| 웹에서 받은 앵커 배치를 태그에 임의 적용하지 않음 | 실제 설치 좌표와 다를 수 있음. 연결 시험 기록 |

## 7. 사용자와 합의할 항목

현장 조건이 필요한 항목은 임의로 확정하지 않는다.

| 결정 | 필요한 정보 |
|---|---|
| 1차 목표 | 웹 표시만 / 사전 경로 이동 / 비행 중 경로 변경 |
| 수평 허용 범위 | 위치 오차·정지 속도·유지시간·최대 이동 속도 |
| 공간 조건 | 선반·벽과의 최소 거리, 허용 구역 |
| 웹 단절 | 현재 임무 계속 / PX4 정지 유지 / 착륙 중 선택 기준 |
| UWB 단절 | PX4 다른 관측 사용 가능 여부와 대응 동작 |
| 수동 개입 | 조종기·시험 담당자·중단 신호 |
| 비상 출력 중단 | 어떤 조건에서 요청할지와 PX4 처리 확인 |
| 경로 변경 | 허용 상태·명령 우선순위·만료·수락 응답 |

현재 질문은 1차 목표부터 확인하는 것이다.
나머지는 목표가 정해진 뒤 시험 설계에 필요한 순서로 정한다.
