# UWB 대화 발췌·확인 기록

첨부 대화의 발언과 코드 확인 결과를 정리한 기록이다.
UWB 구현 범위와 후속 아이디어를 구분할 때 읽는다.

## 후속 상태 — 2026-09-26

사용자 요청으로 보류 아이디어의 [개별 시험 명세](../specs/uwb/README.md)를 작성했다.
입출력·아키텍처·시험·선정 절차를 정의한 단계다.
새 모델 구현·기능 시험·실운용 모델 선정은 아직 수행하지 않았다.
ToF 기반 Z 자료는 추후 제공 예정이다. 계산·전달 게이트는 닫혀 있다.
아래 판단과 보류 표는 2026-09-21 당시 기록으로 보존한다.

## 당시 판단 — 2026-09-21

**후속 제안은 미채택 아이디어로 보관한다.**
2026-09-21 사용자 지시를 반영했다.
입력·편향 차감·기록 파이프라인은 유지한다.
계산·외부 전달 게이트는 계속 닫는다.
후속 게이트와 H80·Q_S10 시험안은 확정 계획이 아니다.

첨부 대화의 핵심은 ESP32 시험과 Jetson 구현의 구분이다.
김찬국은 PDF와 코드를 참고해 별도로 구현하라고 설명했다.
시험 범위는 H80·Q_S10이라고 밝혔다.
가중 평균과 LiDAR 보정은 대화 중 제안이다.

## 후속 문헌 조사 — 보류

GNSS 조사와 관련 논문도 수신·보정 아이디어로 보류한다.
2026-09-21 후속 사용자 지시를 반영했다.
이 절은 첨부 이미지 이후의 조사 기록이다.
확정 개발 계획과 현재 구현에 포함하지 않는다.
기존 입력·보정·기록 파이프라인은 유지한다.
계산·외부 전달 게이트는 계속 닫는다.

## 오후 4:44~4:48 — 자료의 목적

7cm는 이후 성능의 확정 기준으로 채택하지 않았다.

- 오른쪽: “그거 7cm는”
  “일단 없는 수치로 둬야겠음”이라고 말한다.
- 김찬국: ToF 입력을 받아본 뒤 확인해야 한다고 말한다.

- 김찬국: 20cm는 높다고 보고 약 13cm를 예상한다.
  이후 “정확한 수치를 가지고” 재정립하겠다고 말한다.

## 오후 4:51~4:54 — 앵커 제거와 0.8초 처리

- 오른쪽: 앵커 하나를 버리는 방식이 아니었는지 묻는다.
- 김찬국: “그거 안하기로 했어여”라고 답한다.
- 김찬국: 튀는 앵커를 버리면 세 앵커 쪽으로 쏠렸다고 설명한다.

- 안상원 형님: 앵커 배치와 교차 계산에서 튐이 생길 수 있다고 말한다.

- 안상원 형님: 앵커를 완전히 버리면 안 된다는 의견을 낸다.

## 오후 4:54~4:55 — 후보 평균과 가중치 제안

후보를 여러 개 만든 뒤 평균하자는 아이디어가 나온다.

- 오른쪽: 12개 중 신뢰도가 높은 하나를 쓰는지 묻는다.
  이어 상위 세 개를 평균하는지도 묻는다.
- 김찬국: 평균을 생각해 설계했다고 답한다.
- 안상원 형님: 제외된 앵커를 보정 가중치로 쓰는지 묻는다.
- 김찬국: 그 설명에 동의한다.
- 오른쪽: 앵커별 RAW가 아니라 교차 계산 결과를 뜻한다고 보충한다.
  “4*3*2*1 해서”, “값 12개 뽑고서”라고 말한다.
- 오른쪽: 상위 6개 평균에 0.7을 제안한다.
  하위 6개에는 0.3을 제안한다.
  이어 0.3이 너무 높은지 스스로 검토한다.

이 대화만으로 후보 생성식은 확정되지 않는다.
신뢰도 순위의 계산법도 제시되지 않았다.
김찬국의 설명과 오른쪽의 추가 제안을 구분해야 한다.
대화 중 동의가 ZIP의 해당 기능 구현을 증명하지는 않는다.

## 오후 4:55~4:58 — 우려와 추가 보정 제안

가중 평균의 효과와 LiDAR 보정은 검증 전 의견이다.

- 안상원 형님: 시험해 봐야 알 수 있다고 말한다.
  위치 추정값이 튀거나 EKF에서 거부될 가능성을 지적한다.
- 21김용민: 하위 후보에서 튐이 발생할 수 있다는 우려에 동의한다.
- 오른쪽: 평균으로 결측이나 이상치를 완화할 수 있다는 의견을 낸다.
- 오른쪽: “0.03인가 비중인데”라며 다른 보정 비중을 제안한다.
- 안상원 형님: 다시 시험이 필요하다고 말한다.
- 오른쪽: 0.03을 일정하게 적용하는 방안을 말한다.
  이어 LiDAR로 앵커까지의 거리를 계산해 보정하자고 제안한다.
  신뢰도가 높을 것이라는 판단을 덧붙인다.

0.03이 어느 수식의 어떤 계수인지는 확인되지 않는다.
LiDAR의 앵커 식별과 거리 산출법도 대화에 없다.
신뢰도가 높다는 발언은 시험 근거가 제시된 결론이 아니다.
자이로 RAW 자체를 보정한다는 합의도 확인되지 않는다.

## ZIP 소스와 대조

현재 ZIP의 H80은 네 앵커의 거리 이력을 함께 회귀한다.
후보 위치를 상·하위 여섯 개로 나누는 구현과 구분한다.

대조 자료는 `uwb_h80_qs10_reference_source_v1.zip`이다.
내부 `src/ExperimentalPositionFilter.cpp`를 확인했다.
아래 줄 번호는 해당 ZIP 내부 소스 기준이다.

| 대화의 표현 | 소스에서 확인한 사실 | 판단 |
|---|---|---|
| 0.8초 구간 처리 | `collectWindow`, 122~133행이 최근 0.8초 표본 수집 | 대응함 |
| 세 앵커로 쏠림을 방지 | `hasMinimumObservations`, 134~153행이 네 앵커 각각 최소 3개 요구 | 앵커 하나를 통째로 제외하는 풀이가 아님 |
| 12개 값 | 145행의 `n < 12`는 최소 거리 표본 수 | 12개 후보 위치를 뜻하지 않음 |
| 평균·보정 가중치 | `solveH80`, 210~251행이 거리 분산과 Huber 가중치로 회귀 | 대화의 후보별 0.7·0.3 평균과 다름 |
| 모든 값을 계속 수신 | `ingest`, 575~603행은 편향 차감 후 거리 이상치 보류 | 앵커 전체 제외와 개별 표본 보류를 구분 |
| Q_S10 시험 | 566~572행과 631~633행에 단절 후 복구 조건 | 상시 후보 평균 기능을 뜻하지 않음 |

네 앵커 중 세 앵커를 고르는 조합은 `C(4,3)=4`다.
대화의 `4×3×2×1`은 24이며 12가 아니다.
따라서 12개 후보 생성은 별도 정의 없이는 구현할 수 없다.
추가 교차 해를 포함하는지 대화에서 확인되지 않는다.

과거 ESP32 시험 수치를 이번 대화로 재검증하지 않았다.
이번에는 문서 상태와 대화 발췌만 정리했다.
코드 변경·실행 시험·게이트 개방은 수행하지 않았다.
