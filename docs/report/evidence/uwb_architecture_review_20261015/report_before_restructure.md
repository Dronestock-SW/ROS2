드론 UWB 공백 대응과 구조 설정 개선안

2026년 10월 15일 기준 설계 검토다. 기존 기록·코드·논문을 대조해 무엇을 유지하고 무엇을 바꿀지 정리한다. 새 로그 재생·비행·운영 설정 변경은 하지 않았다.

**권고 방향은 현재 PX4 중심의 추정·제어 구조를 유지하면서, UWB 측정의 신뢰성, 실제 제어속도, 공백 중 감속, 좌표 복구 후 재진입을 개선하는 것이다.** UWB 공백 0.7초 자체는 일률적인 착륙 사유가 아니다. 공백을 기다릴 수 있다는 사실도 거리 모순·불필요한 처리 지연·복구 때 급격한 제어를 해결해 주지는 않는다.

비행제어·Physical AI·임베디드/센서의 독립 AI 검토와 Claude Pro 구독 연결의 3차례 기술 검토를 마쳤다. 외부 실기 인증은 아니다. [읽은 자료 75개 경로와 판본 대조](source_inventory.md)를 별도로 남겼다.

**2. 공백과 지연은 다음처럼 구분한다**

| 현상 | 확인된 근거 | 구조·설정에서 할 일 |
|---|---|---|
| Python 실행 정지 | 새 계측 두 사건의 generation 2 GC 약 80ms. 둘 다 150ms 이내에 발행 | 중요한 실행 경로를 GC·기록·임무 부하와 분리. 모든 공백의 원인으로 확대하지 않음 |
| 오래된 입력·처리 대기 | 이미 늦은 입력에 큐 대기가 더해져 만료. 빠른 계산에서도 만료 발생 | 원래 측정 나이·콜백 진입 대기·처리·전송을 각각 관리 |
| 반복 관측 거부 | 부분 입력 8회에서 364~384ms 구간 반복 | 모순된 관측 거부를 유지하고 공백 대응을 설계 |
| 별도 수동 비행의 거리 모순 | 10/14 log49의 약 526ms 공백, 20개 거리 묶음의 기하 모순 | 앵커 배치·거리 교정·ID·단위·시각·입력 처리를 확인 |
| 공백 뒤 제어 중단 | 과거 비행에서 EV 재개·XY 리셋 뒤 companion 점프 보호 착륙 | 정상적인 재획득과 실제 위험을 구분하는 복구 계약 추가 |

약 80ms의 GC 사건, 0.7초의 관측 공백, 초기화 대기 3.86초는 서로 다른 관측이다. 이를 단순히 더해 매번 3초 이상 늦는 구조라고 해석할 근거는 없다. 입력·출력의 각 150ms 검사도 서로 다른 기준 시각을 사용하므로 합계 300ms의 허용 지연이 아니다. [GC 확인 범위](../../btf_gc_latency_20261015.md)

가장 분명한 거리 모순의 예는 A1–A2 간격 6.3m에 대해 두 측정 거리의 합이 6.10296m였다는 것이다. 두 측정 시각 차이 2.360ms 동안 1m/s로 움직이는 양을 허용해도 19.468cm 부족했다. ToF 높이를 15cm에서 17cm로 바꾼 감도 비교에서도 같은 526ms 공백이 남았다. 이 입력을 발행하도록 잔차 기준을 풀면 잘못된 좌표를 더 자주 보내게 될 수 있다. NLOS나 특정 장치 고장이 원인이라고 확정된 것은 아니다. [거리 모순 분석](../../btf_geometry_physical_fc_20261015.md)

**4. 논문에서 가져올 것과 그대로 옮기지 않을 것**

논문은 RPi4에서 UWB 네 거리·optical 속도·거리계·IMU를 융합하고 위치 PID까지 수행한다. Pixracer는 자세제어를 맡는다. 우리 구조에서는 Jetson이 UWB XY를 만들고 PX4가 추정·위치·자세제어를 유지한다. 논문처럼 바꾸려면 optical 전처리뿐 아니라 추정기와 위치제어 책임도 옮겨야 한다.

우리는 이미 UWB 거리→XY 계산을 FC 밖에서 수행한다. XY·공분산을 보내면 PX4가 그 측위 풀이를 할 필요는 없다. 다만 두 구조의 FC 총부하가 측정된 것은 아니다. PX4 표준 optical flow 입력도 원시 영상이 아니라 각도 흐름·적분시간·품질 등의 값이므로, 외부에서 속도로 바꾸지 않는다는 이유만으로 무보정·과부하라고 판단하지 않는다. [PX4 입력 규격](https://docs.px4.io/main/en/msg_docs/SensorOpticalFlow)

논문의 호버 오차 9.59cm는 평균이며 최대 10cm 보장이 아니다. 위치추정 평균은 12.92cm다. 논문은 우리의 공백·재연결·리셋 상황을 입증하지 않는다. 우선 가져올 방법은 독립 기준으로 추정 오차와 실제 제어 오차를 따로 평가한 것이다. [첨부 논문](https://doi.org/10.20965/jrm.2023.p0328)

**5. 비행제어 관점의 구체적인 변경**

원래 목적지, 임시 정지 목표, 재진입 경로를 별도로 관리한다. UWB가 끊겼다고 원래 목적지를 현재 추정 위치로 덮어쓰지 않는다. 마지막 목표가 아직 앞에 있으면 그 목표를 계속 보내는 것만으로는 즉시 정지가 되지 않는다.

| 상태 | 해야 할 동작 | 다음 상태로 넘어가는 조건 |
|---|---|---|
| 정상 진행 | 승인된 경로를 0.25m/s 기준으로 진행 | 관측 거부·노후화 또는 추정 여유 감소 감지 |
| 감속 | 신뢰 가능한 현재 위치·속도에서 수평 감속 경로 생성. 임무 목적지 보존 | 실제 속도가 정지 기준 안에 들고 유지할 추정이 유효 |
| 대기 | 임시 정지 목표와 필요한 Offboard 송신 유지. 도착·임무 진행 인정 중지 | 새 적격 관측 도착 또는 유지 가능 조건 이탈 |
| 좌표 복구 확인 | 새 적격 UWB를 즉시 EKF에 공급. 융합 시각·현재 상태·좌표 관계 확인 | 현재 상태와 목적지 관계를 설명할 수 있고 재개 여유 확보 |
| 저속 재진입 | 보정된 현재 상태에서 원래 목적지까지 경로 재생성 | 속도·가속도·추종 상태가 정상 범위 |
| 대기 불가 | 상태추정 유효성·장애물 여유·고도·배터리·조종권에 맞는 기존 대응 적용 | 이륙 전 정한 대응 정책에 따름 |

첫 정상 관측 전달과 임무 재개 승인은 분리한다. 센서를 무조건 150ms 보류하는 옛 브리지 대기를 되살리지 않는다. 큰 위치 차이가 난다는 이유만으로 정상 복구를 영구 거부하지도 않는다. 큰 차이는 누적 drift 보정일 수도, UWB 이상일 수도 있으므로 같은 측정 시각·기준점에서 다른 근거와 대조한다.

고정 지도에서 현재 위치가 보정된 것이라면 물리적 목적지는 유지한다. 순수하게 좌표 원점·방향의 표현이 바뀐 것이라면 목적지의 표현도 같은 변환을 적용한다. EKF reset counter와 delta는 리셋의 증거이지, 그 물리적 의미를 단독으로 확정하는 정보가 아니다.

임시 정지 참조의 연속성 보정과 지도 변환은 다른 값으로 보관한다. 매번 UWB 위치와 EKF 위치의 차이를 새 지도 원점으로 흡수하면, 실제 drift를 교정하면서 목적지도 같이 움직이는 문제가 생긴다. 지도→EV 입력 변환은 확인된 축·원점·장착 계약으로 관리하고, 실제 좌표계 변경의 근거가 있을 때만 갱신한다.

신뢰할 수 있는 reset 때 임시 참조를 조정해 순간 제어 오차를 유지하는 방안은 후보가 된다. 그러나 PX4가 기존 setpoint에 이미 reset 보상을 적용할 수 있으므로 companion에서 같은 delta를 다시 적용하면 중복 보상이 된다. 반대로 새 시각을 붙여 옛 좌표를 재송신하면 FC 보상을 취소할 수 있다. 따라서 송신 목표의 세대·시각과 PX4 reset 처리의 적용 시점을 한 계약으로 맞춰야 한다. 50ms 송신 주기만으로 이 경합이 50ms 안에 해소된다고 보장할 수 없다.

우선 companion의 상태·참조 관리와 FC의 실제 처리 순서를 대조한다. 이 경계에서 연속성을 보장하지 못하면 작은 FC 측 인터페이스 변경도 별도 후보로 남긴다. reset 없이 점진적으로 위치가 보정되는 경우도 포함한다. 단순한 delta 보정만으로 해결됐다고 판단하지 않는다.

제어 참조에는 FC 부팅·선택된 estimator·reset 묶음의 식별 정보를, 관측에는 시계 세대·지도/장착 개정·원본 sequence와 시각을 연결한다. counter 하나만으로 부팅이나 estimator 교체를 구분하지 않는다. 모호한 동안에는 임무 재진입을 막는다. 이때도 단순히 옛 HOLD 좌표를 반복하면 안전하다는 뜻은 아니며, 유지 명령 자체의 연속성과 상태 유효성이 확보돼야 한다.

기존 코드에는 지도 좌표 변환과 고정 yaw 명령이 있다. 새로 만드는 기능처럼 취급하지 않고, 실내 heading의 실제 출처와 지도 축의 정렬, heading reset 때의 변환 책임을 그 경로에 연결한다. 외부 XY 융합을 켰다는 사실만으로 yaw 정렬까지 입증되지는 않는다.

현재 점프 보호는 연속 pose 차이가 `0.3m + 1m/s × pose_dt`보다 크면 중단하는 휴리스틱이다. 이를 무조건 제거하지 말고, 복구 상태·리셋 정보·좌표 세대와 함께 판정하도록 개선한다. 실제 위치 변화나 불명확한 좌표 변환을 정상 복구로 오인하지 않는 것이 조건이다.

**6. Physical AI 관점의 오차와 정지 공간**

공백 허용시간은 0.7초나 3초 하나로 정하지 않는다. 실제 융합 중인 flow/LiDAR, 추정의 신선도·오차 성장, 현재 속도, 주변 공간을 함께 본다. 센서 토픽이 도착하거나 과거 `fused=True`가 남았다는 사실만으로 정상이라고 판단하지 않는다. 최신 상태 시각, 증가하는 `time_last_fuse`, 현재 융합 활성 상태를 같이 확인한다.

실제 수신 주기와 최근 이력을 고려해야 하며, 한 번의 점검 사이에 융합 시각이 증가하지 않았다는 이유만으로 즉시 실패 처리하지 않는다. 보조센서의 가용성은 대기 허용의 필요 근거 중 하나다. 속도 관측이 계속돼도 절대 위치오차는 커질 수 있다. 상태 진단 메시지의 지연과 FC 내부의 실제 추정 무효도 구분한다.

10cm는 우선 목표 도착·호버의 실제 수평 반경으로 정의한다. X와 Y 각각 ±10cm를 허용하면 대각선 반경은 약 14.1cm가 된다. 추정오차·추종오차·공백 중 증가분은 별도로 평가한다. 평균, 95백분위, 최대 관측값도 구분한다. 공분산의 표준편차 하한 0.10m가 실제 위치오차 10cm의 보증은 아니다.

정지 공간은 다음의 단순 예시로 비교할 수 있다.

`필요 여유 ≈ 실제 속도 × 총 반응시간 + 실제 속도²/(2 × 최소 제동감속) + 위치·추종 오차 예산`

| 설명용 가정 | 반응·제동 거리 | 위치·추종 합계 10cm 포함 |
|---|---:|---:|
| 실제 속도 0.25m/s, 총 반응 0.25s, 감속 1m/s² | 9.375cm | 19.375cm |
| 실제 속도 0.25m/s, 총 반응 0.25s, 감속 0.5m/s² | 12.5cm | 22.5cm |
| 실제 속도 0.5m/s, 총 반응 0.25s, 감속 0.5m/s² | 37.5cm | 47.5cm |

현재 250ms 관측 기준이 총 반응시간 250ms를 보장하는 것은 아니다. 이 계산은 jerk 제한에 따른 제동 지연·외란·거리 측정 오차를 별도로 포함하지 않았으며, 실측 감속도도 없다. 따라서 첫 두 행은 30cm 여유에서 설계 가능성을 보여주는 예시다. 세 번째 행은 복구 때 실제 속도가 커지면 여유가 급격히 사라지는 이유다.

Flow·UWB 높이 보정이 ToF를 공유하고, 여러 관측이 같은 자세를 사용한다면 오차도 상관될 수 있다. 겹치는 H80 창의 연속 출력 역시 완전히 독립적인 표본이 아니다. 센서 수가 늘었다는 이유로 공분산을 작게 만들지 않는다. T-mini Pro는 한 수평면을 보므로 기체 위·아래나 프로펠러 외곽의 모든 장애물을 검출한다고 가정하지 않는다.

**7. 임베디드와 통신 관점의 실행 구조**

```text
DWM3000 거리·TDMA ─→ 시간·쌍 정합 ─→ B_TF·검사·공분산 ─→ PX4 외부 XY
TFmini Plus·FC 자세 ──────────────┘
T-mini Pro ─→ 시각·회전·레버암 보정 ─→ 독립 2D 속도 관측 ─→ PX4
FC IMU·optical·하방거리 ───────────────────────────────→ PX4 EKF

PX4의 신선한 추정·융합 상태 ─→ 임무/감속/대기/복귀 감독 ─→ 독립 20Hz 목표 송신

카메라·QR·웹·LoRa·상세 기록 ─→ 항법·목표 송신을 기다리게 하지 않는 별도 작업
```

센서 수신, 시간 대응, 필수 이력, 계산, 발행까지의 중요 경로를 관리한다. 작은 계산 함수마다 Python↔C++ 경계를 추가하기보다, 필요하면 이 경로를 제한된 C++ 프로세스로 묶는다. 현재 핵심 계산만 C++여도 Python GC 영향이 남았다. 전체 이전 역시 OS 스케줄·잠금·메모리·전송 지연을 제거한다는 보장은 없으므로 단계별 수치·시각·판정 동등성을 보존한다.

센서 이력 버퍼와 계산 대기열은 구별한다. ToF/IMU 이력을 무작정 줄이지 않고, 계산 요청 적체를 제한하되 RAW–TDMA의 완성된 짝과 순서·시계 세대를 보존한다. 오래된 위치에 현재 시각을 붙여 정상 측정처럼 보내거나 FC 추정 위치를 독립 UWB처럼 되먹이지 않는다.

측정 상태는 `정상·입력 없음·품질 거부·처리 만료·시계 무효·기하 불일치`로 나누고, 기존 상태 메시지를 확장해 전달한다. 상태 메시지 자체도 멈출 수 있으므로 측정 원시 시각·상태 시각·새 sequence·시계 세대를 함께 검사한다. 매번 같은 `OK`를 읽는 것은 새 측정이 들어왔다는 뜻이 아니다.

서비스 수명도 분리할 가치가 있다. 현재 센서 서비스 재시작은 MAVROS·UWB·B_TF·스트림 요청까지 함께 재시작한다. B_TF나 기록 모듈을 정비할 때 FC 연결 전체를 재시작하지 않도록 구성한다. 이는 비행 중 교체를 허용하자는 뜻은 아니다. 릴리스가 이전 슬롯의 native 라이브러리를 참조하는 의존성도 후속 패키징에서 제거한다.

2번의 구체적인 확인 대상은 `MPC_XY_VEL_MAX`, `MPC_XY_VEL_ALL`, 해당 모드에서의 속도 제한이다. 10/12 문서의 `MPC_XY_VEL_MAX=2.0m/s`, `MPC_XY_P=0.95/s`에서는 50cm 위치오차의 P항만 약 0.475m/s다. 이는 실제 비행속도 측정값은 아니지만, 경로 0.25m/s만으로 복구 속도를 제한했다고 볼 수 없는 이유다. PX4의 속도 제한도 제어 목표 제한이며 실제 기체의 순간 속도 상계를 물리적으로 보장하지는 않는다.

초기 저속 검토에서는 수평 제어속도 상한도 0.25m/s와 맞추는 안을 우선 후보로 둔다. 실제 제한 경로와 수동 Position 회수 영향, 외란 억제 여유를 확인한 뒤 값을 확정한다. 0.5~0.75m/s로 올린 후보는 현재 30cm 공간 예산으로 뒷받침되지 않아 채택하지 않았다.

수직은 현재 사용자 조건과 기록의 `MPC_TKO_SPEED=0.5`, `MPC_Z_VEL_MAX_UP=0.5`, `MPC_LAND_SPEED=0.25m/s`를 현재 펌웨어·모드별 실제 적용값과 맞춘다. 최신 일반 문서의 기본값·범위를 우리 custom 펌웨어에 그대로 옮기지 않는다. 고도 PID·추력 제어를 companion에 추가하지 않는다.

추정기 기록은 `EKF2_EV_CTRL=1`로 외부 XY만, `EKF2_EV_NOISE_MD=0`으로 메시지 분산과 noise 하한을 사용한다. `EKF2_EVP_GATE=5`, `EKF2_EVP_NOISE=0.10m`, `EKF2_EV_DELAY=0ms`도 확인된 문서값이다. 높이 기준은 기압, 거리계는 조건부 보조라는 기록이 있으므로 이를 무시하고 EV 높이 융합을 추가하지 않는다. 새로운 적용 전에는 해당 펌웨어의 실제 설정 묶음과 맞춘다.

`EKF2_EV_DELAY`는 전송시간의 중앙값을 그대로 넣는 항목이 아니다. 측정 시각이 FC IMU 시계로 정확히 대응되면 0ms도 가능하다. 이미 시각에 반영한 지연을 다시 빼는 중복 보정을 피하고, 남아 있는 측정시각 오차를 판단한다. [PX4 시각 정합 설명](https://docs.px4.io/v1.15/en/ros/external_position_estimation#tuning-ekf2-ev-delay)

현재 Offboard sender는 위치·yaw만 전송하고 속도·가속도 필드를 무시한다. 따라서 `MPC_ACC_HOR`와 `MPC_JERK_AUTO`만 조정해 외부 위치 목표가 자동으로 부드러워진다고 가정하지 않는다. 기존 위치 전용 경로에 연속 경로를 만드는 방안과, 일관된 위치·속도 feed-forward를 사용하는 방안을 실제 송수신 계약에 맞춰 선택해야 한다. 원시 가속도/자세 제어로 변경할 이유는 현재 근거에 없다. [고정 PX4 소스](https://github.com/PX4/PX4-Autopilot/blob/d6f12ad1c4f70ad3230afd7d86e971421e02fef4/src/modules/mc_pos_control/MulticopterPositionControl.cpp)

1~3번의 물리 측정·교정이 끝날 때까지 모든 소프트웨어 검토를 멈출 필요는 없다. 감속·복구 계약과 작은 지연 개선의 정적 대조는 병행하되, 실제 적용과 결과 평가에서는 변경 원인을 섞지 않는다. 현재 B4의 같은 높이 앵커 계약을 유지하며, 비공면 배치를 단순 설정 변경으로 제안하지 않는다.

**9. 적용 결과를 판단할 기준**

계산 결과 발행, PX4 수신, 실제 융합, 실제 위치 유지는 서로 다른 완료 조건이다. 실제 FC 지상 주입에서 수신·융합은 확인됐지만 공백 중 10cm 유지가 입증된 것은 아니다. SIH에서 9.664초 UWB 없이 POSITION을 유지한 결과 역시 공백 변위 18.573cm·복귀 후 24.384cm여서 10cm 목표를 충족하지 못했다.

다음 적용의 결과는 독립 위치 기준에서 정상 이동·정지·관측 거부·재획득을 구분해 판단한다. 실제 속도·최소 감속·반응시간·제어 오차와 함께, 원래 물리적 목적지가 유지됐는지 확인한다. 타임아웃만 늘리거나 도착 반경 숫자만 10cm로 바꾸는 것으로 완료 처리하지 않는다. 기존 FC failsafe와 조종권 전환은 유지한다. [PX4 Offboard 계약](https://docs.px4.io/main/en/flight_modes/offboard)

| 상황 | 대응 계약 |
|---|---|
| UWB만 거부·공백, 다른 항법 보조와 유지 여유 유효 | 임무 진행을 보류하고 감속·대기. 경과시간 하나로 착륙하지 않음 |
| UWB 복귀, 물리 적합성과 새 융합·좌표 관계 확인 | 현재 위치·실제 속도에서 원래 목적지로 제한된 재진입 |
| reset 의미·지도 변환·추정 상태가 불명확 | 자동 임무 재개 금지. 유지가 가능한지부터 판단 |
| Offboard 송신 자체가 소실 | 문서상 `COM_OF_LOSS_T=1.0s`, `COM_OBL_RC_ACT=0`의 Position 대응을 현재 펌웨어와 대조 |
| 수평 추정 유효성도 소실 | Position 유지가 가능하다고 가정하지 않음. 남은 높이·조종권·착륙 여건에 맞는 실제 FC 대응을 이륙 전에 명세 |
| 명시적인 기하·축·장착 개정 불일치 | 비행 중 발견하기 전에 준비/ARM 허용 검사에서 차단 |

이 표의 마지막 불일치 검사는 센서 신원 확인과 설정 개정의 일치를 뜻한다. 제품 모델명이 같다는 이유만으로 물리 교정까지 완료된 것으로 처리하지 않는다.

**10. Claude 검토 반영 기록**

Claude Code 로그인 방식 `claude.ai / firstParty / pro`와 별도 API 키 환경변수 부재를 확인한 뒤, 사용자 지정에 따라 구독 연결을 사용했다. 각 차수에는 앞선 답변과 반론을 함께 전달했다. 세 답변은 모두 정상 반환됐고, Claude의 도구 실행은 비활성화했다. 연결 실패와 응답 형식 오류는 검토 횟수에 포함하지 않았다.

| 차수 | 주고받은 내용 | 최종 반영 |
|---|---|---|
| [1차](review-1.md) | 하드웨어·기존 증거·구조 초안의 반론 요청 | 거리 모순, 제어속도와 경로속도의 차이, 도착 반경 불일치를 우선 과제로 채택 |
| [2차](review-2.md) | 1차의 EV 지연 해석·비공면 앵커·속도 제안·단순 reset 허용을 반박 | 통신 지연 중복 보정, B4 수학 계약을 깨는 배치 변경, 근거 없는 0.5~0.75m/s 상한 제안을 철회 |
| [3차](review-3.md) | 지도 변환이 drift를 흡수하는 오류, FC와 companion의 reset 보상 경합, 고착 상태 진단을 검토 | 고정 목적지·입력 좌표 변환·임시 제어 참조 분리, 새 관측·새 융합·세대 일관성, heading·fallback·이륙 전 정합 조건 추가 |

Claude의 제안도 실제 소스·기록과 충돌하면 그대로 채택하지 않았다. 특히 “companion에서 delta를 더하면 연속성이 보장된다”는 설명은 채택하지 않았다. 현재 결론은 **속도·좌표·센서 계약을 맞춘 뒤, 기존 FREEZE를 감속과 검증된 재진입으로 확장하고, 거리 품질과 처리 지연을 각각 개선한다**는 것이다. 전체 항법 경로의 C++ 이전과 FC 인터페이스 변경은 효과와 필요성이 확인되는 범위의 후속 후보로 남긴다.
