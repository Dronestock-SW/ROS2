## 1. 운영 기준본 r1 확정 범위

**표현 보완이 필요한 점 하나가 있습니다.** r1의 ROS 기준 d586e836은 B1 구조입니다. 여기에는 IMU 수신·계산 분리, 스냅샷, BtfTrace 기본 활성화가 포함되며, 이 구조에서 지연 증가가 관찰된 뒤 아직 해소되지 않았습니다. 그러면 "ToF 100/50/50 수정본을 운영 기준으로 확정"이 "B1 수신 구조까지 검증되어 채택됨"으로 읽힐 수 있습니다.

**제안:** r1 문서에 다음을 명시합니다.
- ToF 변경은 빌드·링크 범위에서 확정되었다.
- B_TF 수신 구조와 trace 기본값은 현 상태를 그대로 포함하며, 지연 회귀는 미해결로 남아 있다.
- r1에 포함된 overlay 25개 파일의 목록과 SHA.
- 그중 재생 시험기 같은 시험 전용 파일이 운영 기준에 들어가는지 여부.

## 2. 계측 구현 전에 확인할 핵심 오류 가능성

**(1) OFF가 실제로 무엇을 제거하는지 코드로 확정하세요.**
- 5차 검토 때는 row 딕셔너리 구성이 남는다고 전달받았습니다. 그런데 이번 문서는 "기존 수신 시각은 내부 기록에 들어가며 OFF에서 사라진다"고 적고 있습니다.
- 이 둘을 구분해야 합니다. `self.trace is None`일 때 row 구성까지 건너뛰는 분기가 있다면, OFF의 효과는 "기록 경로 + 진단 record 구성"으로 귀속되어야 합니다.
- 결과 해석 범위가 여기서 정해지므로, 해당 분기의 위치를 문서에 적으세요.

**(2) ON/OFF의 유효 파라미터가 `trace_directory` 하나만 다른지 확인하세요.**
- 기존 시험기는 ON을 고정합니다. 이를 파라미터화하는 과정에서 다른 값(clock readiness, 큐 크기, record 관련 값 등)이 함께 바뀌지 않아야 합니다.
- 실행마다 SUT의 실제 파라미터 덤프와 해시를 남기고, 차이가 한 항목뿐인지 대조하세요.

**(3) 계측 버퍼는 스레드별로 따로 두고, 미리 할당하고, 넘칠 때의 동작을 정해 두세요.**
- 이벤트는 sensor 스레드와 compute 스레드 양쪽에서 기록됩니다. 공유 버퍼에 lock을 걸면 계측 자체가 잠금 대기를 만들어 t4/t5 해석이 오염됩니다.
- 스레드별로 미리 할당한 int64 배열(`array('q')` 또는 numpy)에 인덱스 증가만 하도록 하세요.
- 용량은 입력 수에서 계산합니다. 예를 들어 IMU 8,427개 × 이벤트 수에 여유를 더합니다. 넘치면 "그 이후 기록 중단 + 넘침 계수"로 처리하고, 해당 run은 불완전으로 표시하세요.

**(4) ON 회차에는 디스크 예산을 별도로 확인하세요.**
- trace 최대 128MiB에 256MiB 하한을 더한 이전 기준(416MiB)을 ON 회차 시작 조건으로 유지해야 합니다.
- 운영 프로세스도 같은 디스크에 쓰고 있습니다. OFF 회차에 이 조건이 필요 없다고 해서 회차 사이의 정리 작업이 순서 효과를 만들지 않도록 하세요.

**(5) 64~66초 구간은 원본 기준 상대 시각으로 정의하세요.**
- 실행별 시각 이동량이 다르므로 벽시계 기준이면 구간이 어긋납니다.
- 원본 첫 행 기준 상대 시각이나 원본 행 범위로 고정하세요.

## 3. 배경 부하 관련

- 운영 중인 `uwb_btf_node`, `mavros`, `lidar` 프로세스가 같은 CPU를 씁니다. "기록하고 변동이 크면 교란으로 표시"하는 방식은 타당합니다.
- 다만 교란 판정 기준(예: 실행 전 60초와 실행 중의 운영 프로세스 CPU 합 비교)을 **실행 전에** 문서에 정해 두세요. 실행 후에 정하면 사후 선택이 됩니다.
- 격리 확인 항목에 다음을 추가하기를 권합니다. 재생 프로세스의 `ROS_DOMAIN_ID=99`와 `ROS_LOCALHOST_ONLY` 환경변수를 실제 프로세스 환경에서 확인하고, 운영 노드의 topic이 재생 도메인에 보이지 않는지 확인합니다.

## 4. 설계 자체에 대한 판단

- ON→OFF→OFF→ON 순서, 새 프로세스 기동, 동일 계측, t3−t1을 GIL로 단정하지 않는 해석 규칙, 세 가지 판정 범주는 타당합니다.
- 추가로 확장할 부분은 없습니다. 위 (1)~(3)을 구현 전에 확정하는 것이 우선입니다.
