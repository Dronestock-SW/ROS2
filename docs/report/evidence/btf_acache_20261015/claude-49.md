## 48차 차단 사항의 해소 여부

- **② 전체 소스 대조: 해소되었습니다.**
  - `verify_release.py`는 후보와 운영 양쪽의 파일 목록이 같은지, 811개 파일의 이전·이후 해시가 일치하는지, 바뀐 파일이 정확히 3개뿐인지를 확인합니다. config 바이트 일치, 계약 시험 통과, 회귀 테스트 로그, import 경로, native .so 해시도 함께 확인합니다.
  - 생성물(`__pycache__`, `.pytest_cache`, `*.egg-info`)을 제외한 기준도 적절합니다.
  - 48차에서 "3개 파일만 대조한다"고 추정한 것은 제 오류였습니다. 정정을 수용합니다.
- **③ 롤백 후 상태 확인: 해소되었습니다.** 롤백 뒤 readiness를 검사하고, 실패하면 주의 표시 파일을 남깁니다.
- **NRestarts와 active 확인:** 반영되었습니다. 검증 중에 자동 재시작이 일어나면 ERR로 롤백됩니다.
- **① 신호 처리: 대부분 해소되었지만, 남은 공백이 하나 있습니다(아래 1번).**

## 남은 결함과 확인 사항

**1. 롤백이 진행되는 도중에 HUP를 받으면 중단될 수 있습니다** (중간 위험)
- `rollback()`이 시작할 때 `trap - ERR INT TERM HUP`으로 트랩을 **기본 동작으로 되돌립니다.**
- SSH가 끊겨 HUP가 다시 오면 롤백 도중에 스크립트가 종료됩니다. 예를 들어 `mv`는 끝났지만 `daemon-reload`나 `restart` 전에 종료되면, **override는 치워졌는데 서비스는 새 슬롯으로 계속 실행되는** 불일치 상태가 남습니다.
- **최소 수정(둘 중 하나):**
  - `rollback()` 첫 줄을 `trap '' ERR INT TERM HUP`(무시)로 바꿉니다.
  - 또는 스크립트 전체를 `setsid nohup` 또는 `systemd-run --user --unit=...`으로 분리 실행해서 세션이 끊겨도 끝까지 실행되게 합니다. 이전 SSH timeout 사례를 생각하면 이쪽을 권합니다.

**2. `tof_valid>100` 여유를 비율로 확인하세요** (거짓 롤백 위험이며, 안전 문제는 아님)
- 사전 점검의 "누적 29만 이상"은 이전 프로세스의 **누적값**이라 비율을 보여주지 않습니다.
- 재시작하면 MAVROS도 다시 연결되고, timesync가 준비되어야 센서가 valid로 판정됩니다. 그동안은 valid가 쌓이지 않으므로, 약 22초 동안 ToF 10Hz 수준이면 100에 겨우 닿을 수 있습니다.
- pre-switch.json에서 **초당 valid 증가율**을 확인하고, 필요하면 기준을 낮추지 말고 **대기 시간을 늘리세요.** 이 조건에서 실패하더라도 롤백은 안전한 방향입니다.

**3. 사소한 사항 (차단 아님)**
- `'111 passed' in regression.log`는 문자열 포함 검사입니다. 다른 숫자와 겹쳐도 통과하는 정도의 약한 확인이지만, 실제 오판 가능성은 낮습니다. 실패 수가 0인지도 함께 확인하면 더 단단해집니다.
- 실행 중 생성되는 `cached_xy.py`의 해시는 기동 후에 직접 확인하지 않습니다. 같은 패키지의 `measured_btf.py` 해시와 기하 해시로 간접 확인되므로 충분합니다.
