# A-cache 채택 후 남은 지연의 구간 비교
2026-10-15 기존 재생 기록을 다시 분석한 보고서다.
큰 지연의 위치와 다음 확인 순서를 정할 때 읽는다.

## 판단과 적용 상태

**큰 지연은 XY 캐시 풀이가 아닌 여러 구간에 남았다.**
50ms 초과 콜백 7건을 확인했다.
전처리에서 4건, native 호출 경계에서 2건이었다.
나머지 1건은 process의 미분해 구간이었다.
이 중 캐시 적용 C는 전처리 2건과 호출 경계 1건이다.
7-C에서는 50ms 초과 콜백이 없었다.
CPU 사용이 큰 전처리와 스레드가 실행되지 않은 시간이 큰 전처리가 함께 나타났다.
모두 C++ 계산이 느려진 경우로 묶을 수 없다.

사용자는 A-cache를 채택했다.
추가 확인 답변에서 운영본 변경·실기 배포도 요청했다.
이 문서의 기존 기록 분석과 배포 결과는 구분한다.
배포 완료 여부는 별도 배포 기록에 남긴다.
큰 지연 관련 코드 수정과 새 재생은 이번 분석에서 하지 않았다.

## 자료와 비교 방법

**기존 증거 파일 56개의 해시를 다시 확인했다.**
8회 ROS 재생의 콜백 16,112개를 읽었다.
그중 전처리를 완료한 계산은 6,495개다.
입력은 13일 전체 원본이 아닌 부분 복구 로그다.
각 재생은 약 24.362초이며 1배속이었다.
A는 563960e와 공통 계측을 적용한 기준이다.
C는 같은 기준에 A-cache만 추가한 시험본이다.
여기서 A는 13일 초기 비행 코드 자체가 아니다.
운영 서비스와 동시에 동작하던 공유 Jetson의 결과다.

- 큰 지연: 이전 보고서와 같은 콜백 wall >50ms.
- 일반 구간: 전처리와 native에 도달하고 콜백 ≤20ms.
- 사건별 대조: 같은 실행·판정·높이 출처·창 표본 수·반복 수.
- 그 조건에서 입력 seq가 가까운 일반 구간 20개를 선택했다.
- 같은 seq의 다른 7회 실행과도 비교했다.
- 20ms·30ms 기준의 건수도 보존했다.

일반 구간은 비행 합격을 뜻하지 않는다.
이번 지연 비교를 위한 운영상 정의다.
비교 대상의 중앙값은 인과 효과의 추정치가 아니다.

## 시간 구간의 뜻

**아래 시간들은 포함 관계가 있으므로 전부 더하면 안 된다.**

```text
재생 발행 → 콜백 시작
             ├─ 입력 해석·센서 스냅샷·입력 기록
             ├─ process
             │   ├─ 시계 맵·입력 검사 등 [별도 타이머 없음]
             │   ├─ 전처리 P
             │   │   ├─ 센서 선택·높이·보정·결과 준비
             │   │   └─ 순간 XY X
             │   ├─ 높이 잔차·관측 guard 등 [별도 타이머 없음]
             │   ├─ native 호출 N
             │   │   ├─ 요청 생성·잠금·JSON·C 경계
             │   │   ├─ C++ 계측 C: 처리 + 결과 JSON 객체 구성
             │   │   └─ 직렬화·Python 복귀·JSON 해석
             │   └─ 결과 조립 등 [별도 타이머 없음]
             └─ 발행 검사·발행·결정 기록
```

wall은 시작부터 끝까지 흐른 시간이다.
CPU는 해당 계산 스레드가 CPU를 사용한 시간이다.
wall−CPU에는 스케줄·잠금·GIL·I/O 등의 대기가 섞일 수 있다.
이 값만으로 대기 원인을 구별하지 않는다.
N−C는 native 호출 중 내부 타이머 밖의 시간이다.
Python만의 비용이나 순수 직렬화 비용으로 부르지 않는다.
C도 steady_clock으로 잰 wall이다.
따라서 순수 CPU 연산 시간과 같지 않다.
process−P−N은 앞·중간·뒤의 합이다.
하나의 연속된 코드 블록으로 해석하지 않는다.
콜백 진입 대기는 해당 TDMA 메시지의 발행 시작부터 잰다.
센서 측정 시점이나 원래 RAW 수신부터의 전체 나이는 아니다.

### 전처리에서 길어진 네 건

**같은 전처리 구간에서도 CPU 사용과 대기 양상이 달랐다.**
2-C는 XY 제외 전처리 84.91ms 중 CPU 72.50ms다.
3-C는 73.13ms 중 CPU 65.02ms다.
단순히 다른 프로세스 때문에 계산 스레드가 쉬었다고 설명할 수 없다.
반면 4-A는 107.88ms 중 CPU 2.45ms다.
5-A는 86.41ms 중 CPU 1.92ms다.
이 두 건에는 큰 대기 성분이 있다.

해당 구간에는 네 앵커의 ToF·IMU 선택이 있다.
높이 투영·거리 보정·메타데이터 생성도 들어 있다.
별도 타이머가 없어 어느 함수에서 늘었는지는 확정할 수 없다.
GC가 그 스레드에서 실행됐을 가능성도 남는다.
GC 이벤트·스택 기록은 없으므로 확정 원인으로 쓰지 않는다.

### native 호출에서 길어진 두 건

**C++ 내부 계측은 짧고 그 바깥의 시간이 길었다.**
1-A는 N−C 92.08ms, C 0.30ms다.
6-C는 N−C 90.02ms, C 0.48ms다.
일반 구간의 N−C 중앙값은 각각 1.66/1.69ms다.
JSON 생성·C++ 입력 파싱·출력 직렬화·Python 해석이 포함된다.
native의 RLock은 계측 범위에 들어 있다.
현재 호출자들은 같은 기본 상호배제 콜백 그룹에 있다.
센서 실행기는 native를 호출하지 않는다.
따라서 이 RLock 경합은 코드상 우선순위가 낮다.
ctypes 복귀 시 GIL 재획득·OS 스케줄 대기는 후보로 남는다.
이 경계의 스레드 CPU는 별도로 기록하지 않았다.
직렬화 연산 폭증인지 대기인지 여기서는 나눌 수 없다.

### process의 나머지에서 길어진 한 건

**8-A는 다른 타이머에 포함되지 않은 시간이 67.95ms였다.**

ClockMap 하나를 원인으로 지정할 기록은 없다.

## 공유 호스트의 관측 한계

**1초 안팎 자원 기록은 배경 자료이며 사건의 원인 계측이 아니다.**
부하와 iowait는 전체 호스트 수치다.
100ms 사건에 어떤 프로세스가 영향을 줬는지 단정하지 않는다.
스레드 CPU가 큰 사건을 외부 부하만으로 설명하지 않는다.
CPU가 작은 사건도 GIL·스케줄·잠금·I/O를 구분할 수 없다.
별도 타이머 밖 C++ 작업도 N−C에 포함된다.

## 공통 정지 가설과 스레드 CPU

**구간별 원인 외에 공통 사건이 측정 위치를 옮긴 가설도 남는다.**
GIL을 오래 점유하는 처리가 계산 스레드에서 일어나면 CPU가 커진다.
다른 스레드에서 일어나면 계산 스레드는 실행되지 못할 수 있다.
C++ 복귀 시 겹치면 N−C가 길게 보일 수 있다.
GC는 후보 중 하나이며 해당 이벤트 기록은 없다.
입력 위치와 프로세스 수명이 함께 고정되어 있었다.
따라서 입력 특성인지 누적 할당·프로세스 수명인지 분리되지 않는다.

기존 /proc의 스레드별 CPU도 추가 대조했다.
사건을 감싼 1~2초 구간을 초당 CPU ms로 정규화했다.
가까운 정상 자원 구간 4개의 중앙값과 비교했다.

| 실행 | 사건 구간 길이 ms | main CPU ms/s | main 일반 중앙값 | 가장 증가한 다른 TID | 그 증가 ms/s |
| --- | --- | --- | --- | --- | --- |
| 1-A | 2001.3 | 529.7 | 545.2 | 208795 | +19.9 |
| 2-C | 999.9 | 590.1 | 549.9 | 209157 | +10.0 |
| 3-C | 998.8 | 580.7 | 549.7 | 209580 | +10.0 |
| 4-A | 998.9 | 560.6 | 554.7 | 209966 | +100.2 |
| 5-A | 999.5 | 570.3 | 530.0 | 210299 | +70.2 |
| 6-C | 1999.9 | 535.0 | 545.1 | 210729 | +35.1 |
| 8-A | 1000.0 | 610.0 | 569.9 | 211474 | +0.0 |

4-A에서 다른 스레드의 CPU가 일반 구간보다 약100ms/s 많았다.
5-A에서는 다른 스레드가 약70ms/s 많았다.
계산 스레드 CPU가 작은 두 사건과 양립하는 신호다.
그러나 TID와 역할 이름을 연결한 자료는 없다.
그 스레드를 trace writer나 센서 스레드라고 단정하지 않는다.
구간은 1초, CPU tick은 10ms이며 읽기도 원자적이지 않다.
동시 정상 처리량의 차이도 합산되므로 GC나 GIL 증명은 아니다.
나머지 사건도 일관된 70~100ms/s 증가는 보이지 않았다.

## 다음 단계와 완료 조건

**다음은 공통 정지의 정체와 평상시 비용을 분리해 확인한다.**

| 우선순위 | 확인 사실 | 남은 가설 | 다음 확인 | 완료 조건 |

새 계측·재생은 이 분석에서 수행하지 않았다.
GC 비활성화·유효시간 완화도 적용하지 않았다.
Python 감시 스레드 자체도 GIL에 막힐 수 있다.
향후 스택 감시는 이 한계를 고려해 설계한다.
원인과 효과가 분리된 뒤 개선 방식을 고른다.
A-cache는 이번에 확인한 국소 절감 효과로 채택한다.
큰 지연의 해결책으로 채택한 것은 아니다.

## 검토 및 재현 자료

Claude 47차에서 구간 분해와 공백 구분을 검토했다.
