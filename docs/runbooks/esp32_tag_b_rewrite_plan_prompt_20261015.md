멀티태그를 제거한 새 구현 계획을 요청할 때 사용한다.

후속 사용자 정정으로 최종 작업 범위가 확대됐다.
[구현·실기기 검증·재설정 실행 프롬프트](esp32_tag_b_rebuild_execution_prompt_20261015.md)가 최신 지시다.

기술 요구와 설계 근거는 계속 참조한다.

너는 드론·Physical AI·실시간 임베디드 전문가다.
ESP32 태그, UWB 앵커, companion 연결을 재설계하라.

LoRa의 지상국 통신 기능은 유지하라.

RAW는 제거 대상이 아니다.
거리·측정 시각·유효성·실패·식별 정보를 보존하라.
기존 TDMA 진단에 있던 필수 정보도 RAW에 통합하라.
제거 대상은 멀티태그 시간 배분과 별도 메시지 대기다.
측정 주기·거래 기한·재시도 제한은 계속 유지하라.
앵커 수정과 companion 수신부 변경을 함께 계획하라.

이번에는 구현 가능한 계획과 인터페이스를 작성하라.
실제 펌웨어 업로드와 운영 설정 변경은 별도 작업이다.
확인할 수 있는 사실은 코드와 자료에서 직접 확인하라.
기존에 확인된 조건을 사용자에게 다시 묻지 마라.

## 1. 목표 구조

**태그 한 대가 네 앵커를 측정하고 LoRa는 독립적으로 서비스한다.**

```text
A1~A4: 주소가 다른 같은 역할의 응답기
          ↕ 태그가 차례로 시작하는 거리 교환
ESP32 Tag B(ID 6) ── RAW·원본 측정 시각 ──> companion
          ↕ 양방향 시각 교환                 │
          <──────── 최신 jetson_pose ────────┘
          │
          └─ 독립 1Hz LoRa 상태 ──> 지상국
          <─ LoRa 수신 ─────────── 지상국
          └─ lora_rx ────────────> companion

companion: 시간 정합 → 위치·공분산 → PX4 관측 입력
PX4: 상태 추정·비행 제어
```

| 항목 | 기준 |
|---|---|
| 태그 | Heltec WiFi LoRa 32 V3 / ESP32-S3 / flash 8MB |
| 무선 장치 | 외부 DWM3000 계열 + 내장 SX1262 |
| 앵커 | nRF52 DK / nRF52832 + DWM3000, A1~A4 |
| companion / FC | Jetson Orin Nano Super / Pixhawk 6C Mini |
| 식별 | Tag B의 ID 6, 기존 순번·부팅 식별 체계 재사용 |
| 좌표(m) | A1=(0,0,.15), A2=(6.3,0,.15), A3=(0,4.6,.15), A4=(6.3,4.6,.15) |
| 새 RAW 목표 | 50Hz, 20ms 주기, 네 거리의 새 측정 시도 |
| LoRa 목표 | UWB와 독립된 명목 1Hz 요약 송신·하향 전달 |

태그가 하나라는 전제를 무선 충돌 설계에 명시하라.
다른 태그가 같은 앵커를 동시에 쓰는 기능은 범위 밖이다.
식별 검증은 충돌 회피나 무선 인증을 대신하지 않는다.

## 2. 제거할 구조와 앵커 변경

**태그와 앵커 양쪽에서 멀티태그 의존성을 제거하라.**

A/B 교대 슬롯, A1의 주기적 SYNC 송신을 제거하라.
태그의 SYNC 대기와 슬롯 승인을 제거하라.
LoRa의 `sf_seq % 40` 위상과 24.5ms 승인 마감을 제거하라.
companion의 RAW/TDMA 두 메시지 짝 맞추기도 제거하라.
이 기능들을 빈 필드나 가짜 SYNC로 유지하지 마라.
현재 데이터의 의미를 흐리고 새 구조를 복잡하게 만든다.

A1은 A2~A4와 같은 거리 응답기로 바꿔라.
태그가 POLL을 보내면 해당 주소의 앵커만 응답한다.
기존 A1은 ID 6의 시간 창을 검사한다.
따라서 태그만 고쳐서는 이 설계가 완성되지 않는다.

가능하면 네 앵커를 주소만 다른 공통 소스로 구성하라.
각 앵커의 거래에는 별도의 시간 제한을 유지하라.
주소·PAN·기능 코드·순번·길이·상태를 검사하라.
단일 태그와 무관한 검증까지 없애지 마라.
잘못된 응답이 현재 거리로 수용되는 것을 막아야 한다.

기존 DS-TWR의 POLL→RESPONSE→FINAL→REPORT를 유지하라.
무선 시각으로 거리를 계산하는 방식도 보존하라.
초기 PHY는 채널 5, 6.8Mbps, preamble 128로 둬라.
PAC8, code 9, 기존 안테나 지연을 기준으로 시작하라.
안테나 지연과 거리 편향의 실제 교정은 따로 계획하라.

radiofix3의 SYS_TIME 조회·리셋·SPI 수정을 보존하라.
검증된 드라이버까지 새로 쓰는 것은 목적이 아니다.
단일 태그 스케줄과 입출력 책임을 새로 구성하라.
현행 프로토콜과 새 프로토콜은 명시적으로 구분하라.
혼합 배포 시 호환 여부를 확인하고 자동 추측을 피하라.

## 3. 주기와 시간 예산

**50Hz를 목표로 설계하고 실제 관측 품질로 채택하라.**

기존 정상 4거리 교환 중앙값은 9.424ms였다.
p95는 9.583ms, 관측 최대는 9.728ms였다.
기존 RAW는 39.98Hz, 새 B_TF 위치는 약 34.71Hz였다.
이것은 이전 펌웨어의 짧은 정지 관찰 결과다.
새 단일 태그의 성능 보증으로 사용하지 마라.

50Hz는 20ms마다 시작하는 설계 목표다.
최대 Hz보다 지연·공백·측정 성공률을 우선하라.
80/100Hz를 채택하려고 복구·진단 여유를 없애지 마라.
성능이 부족하면 원인을 분리해 40Hz와 비교하라.
런타임 자동 주기 전환보다 검증된 고정 주기를 우선하라.

| 초기 예산안 | 계획 기준 |
|---|---|
| 첫 측정 | 앵커별 최대 약 3ms, 네 앵커 약 12ms |
| 재시도 | 첫 측정을 모두 시도한 뒤 남은 예산으로 최대 1회 |
| 재시도 예산 | 기존 대기 포함 약 3.2ms를 출발점으로 검토 |
| UWB 처리 상한 | 18ms 이내를 목표로 세부 오버헤드 검산 |
| 주기 여유 | 다음 20ms 시작을 위한 여유 확보 |
| USB·LoRa | 비동기 처리. 전체 송신 완료를 측정 루프가 기다리지 않음 |

위 값은 새 계획의 예산안이다.
드라이버·앵커 timeout·ISR·SPI 지연을 포함해 검산하라.
3ms에는 거래 정리와 상대 앵커의 종료 대기도 포함하라.
예산이 모자라면 재시도를 생략하고 결측으로 넘겨라.
이전 거래 종료 전에 같은 앵커에 새 요청을 겹치지 마라.

절대 단조 시각 기준으로 다음 시작 시각을 계산하라.
처리 시간 뒤에 20ms를 더하는 방식은 피하라.
기한을 놓치면 밀린 회차를 몰아서 실행하지 마라.
누락을 기록하고 다음 유효 시작 시각으로 진행하라.

PX4에는 새 유효 위치와 공분산을 즉시 전달하라.
RAW 50Hz와 PX4가 실제 수용한 관측률을 구분하라.
기존 좌표에 현재 시각을 붙여 출력률을 채우지 마라.
공식 외부 위치 안내 30~50Hz를 설계 근거로 사용하라.
Offboard 생존 신호의 2Hz는 별도 경로다.

## 4. 작고 완결된 RAW 계약

**한 프레임만으로 관측을 검증할 수 있게 하라.**

921600 baud의 간결한 JSONL을 기본안으로 삼아라.
먼저 크기·직렬화 시간·부하를 계산하라.
바이너리는 실제 병목이 확인될 때 비교하라.
불필요한 프로토콜 복잡성을 먼저 추가하지 마라.

| 정보 | 필수 의미 |
|---|---|
| 형식 | type, 새 schema 또는 protocol version |
| 식별 | ID 6, seq, boot_id, 측정 세션 |
| 시각 | cycle 시작·끝, 앵커별 원본 측정 시각 |
| 값 | A1~A4 RAW 사선거리(m), valid_mask |
| 실패 | 앵커별 짧은 정수 코드 |
| 시간 상태 | clock domain, 변환 세대·유효성 |

순번·boot_id는 기존 체계를 재사용하라.
기존 session은 A1 SYNC에서 온 값인지 확인하라.
새 측정 세션의 발급 주체와 재시작 조건을 정의하라.
의미가 바뀌면 새 schema에 명시하라.
없어진 sf_seq·schedule_id를 가짜로 채우지 마라.

실패 값은 null과 무효 비트로 표시하라.
이전 거리나 0m를 현재 측정처럼 보내지 마라.
부분 RAW는 보내고 위치 사용 여부는 companion이 판단한다.
새 모드에서 TDMA 진단을 기다리는 경로를 제거하라.
새 모드의 신선도·중복·순서 검사는 유지하라.

ESP32에서 XY 풀이와 시간 필터를 걷어내라.
위치·공분산은 companion에서 계산하라.
필요한 RF 진단은 저빈도 상태나 요청형 조회로 둬라.
RAW 필수 필드는 companion 소비 지점과 대조하라.

## 5. 정확한 시각과 밀리지 않는 전달

**측정 시각을 보존하고 companion 시간축에 한 번 대응시켜라.**

ESP32↔companion 양방향 시각 교환을 설계하라.
왕복 지연 이상치와 시계 속도 차이를 처리하라.
측정마다 companion 응답을 기다리지 마라.
DW 시계를 Jetson 시각으로 강제로 변경하지 마라.

DS-TWR에서 거리 대표 시점의 정의를 명시하라.
RF 이벤트와 ESP32 단조 시각의 대응 오차를 확인하라.
기존 REPORT를 읽은 시각은 RF 측정 시각과 구분하라.
변환한 값에 ClockMap을 다시 적용하지 마라.
재부팅·시계 만료·연결 변경을 새 시계 구간으로 처리하라.

송신 큐는 고정 크기와 데이터 만료 기한을 둬라.
관측 출력은 최신의 완결된 프레임을 우선하라.
전송 중인 줄을 끊어서 JSON을 손상시키지 마라.
옛 미전송 프레임은 버리고 누락 카운터를 남겨라.
수신 파서도 길이·처리량·처리 시간에 상한을 둬라.

## 6. UWB와 독립된 LoRa

**LoRa의 기능은 살리고 멀티태그 스케줄 결합을 없애라.**

첨부 LORA_TAG_REBUILD.md의 무선·메시지 계약을 유지하라.
SYNC와 교대 회차 부분은 이번 단일 태그 설계로 대체하라.

| 유지 | 새 설계에서 변경 |
|---|---|
| 915MHz, BW125kHz, SF7, CR4/5 | ESP32 단조 타이머 기반 명목 1Hz |
| 10dBm, preamble 8, private 0x1424 | A1 SYNC 없이 송신 기회 생성 |
| CRC·가변 길이, 최대 255바이트 | UWB 고장 중에도 상태 전송 시도 |
| jetson_pose·ACK·drone.status | 원본 pose 나이와 순번 검증 강화 |
| lora_rx·RSSI·SNR 전달 | UWB 측정에 막히지 않는 수신 처리 |
| IRQ·timer·watchdog·복구 | 송신 승인과 복구를 UWB 세션에서 분리 |

LoRa가 준비되면 자체 일정으로 상태를 보낸다.
UWB가 끊겨도 LoRa 준비 상태는 독립적으로 유지하라.
좌표의 fix는 companion 원본 관측의 유효성과 나이로 정하라.
유효한 최신 좌표가 없으면 fix:false로 보낸다.
마지막 좌표를 새 fix로 재사용하지 마라.

기존 500ms는 LoRa 표시용 신선도 상한이다.
이를 비행 위치의 허용 지연으로 가져오지 마라.
수신 시각만으로 원본 pose 나이를 판단하지 마라.
중복 pose로 freshness가 계속 연장되지 않게 하라.

기존 drone.status의 필드·단위·t 의미를 보존하라.
UWB 고장 사유는 reason과 USB 진단으로 전달하라.
지상국에 새 필드가 필요하면 호환 변경으로 분리하라.
Jetson→태그→LoRa의 지연도 별도로 측정하라.
LoRa의 1Hz 출력에 필요 없는 고속 pose 재전송을 줄여라.

RF 송신이 끝날 때까지 MCU를 대기시키지 마라.
최대 길이 송신은 약 399.616ms일 수 있다.
이때도 UWB의 다음 측정이 진행돼야 한다.
LoRa 송신 중 하향 수신은 가능한 것처럼 표현하지 마라.
송신 완료 후 RX 복귀 시간과 수신 가능 창을 명시하라.
정시 송신 기회를 놓치면 중복·몰아서 송신하지 마라.

SPI 소유권과 장치 전환을 한 곳에서 관리하라.
실제 드라이버가 지원하면 별도 SPI 호스트를 우선 검토하라.
지원 확인 전 두 작업이 같은 전역 SPI를 동시에 쓰지 마라.
공유할 경우 UWB 우선순위와 최대 점유 시간을 정하라.
IRQ에서는 이벤트만 전달하고 무거운 처리는 분리하라.
TCXO·RF 스위치·CS·복구 타이머 처리를 보존하라.

하향 payload는 companion으로 전달하는 기능만 유지하라.
태그에 새 비행 명령 실행 기능을 추가하지 마라.
이는 기존 역할 분리를 유지하기 위한 조건이다.

## 7. 단순한 구현과 시험

**핵심 모듈의 소유권과 종료 조건을 분명히 하라.**

| 모듈 | 책임 |
|---|---|
| UWB 측정기 | 주기 시작, 앵커 순회, 거리·시각·실패 |
| USB 연결 | RAW 전송, pose·시각 교환 수신 |
| 시간 대응 | 원본 시계, 변환 세대, 오차·만료 |
| LoRa 서비스 | 주기 송수신, 하향 전달, 자체 복구 |
| 진단 | 누적 카운터, 고정 RAM 순환 버퍼 |
| 표시 | 필요할 때만 저우선순위 상태 표시 |

한 모듈 실패로 다른 모듈을 함께 재시작하지 마라.
관측 누락을 숨기는 보간·예측은 펌웨어에 넣지 마라.
현재 값을 명확히 전달하는 것이 이 계층의 책임이다.
상태 추정과 비행 제어는 기존 companion/PX4가 담당한다.

새 스케줄에 필요한 상태와 작업만 두어라.
멀티태그 프레임워크나 미래 확장용 추상화를 만들지 마라.
정상 측정 루프의 동적 할당과 대량 로그를 줄여라.
상세 기록은 RAM에 모으고 companion이 비동기 저장한다.
화면은 없어도 UWB·LoRa가 정상 동작해야 한다.

| 시험 | 판정 기준 |
|---|---|
| 정상 지상 10분 | 목표 RAW 50Hz, 유효 관측률·간격 분포 별도 보고 |
| 새 위치 전달 | 정상 완전한 1초 창마다 30개 이상을 초기 시험 목표로 설정 |
| 공백 | 정상 조건 100ms 이상이면 원인 분석 후 재시험 |
| 비교 | 동일 조건의 40/50Hz에서 원본 나이·실패율·LoRa 영향 비교 |
| 장애 | A1 포함 각 앵커 중단, USB 지연, 잘못된 입력, MCU 재부팅 |
| 독립성 | UWB 중단 중 LoRa 상태 유지, LoRa 복구 중 UWB 진행 |
| 부하 | 최대 LoRa 패킷, 하향 수신, 진단, 화면을 동시에 시험 |
| 무결성 | 옛 세션·중복·역순·만료 데이터가 새 관측으로 채택되지 않음 |
| PX4 | 송신·수용·융합을 별도로 확인 |
| RF | 로컬 TX-done과 지상국 실제 수신을 별도로 확인 |

30개/1초와 100ms는 초기 지상 시험 제안이다.
비행 안전 한계나 PX4의 절대 문턱으로 표현하지 마라.
상태 요약만 보고 지상국 수신·비행 성능을 통과 처리하지 마라.

## 8. 산출물과 작업 범위

**태그·앵커·companion을 함께 바꿀 수 있는 계획을 제출하라.**

다음 내용을 구체적으로 작성하라.

1. 제거·보존·재작성할 모듈과 실제 파일 목록.
2. A1~A4 변경 범위와 단일 태그 프로토콜 식별 방법.
3. 20ms 시간 예산과 실패·재시도·SPI 상태 전이.
4. RAW·시각 교환·LoRa 인터페이스와 메시지 예시.
5. companion 파서·시각 처리·PX4 전달 변경점.
6. 빌드·백업·호환 전환·복구와 단계별 시험 계획.
7. 50Hz 채택 조건 및 40Hz 비교가 필요한 조건.
8. 확인 사실·설계 선택·미검증 사항과 최소 질문 목록.

기존 드라이버·라이선스·실물 백업을 보존하라.
앵커와 태그를 함께 바꾸는 전환 순서를 명시하라.
옛 이미지의 복구를 새 실행 경로 안에 끌어들이지 마라.
고도·자세 제어는 기존 PX4 책임으로 유지하라.
Physical AI를 이유로 새 학습 모델을 넣지 마라.
이번 목표는 측정과 통신 경로의 단순화다.
